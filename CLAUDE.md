### REST API signing key

`Avalon.Api` will not start without a JWT signing key, and none is committed (#482). The setting is `Application:Authentication:IssuerSigningKey` (environment variable `Application__Authentication__IssuerSigningKey`). `JwtSigningKey.Create` refuses a key that is missing, has leading or trailing whitespace, is under 32 bytes in UTF-8, or is on `JwtSigningKey.BlockedKeyHashes` (the SHA-256 of the one that used to sit in `appsettings.json`, public now), and the error names the setting. `AddAuth` registers the resulting `SymmetricSecurityKey` as a singleton, which `JwtUtils` signs with and the bearer handler validates with. Set it once per machine:

```bash
# Local runs (dotnet run, or the Aspire AppHost in src/Server/Avalon): Development loads user-secrets.
# Each line generates a key and stores it; run one from the repo root.
dotnet user-secrets set "Application:Authentication:IssuerSigningKey" "$(openssl rand -base64 48)" --project src/Server/Avalon.Api   # bash
$b = New-Object byte[] 48; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); dotnet user-secrets set "Application:Authentication:IssuerSigningKey" ([Convert]::ToBase64String($b)) --project src/Server/Avalon.Api   # PowerShell 5.1 or 7

# Containers and every non-Development host: the environment. Keep the key out of shell history:
# put it in a file (api.env is gitignored) holding the line Application__Authentication__IssuerSigningKey=<key> ...
docker run --env-file ./api.env ...
# ... or name the variable without a value, so docker passes it through from the current environment.
docker run -e Application__Authentication__IssuerSigningKey ...

# Helm: the chart reads every secret through a Kubernetes Secret (secretKeyRef), never a plain env value.
# Either name a Secret you manage (preferred; keys listed in values.yaml; leave the chart's own secret
# values empty, or it refuses to render) ...
helm install ... --set existingSecret=avalon-api-secrets
# ... or let the chart create it, passing the key from a file (a trailing newline is trimmed).
# Without one of the two, the chart refuses to render.
helm install ... --set-file authentication.issuerSigningKey=./jwt.key
```

Rotating the key: with a chart-managed Secret, `helm upgrade` with the new file restarts the pods (a checksum annotation). With `existingSecret`, the chart cannot see the change, so after updating the Secret run `kubectl rollout restart deployment/<release>-avalon-api` (the chart's fullname; the chart renders a Deployment).

`docker-compose.yml` runs only Redis and Postgres, so it needs no key. EF design-time commands (`dotnet ef migrations ...` with `--startup-project src/Server/Avalon.Api`) need no key either: they build each context through its `IDesignTimeDbContextFactory` and never run `AddAuth`. Tests never read one: `ApiAuthHost` and the other API tests make their own key in code. Changing the key invalidates every access token already issued; clients get a 401 and refresh.

## Architecture

Avalon is split into three independently deployable real-time servers plus a REST API:

| Component | Project | Role |
|---|---|---|
| REST API | `Avalon.Api` | HTTPS/JWT, account management, OpenAPI (Scalar UI at `/scalar`) |
| Auth Server | `Avalon.Server.Auth` | TCP login flow, MFA, world-key issuance |
| World Server | `Avalon.Server.World` | Game simulation loop, packet dispatch, world lifecycle |
| Core world | `Avalon.World` | Instanced maps, entities, spell/creature systems, parties, quests, chat commands |
| Combat maths | `Avalon.Combat` | Pure combat rules (stats, hits, haste, costs, regen, heals, ability amounts), shared by the world server, the API and the balance simulator; references `Avalon.Domain` only, pinned by `CombatAssemblyShould` |
| Balance core | `Avalon.Balance.Core` | The balance simulator, grader and run contract (`Simulation.Run`, `Catalog.Describe`, `ConfigFiles.Save`); references `Avalon.Combat` and `Avalon.Domain` only, pinned by `BalanceCoreAssemblyShould` |
| Balance data | `Avalon.Balance.Data` | Reads the World seed (`HasData`) and the balance files for Core; references Core and `Avalon.Database.World` |

Shared libraries under `src/Shared/`:
- `Avalon.Network.Tcp` / `.Packets` / `.Packets.Abstractions` — custom TCP server, packet protocol (Protobuf-net)
- `Avalon.Domain` — rich domain model (Account, Character, Spell, Creature, etc.)
- `Avalon.Common` — `ValueObject<T>`, utilities, JSON converters, math
- `Avalon.Configuration` — strongly-typed config binding classes
- `Avalon.Metrics` — OpenTelemetry integration

Infrastructure: `Avalon.Infrastructure` — `IReplicatedCache` (Redis wrapper), `IMFAHashService`, `CacheKeys` (all Redis key strings centralized here), `ISecureRandom`, and `Login/` (the login policy both the Auth server and the REST API run: `PasswordLoginPolicy`, `MfaLoginPolicy`, the budgets, `RemoteAddress`, `ILoginLimits`; #478).

Three separate Postgres DbContexts (via Npgsql EF Core): `AuthDbContext`, `CharacterDbContext`, `WorldDbContext`. Auth (and Redis) is shared; every world has its own world and characters database. A world server holds one pair (`Database:World`, `Database:Characters`); the REST API holds one pair per world under `Database:Worlds` (see "REST API Worlds"). Design-time factories in each `Avalon.Database.*` project enable `dotnet ef` without a running host; the World and Character ones read their string only from their project's user-secrets and then the environment, which wins (see Commands). Sensitive data logging (parameter values in EF's logs) is on only when the host environment is Development, whatever the configuration says (`AddAvalonDatabases`, #558), for every context, the API's per-world ones included; every `Microsoft.EntityFrameworkCore` category logs at Warning and above for every logging provider, OpenTelemetry's included (`AddCustomLogging`), and `docs/configuration-reference.md` says how to raise the command log in Development.

## Packet Protocol

All client↔server communication is custom TCP with Protobuf-net. Every packet wraps a `NetworkPacket` (header + payload). The header carries `NetworkPacketType` (opcode), `NetworkPacketFlags` (encryption/compression bitmask), `NetworkProtocol` (channel grouping), and `Version`.

**Adding a packet handler:**
1. Define the packet contract in `Avalon.Network.Packets` with a `NetworkPacketType` enum value.
2. For Auth: implement `IAuthPacketHandler<TPacket>` in `Avalon.Server.Auth/Handlers/`.
3. For World (server layer): implement `IWorldPacketHandler<TPacket>` in `Avalon.Server.World/Handlers/`, decorated with `[PacketHandler(NetworkPacketType.X)]` — handlers are registered via reflection scan in `WorldServer` constructor.
4. For World (core layer): implement `WorldPacketHandler<TPacket>` in `Avalon.World/Handlers/`, also discovered by attribute scan.

Auth handlers are registered in DI and resolved manually; World handlers use `ActivatorUtilities.CreateInstance` in `WorldServer`.

**A retired opcode is deleted, not kept (owner decision, #697).** `NetworkPacketType` holds only opcodes in use: one that nothing sends or handles any more is deleted, with its packet class, and the wire schema re-exported (`tools/Avalon.Exporter -- proto opcodes corpus`). Its number may be reused once clients have re-vendored the schema without it. Nothing in `NetworkPacketType` is `[Obsolete]`. The unused chat-window packets (`CMSG_CHAT_OPEN` 0x2008, `CMSG_CHAT_CLOSE` 0x2009, `SMSG_CHAT_OPEN` 0x300A, `SMSG_CHAT_CLOSE` 0x300B) and the retired group opcodes went this way. The unused quest requests (`CMSG_QUEST_STATUS` 0x2040, `CMSG_QUEST_LIST` 0x2041, `CMSG_QUEST_QUERY_AVAILABLE` 0x2042) went this way with #433.

**A new client→server opcode also needs a session filter entry, or the handler never runs.** `MapSessionFilter` (in-map packets) or `WorldSessionFilter` (pre-character packets) must accept the opcode, not just a registered handler for it. `WorldConnection.OnReceive` only queues a packet if a filter accepts it at arrival; one no filter ever accepts skips the queue entirely and is dropped with a "could not find a handler" warning — a missing filter entry fails safe, so debug it by grepping the logs, not by hunting a frozen connection. The queue *can* wedge, but only for the narrower race where a packet's acceptance changes between arrival and dispatch (e.g. `CMSG_CHARACTER_LIST`/`CMSG_CHARACTER_LOADED` around a character spawn) — see `ProcessQueueWedgeShould.cs`. The one case the queue clears by itself is an in-map packet left behind by a character that has gone (a Change Character leave, #663): the session pass drops it while the connection holds no character (`CharacterLeaveQueueShould`).

**Reflection-bound registration — a reference grep proves nothing.** Packet handlers are discovered by attribute scan, and AI/ability scripts by type name: `ScriptManager` keys every `AiScript` subclass by `t.Name` (except those marked `[ChainedScript]`), and `ICreaturePlacementService.AttachScript` resolves `creature.ScriptName` from the DB and builds it with `ActivatorUtilities.CreateInstance(_sp, scriptType, creature, instance)`. So "nothing references this type" says nothing about whether it is used — and note that call site passes exactly two runtime arguments, so a script constructor needing anything beyond `(ILoggerFactory, ICreature, ISimulationContext)` will throw and be swallowed into a logged error. Check constructibility against that call site, not against grep — `AiScriptConstructibilityShould` does exactly that for every nameable script, against the production container. Ability scripts are bound the same way: `ScriptManager` keys every `AbilityScript` subclass by `t.Name`, `AbilityTemplate.ScriptName` names one (the column was `SpellScript` until #163), and `InstanceAbilityCastSystem` builds it with `ActivatorUtilities.CreateInstance(sp, type, ability, caster, aim, arena)` (an `AbilityAim` and the instance as `IAbilityArena`); `AbilityScriptConstructibilityShould` builds every seeded one that way. Quest scripts too (#433): `ScriptManager` keys every `QuestScript` subclass by `t.Name`, `QuestTemplate.ScriptName` names one, and `QuestService` builds it with `ActivatorUtilities.CreateInstance(new QuestScriptServices(services), type)`, no runtime arguments, from a provider that hands over only `ILoggerFactory`, `ILogger<T>` and `TimeProvider` (#738); `QuestScriptConstructibilityShould` builds every shipped one that way (see Quests). Item scripts too (see Item use): `ScriptManager` keys every `ItemScript` subclass (`Avalon.World/Items`, World-side) by `t.Name`, once, at `Load()`; `ItemTemplate.UseScript` names one; `ItemUseService` builds it once per type with `ActivatorUtilities.CreateInstance(new QuestScriptServices(services), type)`, no runtime arguments; `ItemScriptConstructibilityShould` builds every shipped and every seeded one that way. The world publishes their names in its script catalog (`item`), and an item template save checks `useScript` against it.

## Auth Flow

```
CClientInfoPacket → SHandshakePacket → CHandshakePacket → SHandshakeResultPacket
→ CAuthPacket → SAuthResultPacket (per-source limit, per-username limit, lockout, BCrypt verify, then non-Active Status refused as BANNED/DEACTIVATED, then MFA check)
→ [MFA only] CMFAVerifyPacket → SAuthResultPacket (per-source limit, per-hash attempt limit, per-username limit, lockout, TOTP ±1 step, each step once; Status re-checked)
→ CWorldListPacket → SWorldListPacket
→ CWorldSelectPacket → SWorldSelectPacket (past the connection's select budget the connection is closed before any read, #574; non-Active Status closes the connection; an unknown world or one the account may not enter is answered WorldUnavailable, the same for both, with no key or mutex and the connection left open, #554; CSPRNG world key written to Redis, SETNX inWorld mutex)
→ [new TCP to World] CExchangeWorldKeyPacket → SExchangeWorldKeyPacket (key consumed from Redis, access re-checked, inWorld mutex cleared)
```

**World select is budgeted per connection** (#574). Every select reads the account and the world, and a refused one writes a warning, so repeated selects could flood the database and the logs. `CWorldSelectHandler` first takes a slot from the connection's own `WorldSelectBudget` (`IAuthConnection.WorldSelects`): at most `Application:MaxWorldSelectsPerMinute` (default 10, startup refuses one below 1) per window of one minute fixed from its first select, measured on `TimeProvider` timestamps, with no timer. The select past the cap closes the connection before `PostLoginGuard` or any other read, and its warning is written once per window, since selects already sent keep arriving until the connection is gone. The WorldUnavailable refusal is logged at Warning once per connection per window too, and at Debug after that. A select within the cap is answered as before. So a client should not retry `DuplicateSession` automatically (the inWorld slot lasts up to 5 minutes) and should back off after `WorldUnavailable`: every select, whatever its answer, counts against the budget, and the one past it closes the connection.

**Spending the world key** (`ExchangeWorldKeyHandler`): the `DEL` spends the key, not the `GET`. Two connections presenting the same key can both read it, so the handler goes on only when `RemoveAsync` reports it deleted the key — Redis tells exactly one caller that (#450). The key is spent before any other check, so a refused exchange cannot retry it. The handler then re-checks the account against a freshly read `World` row — `Status == Active` and the same `AccessLevels.ForWorld(...).Allows(...)` rule — because the key lives five minutes and the account may have been banned or demoted since it was issued. The `inWorld` mutex is cleared only once every check has passed; a refused exchange leaves it to expire on its TTL.

**Login throttling** (`CAuthHandler`, `CMFAVerifyHandler`, `SourceBudget`, #471). The rules in this paragraph and the next live in `Avalon.Infrastructure.Login` (`PasswordLoginPolicy`, `MfaLoginPolicy`), and the REST API runs them too, over the same keys (see "REST API Auth", #478). Every password or MFA-code attempt takes a slot from its source's budget *before* any work, by an atomic increment whose returned value decides: past `MaxFailedLoginsPerSource` inside `FailedLoginSourceWindowMinutes` it is answered `LOCKED` before any account is looked up, so parallel connections cannot all slip past a check made before the first is counted. A slot is given back (`DecrementFloorAsync`, only its own, never the whole count) only once an MFA hash is issued or a login completes, as the per-username budget below describes; every other attempt keeps its slot, a correct password refused on the way and an attempt on a locked account included. The source is the full IPv4 address, or the /64 prefix for IPv6 (IPv4-mapped addresses count as IPv4); `LastIp`/`LastAttemptIp` store the full address (`RemoteAddress`). An unknown username still costs one BCrypt verify, against `BCryptPasswordVerifier.UnknownAccountHash`, and a wrong password is answered *before* its write, so response time does not reveal which usernames exist.

**The account lock is a per-username budget** (`UsernameBudget`, #484), built on the same `AttemptBudget` mechanics as the source budget. Every password attempt takes a slot keyed by the username as it is looked up (trimmed, upper-cased, then SHA-256 in the key) *before* `FindByUserNameAsync`, from every source alike and whether or not an account has that username, and every MFA code takes one from its account's username before the code is checked. The count the increment returns is the attempt's place in the window (`LockoutDurationMinutes`, fixed from the first attempt), and it alone decides, never the row as read: past `MaxFailedLoginAttempts` the attempt is answered `LOCKED` before the lookup; a wrong password (or wrong code) in the last slot is answered `LOCKED`, locks the row, and holds the key with `HoldCounterAtLeastAsync`, one Lua script that raises the count to at least `MaxFailedLoginAttempts + 1` (`UsernameBudget.HeldValue`, one past anything a run of failures reaches, so the reset below can tell a held key apart) and restarts its expiry, recreating the key if it expired after the take (a plain `EXPIRE` did nothing then, and an unknown username went back to `INVALID_CREDENTIALS` while a known one's row stayed locked); `UsernameBudget.RecordFailureAsync` computes the row's `LockedUntil` before the hold, so it always ends first, catches and logs a hold error, writes the row anyway (with `CancellationToken.None` whenever it locks, so a closing connection never skips the lock), and only then rethrows, which closes the connection; an earlier one is answered `INVALID_CREDENTIALS` (`MFA_FAILED`). An unknown username goes through exactly the same steps, answers and expiry, minus the database write. Before it, the lock was decided from the row each request read before its BCrypt verify, so parallel guesses spread over sources got about ten verifies per lockout, and the right password, reaching its success write after the batch's failures had locked the row, was the one answered `LOCKED`. Slots are given back late: a correct password gives back its own source and username slots only when it issues an MFA hash (no reset there: each password login makes a fresh hash, so a reset would hand out a fresh set of code guesses per login), and otherwise only once `TryRecordLoginAsync` has recorded the login. A **completed** login (non-MFA once recorded; MFA once the code is accepted and the login recorded) gives the source its own slot back and deletes the username's key (`UsernameBudget.ResetAsync`, owner decision), so a player's own typos do not carry over. The delete is one script (`RemoveCounterIfBelowAsync(key, heldValue)`) that runs only while the count, which still includes the login's own slot, is below `HeldValue` (the limit + 1): four typos and a login leave five and the key goes, but a hold that a concurrent last-slot failure set (with its row lock) is not deleted by a reset. The MFA-hash give-back cannot bring a hold back within reach either: `UsernameBudget.GiveBackAsync` is its own script (`DecrementCounterIfAtMostAsync(key, limit)`) that decrements only while `0 < v <= limit`, so a held value is left alone (a plain floored `DECR` let a give-back lower six to five, after which a reset deleted it, or two give-backs reached four and the next guess was verified); `SourceBudget` keeps the floored `DECR`. Known edge case: an attempt refused past the budget that lands between a login's take and its reset raises the count to six or more, so the reset keeps the key and the player is answered `LOCKED` until the window ends, with no row lock behind it. It fails closed and needs a race of a few milliseconds. The source key is never reset. Known limit: the window is fixed, not sliding, so an attacker who stays one short of the limit, four guesses every 15 minutes, never locks the account: about 384 guesses a day per username (4 × 96 windows). A budget window longer than the lockout (say a day, with the refusal still ending when the row's lock does) would close that; the mechanism is unchanged for now. Failed logins are still counted in SQL (`IAccountRepository.RecordFailedLoginAsync`, one `UPDATE` whose right-hand sides all read the old row), never by writing back the row that was read, so concurrent failures are not lost; the caller passes `lockUntil` when the budget says the failure locks, and the row stays locked until `LockedUntil`. An expired lock is lifted there too, and by the success write, `TryRecordLoginAsync`, which refuses if the account is locked at write time, so a success can never write away a lock set after it read the row; that refusal is answered as a wrong password in the same slot would be (`INVALID_CREDENTIALS`/`MFA_FAILED`, or `LOCKED` in the last slot) and keeps both slots, so on the offline, Active, non-MFA path (and at MFA verify, the offline Active path) it does not single out the right password in a parallel batch. `MFA_REQUIRED`, `ALREADY_CONNECTED` and `BANNED`/`DEACTIVATED` do single out a correct password inside the budget, by design. A lock with `LockedUntil = null` never expires; the migration that added the column gave every earlier lock a 15-minute end. The row's lock check stays before the password (and code) check on purpose: after it, a locked account would still tell right from wrong passwords. Each MFA hash allows `MaxFailedMfaAttempts` codes, counted on the `auth:account:{accountId}:mfa` hash before the code is checked; the last failure deletes the hash, so the client must log in again, and a code whose hash is gone (no reverse key, or `attempts` of -1) is refused without being checked. All these settings are under `Application` in the Auth server's config, and again, with the same names, under `Application:Authentication` in the API's; the two must match, since both count on the same keys.

**Account rows are written by column, never whole** (#484). The auth server never calls `UpdateAsync(account)`: clearing a stale `Online` flag at login or MFA verify is `MarkOfflineAsync`, a disconnect is `MarkOfflineAsync` with the session's seconds added to `TotalTime` (`AuthConnection.RecordDisconnectAsync`), the start-up reset is one `MarkAllOfflineAsync`, and world select stores its key with `SetSessionKeyAsync`. Each is an `ExecuteUpdate` that never touches `Locked`, `LockedUntil`, `FailedLogins` or `Status`, so a ban or a lock written between the read and the write survives it.

**`Online` belongs to one connection (#487).** A TCP login (`TryRecordLoginAsync`) stores the logging-in connection's `Id` in `Accounts.OnlineSessionId` with `Online = true`. `MarkOfflineAsync(id, sessionId, seconds)` clears both only while `OnlineSessionId` still equals `sessionId`, in one statement, and adds the seconds to `TotalTime` either way, so a close that lands after a newer session of the account logged in leaves that session online. A disconnect passes its own connection id; the stale-flag clear at login or MFA verify passes the session id it read. **Exactly one auth server is supported:** the start-up `MarkAllOfflineAsync` clears every `Online` flag and session, and the `ALREADY_CONNECTED` check looks only at this server's connections, so a second server would break both (the Helm chart runs one replica). **A liveness sweep (#555)** relies on the same assumption: every `Application:OnlineSweepIntervalSeconds` (default 30, startup refuses below 1), `OnlineSweep`, run from `AuthServer.ExecuteAsync` on an absolute `TimeProvider` due time (a late pass sweeps once), reads only the online rows' id and session (`ListOnlineSessionsAsync`) and calls `MarkOfflineAsync(id, sessionId, 0)` for each whose session is none of this server's live connections, so a close whose write failed does not leave the account online until the next restart; the compare keeps a login that landed since, and a sweep that throws is logged and the next still runs. A half-open TCP connection is still live to it, so every socket the shared `ServerBase` accepts (auth and world) has TCP keepalive on (#571, `TcpKeepAlive`; `Hosting:TcpKeepAliveTimeSeconds`/`TcpKeepAliveIntervalSeconds`/`TcpKeepAliveRetryCount`, default 60/10/3, startup refuses below 1 or above the OS maximum), and the OS closes one within about 90 s, which runs the close path. **The accept loop (#578, #584)** is one awaited `AcceptTcpClientAsync` loop started by `ServerBase.StartListening`, which `ServerBase.StartAsync` calls at host start unless the server's `ListenOnStart` is false; the world server's is (#665), and it calls `StartListening` at the end of `ExecuteAsync`, once scripts, the world, the cache subscription, the connection listener and the tick thread are ready, so no client is accepted while the world loads or after a load that failed (a port that cannot be bound fails the start and stops the tick; `WorldServerStartupShould`): only a stop ends it (`StopAsync` cancels it and awaits it before `OnStoppingAsync`, and is idempotent); a failed accept outside a stop is counted (`avalon.tcp.accept.errors`), warned at most once per 10 s, and retried, at once for a peer reset and otherwise after a backoff of 100 ms doubling to 5 s. A client accepted once the stop began is closed, and a packet arriving then is dropped, not dispatched; the shutdown closes its connection.

**What a username may be (owner decision, #487 re-review):** 3 to 16 ASCII letters, digits or underscores (`UsernameRule`, `^[A-Za-z0-9_]{3,16}$`), checked as sent, before trimming or upper-casing. `POST /account/register` refuses anything else with a 400 validation error (`UsernameRuleAttribute` on `RegisterRequest.Username`, and again in `AccountService.Register`). A login with anything else (`PasswordLoginPolicy`, so TCP and REST alike) is answered exactly as an unknown username: both budgets, the lookup, one dummy verify, `INVALID_CREDENTIALS` or the generic 401, whatever row holds the normalised form. With ASCII letters only, .NET and Postgres upper-case alike, so the check constraint below cannot disagree with the code.

**One account per username (#487).** `Accounts.Username` has a unique index (`IX_Accounts_Username`). Usernames are stored trimmed and upper-cased, the form login looks up, so the index is on the normalised name. Registration still checks first; a registration that loses the race to the index gets the check's answer, "Username already exists". A check constraint, `CK_Accounts_Username_Normalised` (`"Username" = upper(trim("Username"))`), refuses a row that is not stored normalised, whoever writes it. The migration that added the index refuses to run, naming the accounts, when two accounts share a normalised username or a username is not stored normalised; it never deletes or rewrites a row.

**One account per email (#503).** `Accounts.Email` has a unique index (`IX_Accounts_Email`) and a check constraint, `CK_Accounts_Email_Normalised` (`"Email" = lower(trim("Email"))`). Emails are stored trimmed and with the whole address lower-cased, local part included (`AccountEmail.Normalise` in `Avalon.Domain.Auth`, chosen over folding the domain only), and `FindByEmailAsync` normalises what it is given, so `A@x.com` and `a@x.com` are one account. An email must be printable ASCII with exactly one `@`, neither first nor last (`AccountEmail.IsValid`; `[EmailAddress, AccountEmailRule]` on the request and again in the service, 400 otherwise): outside ASCII .NET and Postgres can lower-case differently, and the check constraint would refuse what the code stored. A check violation (SQLSTATE 23514) on `Accounts` that still reaches the API, direct or wrapped by SaveChanges, is a 400 (`ExceptionHandlerMiddleware`), not a 503. Registration and the start of an email change refuse a taken address as "Email already exists"; both take a slot of the source's budget before the lookup, kept on that answer, so it is never free; a registration or an email confirm that loses the race to the index gets the same answer. The migration that added the index refuses to run, naming the accounts, when two accounts share a normalised email or an email is not stored normalised; it never deletes or rewrites a row.

**TOTP codes are single-use** (`MFAService`, #471). `MfaSetups.LastAcceptedTotpStep` stores the step of the last accepted code, set at confirm and advanced by `TryAcceptTotpStepAsync`, which writes only when the new step is later. A code at or before that step is refused, and the window is ±1 step for both confirm and verify. A hash has one winner (#478): once a right code's step is accepted, the code spends the hash with `IMFAHashService.TryConsumeAsync`, and only the caller whose `DEL` removed the reverse key goes on, so two verifies of one hash with codes of adjacent steps cannot both pass. The step is accepted first on purpose: a replayed code (right, already used) is refused as `MfaCodeRefusal.Replayed` without spending the hash, and like a code that lost the hash (`HashSpent`) it is not a failed login: `MfaLoginPolicy` gives its slots back and writes nothing to the row. A replay also gives back the attempt it counted on the hash (`IMFAHashService.GiveBackAttemptAsync`, a script that decrements `attempts` only while the hash exists, never below zero); a code that lost the hash does not, since that per-account key may already hold the next login's hash.

**Every post-login auth handler starts with `PostLoginGuard.AccountOrCloseAsync`** (#495 review): MFA setup, confirm and reset, the world list and world select. It reads the account fresh and closes the connection unless it is logged in, the account exists, is `Active`, and is still at the `CredentialsVersion` this connection's login proved; so a session banned, deactivated or outdated by a credentials change since its login can neither change MFA nor get a world key. MFA confirm and reset also carry the session's version into their write (`IMFAService.ConfirmMFAAsync`/`ResetMFAAsync(accountId, credentialsVersion, ...)`): `MfaSetupRepository.TryConfirmAsync` and `ResetConfirmedAsync` start their transaction with `HoldCredentialsVersionAsync`, so a change committed between the guard and the write refuses it (`MfaSetupWrite.CredentialsChanged`, `CredentialsChanged` on the result); the TCP handler then closes the connection and the REST endpoint answers 401.

**World access** is decided by `AccessLevels.ForWorld(world.AccessLevelRequired).Allows(account.AccessLevel)`, the same test in `CWorldListHandler` (what is listed) and `CWorldSelectHandler` (what can be entered). A Player world admits every player, Tournament and PTR included; a Tournament or PTR world admits holders of that flag plus staff; a staff-gated world admits its staff mask. Never compare a world's level with `<=`: `AccountAccessLevel` is `[Flags]`, and PTR (32) and Tournament (16) are numerically above Admin (4), which is how PTR accounts used to reach the Admin-only world.

**Key Redis patterns** (all string literals in `CacheKeys`):
- `world:{worldId}:keys:{base64}` — one-time world entry token (5 min TTL)
- `account:{accountId}:inWorld` — duplicate session mutex via `SETNX` (5 min TTL)
- `auth:mfa:hash:{hash}` — an MFA hash's reverse key, `{accountId}:{credentialsVersion}` (#495), 2 min TTL; its `DEL` spends the hash
- `auth:account:{accountId}:mfa` — Redis Hash with MFA state (2 min TTL); its `attempts` field counts MFA codes tried against it (`HINCRBY`, only while the hash exists); a replayed right code gives its attempt back (one script: `HINCRBY -1` only while the hash exists and the field is above zero)
- `auth:source:{source}:failedLogins` — attempt budget per source (IPv4 address, or IPv6 /64 as `prefix::/64`), shared by the TCP login and the REST API (#478), `INCR` with the expiry set on the first attempt (fixed window, default 15 min); a correct password or MFA code gives its own slot back with a floored `DECR`
- `auth:source:{source}:accountsCreated` — accounts created by one source through `POST /account/register` (#495 review), `INCR` before the insert with the expiry set by the first (fixed window, default 60 min, cap default 5); given back only when no account is created
- `auth:emailChange:{sha256}` — a pending email change, keyed by the lowercase hex SHA-256 of its confirm token, never the token itself (#510 review); value `{accountId}|{credentialsVersion}|{email}`, 15 min TTL; the confirm hashes the presented token, and its `DEL` spends it
- `auth:account:{accountId}:emailChangePending` — the token hash of the account's one pending email change (15 min TTL). A start whose confirmation was sent swaps it in one script (`SwapAsync`: `GET` and `SET ... PX` together) and deletes the entry the old value names, so only the latest token confirms; a successful confirm deletes it only while it still names the confirmed token's hash (`RemoveIfEqualsAsync`, one script)
- `auth:account:{accountId}:emailChangeSends` and `auth:email:{sha256(normalised new email)}:emailChangeSends` — email-change confirmations sent per account and per new address (#510 review), `INCR` just before the send with the expiry set by the first (`Application:Authentication:EmailChangeSendWindowMinutes`, default 60; `MaxEmailChangeSendsPerAccount` and `MaxEmailChangeSendsPerAddress`, default 3 each, startup refuses below 1); never given back; past either, 429 `LOCKED` and nothing is stored or sent
- `auth:username:{sha256}:failedLogins` — attempt budget per username (lowercase hex SHA-256 of the trimmed, upper-cased username, whether or not an account has it), shared by password and MFA-code attempts from every source and by both servers (TCP and REST, #478); `INCR` with the expiry set on the first attempt (`LockoutDurationMinutes`, default 15 min); the failure that reaches `MaxFailedLoginAttempts` holds it with one script (raise to at least the limit + 1, `SET ... PX` the window, recreating an expired key); a correct password that issues an MFA hash gives its own slot back with one script that decrements only while `0 < v <= limit` (never lowering a held value); a completed login deletes it with one script, only while its value is below the held value, limit + 1 (so a reset never deletes a hold)
- `world:accounts:disconnect` — pub/sub, force-disconnect by accountId: published by the Auth server and the API (duplicate login, password change, MFA reset or removal, ban, email change, role change, refresh-token reuse); subscribed by the World server, which closes every connection of the account (`WorldServer.CloseAccountSessions`, #504 review; not only the first), and, since #495, by the Auth server, which closes that account's logged-in TCP connections with `DisconnectReason.Kicked` (`AuthServer.CloseAccountConnections`). The message is the bare id and cannot say why, so both servers tell the player the same neutral "Your session has ended. Please log in again." with `Kicked`; only the world server's own duplicate-login kick at character select says "logged in from another location". A TCP MFA reset therefore ends the connection that made it, too. The message is the bare account id the World server parses, so it carries no origin: before its own duplicate-login publish (`ALREADY_CONNECTED`) the auth server notes it (`NoteOwnDisconnectPublish`), and for `OwnPublishWindow` (10 s) a connection of that account that logged in after the note (`IAuthConnection.LoggedInAt`) is spared, so the retry that follows is not kicked by its own attempt (the note lasts its whole window, whatever messages arrive, because a ban and the echo cannot be told apart and a note consumed by the first let the second kick the retry; expired notes are dropped on read and pruned on every write, so the map holds only the last window's publishes); world select's version and status checks cover anything else that lands in that window. One connection that throws while closing is logged and the rest are still closed.
- `auth:accounts:online` — pub/sub: login event (reserved, no subscriber yet)
- `world:{worldId}:select` — pub/sub: world-select event (reserved, for future sharding)
- `world:{worldId}:presence` — one world's live presence snapshot (`WorldPresenceSnapshot`: its instances and the characters in them), captured on the tick about once a second by that world server's `PresenceCapture` (`Avalon.World/Presence`; `WorldServer.Update` calls `CaptureIfDue` in the serial phase after the world update, timed by the container's `TimeProvider`, no timer) and handed through one volatile reference to `PresenceSnapshotService` (`Avalon.Server.World`), which polls every 250 ms off the tick and writes each snapshot it takes once (#639), with `CacheKeys.PresenceTtl` (5 s); a stalled tick captures nothing, so the keys expire, and a capture that finds nobody in the world drops any snapshot not yet written
- `presence:world:{worldId}:character:{id}` — which instance of that world holds character `{id}` (`CharacterPresenceIndex`), same writer and TTL. It names the world because character ids are unique only per world (#556). A deploy that changed a presence key loses the entries under the old key; they expire within the TTL and each world server writes the new ones on its next capture, so nothing needs migrating

## REST API Auth

`Avalon.Api` takes two credentials:
- an access JWT, sent as `Authorization: Bearer` or in the `AVToken` cookie, and minted by `JwtUtils` at login, MFA verify and refresh;
- a personal access token, sent as `Authorization: Avalon avp_...` and read by `AvalonAuthenticationHandler`.

**Neither is believed on its own (#451, #480).** On every request both go through `AccountAccessCheck` (`Avalon.Api/Authentication`):
- the account is reloaded;
- a missing or non-Active one (Banned, Deactivated) is refused with 401;
- the request carries only `credential roles & account.AccessLevel` as `GroupSid` claims. That is a mask, never `>=`.

For a JWT this runs in `JwtBearerEvents.OnTokenValidated` (`JwtAccountRevalidation`), after the bearer handler has checked the signature (HS256 only, `ValidAlgorithms`), issuer, audience and lifetime. The loaded account is kept in `HttpContext.Items`, and `AvalonAuthHandler` (the default policy's requirement) reuses it rather than loading it again. A ban therefore takes effect on the next request. A role change, promotion or demotion, raises the credentials version (#504), so every token issued before it is refused and the account signs in again to get its new roles. A database failure during that lookup is a 503 (`ExceptionHandlerMiddleware` maps `DbException`), never a pass.

The JWT's lifetime is enforced: `ValidateLifetime = true`, with `AccessTokenLifetimeMinutes` (default 15) plus `ClockSkewInMinutes`. An expired JWT gets a 401, and the client renews it with `POST /account/refresh`. That endpoint is `[AllowAnonymous]` and reads only the HttpOnly refresh cookie, so an expired access token does not stand in its way.

**A refresh token rotates once (#495).** `RefreshTokenRepository.RotateAsync` revokes the parent with a conditional `UPDATE ... WHERE Id = @id AND NOT Revoked` and inserts the child, in one transaction, only when that write revoked the row: of two rotations of one token that both read it live, exactly one gets a child. The other (`RefreshRotation.ParentNotLive`) is answered as the same token presented a moment later would be. A revoked token presented within `RefreshTokenService.RotationGrace` (5 s) of the rotation that replaced it, while that rotation's child is still unused (not revoked, `Usages == 0`) and by the caller that rotated it (the child records its source, the login budget's IPv4 address or IPv6 /64, in `RotatedBySource`, and a SHA-256 of its User-Agent in `RotatedByAgentHash`; `RefreshCaller`; a caller whose address, after the forwarded-headers middleware, is still a trusted proxy (loopback or `Application:ForwardedHeaders` proxies and networks, i.e. a proxy that forwarded no client) gets no source and so never the grace, since everyone behind that proxy shares it), is two tabs or a client retry: 401 (`RefreshAlreadyRotatedException`), with the family, the refresh cookie and the account's sessions left alone. Anything else is a reuse: the family is revoked, `RefreshTheftException`, a world disconnect is published, the cookie is cleared and the caller gets 401. A reuse is logged at Warning with the account, the family and which condition of the grace it missed (no successor, successor revoked or used, after the grace, caller without a source, another caller), never the caller's address or the token, so a session ended by two tabs refreshing at once can be told from a sign-out.

**Nothing issues a credential to an account that is not Active** (`AccountAccessCheck.MayHoldSession`):
- password login (`AccountService.Authenticate`) checks after the BCrypt verify, and MFA verify after the code is accepted. Both throw `AccountInactiveException`, which `ExceptionHandlerMiddleware` answers as 403 ProblemDetails with `Detail` BANNED or DEACTIVATED, as the game client is told. A wrong password or bad code still gets the generic 401, whatever the status, so nothing about the account leaks before the proof;
- refresh revokes every refresh token the account holds, clears the cookie and returns 401.

**REST login and MFA verify run the game client's login policy (#478).** `AccountService.Authenticate` runs `PasswordLoginPolicy` and `MFAController.VerifyMFA` runs `MfaLoginPolicy`, the classes `CAuthHandler` and `CMFAVerifyHandler` run, in the same order: source slot, username slot before the lookup (a dummy BCrypt verify for an unknown username), the row's lock before the password or code, per-hash attempts (the last wrong code deletes the hash), failures counted with `RecordFailedLoginAsync` and locking in the budget's last slot, and on a completed login the source's slot back and the username's count cleared. The keys are the same on both servers, so a guess over REST and one over TCP spend one per-username budget and lock at one threshold; the per-source key is shared too, since that budget is per address across every account and a guesser must not get it twice by splitting guesses between servers. The API's source is `HttpContext.Connection.RemoteIpAddress` after `UseAvalonForwardedHeaders` (`Middlewares/ForwardedHeadersSetup.cs`), which believes `X-Forwarded-For` only from loopback and from `Application:ForwardedHeaders:{KnownProxies,KnownNetworks}` (with `ForwardLimit`, default 1; Helm `forwardedHeaders.*`). Behind an ingress not listed there every REST caller is one source, so outside Development the API warns at startup when none is configured, and it logs a header from an untrusted peer at most once a minute (`UntrustedForwardedHeaderLog`). An entry that does not parse, a trusted network wider than /8 (IPv4) or /32 (IPv6), `0.0.0.0/0` and `::/0` included, or a limit below 1 stops startup. A caller with no peer address has its `X-Forwarded-*` headers dropped before they are read, so it cannot name one, and is refused with 400 on every endpoint that spends a source budget (`BaseController.SourceAddress`), rather than sharing one `IPAddress.None` budget. A locked row pays the same dummy BCrypt verify as an unknown username, so it does not answer faster when its budget hold is gone. A refusal by a budget or a locked row, and the failure in the last slot, is **429** ProblemDetails with `Detail` `LOCKED` (`AccountLockedException`); a wrong password or code stays the generic 401, and 403 `BANNED`/`DEACTIVATED` still comes only after the proof (#480). HTTP cannot answer before its write, so an unknown username runs the same failure statements against `LoginPolicy.NoAccount` (id 0, which no account has). A REST login never touches `Online`, the game client's session flag: the success write is `TryRecordApiLoginAsync` (by column, refused while locked, answered as a wrong password in that slot). The limits are `Application:Authentication:{MaxFailedLoginAttempts,LockoutDurationMinutes,MaxFailedLoginsPerSource,FailedLoginSourceWindowMinutes,MaxFailedMfaAttempts}`, defaults equal to the Auth server's, which they must match; `AddInfrastructure` refuses one below 1, and both hosts log all five at Information at startup (`LoginLimitsValidation.LogAtStartup`) so a drift shows.

**Sensitive actions need the current password (#478, #483).** `IReauthentication.RequireCurrentPasswordAsync` runs `PasswordLoginPolicy` against the signed-in account, so a wrong current password is a failed login in every respect (both budgets, the row's count, the lock); a right one gives back only its own slots. It guards `POST /account/password`, the start of an email change (`InitiateEmailChangeAsync`, a `currentPassword` field, #503), `POST /mfa/setup` (was `GET`; body `SetupMFARequest { currentPassword }`), and `POST /pat` and `POST /pat/admin` (a `currentPassword` field; the admin route takes the admin's own, since it can mint for any account, the admin's included). Missing or wrong: 401 `Invalid current password`; budget spent or account locked: 429 `LOCKED`. New passwords are measured trimmed, the form they are hashed in: `POST /account/password` (`newPassword`) and `POST /account/register` (`password`, with `username` and `email` required) refuse one under 8 characters with a 400 validation error (`TrimmedMinLengthAttribute`).

**Every request is rate limited (#561)**, on top of the budgets above, which count attempts and are unchanged. `ApiRateLimiting` (`Middlewares/`) puts ASP.NET Core's limiter, a sliding window of one minute in six segments, in memory (one replica), after `UseAuthentication` and before the world routes and authorization. A request with a valid JWT (after its account revalidation) or personal access token (authenticated there, since it is not the default scheme, and only on an endpoint that requires authorization, while enabled, and while its source has failed fewer than `FailedPatLookupsPerMinute` (10) lookups and has fewer than 2 in flight, so made-up tokens cannot force a query per request; the handler's cached result is reused by authorization) counts against its account, `AuthenticatedPermitsPerMinute` (default 300); any other, an invalid token included, against its source, `RemoteAddress.SourceOf` after the forwarded headers (IPv4 address, IPv6 /64), `AnonymousPermitsPerMinute` (default 60), and so does a PAT on the public endpoints (`/public/...` have no `IAuthorizeData`, so it is not identified before the limiter; it counts against its source's anonymous budget, and `PublicCaller` looks it up afterwards, outside the `FailedPatLookupsPerMinute` budget); every caller with no peer address shares one "unknown" partition. `/health` and `/alive` are exempt (`DisableRateLimiting` in `MapDefaultEndpoints`). A refusal is 429 ProblemDetails `LOCKED` with `Retry-After` (a lower bound, one segment when the limiter gives no hint), alike for both partitions, and increments `avalon.api.rate_limit.rejections` (meter `avalon-api`, tag `partition`). Settings under `Application:RateLimiting` (`Enabled` too); a limit below 1 fails the startup validation `ApiStartup` runs, naming the setting.

**Registration is budgeted per source (#495).** `POST /account/register` still answers "Username already exists" and "Email already exists" (a registration form cannot hide a taken username, and merging the two answers would still reveal the email by pairing it with a fresh username), so it takes a slot from the source's budget (`SourceBudget`, the key TCP and REST logins spend) before any lookup; past the budget it is 429 `LOCKED`, whatever the name. A registration that creates its account gives the slot back; "already exists" and every other ending keep it. That budget alone does not bound account creation, since successes are refunded, so a second, separate cap counts created accounts per source: `Application:Authentication:MaxAccountsCreatedPerSource` (default 5) per `AccountCreationWindowMinutes` (default 60, fixed from the first), on `auth:source:{source}:accountsCreated`. Its slot is taken just before the insert and given back only when no account comes of it; past the cap the answer is 429 `LOCKED`. API only; startup refuses a value below 1. A caller with no peer address is refused with 400, as at login.

**A password change and an MFA reset revoke every token (#483).** `ChangePasswordAsync` writes the verifier by column (`AccountRepository.SetPasswordAsync`, a compare-and-set on the `CredentialsVersion` the current password was checked at, so of two changes that proved the same password only the first lands and the other is 401 `Credentials changed; sign in again`, #495 review) and revokes every refresh token and personal access token in one transaction; `MFAService.ResetMFAAsync` (both servers) deletes the confirmed row and revokes both kinds in one transaction (`MfaSetupRepository.ResetConfirmedAsync`, which also makes a concurrent second reset fail). Each then publishes the account on `world:accounts:disconnect`, best-effort, as the admin MFA removal (#475) and a ban do. `POST /mfa/reset` returns 204 and enrols nothing: the client enrols again with `POST /mfa/setup`, which needs the password, since recovery codes are not the password.

**A role change and an email change are credentials changes (#503, #504).** `AccountService.UpdateRolesAsync` (`PATCH /account/{id}/roles`, now with the admin as `actorId`) writes the level and raises the version in one statement (`AccountRepository.SetAccessLevelAsync(context, ...)`), and revokes every refresh token and personal access token in the same transaction; a promotion does it too, since only a new login gets the new roles onto the game client's TCP session. `ConfirmEmailChangeAsync` does the same with `AccountRepository.SetEmailAsync(context, ...)`, a compare-and-set on the version the current password was checked at when the change was started (the pending change in `auth:emailChange:{sha256(token)}` is `{accountId}|{version}|{email}`), so a credentials change in between voids it, answered "Invalid or expired token". Each then clears the account's pending MFA login state and publishes the account on `world:accounts:disconnect`, best-effort, as a password change does. **Email change is on only when `Application:Email:Sender` is configured (#510):** `ServiceRegistration.AddEmail` registers an `IEmailSender` (`Avalon.Api/Services/Email`) for a configured sender and none for `None`, the default, and `AccountController` takes it as an optional dependency: with none, `POST /account/email/change` and `POST /account/email/confirm` both answer 501 ProblemDetails "Email change is unavailable until email delivery exists" and never reach the service. `Pickup` (`PickupEmailSender`) writes each email as an RFC 5322 `.eml` file into `Application:Email:PickupDirectory` (default `avalon-mail` under `Environment.SpecialFolder.LocalApplicationData`, created 0700 on Unix), refuses a line break in the recipient or subject, and is Development-only: startup refuses it elsewhere, naming `Application:Email:Sender`, and refuses it without a bare-address `Application:Email:From`. With a sender, the start sends the confirm token to the **new** address and a notice with no token to the old one, and answers 202 with no body; the token is never in the response or a log (sender failures are logged by exception type and recipient domain only). Before anything is stored or sent, the start takes a slot of two send budgets that are never given back, per account and per new address (keys above; past either, 429 `LOCKED`). Accepted: the per-address send budget can be spent by any accounts, so three accounts can block an address as a change target for the window; account creation is capped per source, which keeps the impact small. Once its confirmation is sent, a new start deletes the account's earlier pending change, so only the latest token confirms; a start that could not send leaves the earlier one intact. Once the change is stored, each email is sent with its own `AccountService.EmailSendTimeout` (30 s) token, never the request's, so a caller dropping the connection cannot suppress the notice. A confirmation that cannot be sent deletes the pending change (a failed delete is logged by exception type, and the key expires on its TTL) and is 503 "Email could not be sent" (`EmailDeliveryException`), keeping the source slot and both send slots; a cancelled send is logged at Information, any other failure at Error. A failed notice is a Warning and the change still starts. No real provider exists yet; one goes behind the same interface. **For whoever adds one:** a sender that delivers the email and then throws (a timeout after the provider accepted it, say) leaves a delivered token whose pending change was deleted. That fails closed: the token answers "Invalid or expired token" and the player starts again, within the send budgets.

**Credentials version (#495).** `Accounts.CredentialsVersion` is an integer raised by one, as the first statement of the change's transaction, by every password change (`AccountRepository.SetPasswordAsync`), role change (`SetAccessLevelAsync`, #504), email change (`SetEmailAsync`, #503), owner MFA reset (`MfaSetupRepository.ResetConfirmedAsync`, both servers) and admin MFA removal (`AccountService.RemoveMfaAsync`, via `BumpCredentialsVersionAsync`). Whatever a proof of the credentials issues carries the version of the very row the proof was checked against, and every check is an equality with the account's current version: the access JWT's `cver` claim (`JwtUtils.CredentialsVersionClaim`; `JwtAccountRevalidation` refuses a missing, malformed or different one with 401); each refresh token's `CredentialsVersion` column, set when its family is opened and copied to every child (`IssueAsync(accountId, version)` at login, MFA verify and registration, and every rotation, refused when it no longer matches; the refresh endpoint also refuses when the account read after the rotation is at another version); the MFA hash's own reverse key, `auth:mfa:hash:{hash}` = `{accountId}:{version}` (`IMFAHashService.GetHashCredentialsVersionAsync(hash)`, -1 when absent; the presented hash's version, never the per-account record's, since two logins racing with the old and the new password share that record, #495 review; `MfaLoginPolicy` treats a mismatch as a hash that is gone, on both servers, checked before an attempt is counted so a stale presentation spends none of a newer login's tries, and `CleanupHash` deletes the per-account record only while its `hash` field is the hash being cleaned (`RemoveHashIfFieldEqualsAsync`, one Lua script), and a live hash is reused only at the same version); `Reauthenticated(AccountId, CredentialsVersion)` for a personal-access-token mint (the admin's own account on `POST /pat/admin`); and, on TCP, `IAuthConnection.CredentialsVersion`, set at login and MFA verify, checked by `PostLoginGuard` and stored in the world key's value (`CacheKeys.WorldKeyValue`, `{accountId}:{version}`), which `ExchangeWorldKeyHandler` checks against a fresh read. Issuing a refresh token, rotating one and minting a PAT each open their transaction with `AccountRepository.HoldCredentialsVersionAsync`, a no-op `UPDATE ... WHERE Id = @id AND CredentialsVersion = @v`: it takes the row lock, so a change that committed first refuses them, and one still in flight waits for them and then revokes what they issued. A password change also clears the account's pending MFA state in Redis, as an admin's MFA removal does. A refused refresh issue or PAT mint is 401 `Credentials changed; sign in again`.

**The API writes account rows by column (#478)**, as the Auth server has since #484: login and MFA verify `TryRecordApiLoginAsync`, password `SetPasswordAsync`, email `SetEmailAsync`, roles `SetAccessLevelAsync` (the last three on the context of the transaction that revokes the tokens). None writes back a row it read, so a ban or a lock written in between survives (`ApiWriteRaceShould`).

## REST API Worlds

A deployment runs any number of world servers, one per auth `Worlds` row, each with its own world and characters database (#523). The API reaches every configured world; adding one is configuration only.

- **Configuration:** `Database:Worlds:<id>:World:ConnectionString` and `...:Characters:ConnectionString` (environment `Database__Worlds__2__World__ConnectionString`), `<id>` the auth `Worlds` row's id. `WorldDatabaseSettings.Parse` reads it, and `WorldDatabaseSettings.TryParseWorldId` is the one parse of a world id, for the configuration keys and the route alike (ASCII digits, 1 to 65535, no sign, no leading zero: `01` is refused, never read as world 1). It is deliberately not an options validation: `ApiStartup.ValidateAndMigrateAsync` resolves `WorldDatabases` right after `IStartupValidator.Validate()` (which checks `Database:Auth:ConnectionString` through `ValidateDatabasesOnStart(DatabaseConnections.Auth)`), and that stops startup, naming the setting and never its value, for no world, an id not in that form, half a pair, or a blank string. OpenAPI generation starts the host but skips `ApiStartup`, and `WorldDatabases` is built only when first resolved, so generation needs no world. The API reads no singular `Database:World`/`Database:Characters`. `appsettings.json` lists no world, so the published image ships none; `appsettings.Development.json` holds world 1 (the docker compose databases) for local runs, and the Aspire AppHost sets the same pair through the environment.
- **Helm:** a `worlds` map keyed by world id (`worlds.<id>`), every string held in the Secret (`secretKeyRef`). Chart-managed Secret: give `worlds.<id>.world.connectionString` and `worlds.<id>.characters.connectionString` (`--set-file`), stored under `database-world-<id>-connection-string` and `database-characters-<id>-connection-string`. With `existingSecret`: give no strings; the Secret holds those default keys, or the names in `worlds.<id>.worldKey`/`charactersKey`, which are accepted only with `existingSecret`. The chart refuses to render with no world, a world id not in the API's form, half a pair (chart-managed), an inline string with `existingSecret`, a key that is not a valid Secret key name or that two settings would read (the chart's own keys included), and the removed `database.world`/`database.characters` values.
- **Per-request world:** repositories stay singletons over `IDbContextFactory<WorldDbContext>`/`<CharacterDbContext>`, which in the API are `CurrentWorldDbContextFactory<T>`: they read the request's scoped `ICurrentWorld` through `IHttpContextAccessor` and throw `InvalidOperationException` ("No world selected for this request") when there is none, never falling back to a world. Code that needs a named world uses `IWorldDbContextFactory` (`CreateWorld`/`CreateCharacters`, caller disposes) or `IWorldRepositories` (the same repositories over one world).
- **Routes:** world content and characters live under `/world/{worldId}/...` on controllers marked `[WorldScoped]` (character, with its `inventory`, `abilities`, `stats` and `quests` sub-resources, map-template including `chunk-asset`, item-, ability-, creature- and quest-template, and `observability/character/{id}`); a test pins that a route names `{worldId}` exactly where `[WorldScoped]` is. `[PublicWorldScoped]` (`PublicController`) is the anonymous-friendly variant, under `/public/world/{worldId}/...` (item and ability tooltips; `GET /public/world` lists readable worlds, default from `Application:PublicWorldId`), pinned the same way: an anonymous caller counts as a Player (`PublicCaller`; a signed-in one has their own level, floored at Player), a world they may not enter is the same empty 404 before any 503 (same non-disclosure order as below, one shared helper in `WorldRouteMiddleware`), and the response is `Cache-Control: public, max-age=300` on a world every player may enter and `private, max-age=300` on one only the caller may (the world list is `private, no-cache`). A guard test allows only GET on these routes. **Link previews (#308):** `PublicPreviewController` serves `GET /public/preview/item/{id}` and `/ability/{id}` (`?world=N`, else the default world `GET /public/world` would pick, through the shared `PublicWorlds`), a tiny scriptless HTML page of `og:`/`twitter:` tags for bots that run no JavaScript (the public site's nginx routes them here). The route names no world, so the controller applies the same order itself (bad or unreadable or unconfigured world, or missing id: a 404 page "Not found · Avalon"; 503 only for a readable world whose databases failed); `Cache-Control: public, max-age=300` (private for a world only the caller may enter, or a default that depends on the caller). Everything from game data is HTML-encoded; `og:url` is `Application:PublicSiteUrl` (no default; Helm `publicSiteUrl`; validated at startup, trailing slash dropped) + `/item/{id}`, with `?world=N` only when named, and unset it is left out and the link is relative. The site name and the rarity and ability colours are `Application:Previews` (defaults in `appsettings.json`, mirroring the Dashboard's `rarity.ts`; an invalid colour means no `theme-color`). `LinkPreviewText` builds the one-line description (capped at 200 characters) from the tooltips' wording; templates have no description or flavour text, so abilities end with the tooltip's amount line. `WorldRouteMiddleware`, between authentication and authorization, in order: a world endpoint that allows anonymous callers → 404 (fails closed; none does); it then authenticates through the default policy (so a PAT is checked like a JWT), and an unauthenticated caller passes on to the 401; a world id not in canonical form → 404 with nothing looked up; no auth row, `AccessLevels.ForWorld(world.AccessLevelRequired).Allows(caller)` fails, or not under `Database:Worlds` → the same empty 404 (the row is read before the configuration is asked, so an unconfigured world costs the same lookup as a restricted one, and a restricted world is never revealed, even while unavailable); unavailable → 503 ProblemDetails "World {id} is unavailable"; otherwise it selects the world and the endpoint's role policy decides. `GET /world/{id}` is the auth world lookup, not world-scoped.
- **Availability:** `ApiDatabaseMigrator`, called by `ApiStartup` after the checks above, migrates auth (a failure stops the API), then each world's World and Characters databases; a failure is logged with the world id and exception type only and marks the world `Unavailable` until the next restart. No retry; each unreachable world adds the driver's connect timeout to startup. `IWorldDatabases.IsAvailable` is the one test of "this API can serve that world". A database error mid-request is still a 503 through `ExceptionHandlerMiddleware`.
- **Cross-world views:** `GET /character` (`AccountCharactersController`) returns `{ characters, unavailableWorlds }` across every configured, available world the caller may enter, each `CharacterDto` carrying `worldId`/`worldName`; a world unavailable or whose read fails goes in `unavailableWorlds`, a world the caller may not enter appears nowhere. `GET /world` lists only permitted worlds, each with `configured`/`available`. Observability stays cross-world (Redis), shows only permitted worlds, and reads template names and layout staleness from each presence's own world, with its memo and pool cache keyed per world; a failed name lookup falls back to `#id`.
- **Character ids are unique only per world** (each world has its own characters database). Consumers key a character by `(worldId, id)`, never by `id` alone. The Redis presence keys are per world too (#556): `presence:world:{worldId}:character:{id}` (`CacheKeys.CharacterPresenceIndex(worldId, id)`), written by each world server with its own world id. One character's presence is `GET /world/{worldId}/observability/character/{id}` (`WorldObservabilityController`, `[WorldScoped]`, GameMaster), which reads only that world's keys and refuses an index entry naming another world. `GET /observability/online` and `GET /observability/instance/{instanceId}` stay cross-world: they read each permitted world's own snapshot, and instance ids are GUIDs (`Guid.NewGuid()` in `MapInstance`), so they cannot collide across worlds.
- The world servers are unchanged: each serves one world with its singular pair.

## World Simulation

`WorldServer` is an `IHostedService` that runs the tick loop at ~60 Hz (16.67ms intervals). On each tick it calls `World.Update(deltaTime)`, which ticks all active `MapInstance` objects via `IInstanceRegistry`.

**Two-pass tick architecture:** Each tick runs in two passes. Pass 1 — `WorldServer.Update` calls `connection.UpdateSession(deltaTime)` on every connected client, processing pre-character packets (`CMSG_PONG`, character list/select/create/delete) via `WorldSessionFilter`. Pass 2 — `World.Update → MapInstance.Update` calls `connection.UpdateMap(deltaTime)` on every in-map client, processing in-map packets (movement, attack, chat) via `MapSessionFilter`. `LockedQueue.Next(check)` uses peek-first semantics: a packet that fails the first-pass filter stays at the queue head and is picked up by the second pass. Both filter instances are stored on `WorldConnection` and reused each tick — no per-tick allocation.

**Tick-thread rules (#639).** World state changes on the tick thread only. Slow work (database reads, the navmesh bake, a whole instance build, saves, reload prepares, script compiles, Redis writes) runs off the tick and hands its result back through a queue the tick drains or a connection continuation (`EnqueueContinuation`, flushed at the end of `WorldServer.Update`); it touches only what it owns and immutable snapshots, never a live instance, index, party or character. Instance membership (`World.SpawnInInstance`, `TransferPlayer`, `LeaveWorldAsync`'s synchronous part), the registry's indexes and pending builds, every `PartyService` mutator, `OnlineCharacters` writes and `IgnoreList` writes call `TickThreadGuard.AssertOnTick` (`Avalon.World/Threading`, a DI singleton): `WorldServer`'s tick loop binds its thread to it when it starts and unbinds it when it ends, and while the check is enabled and a thread is bound, a call from any other thread throws `InvalidOperationException` naming the operation. It checks the thread only (every serial step and every instance tick run on that one thread today; a phase check is for parallel ticking, not built). It is compiled into every build and checks only while enabled (owner decision): `Game:TickThreadGuard` (bool, default `false`; a local World server turns it on with `Game__TickThreadGuard=true` in its environment, since the World server has no `appsettings.Development.json`) turns it on when `WorldServer.ExecuteAsync` starts the tick, and the World test assembly turns it on for itself with a module initializer (`TickThreadGuardOn`), so its tests exercise it in Debug and Release alike. The switch is one process-wide static volatile flag that is only ever turned on, so off it costs one read per check. It throws rather than `Debug.Assert`, which would end the process. Unbound (before the tick starts, the shutdown despawn after it is joined, and tests that bind nothing) it lets every thread through; the shutdown despawn calls each connection's despawn on its own, so one the guard refuses (a tick that outlived its 5 s join) costs the others neither their despawn nor the wait for saves. Reads stay free (telemetry reads the instance list). The holders take it as an optional constructor parameter; `WorldHostGraphShould` pins that production hands the one instance to the world, the party service, `OnlineCharacters` and `CharacterSelectHandler` (for each `CharacterEntity`'s ignore list).

- **MapInstance** (`Avalon.World/Instances/MapInstance.cs`) is the core simulation unit: manages entities in a flat tick context, runs `InstanceAbilityCastSystem`, creature AI scripts, broadcasts state to clients. Implements `ISimulationContext`. Holds a single `MapNavigator` (combined navmesh) and the `ChunkLayout` that produced it.
- **Each instance is ticked on its own (#639).** `World.Update` hands the live instances to `InstanceTicker` (`Avalon.World/Instances`), which contains every `instance.Update`: one that throws is logged at Error (at most once per instance per `InstanceTicker.FailureLogInterval`, 10 s, with how many throws were left out since) and the other instances, and the tick loop's flushes after the world update, still run; the instance stays live. Before, the throw left `World.Update`, so every instance after it went unticked and that tick's flushes and continuations were skipped. Each update is timed into `world.instance.update.duration` (µs) and each throw counted in `world.instance.update.failures`, tagged `map.type` only. The instances are still ticked one after another on the tick thread; #639 records what parallel ticking would need.
- **InstanceRegistry** (`Avalon.World/Instances/InstanceRegistry.cs`) owns all live instances. `GetOrCreateTownInstanceAsync` returns a shared persistent instance; `GetOrCreateNormalInstanceAsync` returns per-player instances with 15-min re-entry windows. `ProcessExpiredInstances` cleans up expired normal instances. Both creators dispatch to `ChunkLayoutInstanceFactory.BuildAsync` for actual instance construction. **A build runs off the tick; it is published on the tick (#639).** The build (layout reads, navmesh bake, `MapInstance` construction, creature placement, script attach) touches only the instance it is building and immutable snapshots, and its last step only queues its outcome (a `ConcurrentQueue`). `World.Update` calls `World.PublishBuiltInstances` after the reference-data patches and the AI script hot reload are applied (so a just-published instance is brought up to date with the reload once, not rebuilt by its walk) and before the party tick and the instance ticks; it is contained, so a throw there costs the instances nothing. `InstanceRegistry.PublishFinished` registers each finished instance, writes its index entry (the character's, or the party's unless the party was forgotten meanwhile), drops the build's pending entry and only then completes the `TaskCompletionSource` its requesters hold; each build's step is contained on its own, so one that throws still answers its requesters (with the failure) and the builds behind it are still published. A requester that polls the task (a connection continuation) runs in that tick's flush; one that settles it through a continuation of its own first (`TownReturn`, `ctx.Then`) runs a tick later. Either way it is answered, never left waiting. One build per town map, per character and map, and per party and map is in flight at a time, kept in a plain dictionary of pending builds: a request arriving mid-build gets the same task (#442), and a build that failed is published as a failure, so its requesters get the exception and the next request starts afresh. Every index and pending map is written on the tick alone (`_partyIndexGate` and its forgotten-party set are gone: a forget marks the party's pending builds instead); only the instance list stays a `ConcurrentDictionary`, because telemetry reads it from its own thread. Freeing an expired instance removes an index entry only while it still names that instance (a newer build of the map keeps its entry). An instance published after an AI script hot reload was applied gets the reloaded scripts as it is published (`World` keeps every hot-reloaded type by name and rebuilds each living creature whose script is not of that type).
- **ChunkLayoutInstanceFactory** (`Avalon.World/ChunkLayouts/IChunkLayoutInstanceFactory.cs`) — single entry point that builds both town and procedural instances. `IChunkLayoutSourceResolver` picks `PredefinedChunkLayoutSource` (DB-backed `MapChunkPlacement` rows for towns) or `ProceduralChunkLayoutSource` (RNG + `ProceduralMapConfig`) per `MapType`. `ChunkLayoutNavmeshBuilder` stitches chunk objs → DotRecast bake → `MapNavigator`. Server emits `SChunkLayoutPacket` to clients on instance enter; client `ClientMapNavigator` bakes the same navmesh from the same chunk objs (deterministic mirror) for prediction parity. See `docs/map-generation.md` for the full pipeline.
- **Creature placement has two paths, and both run from `BuildAsync`.** `CreaturePlacementService.PlaceAsync` rolls a `SpawnTable` against chunk spawn slots and is procedural-only, because it needs a `ProceduralMapConfig` and slots. `PlaceAuthoredAsync` reads `MapCreatureSpawn` rows — hand-placed creature, map, offset from the map's entry spawn point, facing — and runs for every layout kind; it is the only path that puts a creature in a town. Offsets, not world coordinates: a town's coordinates fall out of its `MapChunkPlacement` rows and the cell size. `OffsetY` only centres the navmesh search box, and `SampleGroundHeight` decides the real height (an authored column off the mesh keeps its authored height). **Procedural spawns stand on the ground too (#720):** a slot's height (and a pack member's spread position) only centres the same search, through `MapNavigator.FindGround` (World-side `IGroundNavigator`, the one query `SampleGroundHeight` also runs): with the mesh under it the creature keeps the slot's X/Z at the ground's height; just beside the mesh (a pack spread past its edge, within the 2 m search box) it goes to the mesh's nearest point; with no mesh within the box it is not placed, and a Warning names the slot, creature and position; a map with no navmesh keeps the slot as it is. Skipping rather than guessing, because a creature there has no ground to stand on and a home it cannot walk back to. Both paths wrap each creature in its own try/catch — placement runs inside `MapInstance` construction, so a throw would make the map unenterable for everyone. **On a map with depth bands** (`ProceduralMapConfig.DepthBands`, forest content pass) each procedural creature's level is rolled from its piece's band (`DepthBandLevels`, by `PlacedChunk.Depth`, the grid steps from the entry; every set piece, `PlacedChunk.Group`, from the highest band) and passed to `ICreatureSpawner.Spawn(CreatureInfo, ushort level)`; a depth no band covers rolls from the template's range, a `boss` slot stands at the highest band's top, and a `leader` slot spawns its `leader` entry then a roll of `leader_pack` entries around it (no slot carries `leader_pack`). A map without bands places exactly as before. Set pieces are `ChunkGroups` (`Maps/chunk-groups.json`), placed atomically by `ProceduralLayoutGenerator` as one main-path step, on the main path only: a boss set piece only as its last step, every other one at most once per layout and not before the config's `MinSetPieceStep` (`Maps/ProceduralMaps/<mapId>.json` `minSetPieceStep`, 0 or left out for no limit; the forest's is 8, where its 5-8 band begins, and its main path is 12-16 steps so every run has room for one, owner decisions). A failed layout attempt is retried with the next seed up to 10 times (`MaxRetries`, raised from 3 when the committed forest failed some seeds at 3; `CommittedForestGenerationShould` generates it for 1000 seeds). The forest's `boss` and `leader` slots exist only in its set pieces, so `chunk-groups.json` is required: without it the spawn table's `boss`, `leader` and `leader_pack` entries match no slot and the seeder refuses the catalog, which stops the World start. The generated forest pieces are written by `tools/Avalon.ChunkGen` (see Commands), and `.gitattributes` pins every `.obj` and `.json` under `Maps/` to LF so a regeneration is byte-identical on any machine. See docs/map-generation.md.
- **Town NPCs are creatures.** Templates 1-3 (Uriel, Borin Stoutbeard, Innkeeper), 11 (Marta Ledgerwell, the banker, #463) and 12-14 (Garrick Emberforge, Hilde Brassbuckle and Tobin Marrowfield, the vendors, #432) are placed on map 1 by `MapCreatureSpawns`, carry `Invulnerable = true`, and run `TownNpcScript`. Since the town beautification (2026-10-01) the four squares are generated by `tools/Avalon.ChunkGen -- town` (`TownPieces.cs`: a town hall, a fountain, a gate arch, a watchtower, a hunter's lodge, a smithy, two stalls, a bank, an inn, two houses and a well, each shape an obj object with a `usemtl` line the server ignores and the client colours; `stone`, `wood`, `roof`, `cloth`, `cloth_2`, `plaster`, `metal`, `water`), and each NPC stands in front of its own building: Uriel on the town hall porch, Borin on the lodge porch, Garrick under the smithy's lean-to, Hilde and Tobin behind their counters, the Innkeeper on the inn porch, Marta on the bank steps (migration `MoveTownNpcsToTheirBuildings`; `TownNpcPlacementShould` checks every spot against the generated squares: 2 m from any wall, 1 m from any solid, within 3 m of its building, off the doorway lanes, reachable on the baked navmesh, and every doorway and the gate arch walkable). The navmesh climbs any step of 0.8 m or less (`floor(0.9 / 0.2)` voxels, a top rounded up to a 0.2 m voxel), so a top at or under 1.0 m above the ground beside it would be walked over: every solid prop's top is at least 1.05 m up (benches, crates, barrels, counters, the well ring, the cart's shaft included; owner decision), and `TownPiecesShould` pins that every solid piece stops a walk at its edge and that no piece's top is reachable from the arrival point on the baked navmesh (roof tops and building interiors are unreachable islands, as the forest's blocker tops are). A geometry change here needs a restart and a re-export of the navmesh vectors (`schema/vectors/navmesh-v1.txt`, `tools/Avalon.Exporter -- navmesh`), which the client checks its bake against. Each has a dialogue root (`DialogueNodes`, seeded in `WorldDbContext`), so a player can talk to them (#431, closed): `CMSG_INTERACT` (accepted by `MapSessionFilter`) reaches `InteractHandler`, which checks the target is a live creature in the instance, has a dialogue root and is within 5 m, then sends `SMSG_DIALOGUE_NODE`; `CMSG_DIALOGUE_CHOOSE` advances through `DialogueChooseHandler` and `SMSG_DIALOGUE_END` closes it. A rejected interact is a silent drop — a monster's interact gets no reply. `DialogueChooseHandler` drops most rejected choices silently too, but closes the window with `SMSG_DIALOGUE_END` when the NPC is gone or dead, the open node does not belong to it, or an option leads to an unknown node; it also sends it as the ordinary close when the chosen option ends the conversation. **Every choose re-checks range against the dialogue leash (#492)**: `NpcInteraction.IsWithinLeash`, `LeashRange = 6f` (#678, was 15 m), inclusive, NaN counted as out of range. Past it the handler ends the conversation (clears `CurrentDialogue`, sends `SMSG_DIALOGUE_END`) and advances nothing. It is deliberately not the 5 m interact range, which still gates opening a conversation, because stepping back a metre mid-sentence must not close the window; it is only just past it, so walking off does. It is checked only on choose, never on the tick. **Any handler that acts on an open NPC conversation must pass the same check** (a vendor, quest, payment or item effect, #432): `CurrentDialogue` lives until the connection leaves the instance, so an unchecked effect would work from anywhere on the map. A client must not re-check range itself; the server decides whether a conversation is open. Dialogue text lives in `IDialogueCatalog` and `ILocalizedTextCatalog` on `StaticData`, read in memory on the tick. Interacting with a different NPC mid-conversation always ends the old conversation out loud first (`SMSG_DIALOGUE_END` for the old NPC, then the new node); interacting with the same NPC again restarts at its root, and ends the old conversation out loud only when it had the bank or a shop open. A dialogue option can also carry an action (`DialogueOption.Action`, #463), indexed by `DialogueActions` on `StaticData` (rebuilt by `/reload dialogue`) and deliberately not on the World.Public `DialogueOptionView`, so the modding API cannot read or invent one: `DialogueChooseHandler` runs it after the leash check and only on an option that keeps the conversation open, so an `OpenBank` on an option that ends the conversation (or leads to an unknown node) opens nothing. The actions are `OpenBank` and `OpenShop` (#432, stored as 0 and 1, append-only). Each option on the wire carries `Kind` (`SDialogueOptionInfo` field 3): the action choosing it will actually run, or `Conversation` when it runs none, so a client can hide what it has not built; `DialogueOptionKinds` holds the rule for both handlers (#522). A creature whose dialogue offers `OpenBank` anywhere is a banker (`NpcInteraction.IsBanker`), and one that offers `OpenShop` anywhere is a vendor (`NpcInteraction.IsVendor`). `NpcInteraction.EndConversation` is the one way a conversation ends out loud; despawn clears it silently, because the client is gone. It calls `CharacterEntity.CloseNpcWindows()`, which closes the bank and the shop together. Quest options are added to the root per character (see Quests).
- **`ObjectState.CanInteract` (field 20) tells a client whom it can talk to (#489).** It means "interacting with this will do something", so a client can offer an interact prompt without guessing. It is "the template has a dialogue root". A banker and a vendor are both reached through their dialogue, so neither changed it. The rule is one function, `NpcInteraction` (`Avalon.World/Dialogue/`): `InteractHandler` uses it to find the root it opens, and `CreatureSpawner.Spawn` uses it, over `world.Data.Dialogue` read once per call, to fix `Creature.CanInteract` at spawn — so the prompt the client shows and the interact the server accepts cannot drift apart. The value lives on the World-side `Creature`, init-only and deliberately not on `ICreature`, so no mod can make a creature advertise an interaction. `ObjectStateWriter.From(ICreature)` sends it on every creature state whatever is marked changed, like `CreatureMetadataId` and `Name`, and only as `true`: a monster leaves it out, and characters, portals and spells never carry it, so absent means false. It is fixed at spawn, so `/reload dialogue` reaches only creatures spawned afterwards; one already standing keeps the flag it spawned with, while `InteractHandler` still answers from the current catalog. Creatures never respawn and the town instance persists, so after a `/reload dialogue` a town NPC's flag stays stale until the server restarts. Any `ICreature` that is not the World-side `Creature` never advertises the flag: that fails safe, and the handler stays authoritative.
- **`ObjectState.IsDead` (field 12) is true on a dead creature too (#672).** A creature is dead at 0 health, the rule the hit query, `ApplyHeal`, the kill (`CreatureKilled`, from above 0 to 0) and the death broadcast already use, so `ObjectStateWriter` derives it from `CurrentHealth == 0` rather than keeping a flag of its own (a character keeps `CharacterEntity.IsDead`, since it is revived). Nothing is added to `ICreature`, and any `ICreature` reports only what its health says. A creature's add (`GameEntityFields.All`) always carries it; its routine update (`CreatureUpdate`) does not, so a living creature's updates pay nothing for it. `Creature.CurrentHealth` marks `GameEntityFields.IsDead` changed when health reaches 0 (or leaves it), and `MapInstance.DescribeUpdatedObject` adds that mark to the creature's selection, so the broadcast that carries the corpse's 0 health carries `IsDead = true` with it; a client that first sees the corpse later gets it on the add (`CreatureDeathReplicationShould`).
- **`ObjectState.Rarity` (field 22) tells a client how dangerous a creature is (#709)**, for a nameplate coloured by rarity. It is a wire enum, `Avalon.Network.Packets.State.CreatureRarity` (Normal 0, Elite 1, Rare 2, Boss 3, append-only), a copy of the domain's `Avalon.World.Public.Enums.CreatureRarity` declared beside `PowerType` because the packets do not reference the world's domain and the exported schema reaches only packet types; `ObjectStateWriter.ToWire` maps one onto the other value by value, and `ObjectStateWriterShould` pins the two together (a file that imports both namespaces aliases the one it means). `CreatureSpawner.Spawn` fixes it on the World-side `Creature` from the template's `Rarity` (`Creature.Rarity`, init-only, deliberately not on `ICreature`, so no mod can change what a creature advertises), and `ObjectStateWriter.From(ICreature)` sends it on every creature state whatever is marked changed, like `CanInteract`, and only when it is not Normal: absent on a creature state means Normal, so most creatures pay nothing. Characters, portals and projectiles never carry it, and any `ICreature` that is not the World-side `Creature` is sent as Normal. It is fixed at spawn, so `/reload creatures` reaches only creatures spawned afterwards; one already standing keeps the rarity it spawned with (the stats that rarity scaled were fixed then too).
- **Every script resolvable by name must construct from `(creature, instance)` alone.** `AttachScript` builds it with `ActivatorUtilities.CreateInstance(sp, type, creature, instance)` — exactly two runtime arguments, anything else resolved from DI; a constructor wanting a plain `float` or array throws, and the throw is swallowed so the creature silently has no script. `ILoggerFactory` is fine (`AggroDefendScript` takes one). `AiScriptConstructibilityShould` builds every nameable script that way through the real World container. A component another script builds and chains with extra arguments (`CreatureRangeDetectorScript`, chained by `AggroDefendScript`) is marked `[ChainedScript]` (`Avalon.World.Public/Scripts`), and `ScriptManager` does not register it by name. `CreatureIdleScript` is gone (#437); use `TownNpcScript` for a passive creature.
- **Patrol paths are data, authored spawns only.** A `CreaturePath` (table `CreaturePaths`) holds ordered `CreaturePathPoint`s (`CreaturePathPoints`, keyed `(PathId, Sequence)`), each an offset from the map's entry spawn point plus a `WaitMs`; `MapCreatureSpawn.PathId` (nullable, shareable between spawns) names one. `PlaceAuthoredAsync` sets each point's height from the navmesh like the spawn itself (`SampleGroundHeight`; X and Z stay as authored) and sets `ICreature.PatrolPath` before attaching the script. `CreaturePatrolScript` walks it in a loop, standing at each point for its wait. **A patrolling creature fights, then resumes (#600):** the patrol chains a `CreatureCombatScript`, as `AggroDefendScript` does, and forwards `OnHit`, `Update` and `OnCharacterLeft` to it; a hit starts the fight under the normal combat rules (health, one kill with loot and experience, the leash). While the combat script's `State` is anything but `None` it drives the creature (the patrol stops its leg at the handover and then issues no `MoveTo`, `Stop` or `MoveState`) and the patrol's point and wait do not advance; once it is back to `None` (home after the leash, a lost, dead or unreachable target, or its target leaving), the patrol resumes at the path point nearest the creature and walks on in the path's order, dropping any interrupted wait. A hit that leaves it at 0 health stops the patrol for good. An invulnerable walker never fights: `CombatService` refuses the hit before any script hears of it. The path does not choose the AI: the template's `ScriptName` still does, and only a script reading `PatrolPath` walks it. No path is seeded, and procedural spawns never get one.
- **ISimulationContext** — minimal contract used by AI scripts, spell system, and respawner instead of the old `IChunk`. Exposes `Locomotion` and `MeleeSlots` to scripts.
- **Unit broadcasts go through the unit's own instance (#546); there are no static events.** Swings and cast finishes and interrupts are `ISimulationContext.BroadcastAttackAnimation`/`BroadcastFinishCast`/`BroadcastInterruptedCast` (the cast system calls them through its `IAbilityArena`), each sent only for a unit in that instance. A hit's outcome is reported by the instance's own `CombatService` right after the target's `OnHit` returns, through the World-side `ICombatOutcomes` that `MapInstance` implements: a living character's own `SCharacterDamagePacket` then the instance-wide hit (`CharacterDamaged`), and a creature brought from above 0 to 0 health killed once (`CreatureKilled`: corpse, loot, experience), before the encounter death and the death broadcast. `ICreature` has no `Died`, since the modding API must not grant a kill. A character leaving an instance is `AiScript.OnCharacterLeft`, called by `RemoveCharacter` on that instance's own creature scripts only and forwarded to chained scripts.
- **ICreatureLocomotion** (`Avalon.World.Public/Creatures/`) — the only thing that writes a creature's position. Scripts call `MoveTo` / `Stop` / `Teleport` / `HasArrived` and never touch `Position` themselves. `MapInstance` owns one, registers each creature in `AddCreature`, unregisters in `RemoveCreature`, and ticks it **after** the AI scripts — the scripts choose destinations, the locomotion consumes them, so the order matters and is pinned by a test. Two implementations in `Avalon.World/Creatures/Locomotion/`, selected by `GameConfiguration.CreatureLocomotion`: `WaypointLocomotion` (default; walks a navmesh path with no awareness of other agents) and `CrowdLocomotion` (DotRecast `DtCrowd`; agents steer around one another, and around players when `CrowdIncludesPlayers` is set). `Crowd` falls back to `Waypoint` with a warning on a map with no baked navmesh.
- **MeleeSlots** (`Avalon.World/Creatures/MeleeSlots.cs`) — hands each attacker a distinct standing position on a ring around its target so chasers surround rather than stack. Claims are keyed by target, world-fixed in angle (not facing-relative, which would churn every time the player turns), and handed out nearest the claimant's bearing. Attackers beyond `MeleeSlotCount` get no slot and stand off at attack range along their own bearing.
- **`CreatureCombatScript` gives up** and runs home at full health (slot released, target dropped) when a character target dies, the target leaves the instance, the creature is more than 40 m from where the fight began (its home, which may be any position, the origin included), or it has had no way to reach the target for more than 5 s in a row (#606: out of attack range while `ICreatureLocomotion.ResolvedDestination`, where its route really ends, is null or ends farther than attack range plus arrival tolerance from the target (a settled creature out of range re-plans every tick, so the route judged is fresh); never `HasArrived`, which flips while a creature stands at the end of a partial route; the count restarts on a tick that can reach and on a change of target). On the way home it ignores hits entirely (owner decision, #606; how, below under #610). **It always ends the walk home (#715).** Home (where the fight began, often the spawn) need not lie on the navmesh: a procedural spawn keeps its slot's height, a spawn by a wall sits in the mesh's eroded border, and a route's points carry the mesh's own height, so a route home ends at the nearest point the mesh has and a crowd stops within its arrival tolerance of that. It is home once the locomotion has nothing left to walk and it stands within `ArrivalTolerance` (+ 0.05) of home on X/Z (or within 0.1 m in 3D); before #715 only the exact 0.1 m test counted, so such a creature re-planned the same route for ever, standing still and unhittable (reproduced under both locomotions, `CreatureReturnHomeShould`). A route home that ends short (its end farther than the tolerance from home, and the creature standing at it), no route at all, and the safety net all `Teleport` it home and reset it (`SnapHome`), logged once at Warning with the creature and why: the net fires when it has come no 0.5 m closer to home on X/Z for 5 s (`ReturnStallLimit`) or has been returning for 15 s (`ReturnHomeLimit`), timed by the tick's delta. Home rather than where it stands, so repeated kites never drag a creature away from its spawn. The reset is `ResetToIdleAtSpawn` either way (#614: taunt cleared, dropped from its encounter).
- **Creatures fight with abilities (#163).** A creature attacks only with abilities: the raw swing (`RollDamage` and a bare `ApplyDamage`) is gone. **Holding:** `CreatureAbilities` (`Avalon.World/Creatures`), owned by the World-side `Creature` (`Creature.Abilities`, never on `ICreature` or World.Public, #622), holds the creature's own clones of the ability rows its script declares, their cooldowns and its cast state (`IsCasting`). A creature type's script declares a `CreatureAbilityKit` (a basic and its specials, as ids) and passes it to `CreatureCombatScript`'s protected constructor, which loads it from the current `AbilityCatalog` (`StaticData.LoadedAbilities`, null before the first load) when the script is built; an id the catalog lacks is logged at Error and left out, and the creature fights with the rest. So `/reload abilities` reaches creatures spawned (or hot reloaded) afterwards; the rotation is code. The combat script ticks the cooldowns, first thing in each `Update`, and `ResetToIdleAtSpawn` clears them. The scripts data can name as they are (`CreatureCombatScript`, `AggroDefendScript`, `CreaturePatrolScript`) carry no kit: a creature on one chases but never attacks. So no data-named script combines a patrol path with abilities yet: a creature type that should patrol and fight needs its own `CreaturePatrolScript` subclass. `AggroDefendScript` and `CreaturePatrolScript` take a creature type's own combat script through a protected constructor. **The seven forest scripts** (`Avalon.World/Scripts/Creatures/Forest`: `ThornbackBoarScript`, `GreyFenWolfScript`, `BlightflySwarmlingScript`, `HuskOfTheWoldScript`, `BramblemawAlphaScript`, `OldTuskrootScript`, `MotherBrambleScript`, templates 4-10) each subclass `AggroDefendScript` with a nested `[ChainedScript]` combat script (named `<Creature>Combat`, never registered by name) and take an optional `IWorld` from DI; each prefers a ready special whose reach fits, then its basic, and the Blightfly spits only while Sting cannot reach. **Casting:** the cast path takes any `IUnit` (`ISimulationContext.QueueAbility(IUnit, ...)`); a creature's casts are free (`AbilityCost` is skipped for an `ICreature`); its haste is `min(HastePct, HasteCap)`, scaling cast times and cooldowns; its basic's cooldown is its `SwingInterval` (which already carries the haste, so it is not divided twice), every other one its row's `Cooldown` divided by the haste. A creature that dies or turns for home (`IReturningHome`) during a wind-up has the cast dropped on the cast system's next tick, with the interrupt broadcast, however much was left, and nothing fires; a projectile it loosed that is still in flight is dropped then too, so no corpse or creature walking home deals damage or rejoins an encounter; `MapInstance.RemoveCreature` cancels both as well (a corpse removed or a script hot reloaded). A creature is never interrupted by being moved (a crowd's separation pushing it), only a character is. **The AI hook:** `CreatureCombatScript.ChooseAbility(target, distance)` (protected virtual) answers which ability to start, every tick it fights and is not casting, in reach or not; the base answers the basic when it is ready and reaches; `Ready(id, distance)` and `InReach(ability, distance)` are the helpers. `distance` is to the edge of the target's body (its centre distance less `BodyRadius`), the real reach, with no allowance. Instead the creature's slot or stand-off point is pulled in toward the target so its basic reaches from anywhere within the locomotion's arrival tolerance of it (`WithinBasicReach`); with waypoint locomotion and the default slot nothing moves, while a crowd's 0.6 m tolerance brings the Blightfly's slot in to 1.3 m. What it answers is started only when the creature holds it, it is ready, and it reaches: an instant ability through `RunInstantAbility`, aimed along the facing toward the target (Movement) or at the target's position (Cursor), captured now. **Wind-ups:** a `CastTime` ability is queued with that aim; the creature `Stop`s, the cast system sends the start (with its footprint, #648), and it asks for no movement until the cast ends (fired, or dropped because it died or turned for home), so its own steps never interrupt it and a player can step out of it. The shape scripts' own broadcasts replace the old plain attack animation, and every creature hit carries its ability id. A creature's hit on a player adds no threat, as before.
- **InstanceAbilityCastSystem** (`Avalon.World/Abilities/`, one per `MapInstance`) runs casts: `QueueAbility` for a cast-time cast, `RunInstant` for an instant one, and ticks the unfinished ability scripts (projectiles). The one power rule is `AbilityCost` (#521): the handler checks it and the cast system checks it again and pays it on both paths, only once the cast is accepted (for a queued cast, once its script is built and the queue has taken it), so a refused cast spends nothing. A character leaving an instance (`MapInstance.RemoveCharacter`) has its queued casts interrupted (`CancelCasts`) and its still-running scripts dropped (`CancelScriptsOf`, #541), so a projectile in flight never lands for a caster who is gone: no damage, threat, credit or loot; it leaves the next tick's world objects, so every watcher gets one remove. A script whose `Prepare` or `Update` throws is contained (#530): logged at Error with the ability and caster, dropped (a projectile gets its remove the same way), and its caster sent the interrupt (`SCharacterInterruptedCastPacket`, broadcast to the instance); the other scripts in that tick still run, and what the cast spent stays spent.
- **`AiScript` hot reload** — `IScriptHotReloader` (`Avalon.World.Scripts.Abstractions`) reloads only `AiScript` types from compiled script assemblies; `World.Update` polls it every `Game:ScriptHotReloadIntervalSeconds` (default 5) and applies the reload on the tick thread. It reaches every registered instance, and an instance whose build was in flight during the reload gets the reloaded types when it is published (#639). `AbilityScript` and `QuestScript` types are not hot-reloaded: `ScriptManager` finds them once, at `Load()`.
- **Skills aim; they do not target (#164).** A cast carries an `AbilityAim` captured at cast start: a direction (a Movement skill: toward the cursor when the cast sends a `GroundPos`, else the caster's facing, #716) or the cursor's ground point (a Cursor skill; `CCastAbilityPacket.GroundPos`, refused as `NoAimPoint` when missing or non-finite). `TargetGuid` is ignored. The ability's `Shape` decides who is affected, through one generic script per shape: `CircleAbilityScript` (on the caster, or on the aim point clamped to `Reach` and pulled back from walls by `RaycastWalkable`), `ConeAbilityScript` (never clipped by walls), and `ProjectileAbilityScript`: a world object (`ObjectType.SpellProjectile`, replicated through the world-state add, update and remove packets like any entity, drawn `HeightOffset` 0.5 m above the ground it flies along) spawned at the caster and flying flat toward the aim point at `ProjectileSpeed` metres per second. Each tick it sweeps its whole step, capped at the `Reach` left and cut by `RaycastWalkable`, so a long tick tunnels through nothing; it ends at `Reach`, at a wall (a caster off the navmesh ends it on the first tick), or on its first qualifying hit, where it stops at the point of its step nearest the unit's centre, while with `Pierce` it hits each unit once and flies on. A finished projectile is never ticked again and stays a world object until its final state (where it stopped, zero velocity) has been taken for a broadcast; `InstanceAbilityCastSystem` removes it on a later update, so a client sees every projectile's add, final update and remove, even one that ended on the tick it was first seen. An instance nobody is in drops its finished projectiles at once (`IAbilityCastSystem.DropFinished`, on `MapInstance.Update`'s empty-instance return), since nobody is there to send them to, so the next player to enter never sees one frozen where it stopped. The shapes ask `IAbilityArena.Hits` (`IHitQuery`, World-side, implemented by `MapInstance` over its characters and creatures) for living units whose body circle (`IUnit.BodyRadius`: `CreatureTemplate.BodyRadius`, characters a fixed 0.5 m) overlaps the shape on X/Z, nearest-first, and each unit is affected at most once per cast (`AbilityEffect`). `Hostility` decides: a creature is hostile to a player unless `Invulnerable`; two players only when both are PvP-flagged, the map is not a town and they are not in the same party (`CharacterEntity.PartyId`, see Parties); a creature caster (#163) finds every living player hostile on every map type, and no creature; `Affects = Ally` heals the caster and every player not hostile to it through `ApplyHeal`, which restores health. Heal threat counts the health actually restored, so overheal adds none, and a heal that restores nothing does not add the healer to the encounter (#531). A skill that affects nobody still spends its cost and cooldown. Circles and cones broadcast `SMSG_ABILITY_FIRED` (`SAbilityFiredPacket`: caster, ability, origin, and a circle's centre or a cone's direction, plus the cast id and the whole footprint, #648); hits arrive as the usual damage packets, and `SCharacterDamagePacket.AbilityId` is filled. A shape script resolves from `AbilityScript.Origin`, the caster's position when the cast started (`AbilityAim.Origin`, stamped by the cast system when it takes the cast, #648), never from where the caster stands when it fires, and does it in `Prepare`, never in its constructor. `AbilityCatalog` (the Abilities reload area) refuses an invalid shape row, or one whose `ThreatMultiplier` or `HealThreatPerHp` is not finite and 0 or more (#529, also a database check), with an error naming it.
- **PvP is a flag on the character row (#164).** `Characters.PvpEnabled` and `PvpOffAt` (UTC; null means no timer) are read World-side through `CharacterEntity` and written only by `PvpToggle` (`Avalon.World/Pvp`), never through the modding API. `CMSG_PVP_TOGGLE` (`MapSessionFilter` entry, `PvpToggleHandler`) and `/pvp` (`PvpCommand`, Player access) both call `PvpToggle.Toggle`: off turns on at once; on with no timer starts `Game:PvpOffDelay` (default 5 min), during which the player stays hostile; on with a timer cancels it. Each is answered with `SMSG_PVP_STATE { Enabled, OffInMs }`, which is also sent when the timer turns the flag off (checked each tick in `MapInstance` against the container's `TimeProvider`) and when a character enters an instance. Every player-on-player hit that deals damage to a living player (`CombatService.ApplyDamage` between two `CharacterEntity`) restarts both players' running timers, and the countdown is re-sent when a hit moves the deadline by more than a second (`PvpToggle.CountdownOwed` against `CharacterEntity.PvpOffAtTold`, World-side and never saved), so the client's countdown is exact; the reset does not re-check the town rule itself, relying on `AbilityEffect` checking `Hostility` first. A timer that ran out while the player was offline is expired on entry, before the state is sent. A dead character may toggle. Towns never allow player hostility whatever the flags, and neither does a shared party. The flag is replicated as `ObjectState.PvpEnabled` on every character state, only as true, and saved with the row by every save (`SaveStateTracker.PvpChanged` marks it).
- **The seeded creature abilities** (migration `SeedCreatureAbilities`, #163): ids 300-316, creature-only (`AllowedClasses` empty), cost 0, `EffectValue` 0, damage from the creature's natural range through `BaseDamageCoefficient` (1.0 for each basic, so a basic deals what the old swing did). Gore 300/Trample 301 (boar), Bite 302/Ravenous Claw 303 (wolf), Sting 304/Blight Spit 305 (Blightfly), Slam 306/Rotting Burst 307 (Husk), Maul 308/Rending Frenzy 309/Howling Roar 310 (Alpha), Tusk Gore 311/Earthsplitter 312/Thorn Volley 313 (Tuskroot), Bramble Lash 314/Bramble Nova 315/Thornspray 316 (Mother Bramble). Basics are 90-degree cones listing the 2250 ms swing interval; the wind-ups are 310 (1 s), 312 and 315 (1.2 s); projectiles aim at the cursor (Blight Spit 14 m/s, Thorn Volley 16 m/s and piercing). `SeedIntegrityShould` pins every row and each template's script. `tools/Avalon.Exporter -- ability-catalog` writes `schema/abilities/ability-catalog-v1.json` (id, name, shape, aim, anchor, affects, radius, reach, arc, projectile speed, pierce, cast time, cooldown), for the client to name and draw creature abilities and wind-ups; like `item-catalog` it needs a World database.
- **The seeded starter kit** (migrations `SeedStarterSkillKit`, World, and `GrantStarterSkillKit`, Character): three skills per class, ids 200-202 Warrior, 210-212 Wizard, 220-222 Hunter, 230-232 Healer, each with `AllowedClasses` its class and one of the three shape scripts; `CharacterCreateInfos.StartingSpells` grants them, and the Character migration replaced every existing character's abilities with its class's three. The retired abilities 1, 2 and 100-103, and the two scripts they ran, are gone, and their ids are never reused. 232 Mending Circle is the only ally heal. Every kit cost is payable from its class's pool (`ClassPowerType`: Warrior Fury, Wizard and Healer Mana, Hunter Energy); a Warrior enters with no Fury and builds it with Cleave, which costs nothing (#526). `SeedIntegrityShould` pins it.
- **Every refused `CMSG_CAST_ABILITY` is answered (#512).** `CastAbilityHandler` sends exactly one `SAbilityNotReadyPacket` per refusal, carrying a `CastRejectReason` (`Gcd`, `Cooldown`, `RequiresOutOfCombat`, `RequiresInCombat`, `NotEnoughPower`, `Dead`, `NotOwned`, `InternalError`, `NoAimPoint`, `AlreadyCasting`, `WrongPowerType` (#652); `Unknown = 0` is only what a payload without the field decodes as). `OutOfRange`, `TargetNotFound` and `NotFacing` stay in the enum (append-only) but are no longer sent. `CooldownMs` is the time left for `Gcd` and `Cooldown`, rounded up so it is at least 1, and 0 for every other reason. The one silent path is a connection with no character. A cast the cast system refuses (`QueueAbility` or `RunInstantAbility` returning false: a missing script, or one that cannot be built) is `InternalError` and starts no global cooldown. `CombatConfig` is registered with its defaults and not bound from configuration.
- **Casts aim, they do not target (#164).** `CastAbilityHandler` ignores `CCastAbilityPacket.TargetGuid` and does no range or facing check; there is no facing cone any more, and `AbilityInfo.FacingAngle` is never set. At cast start it captures an `AbilityAim`: the caster's facing from its yaw (`AbilityAim.FacingFromYaw`, a non-finite yaw aims along +Z) and, for a `Cursor` skill, the ground point (`GroundPos`, missing or with a non-finite component is `NoAimPoint`). **A `Movement` skill aims toward the cursor (#716):** when the cast carries a finite `GroundPos`, the handler replaces the facing with the X/Z direction from the caster's position (the position the cast system stamps as `AbilityAim.Origin` in the same call) to it (`AbilityAim.Toward`), so a player walking backwards does not swing behind; missing, non-finite or within a millimetre of the caster keeps the yaw, and a Movement skill is never refused for its point. `Point` stays null for it, so the footprint stays anchored on the caster and its reach measured from there. Resolved once, into `AbilityAim.Facing`, so the footprint, the start and fired broadcasts and the shape script agree by construction (#648). Creatures send no point: their Movement casts still aim along their facing toward the target. The enum keeps the name `Movement` (stored data and in the exported catalog). A cast-time cast fires with the aim it started with. A cast while `Spells.IsCasting` is `AlreadyCasting` (#521). Scripts are `AbilityScript(IAbility, IUnit caster, AbilityAim aim)` and are built by `InstanceAbilityCastSystem` with `ActivatorUtilities.CreateInstance(sp, type, ability, caster, aim, arena)`, where the arena is the `MapInstance` as `IAbilityArena` (World-side, not the modding API). **One power rule on both paths (#521):** `AbilityCost.Check`/`Pay`; a cost above 0 is spent from the pool the ability names (`AbilityTemplate.CostPowerType`, #652: Mana, Fury or Energy, carried to `AbilityMetadata` and sent as `AbilityInfo.CostPowerType`, field 17; in the REST API as `costPowerType` on `AbilityTemplateDto` and `CharacterAbilityTemplateDto`, the string enum `Avalon.Api.Contract.PowerType`), and only a caster whose own `PowerType` is that pool, holding at least the cost, pays it. Points in another pool never count, whoever assigned the ability: a mismatch is refused as `CastRejectReason.WrongPowerType` (14), before anything is built or paid, by the handler and again by the cast system on both paths. A cost of 0 names no pool and is castable by anyone, `PowerType.None` included. A cost whose row names no pool is a data fault: `AbilityCatalog` refuses the row, a check constraint (`CK_AbilityTemplates_CostPowerType`) refuses it in the database, and one that slips through is `InternalError`. The kit's costs are spent from their class's pool (the seed's `ClassPool`, as `ClassPowerType`); the migration `AddAbilityCostPowerType` gave every other row with a cost the pool its allowed classes share, and refuses to run, naming the rows, when their classes spend from different pools or the row allows none. Fury is spent like the others. Fury (#526) is gained per unit an ability damages (`AbilityTemplate.PowerGainPerHit`, Cleave 8, every other seeded ability 0; `AbilityCatalog` and a check constraint refuse a negative one) and from damage taken (`floor(health lost / max health × Game:FuryFromDamageTaken)`, default 50, the health lost capped at what the character had, from any source, only while alive), both in `CombatService` and capped at the maximum, drains at `Game:FuryDecayPerSecond` (default 5) out of combat, with the fraction carried between ticks, and is 0 on select, on every instance transfer (`MapInstance.AddCharacter`) and on death; a level-up or gear change keeps it, capped. `CharacterEntity.GainPower` and `ResetFury` are World-side, not on the modding API. The cast system sets `Casting` and pays only once the queue took the cast, builds a queued cast's script when it is queued, before paying (a script that is missing or cannot be built is refused and costs nothing, and the prebuilt script fires at completion with the aim captured at cast start), drops a cast whose caster died before it completed (clearing `Casting`, and broadcasting the interrupt, so every client's cast bar for it ends, #530), removes finished and interrupted casts after the loop, and keeps only unfinished scripts (projectiles) ticking. `SUnitStartCastPacket` carries the `AbilityId` (#521 item 9).
- **Cast telegraphs (#648).** A cast lands exactly where its telegraph was drawn. `AbilityFootprint` (`Avalon.World/Abilities`) resolves an ability's footprint once, from its row, its aim and its origin: a circle's centre (the origin, or the aim point clamped to `Reach` and cut by `RaycastWalkable`) and radius, a cone's origin, direction (the aim's facing for Movement, already toward the cursor when one was sent, #716; toward the aim point for Cursor), reach and arc, a projectile's lane (toward the aim point, `Reach` cut where the walkable ray stops). The shape scripts fire with `AbilityFootprint.Resolve`, and the cast system resolves the same at queue time, so the two agree by construction; the origin is the caster's position at cast start (`AbilityAim.Origin`), which for a character is where it fires (moving interrupts) and for a creature pushed by a crowd during a wind-up is where it began, so a pushed creature still fires on its telegraph. **The cast system sends the start (#648):** `QueueAbility` broadcasts `SUnitStartCastPacket` once it has taken the cast (`IAbilityArena.BroadcastUnitStartCast`), with `CastId` (field 4) and `Footprint` (field 5, `AbilityFootprintDto`, absent only if resolving it threw, which is logged); `ISimulationContext` has no start broadcast any more, and neither `CastAbilityHandler` nor `CreatureCombatScript` sends one. The start is heard near the caster or near a circle's centre. **Cast ids:** `InstanceAbilityCastSystem` numbers every cast it takes, queued or instant, per instance, never 0 (0 is what a payload from before #648 decodes as), and the start, the finish (`SUnitFinishCastPacket.CastId`, field 3), the interrupt (`SCharacterInterruptedCastPacket.CastId`, field 3, every way a cast is interrupted or dropped) and the fired broadcast (`SAbilityFiredPacket.CastId`, field 6, through `IAbilityArena.CastInFlight`, set only while the script's `Prepare` runs) of one cast carry the same one. The public `ISimulationContext.BroadcastFinishCast`/`BroadcastInterruptedCast` send cast id 0. **Instant casts** send no start and no telegraph (they fire on the tick they are cast); their fired broadcast carries the whole footprint (`SAbilityFiredPacket.Footprint`, field 7) and the finish the same id. Projectiles send no fired broadcast: a cast-time projectile's start carries its lane, and once fired the projectile is a world object. A client draws a telegraph from the start alone, keyed by caster and cast id, and clears it on the finish or interrupt with that id, on a new start from the same caster, when the caster leaves its view, or once `CastTime` has passed. `docs/client-combat-protocol-migration.md` is the client-facing contract.
- **Combat reads the derived stats (#506 slice A).** Every hit resolves in `CombatService.ApplyDamageCore`, after the early returns (invulnerable, corpse, walking home), so nothing refused draws a roll; the maths is `HitResolver` (`Avalon.Combat`, pure). The order: **base**, then **dodge** (the hit deals 0 and nothing else is rolled), **crit** (x `CritMultiplier`), **block** (x `BlockMultiplier`), **armour** (x `1 - min(A / (A + ArmorBase + ArmorPerLevel x attackerLevel), ArmorCap)`), floored with a minimum of 1. An ability's base is `EffectValue + ScalingCoefficient x stat + BaseDamageCoefficient x roll` (`AbilityTemplate.ScalingStat` picks AttackDamage or AbilityDamage; the roll is uniform and inclusive over the attacker's base damage: a character's main hand, `DamageMin1..DamageMax1`, none with no weapon, and a creature's natural `DamageMin..DamageMax`, #163; the column was `WeaponCoefficient` until #163); a raw hit's base (the `ApplyDamage` overload with no ability; creatures no longer swing raw, #163) is the damage passed. Chances are percentage points clamped to the formula's caps. A heal (`ApplyHeal`) takes the base and a crit only; one that restored more than 0 is reported through `ICombatOutcomes.UnitHealed` and sent as `SMSG_UNIT_HEALED` (below). Threat, the #526 per-hit gain and the PvP reset read the resolved damage; Fury from damage taken reads the health actually lost. **A dodge still counts as combat**: the encounter forms, the creature gets threat for the base, both sides are tagged in combat, and a creature's script is told through `AiScript.OnAttacked(attacker)`, forwarded down the chain, so it engages the attacker as a landed hit would; but the script is not hit, nobody gains power and nobody dies. A creature's killing blow is broadcast as a hit (0 health left, marked with its result) before the death. Characters attack and defend with `CharacterEntity.Combat`/`Defence`, from the `DerivedCharacterStats` (damage stats, crit, dodge, block, armour, main-hand weapon range) the last stats refresh wrote; creatures with `Creature.Combat` (its natural `DamageMin..DamageMax` as the weapon range, #163)/`Defence`, fixed at spawn by `CreatureStatDeriver` (armour = `round(CreatureBaseStat.Armor x ArmorModifier)`, a modifier of 0 or less counting as 1; crit, dodge and block from `CreatureRarityModifiers`). Both World-side and read-only, never on the modding API. Every roll goes through `ICombatRandom` (`CombatRandom` over `Random.Shared` in production; a service built without one uses `CombatRandom.Steady`, which never procs), creature abilities included (a creature's base-damage roll is the combat service's, #163). **Data:** `CombatFormula` (one row, id 1) and `ClassStatFactors` (one row per class, which `CharacterStatsCalculator` reads instead of constants) are the `/reload combat` area; `CreatureBaseStats.Armor` and the rarity `CritPct`/`DodgePct`/`BlockPct` stay in the creatures area; a bad row fails the reload (or the startup) naming it, and the previous values stay. Each hit reads the formula once. **Wire:** `SUnitDamagePacket.Result` (field 5) and `SCharacterDamagePacket.Result` (field 6) carry `HitResult` (`[Flags]`: None 0, Crit 1, Dodged 2, Blocked 4); a dodge is sent as a hit of 0 marked Dodged, to the same watchers a hit reaches (#532). A creature's own hit broadcast, made by its script's `OnHit`, is marked through `ICombatOutcomes.HitInFlight`, set only for that call.
- **ICorpseRemover** / **CreatureCorpseRemover** — removes a dead creature's corpse from the instance after `ICreatureMetadata.BodyRemoveTimer`. Creatures do not respawn on a timer; the time-based respawn scheduler was removed deliberately.
- **Ground loot (#460)** lives in `Avalon.World/Loot/`. `CreatureTemplate.LootTableId` (nullable) names a `LootTable`; its `LootTableEntry` rows each drop an item or roll another table, exactly one of the two (a check constraint enforces it). Ungrouped entries roll on their own against `Chance` (a percentage); entries sharing a `GroupId` always drop exactly one of them, weighted by `Chance`, so a group that should not drop on every kill belongs in its own table, referenced at the chance it should drop with. `MinGold`/`MaxGold` are **copper** and make one pile. Tables load as the `/reload loot` area into `StaticData.Loot`, a `LootCatalog` that refuses a bad table (a reference cycle, a missing reference, both targets or neither, counts out of order or above 1000, a chance outside 0-100) with an error naming it, and keeps the rest. `MapInstance.CreatureKilled` rolls on the tick (`ILootRoller`), asks `ILootAllocator.Allocate(instanceOwner, instanceParty, eligible)` for an owner once per drop (`PartyLootAllocator`, the only implementation: a solo instance's drops are reserved for its owner character, a party instance's each for one member drawn from the kill's eligible members, see Parties, and either is free for all after `GameConfiguration.LootGracePeriod`; an instance with neither owner, a town, and a party kill with nobody eligible drop free for all at once; the owner and `FreeForAllAt` ride on `LootDropDto`), places each drop on a ring around the corpse snapped to the navmesh, keeps them in the instance's `GroundLootStore`, and broadcasts `SLootSpawnedPacket`. A character entering an instance gets the drops already there at the start of the instance's next tick, after the map transition packets. Drops are never persisted and never despawn on a timer: they leave when picked up, or when the instance is disposed. `CMSG_LOOT_PICKUP` (`LootPickupHandler`, with its `MapSessionFilter` entry) runs its checks in a fixed order in `LootPickup.TryPickUp` and answers with `SLootPickupResultPacket`; a dead character gets no answer.
- **EntityTrackingSystem** tracks which objects each client sees. `CharacterCharacterGameState` feeds it only what `Interest.IsVisible` accepts (#593). Your own character is always visible. Other characters, creatures and projectiles are added within `Game:InterestRadius` (60 m) and removed beyond it plus `Game:InterestRemoveMargin` (10 m), on X/Z, so an object at the edge doesn't flicker. Leaving view is a remove, and coming back is a fresh add with full state. Loot, said chat (`ChatChannel.Say`), PvP state and threat are still instance-wide. **The replication state is World-side (#612)**: `CharacterEntity.CharacterGameState` (a `CharacterCharacterGameState`), not on `ICharacter`, and World.Public has no `ICharacterGameState`, so no mod can drive what a client is told it sees; `MapInstance` replicates only to characters that are `CharacterEntity`. **Changing instance starts replication over (#611).** The client (`AvalonSession`'s world-object table) keeps every object until a remove names it, even across a map transition, so `MapInstance.AddCharacter` resets the arriving character's state (`Reset`, which forgets everything without raising removes) and sends, at once and only when it had any, one `SMSG_WORLD_STATE_REMOVE` naming everything the client knew in the instance left, its own character included; that goes out ahead of the map transition the handler sends next. The first tick in the new instance then adds, in full, the character itself and everything in view there, a character that crossed just before it included. Every move between instances (map entry, respawn at town, a transfer into the instance the character is already in) goes through `World.TransferPlayer` and so through `AddCharacter` (`InstanceTransferReplicationShould`). Today portals come only with the map, in `SChunkLayoutPacket.Portals`, and are not put into the tracking systems. A portal spawned at runtime (on a kill, say) is meant to replicate as a world object through `ObjectState`'s portal fields, which stay in the wire schema for that; the server writer for it gets built, and tested through the tracking systems, when runtime portals are designed.
- **Effect broadcasts are local (#532).** `MapInstance`'s one-shot effect broadcasts (unit hit, heal, start, finish and interrupted cast, ability fired, attack animation, death, revive) go only to connections within `Game:InterestRadius` (default 60 m, X/Z, inclusive) of the effect or involved in it (`EffectAudience`).
- **CreatureStatDeriver** (`Avalon.Combat`) — turns a creature template plus a rolled level into the stats it spawns with: `CreatureBaseStats` by level, scaled by the template's modifiers and its `CreatureRarity` via `CreatureRarityModifiers`. It lives on `StaticData` (`StaticData.CreatureStats`), and `CreatureSpawner.Spawn` reads it, together with the templates, off `world.Data.Creatures` once per call; before it existed every creature spawned as level 1 with 100 health whatever its template said. The level is the template's own roll, or the depth band's on a banded procedural map. `CreatureTemplate.Exp` overrides the derived experience when set — `null` means derive.
- **`/reload <area>`** (`Avalon.World/Chat/ReloadCommand.cs`, game-master only) drives `IReferenceDataReloader` to apply changed dialogue, creature, ability, item, progression, loot, vendor, combat, or quest rows without a restart. Forward-only: `StaticData.PrepareAsync` reads the database and builds a whole `StaticDataPatch` off the tick thread; `ApplyOnNextTickAsync` queues it, and `World.Update` applies every queued patch at the top of `World.Update`, before the map pass and any instance ticks (the session pass — character create/select — runs earlier, in `WorldServer.Update`, so it sees a reload one tick later) — so nothing already spawned or already built is touched, only what gets built afterward. Each area is published as a single immutable `volatile` reference to its patch, because instance construction — and therefore `CreatureSpawner.Spawn` — runs on the thread pool, not the tick thread; a reader that needs more than one creature-area property together must take the `StaticData.Creatures` snapshot once rather than chain two property reads, or a reload landing in between could pair a new template with an old deriver. Maps and chunk layouts are excluded: live instances have already baked a navmesh from them, and the client mirrors that bake, so a change needs a restart. Spawn tables and town spawns need no reload of their own — `CreaturePlacementService` reads `ISpawnTableRepository`/`IMapCreatureSpawnRepository` straight from the database on every instance build, never from `StaticData`. Spawn tables and procedural map configs (with their depth bands) are themselves seeded from `Maps/spawn-tables.json` and `Maps/ProceduralMaps/<mapId>.json` by `ChunkCatalogSeeder` on every World start (like chunks, town layouts, pools and `Maps/chunk-groups.json`), not by migrations (owner decision, forest content pass), so a change to them needs a restart. Trade-offs: the balance simulator reads `HasData` only and never sees them, and the REST API's layout preview and observability show them as of the last World start. `/reload vendors` rebuilds the `VendorCatalog` from `VendorStocks`, validating it against the item templates it reads in the same prepare. On their next vendor pass, the town instances carry each live stock count over by row id, and every open shop hears the new list. `/reload quests` rebuilds the `QuestCatalog`, validated against the creature and item templates and the dialogue nodes read in the same prepare (#737) and the loaded quest scripts; characters keep the quests they hold, each settled once against the new catalog on the next flush (#738, see Quests).
- **The seeded loot** (migration `SeedForestLoot`): hostile templates 4-10 each name their own table (2-8) and a copper range; the town NPCs (1-3) name none. Loot tables are generic, and shared tables are pools. Each creature table rolls a Health Potion and a Mana Potion on their own, then references the pools: table 1 "Forest common", table 9 "Forest weapons" at 2 % (a group of one weapon per class, items 5-8), table 10 "Forest scrolls" at 10 % (a group of three collectible scrolls, items 9-11, which do nothing when used yet), and table 11 "Forest armour" at 100 % (20 Uncommon pieces, items 12-31, one per class in each of five slots, each its own entry at 2 %). So a kill drops at most one weapon and at most one scroll. Item 4, the Rusted Sword, is left as it is (it may become a starting item) and is in no table. Items 5-31 can be sold (no `NoSell`). Every armour piece carries Armor, cloth (Wizard, Healer) below leather (Hunter) below plate (Warrior) in each slot. Potion and common-table chances rise with the creature's rarity; the pool references are the same for every creature. `SeedIntegrityShould` pins all of it.
- `CreatureTemplate.Invulnerable` **is** read — `CreatureSpawner` copies it onto the creature and `CombatService.ApplyDamageCore` returns early on it, ahead of `ResolveOrSpawn`, so an invulnerable target also creates no encounter and does not combat-tag its attacker.
- **A creature walking home ignores hits entirely (#610).** Once its `CreatureCombatScript` is `Returning` (after the leash or a lost target), `ApplyDamageCore` returns early beside the invulnerable and corpse checks: no encounter, no threat, no `OnHit`, no broadcast, no combat tag, and `ApplyHeal` gives it no heal threat (splitting it across the hostiles still fighting), so nothing from the walk home outlives the reset at home. It asks `IReturningHome` (`Avalon.World/Scripts/Creatures`), internal and read-only: `CreatureCombatScript` answers it, and a script that chains one (`AggroDefendScript`, `CreaturePatrolScript`) must forward it, or its creature takes hits on the way home. Being internal, no mod or script can declare it directly, so none can make a creature unhittable on its own; a subclass of `CreatureCombatScript` (hot-reloaded or not) inherits it, with its behaviour. `ApplyTaunt` and `EnterCombat` do nothing on a returning creature either (#614). **Home and reset, a creature leaves its encounter** (#614): `ResetToIdleAtSpawn`, the one place `Returning` goes back to `None`, clears the creature's taunt (`TauntedBy`, `TauntExpiresAt`) and calls `IHostileEncounterExit.DropHostileFromEncounter` (`Avalon.World/Combat`, internal, implemented by `CombatService` and deliberately not on the modding API's `ICombatService`, where a mod could call it every tick to keep a creature from ever holding threat), which removes the creature and its threat list (`Encounter.RemoveHostile`) and leaves the players in the encounter with their threat on every other hostile; an encounter left with no hostile ends after its grace, as after a kill. So no threat from before the leash, not even a seed from a player it swung at, and no old taunter steers its next fight. **Combat runs on the container's clock** (#610, #614): `CreatureCombatScript` times taunts by `TimeProvider` (an optional constructor parameter, resolved from DI by `AttachScript` and passed down by the chaining scripts), and `MapInstance` hands its own `TimeProvider` to `EncounterRegistry` (and so every `Encounter`: last damage and the end grace), `CombatService` (a taunt's end) and `ThreatBroadcastService` (the broadcast throttle), and uses the same clock for `LastEmptyAt` (instance expiry). `CharacterEntity` takes the container's `TimeProvider` (an optional constructor parameter, passed by `CharacterSelectHandler`) for the combat tag (`MarkCombat`/`IsInCombat`, so `RequiresOutOfCombat` and in-combat regen) and the cast-regen suppression. Threat decay itself runs on the tick's delta.
- **Haste, creature cadence and movement speed (#627).** One rule, `Haste.Scale` (`Avalon.Combat`): a time becomes `time / (1 + haste / 100)`, a negative or unreadable haste counting as none. **Haste** is a character's worn `StatType.AttackSpeed` total (`DerivedCharacterStats.HastePct`, a percentage; swords and bows seed 3, maces 2, staves 0), and `CharacterEntity.EffectiveHastePct` is that, 0 to `CombatFormula.HasteCap` (50), fixed at each stats refresh. `InstanceAbilityCastSystem` reads it once per cast: a queued cast's `CastTimeTimer` is the scaled cast time, fixed at its start (the start-cast broadcast carries it), and the cooldown a cast sets when it fires is scaled by the same value, set once, so a gear change mid-cast changes neither and never rescales a running cooldown. The global cooldown (`CombatConfig.GcdMs`), costs and damage are not scaled; a `CharacterEntity` caster has its haste and a World-side `Creature` its own (`min(HastePct, HasteCap)`, #163). **Creature cadence:** a creature's basic ability waits `Creature.SwingInterval` (#163; the raw swing is gone) = `BaseAttackTime` (seconds, a real, 2.25 for every seeded template, at least 0.5 and finite: a check constraint, and the Creatures reload area refuses the area naming the template) divided by `1 + min(Creature.HastePct, HasteCap) / 100`, both fixed at spawn except `HastePct`, a World-side value (never on `ICreature`, #622) that nothing sets yet. The first attack lands at once (cooldowns are cleared when the creature resets at home), the cooldown runs down every tick its combat script runs, in reach or not, and the basic is cast on the tick it reaches 0; the interval is read when the basic fires, so a haste change applies from the next. Any other `ICreature` waits its basic row's own cooldown. **Movement speed** is `CharacterMovement.SpeedFor`: `4.0 x (1 + clamp(gear MovementSpeed %, MoveSpeedFloor, MoveSpeedCap) / 100)`, floor -50 and cap +35 (`CombatFormula`, the cap owner-set so a whole change from the base, 4 x 0.35 x 0.1 s = 0.14 m, stays under the client's 0.15 m snap, validated finite with `-100 < floor <= cap`), recalculated at every stats refresh; `PlayerInputHandler` steps at `GetMovementSpeed()`. Select's `CharacterInfo.MovementSpeed` is the speed held when the selected packet leaves (the base, since the gear is read later in the chain); the derived one reaches the client in the sheet. No seeded item carries MovementSpeed; a +10 % change drifts the client's prediction 0.04 m over a 100 ms round trip, under its 0.15 m snap (`CharacterMovementSpeedShould` pins it for the default cap, which fails past 37.5 %, and against every seeded item). The three formula columns are part of `/reload combat` and reach a character at its next refresh, a creature at its next spawn.
- **Regeneration carries the fraction of a point.** `CharacterEntity.Update` regenerates, each tick: health out of combat (`Stamina x HealthRegenOutOfCombatPerStamina` a second, 0.5), never in combat or dead; Mana and Energy from the class's stat (`PowerRegen.StatOf`: Intellect for Wizard and Healer, Agility for Hunter) at `PowerRegenOutOfCombatPerStat` (0.3) or, in combat, `PowerRegenInCombatPerStat` (0.05) a second, none within `PowerRegenCastSuppressSeconds` (5 s) of a cast in progress (`RegenConfiguration`). Each earns `rate x dt` into its own carry and gives only the whole points (`PowerRegen.Amount` for power, `PowerRegen.TakeWholePoints` for health), keeping the fraction for the next tick, so the per-second rate holds at any tick rate; the carry is dropped whenever the pool cannot regenerate (full, suppressed, in combat for health, dead). Before, every tick that regenerated gave at least one whole point, 60 a second at 60 Hz whatever the stat. Fury never regenerates. The arithmetic the server and `tools/Avalon.Balance` share lives in pure rules in `Avalon.Combat`: `PowerRegen`, `PowerPool` (`Gain`, a power gain capped at the maximum and nothing for a dead unit or a pool a cast does not spend; `EmptiesOnReset`, Fury only, on death and every transfer) and `HealRules.After` (a heal never raises health past the maximum and never lowers health already above it, #548), called by `CharacterEntity.GainPower`/`ResetFury` and `CombatService.ApplyHeal`.
- Deliberately still unread on `CreatureTemplate`: `ManaModifier` (creature casts are free and creatures have no pool, #163) and `RegenHealth`. Do not assume any of them work.

**Two contracts worth knowing before touching creature movement or AI scripts:**
- The calling script owns the *moving* `MoveState` and `Speed`; a locomotion writes `MoveState` only when a creature comes to rest, setting `Idle` and zeroing `Velocity`. A locomotion that writes a moving value stomps the script every tick.
- `HasArrived` means "no further destination", which includes *no destination was reachable*. Treating it as "arrived successfully" turns a pathing failure into a silent success.
- `Velocity` is metres per second in both locomotions, the same as a character's, and zero at rest (#424). The client extrapolates by `position + Velocity * secondsSinceUpdate`, so a bare unit direction would move every creature at 1 m/s between broadcasts. `LocomotionVelocityUnitsShould` pins it for both. The same rule holds for every `IWorldObject.Velocity` writer — characters publish the step `PlayerInputHandler` actually took (zero against a wall, zero once dead), a projectile its flight speed (`ProjectileSpeed`) — and the rule is listed per writer on that property.

## Parties

Party play: players form a **party** (the one term in code, packets, commands and messages) and share a procedural instance, its kills, its loot and its experience. `docs/party-protocol.md` is the client contract.

- **`PartyService`** (`Avalon.World/Parties`, a DI singleton, World-side; nothing about parties is on `Avalon.World.Public`) holds every party **in memory only**: a restart disbands them all, and a party lives on one world server (no cross-world party). **Tick thread only, every method**: the six handlers, the party commands, `World.SpawnInInstance`/`TransferPlayer`/`LeaveWorldAsync`, `World.Update` (`Tick`) and `WorldServer.Update` (`FlushMemberStatus`) all call it on the tick. No timers: every deadline is read from the container's `TimeProvider` inside those calls. A `Party` (`PartyId`, a `ValueObject<uint>` numbered from 1 per run; `Leader`; `Members` in join order, so the first is the longest-standing; `ExperienceMode`; `ExperienceModeLockedUntil`) is changed only by the service. A character is in at most one party, and `CharacterEntity.PartyId` (World-side, `internal set`) mirrors it for `Hostility`. A member who logs out stays a member, shown offline with its last known level; `CharacterOnline` (from `SpawnInInstance`) sets or clears its `PartyId` and sends its party the roster, and `CharacterOffline` (from `LeaveWorldAsync`, contained, before the logout save) sends the others the roster.
- **Requests and their answers** (a `PartyResult` each; refusals listed in the order they are checked):
  - `Invite(inviter, name)`: the name is looked up among online characters, ignoring case and surrounding spaces. `NotFound` (the inviter is not online), `NotLeader` (the inviter is in a party it does not lead), `NotFound` (the target is not online), `Self`, `AlreadyInParty`, `InvitePending` (the target already holds one), `PartyFull` (at `MaxPartySize`). An invite that passes sends the target `SMSG_PARTY_INVITE` and expires after `PartyInviteTimeoutSeconds`; one to a target that ignores the inviter is answered the same and never sent (see the ignore list under Chat Commands, #723). No party exists until an invite is accepted: an inviter with none leads the one formed then.
  - `Respond(target, accept)`: `NoInvite` without one; the invite is spent either way. A decline tells the inviter `InviteDeclined`. An accept is refused `AlreadyInParty`, `NotFound` (the invite's party is gone, the inviter now sits in a party it does not lead, or it went offline before any party existed) or `PartyFull`; otherwise the target joins: roster to every online member and "X joined the party.". An expiry tells both sides `InviteExpired`, naming the other; a character going offline ends every invite it sent or holds, the other side told `InviteExpired`.
  - `Leave(member)`: `NotInParty` or Ok. `Kick(leader, member)` and `Promote(leader, member)`: `NotInParty`, `NotLeader`, `Self`, `NotFound` (not a member, or, for a promote, offline: `Tick` would hand leadership straight back). A leave or a kick tells the others "X left the party." / "X was removed from the party.", sends the removed character an empty roster and clears its `PartyId`, and gives it the leave countdown when it stands in that party's instance.
  - `SetExperienceMode(leader, mode)`: `NotInParty`, `NotLeader`, `Invalid` (mode `Unknown`), `OnCooldown` (within `PartyExperienceModeCooldownSeconds` of the last switch), `InCombat` (any online member `IsInCombat`). The mode already set is Ok and changes nothing (the cooldown and combat are checked first); a switch applies at once, restarts the cooldown, and sends the roster and "Experience is now shared evenly." / "Experience is now shared by level.". `Even` is the default.
- **Leadership and disband.** A promote, and every handover, sends the roster and "X is now the party leader.". A leader that leaves, goes offline, or is found offline by `Tick` hands leadership to the longest-standing **online** member; with nobody else online a leader that went offline keeps it, and one that left hands it to the longest-standing member, offline as it is (`Tick` then passes it on once a member is online). A character deleted while in a party stays on the roster (offline) until the party disbands or the server restarts; `CharacterDeleteHandler` does not touch parties. Fewer than 2 members disbands the party: `IPartyInstanceRegistry.ForgetParty`, every member detached (empty roster, `PartyId` null) and told "The party was disbanded." (one inside the party's instance gets the countdown line as well).
- **Hostility.** Two members of one party are never hostile, whatever their PvP flags (`Hostility.IsHostile`, `SameParty` on `CharacterEntity.PartyId`), so an `Affects = Ally` heal reaches them unchanged.
- **Party instances.** `IPartyInstanceRegistry` (`Avalon.World/Instances`, World-side, `World.PartyInstances`; `InstanceRegistry` implements it, and the modding API's `IInstanceRegistry` does not have it). In `EnterMapHandler` (which first refuses any portal entry while a move is under way, `MoveInProgress`, see Item use) step 8 a character in a party whose portal leads to a Normal map goes to `GetOrCreatePartyInstanceAsync(party, map)`: an index party → map → instance, with the build de-duplicated per (party, map) as for #442 and published on the tick like every build (see InstanceRegistry), so members entering at once share one instance. `MapInstance.OwnerPartyId` is set at construction (init-only) and a party instance has no `OwnerCharacterId`. Once the build returns the handler re-checks that the character is still in that party (otherwise `MapTransitionResult.MapNotFound`) and that `PlayerCount` is below `min(MaxPartySize, map.MaxPlayers ?? MaxPartySize)` (otherwise `InstanceFull`, 6; so a procedural map must seat at least `MaxPartySize`: the seeded forest, map 2, holds 6, migration `RaiseForestMaxPlayers`, #707, after a seed of 1 let only the first member in, and `SeedIntegrityShould` pins every seeded Normal map); continuations run one after another on the tick and `TransferPlayer` adds at once, so two members arriving in one tick are counted right. Outside a party nothing changed (the character's own instance and its re-entry window); joining a party leaves a character's solo instances alone, but its portals no longer lead to them. Towns are unchanged. **Login always lands in a town** (owner decision; `CharacterSelectHandler`), never back in a party instance: a member re-enters through a portal. A disband forgets the party's index at once (a build published after the forget, wherever it finished, stays unindexed); its instances empty and expire on the usual 15-minute rule, and since `MapInstance` stamps `LastEmptyAt` at construction, an instance nobody ever entered expires too. A new leader changes nothing.
- **Leave countdown.** A character removed from a party (leave, kick, disband) while online in an instance that party owns (`IsPartyInstance`, which reads `OwnerPartyId` and so still holds after `ForgetParty`) gets a countdown of `PartyLeaveGraceSeconds`: at once "You left the party." / "You were removed from the party." / "The party was disbanded." followed by " Returning to town in 60 seconds.", then "Returning to town in N seconds." at 30, 10, 5, 4, 3, 2 and 1 (marks at or above the grace are skipped; a late tick announces only the lowest mark it passed). `PartyService.Tick`, run by `World.Update` before the instances tick, returns the connections whose deadline passed while still in that instance; `World` hands them to `PartyService.StartReturns`, which starts `TownReturn` (`Avalon.World/Respawn`, the move `RespawnAtTownHandler` uses) with `dropEncounter: true` and `revive: IsDead`, setting `RespawnInFlight` (a connection already returning is not started twice, see below), and the move goes through `World.TransferPlayer`; a character that died on the way arrives revived too. `TownReturn` settles both of its tasks (the town lookup and the town instance) before its continuations, as `CommandContext.Then` does, so a lookup or build that faults, or a step that throws, clears `RespawnInFlight` (only while the connection still holds that character) rather than leaving it set for good, and is logged at Error, or handed to the caller's `failed` callback when it passes one (`RespawnAtTownHandler` passes none). **A failed countdown return is retried (#700):** `StartReturns` passes `failed` as `PartyService.ReturnFailed`; the service remembers each return under way (forgotten by `InstanceChanged`, so a transfer that happened settles it, and on going offline) and, while the character is still online, still in the instance the countdown was for and not back in that party, re-arms a silent countdown of `Game:PartyReturnRetrySeconds` (default 5, 1-3600) with no marks announced, logging the failure at Warning; after `PartyService.MaxReturnRetries` (5) retries, or when those conditions no longer hold, the failure is logged at Error and nothing more is tried. A countdown that runs out while `RespawnInFlight` is already set (a respawn under way) is re-armed the same way rather than started twice, and a `TownReturn` that cannot be resolved counts as a failure for each. The player is told nothing more after the countdown reached zero. The party tick and each return are contained in `World.Update` (the tick's throws logged at most once per 10 s, `ThrottledErrorLog`), and so are the party calls in `SpawnInInstance`, `TransferPlayer`, `WorldServer.Update` (`FlushMemberStatus`, throttled the same way) and the kill's eligibility (`CreatureKilled` falls back to nobody eligible), so a party throw never costs the instances their tick, the online row, a transition or a corpse its teardown. It is cancelled by joining the same party again, by being in any other instance when checked (a portal, a respawn in town, any transfer) and by going offline. During it the character shares no kill (below) but still counts for health scaling.
- **Health scaling.** Party instances only. `MapInstance.HealthFactorFor(players, PartyHealthPerExtraPlayer)` = `1 + perExtra × (players − 1)`, 1 for one player or none; players are every character in the instance, the dead and those in a countdown included. `AddCharacter`/`RemoveCharacter` only mark it owed; the start of the instance's next `Update`, before the creature scripts, recomputes once, so several changes in one tick make one rescale and one message. When the factor changed, each creature gets `Creature.Rescale(factor)` (World-side, not on `ICreature`): maximum `round(BaseMaxHealth × factor)`, at least 1, `BaseMaxHealth` fixed by `CreatureSpawner` at spawn; current health keeps its share (`CharacterStatsCalculator.KeepShare`); a creature at 0 health is never rescaled (#672). Every connection in the instance gets one system line, "Creatures now have 220% health (3 players).", prefixed with "X has entered." or "X has left." when exactly one arrival or departure caused it. A creature spawned later starts at the current factor. The `Health` mark rides the creature's next update broadcast (`DescribeUpdatedObject` adds `Health` and `IsDead` to `CreatureUpdate` when marked), so clients already watching see the new maximum. Damage, armour, experience and loot are not scaled.
- **Kills.** `MapInstance.CreatureKilled` takes `PartyEligibility.For` once, first, on the tick, while the creature is still in its encounter (pure): a killer that is not a character or is in a countdown makes nobody eligible; a killer in no party is eligible alone; in a party, every member present in this instance, alive or dead, not in a countdown, and in the creature's encounter or within `PartyEligibilityRange` of the corpse on X/Z, and the killer always. It applies wherever the kill happens. **Loot**: `PartyLootAllocator` (see the ground-loot bullet) draws one eligible member per drop, uniformly through `ICombatRandom.NextInt64(0, n − 1)` (no draw for one), reserved for `LootGracePeriod`; with nobody eligible a party instance's drop is free for all at once. **Experience**: `PartyExperience.Split(creature.Experience, creature.Level, eligible, mode, PartyExperienceBonusPerExtra, PartyExperienceLevelGap, member => ExperienceAward.CanGainExperience(member, data))`, pure: a member at `creature level + gap` or more, or one that can gain no experience (at the maximum level or before a gap in the levels, #735, owner decision), gets nothing and is not counted, **solo too** (a character 5 levels above a creature earns nothing from it, and the others share the whole pool); n = 1 takes everything with no bonus; otherwise the pool is `xp × (1 + bonus × (n − 1))`, `Even` gives `floor(pool / n)` each and `LevelWeighted` `floor(pool × level / Σ levels)`. The mode is the first eligible member's party's. Each share then goes through the map's level band for that member (`ScaledExperience`) and the usual level-up (`Refill`, or `KeepShare` for a dead member); a level-up resends the roster (`LevelChanged`).
- **Protocol.** Six requests, each with a `MapSessionFilter` entry and a handler in `Avalon.World/Handlers`: `CMSG_PARTY_INVITE` (0x20B0, `TargetName`), `_INVITE_RESPONSE` (0x20B1, `Accept`), `_LEAVE` (0x20B2), `_KICK` (0x20B3, `CharacterId`), `_PROMOTE` (0x20B4, `CharacterId`), `_EXPERIENCE_MODE` (0x20B5, `Mode`). Each runs through `PartyReplies.Handle` and gets **exactly one** `SMSG_PARTY_RESULT` (0x30B1: `PartyResult`, append-only, and the name involved where known), sent after any roster or line the request caused; a request that throws is logged at Error and answered `Error` (15); a connection with no character gets nothing. `SMSG_PARTY_INVITE` (0x30B0) carries the inviter's name, class, level and `ExpiresInMs`. `SMSG_PARTY_ROSTER` (0x30B2: `PartyId`, `ExperienceMode`, `ModeLockedForMs`, members with `CharacterId`, `Name`, `Class`, `Level`, `IsLeader`, `Online`, `SameInstance` relative to the recipient) goes to every online member on a join, a leave, a kick, a leader change, a mode switch, a member coming online or going offline, any member's instance change (`World.TransferPlayer` calls `InstanceChanged`, so every map entry and respawn) and a level-up; an empty one (`PartyId` 0, no members) tells a character it is in no party. `SMSG_PARTY_MEMBER_STATUS` (0x30B3: health, maximum, power, maximum, power type, dead) is `FlushMemberStatus`, run by `WorldServer.Update` after `AbilityAmountsFlusher`: each online member whose values differ from what was last sent for it, and last sent at least `PartyService.StatusInterval` (250 ms) ago, goes to the other online members in its own instance, never to itself; the memory is dropped on a join, an instance change and a login, so they are sent afresh. The retired group opcodes (`CMSG_GROUP_INVITE_RESULT` 0x200A, `SMSG_GROUP_INVITE` 0x300D, `SMSG_GROUP_INVITE_RESULT` 0x300E) were deleted from `NetworkPacketType` (#697), and their numbers are free.
- **Commands** (`Avalon.World/Parties/PartyCommands.cs`, Player access): `/invite <name>` (`/inv`), `/leave`, `/kick <name>`, `/promote <name>` and `/partyxp even|level` make the same `PartyService` calls and are answered with the same `SMSG_PARTY_RESULT`, plus a system line on a refusal (`PartyReplies.Describe`) and "You invited X to the party." on an invite; kick and promote take a name among the caller's party members. `/p <message>` (`/party`) sends the text as typed (after the command word, trimmed; leading spaces and slashes skipped as the dispatcher skips them; none is answered "Usage: /p <message>") to every online member of the sender's party, the sender included, on `ChatChannel.Party`, wherever they are.
- **Settings** (`GameConfiguration`, range-validated at startup): `MaxPartySize` 6 (2-40), `PartyInviteTimeoutSeconds` 60 (1-3600), `PartyLeaveGraceSeconds` 60 (1-3600), `PartyReturnRetrySeconds` 5 (1-3600), `PartyExperienceModeCooldownSeconds` 60 (0-86400, 0 turns it off), `PartyHealthPerExtraPlayer` 0.6 (0 or more), `PartyEligibilityRange` 60 m (1 or more; its own setting, with `InterestRadius`'s default), `PartyExperienceBonusPerExtra` 0.10 (0-10), `PartyExperienceLevelGap` 5 (1-1000).

## Quests

Quests (#433): NPCs offer and take back quests through their dialogue; kills, conversations, collected items and quest scripts move a quest through its ordered stages; a turn-in pays experience, money and items. `docs/quest-protocol.md` is the client contract.

- **Data** (World DB reference data, migrations `ReshapeQuests` and `SeedQuestStoryline`): `QuestTemplates` (title, description and completion texts as `LocalizedTextId`s, giver and ender creature templates, `LevelRequirement`, nullable `ClassRequirement`, one nullable `RequiredQuestId`, `RewardExperience`, `RewardMoney` in copper, nullable `ScriptName`; `Environment`, `Type`, `Rarity`, `IsRepeatable` and `RepeatFrequency` are kept but unread, repeatables are #710), `QuestStages` (keyed `(QuestId, Sequence)`, an optional description text; `CK_QuestStages_Sequence`), `QuestObjectives` (an id set in the data, unique across quests; its stage, type `Kill` 1, `Collect` 2, `Talk` 3 or `Scripted` 4, a creature or item target, `Count`, a description text; `CK_QuestObjectives_TargetFitsType`, `CK_QuestObjectives_CountPositive`), `QuestItemRewards` (fixed items; choice rewards are #711) and `QuestItemDrops` (a Collect objective's item from a creature at `Chance` percent; `CK_QuestItemDrops_Chance`). The old `QuestRewards`/`QuestRewardTemplates` tables are gone. `ItemTemplateFlags.QuestItem` (2048) marks a quest item, and `ItemSubClass.Amulet` (206, an Armor subclass, worn in Neck) was added for the storyline's pendant; both are in the API contract enums too.
- **Catalog.** `QuestCatalog` (`Avalon.World/Quests`; the Quests reload area, `StaticData.Quests`, empty before the first load) validates every quest against the creature and item templates read in the same prepare, refuses a bad one with an Error naming it (`QuestRefusal`), and loads every other. It refuses an id of 0 or above `int.MaxValue` (quest options carry it negated), a missing giver or ender, a quest that is its own prerequisite, no stages, stages not numbered 0..n, a stage with no objectives or more than 4 (`MaxObjectivesPerStage`), an objective naming a stage the quest lacks, a count of 0, a target that does not fit the type, a missing creature or item, a Collect item that is not a `QuestItem`, one quest collecting an item twice, drops on an objective that is not Collect (no check constraint can say it), a drop from a missing creature or outside 0-100, a missing, zero-count or `Unique` reward item, a `Scripted` objective on a quest with no `ScriptName` (only its script can move it), and a `ScriptName` that is not a loaded `QuestScript` (`IScriptManager.GetQuestScript`). It also refuses a giver, an ender or a Talk objective's creature whose template has no dialogue root (#737, `has no dialogue root`), against the `DialogueNodes` read in the same prepare, startup included, since `InteractHandler` opens a conversation only at a root and such a quest could never be accepted, handed in or finished. The other direction refuses nothing: applying a dialogue patch, or a quests patch (whose prepare may have read other roots than the ones live), logs one Error per loaded quest whose giver, ender or Talk target has no root in the live dialogue, listing its problems (`QuestCatalog.NpcsWithoutDialogue`, from `StaticData.Apply`), and the quest stays loaded until a `/reload quests` refuses it. Markers are unchanged, still built from the catalog. Then, to a fixed point, a quest whose prerequisite is in a cycle, missing or refused, and, by id, every later quest collecting an item an earlier surviving quest collects, so a drop or a pickup credits exactly one quest. `GivenBy` (by level then id), `EndedBy` (by id), `DropsFrom` and `IsQuestNpc` are its lookups. `/reload quests` rebuilds it, effective from the next tick; characters keep the quests they hold, and a held quest the catalog no longer has is left out of the log, counts nothing, and can still be abandoned. **Every held quest is settled once against a new catalog (#738)**: `QuestFlusher`'s first step, `QuestService.SettleAfterReload`, compares `QuestLog.SettledCatalog` (never saved; set by the select recount) with the catalog by reference and, once per reload, caps each count above its objective's count, recounts the current stage's Collect objectives, sends a `ReadyToTurnIn` quest back to `Active` ("X: no longer ready to turn in.") when its stage is no longer the last or a Collect objective of its last stage is short in the Bag, and settles the stages (so a stage added after the last starts), with the usual lines and updates. `TurnIn` and `DialogueOptionsFor` run the same check first (one reference compare), so a turn-in or an NPC's options on the reload tick, before the flush, see settled quests. The select recount (`RecountAtSelect`) does the same settle quietly, so a reload while a character was offline is settled at login. A quest whose current stage a reload removed is left as it is (abandon still works) and logged at Warning, at most once per quest per 10 s; a ready quest whose Kill or Talk count a reload raised stays ready.
- **`QuestService`** (`Avalon.World/Quests`, a DI singleton, World-side): everything a quest does at run time. **Tick thread only**, no timers and no awaits: its callers are the three quest handlers, `InteractHandler`, `DialogueChooseHandler`, `LootPickupHandler`, `MapInstance.CreatureKilled`, `CharacterSelectHandler` and `QuestFlusher`; the clock is read only to stamp accept and completion times and the lines. It changes a character only through its `QuestLog`, `IInventoryService` and `IWallet`. `MapInstance`, `WorldServer` and every handler but the three quest handlers take it as an optional dependency; `WorldHostGraphShould` pins that production registers it, `QuestProgress` and `ICharacterQuestRepository`, and that `InteractHandler`, `DialogueChooseHandler`, `CharacterSelectHandler` (with the repository too) and `LootPickupHandler` receive it (`Hand_the_quest_service_to_the_handlers`).
- **Availability** (`QuestAvailability.Check`, pure, in this order): not completed and not held, the prerequisite completed, `Level >= LevelRequirement`, the class when one is required, the script's `CanAccept`, then room in the log (`Game:MaxActiveQuests`, default 20, range 1-100). All but the last answer `NotAvailable`; a full log answers `LogFull`, and a quest refused only by a full log is still offered and still marked available, so the accept can say why.
- **Dialogue.** `QuestService.DialogueOptionsFor` adds quest options only at the NPC's root: one `QuestTurnIn` per quest this NPC ends that the character holds `ReadyToTurnIn` (by id), then one `QuestOffer` per quest it gives that is `Ok` or `LogFull` (by level, then id); `InteractHandler.Send` puts them before the node's own options. An option's id is the quest id negated, and `SDialogueOptionInfo.QuestId` (field 4) names the quest. `DialogueChooseHandler` hands a negative option id, after its usual checks (alive, the NPC there and alive, the leash, the node), to `QuestService.TryChoose`, which sends `SMSG_QUEST_OFFER` only for an option this character is offered at this node now (anything else is logged and ignored) and leaves the conversation where it is. `InteractHandler` contains the options and the talk credit: a quest that throws loses them, and the NPC still opens.
- **Accept, abandon, turn-in.** `Accept` and `TurnIn` first check the conversation: the character alive and `CurrentDialogue` with that NPC (else `NoConversation`), the NPC in the instance and alive (else `NoConversation`, ending the conversation out loud), inside `NpcInteraction.IsWithinLeash` (else `TooFar`, ending it), as the dialogue leash rule above requires. **Accept:** the quest known and this NPC its giver (else `NotAvailable`), then availability; it starts at stage 0 with every count 0 ("Quest accepted: X."), runs the script's `OnAccepted` then stage 0's start, settles, and re-sends the NPC's root. **Abandon**, anywhere in a map: `NotActive` unless held; every copy of the quest's Collect items leaves the Bag and the Bank, the quest and its progress are dropped ("Quest abandoned: X.", "#id" for a quest the catalog lacks), and it can be accepted again. **Turn-in, all or nothing:** held and known (else `NotActive`), this NPC its ender (else `NoConversation`), the Bag recounted as it is now, then `QuestTurnInRules.Decide`, pure: `ReadyToTurnIn` and the last stage's Collect items all in the Bag (else `NotReady`), every reward template known and not `Unique` (else `Error`, logged at Error naming the quest and the template, since a reload made it unpayable), the rewards fit the Bag as it will be once the quest items have left (`Fits`, stacking as `TryAdd` does; else `BagFull`), the money under `Game:MaxMoney` (else `MoneyCap`). Only then are the quest items taken (Bag and Bank), the experience granted, money and items paid, the quest completed ("Quest completed: X.") and the root re-sent. A step refusing after the checks passed is logged at Error and not rolled back (the `VendorTrade` stance). The root re-sent after an accept or turn-in is contained: a throw there is logged at Error, throttled per quest, and the request is still answered `Ok`, since it has happened. A quest is completed once; repeatables are #710.
- **Progress.** `AddProgress` adds to one objective of an Active quest's current stage, capped at its count; it refuses 0, a quest not Active, an objective outside the current stage, and any Collect objective. **Kill:** `MapInstance.CreatureKilled` calls `QuestService.CreatureKilled` (`CreditQuests`, contained) with the kill's `PartyEligibility` list, before the drops and the experience: every eligible character (the killer alone outside a party; dead members included) gets +1 on each Kill objective for that creature template in the current stage of each Active quest, wherever the kill happens. **Talk:** `InteractHandler`, for an interact it accepted (alive, within 5 m, an NPC with a dialogue root), calls `Interacted` before building the node, which meets every Talk objective for that template in the current stage, so a quest made ready by the conversation already shows its turn-in. A Talk target therefore needs a dialogue root, which the catalog checks (#737, see Catalog). **Collect** counts the item in the **Bag only** (`QuestService.HeldInBag`), capped, for the current stage of every held quest (`RecountCollect`): from `QuestFlusher` on a tick whose inventory changes touched a Bag slot (so every path counts: a pickup, a move, a destroy, a vendor), at each stage start, at turn-in, and at select (`RecountAtSelect`, which then drops the lines and updates it queued, since the log already shows the counts). **Scripted** objectives move only through the quest's script (`IQuestContext.Advance`).
- **Stages.** `Settle` runs after each change: while every objective of the current stage is met, the next stage starts ("X: stage complete.", its Collect objectives counted from the Bag, then the script's `OnStageStarted`), or after the last the quest becomes `ReadyToTurnIn` ("X: ready to turn in."). A Collect recount that leaves a ready quest short sends it back to `Active` ("X: no longer ready to turn in."); nothing else does. A count change says "<objective text>: n/m". A stage-start hook that advances its own quest is settled by the loop already running for it; any other quest settles at once.
- **Quest drops and items.** In `MapInstance.DropLoot`, `RollQuestDrops` (contained) rolls each of the creature's quest drop rows once for each eligible character with an Active quest whose current stage has that Collect objective and fewer of the item in the Bag than its count (`StillNeeds`, the one rule the pickup shares), at `Chance` percent through `ILootRandom`; each success is one item, owned by that character with `FreeForAllAt = DateTime.MaxValue`, placed in the same ring as the table drops (a creature without a loot table can still drop quest items). `LootPickup.TryPickUp` refuses, with `NotYours`, a quest item the picker no longer needs (`QuestService.MayPickUp`, by the Bag; a throw refuses too), its owner included, and the drop stays. Drops on the ground do not count, so an owner short of its count may see more drops than it can take. Quest items are never sold: `VendorRules` refuses selling one (`NotSellable`) and `VendorCatalog` refuses a stock row of one; a stocked item that a `/reload items` flags `QuestItem` is hidden from the list and its buy answered `NotFound` at once (`VendorRules.IsStockable`), as the price floor holds, and so is a buyback of one sold before the flag (#738). Turn-in and abandon take every copy from the Bag and the Bank; equipped copies are not searched (quest items have no slot).
- **Experience** (owner decision): `ExperienceAward.Grant` (`Avalon.World/Characters`) gives a character experience its caller worked out and levels it past **every** requirement the total covers, carrying the rest; each new level refreshes the stats (`Refill`, or `KeepShare` for a dead character), and the party roster is resent (`LevelChanged`). A character can gain experience only while its level and the next both have a `CharacterLevelExperiences` row (`ExperienceAward.CanGainExperience`, the one rule the award and the party split share, never a constant, #735). So at the maximum level (the highest row, 15 today), and on a level whose next level is missing (a gap, treated exactly like the maximum, owner decision), a character gains no experience from any source (kill, party kill, quest), and an award that levels a character onto such a level stops there, the rest discarded, so it arrives with 0; nothing is logged for either. A character whose current level has no row is awarded nothing and a warning is logged. A quest's `RewardExperience` is personal: no party split, no level gap, no map band. Kills use it too, after `PartyExperience.Split` and `ScaledExperience`, so one kill's share can now raise several levels, where it raised one before.
- **The quest log and saves.** `CharacterEntity.Quests` is a `QuestLog` (World-side, never on `ICharacter`): the `ActiveQuest`s (state `Active` 1 or `ReadyToTurnIn` 2, stage, the counts above 0, the accept time) and the completed ids with their first completion time. Only `QuestService` calls its mutators; each marks `SaveStateTracker.QuestChanged(questId)` and the client change for that quest, and raises `Version`. The next save carries a `CharacterQuestWrite` (built in `CharacterSaveSnapshot`) in the same transaction as the rest: for each marked quest its `CharacterQuests` row and `CharacterQuestObjectives` rows are deleted and, for a quest still held, the current ones inserted; a `CharacterCompletedQuests` row is inserted when missing (migration `AddCharacterQuests`; all three cascade from `Characters`, the objectives from their quest row). Memory is authoritative, as for the inventory. Select loads the rows (`ICharacterQuestRepository.GetByCharacterIdAsync`, one more `CharacterSelectHandler.Step` after the abilities), copies the connection's locale for the lines (an account lookup that lands later sets it too) and runs `RecountAtSelect`, contained.
- **Vendor quest gates** ask `IQuestProgress`; production's `QuestProgress` answers from the quest log (`Active` = held, active or ready; `Completed` = turned in). An open shop's list is sent again on the vendor pass after an accept, an abandon or a turn-in (#738); progress alone sends none. `NoQuestProgress` is only a handler's fallback when built without the container. No seeded row is gated.
- **Quest scripts.** A `QuestScript` (`Avalon.World.Public/Scripts`) is named by `QuestTemplate.ScriptName` and found by type name: `ScriptManager` keys every subclass by `t.Name`, once, at `Load()` (never hot-reloaded, like `AbilityScript`). `QuestService` builds one per quest with `ActivatorUtilities.CreateInstance`, **no runtime arguments**, over `QuestScriptServices` (`Avalon.World/Quests`, #738), a provider over the world's container that hands over **only `ILoggerFactory`, `ILogger<T>` and `TimeProvider`** and answers null for everything else, the provider itself included, so no script can obtain `QuestService`, `IWorld` or any other service that writes; the one instance serves every character, so it keeps no per-character state. One whose constructor asks for anything else (or otherwise cannot be built) is logged at Error once and its quest cannot be accepted; a reload pointing the quest at another type builds that one. `QuestScriptConstructibilityShould` builds every shipped one through the production container wrapped in `QuestScriptServices` (none is seeded yet), and pins that a script asking for `QuestService`, `IWorld` or `IServiceProvider` builds from the bare container but not through it. AI scripts are unchanged: still built from the full container. The modding surface is `QuestScript`, `IQuestContext`, `IQuestCharacter` (id, name, level, class) and the read-only snapshots `QuestCreatureView` and `QuestInstanceView`, nothing else: a hook reads the world only through them, and its one write, enforced by what its constructor can receive, is `IQuestContext.Advance`, which adds to one of **its own quest's Scripted objectives in the current stage**, judged by the live catalog, while the character still holds that very copy and it is Active; anything else returns false, changes nothing and is logged at Warning, at most once per quest per 10 s. Hooks: `CanAccept(character)` (can only narrow availability), `OnAccepted`, `OnStageStarted(stage)` (stage 0 right after `OnAccepted`, then each stage as it starts, each once and in order; also for a character still being selected when its select recount completes a stage), `OnCreatureKilled` (the character shared the kill), `OnInteract` (it opened a conversation) and `OnEnterInstance`. Each runs contained: a throw is logged at Error with the quest, the hook and the character, at most once per quest per `ThrottledErrorLog.Interval` (10 s, counting the throws left out), and the quest, the kill, the conversation, the accept or the select goes on; a `CanAccept` that throws refuses. **For script authors:** hooks run only while the quest is Active, so a kill or a talk that made it ready reaches no hook and a ready quest hears nothing; `OnCreatureKilled` after a kill that changed the stage gets the new stage's context (`Stage`, `ProgressOf`); `OnEnterInstance` fires on each arrival in an instance other than the one it last ran for, checked by `QuestFlusher` every tick once the character stands in a live instance, after every login too (the memo, `QuestLog.ScriptsInstance`, is never saved); the memo is per character, not per quest, so a quest accepted while already inside an instance, or one going from ready back to Active, hears it only on the next arrival.
- **Flush.** `QuestFlusher.Flush` runs from `WorldServer.Update` after both passes and **before** `InventoryUpdateFlusher`, whose slot changes it reads, each step contained on its own (`QuestService.FlushStepFailed`, a `ThrottledErrorLog` per step, so a recount that throws every tick still lets the log, updates, lines and markers out), for a connection holding a `CharacterEntity`: the settle after a `/reload quests` (#738), the Collect recount if the Bag was touched, `EnteredInstanceIfChanged`, `FlushClient` (the whole `SMSG_QUEST_LOG` the first time, `QuestLog.LogSent`, which carries every change already; afterwards one `SMSG_QUEST_UPDATE` per changed quest in id order; then the milestone lines, `SChatMessagePacket.System`), then `FlushMarkers`. So within a tick a quest's update and lines precede the inventory update: a turn-in's `Completed` arrives before its reward items and gold. A quest whose log entry or update cannot be built is left out and logged at Error, throttled per quest. **Markers:** `SMSG_QUEST_MARKERS` lists every quest NPC (`IsQuestNpc`) in the character's instance, with no interest radius, with `MarkerFor` (`ReadyToTurnIn` over `Available` over `None`); worked out again only when the instance, the level, the log's `Version` or the catalog generation changed, and sent only when the list differs from the last one sent. A quest NPC spawned or removed later is not noticed until one of those changes (the seeded ones are town NPCs, which stay).
- **Protocol** (`Avalon.Network.Packets/Quest`): `CMSG_QUEST_ACCEPT` (0x20C0, `QuestId`, `NpcGuid`), `CMSG_QUEST_TURN_IN` (0x20C1, the same) and `CMSG_QUEST_ABANDON` (0x20C2, `QuestId`), each with a `MapSessionFilter` entry and a handler in `Avalon.World/Handlers` running through `QuestReplies.Handle`: **exactly one** `SMSG_QUEST_RESULT` (0x30C1, `QuestResult`: `Ok` 1, `NotAvailable` 2, `NotActive` 3, `NotReady` 4, `LogFull` 5, `BagFull` 6, `MoneyCap` 7, `TooFar` 8, `NoConversation` 9, `Error` 10, append-only), sent after any dialogue node the request caused and before its updates; a throw is logged at Error and answered `Error`; a connection with no character gets nothing. `SMSG_QUEST_OFFER` (0x30C0), `SMSG_QUEST_LOG` (0x30C2), `SMSG_QUEST_UPDATE` (0x30C3: `Accepted` with the display, `Progress`, `Removed`, `Completed`; at most one per quest per tick, an accept staying `Accepted` for its tick) and `SMSG_QUEST_MARKERS` (0x30C4) are self-describing: `QuestDisplayDto` (`QuestDisplay.Build`) carries every text resolved in the character's language, the stages, objectives and rewards, so the client needs no quest catalog. `DialogueOptionKind` gained `QuestOffer` 3 and `QuestTurnIn` 4.
- **Read-only outside the world server (#714).** `GET /world/{worldId}/quest-template` (paged by id, page size at most 50) and `/{id}` (`QuestTemplateController`, `[WorldScoped]`, **GameMaster** policy, since stages, drops and scripts are the storyline ahead of a player; 404 for an unknown id) return `QuestTemplateDto`: the header (title, description and completion text each resolved to the base-locale (enUS) wording of `LocalizedTexts`, beside its text id, an id with no row reading as an empty string, placeholders such as `{name}` left as stored), giver and ender creature template ids, level, class and prerequisite requirements, script name, experience and copper, the stages in order with their objectives by id (type as the string enum `Avalon.Api.Contract.QuestObjectiveType`, creature or item target, count, text), item rewards and every Collect objective's drops (`IQuestRepository.PaginateAsync`/`FindByIdAsync`, `ILocalizedTextRepository.GetByIdsAsync`); `Environment`, `Type`, `Rarity`, `IsRepeatable` and `RepeatFrequency` are left out, being unread in v1 (#710). `tools/Avalon.Exporter -- quest-catalog` writes `schema/quests/quest-catalog-v1.json` (`QuestCatalogExport`, pinned by `QuestCatalogExportShould`, which also fails when the committed file differs from the seed rendered, so a seed change needs a re-export): per quest the id, the enUS title, the stages with each objective's id, type (as its number, the wire's `QuestObjectiveKind`), target id (0 for Scripted) and count, and the rewards (experience, copper, items); for tooling only, the client needs none of it; like `ability-catalog` it needs a World database and is reviewed as a data diff. A character's quest log is `GET /world/{worldId}/character/{id}/quests` (`CharacterController.GetQuests`, the owner or a game master, as the other character sub-resources; 404 for an unknown character): `CharacterQuestLogDto`, the held quests by id (state as the string enum `Avalon.Api.Contract.CharacterQuestState`, stage, accept time, and the saved objective counts by objective id, **an objective with no entry standing at 0**, since only counts above 0 are saved) and the turned-in quests with their first completion time, as the world server last saved them (`ICharacterQuestRepository`, no World DB lookup, no titles).

## Inventory, Gold and Character Saves

- **Everything a player owns lives in the Character DB**: `Character.Money` (the character's gold balance, in copper, a `ulong`), `ItemInstance`, and `CharacterInventory`, whose `ItemId` is a real FK to `ItemInstance` (cascade). `ItemInstance.CharacterId` is a real FK to `Characters` (cascade), so the hard delete in `CharacterDeleteHandler` takes the character's items with it, as it already did its slots. The World DB holds reference data only; `ItemInstance.TemplateId` points into it with no FK, and the REST API looks templates up with `IItemTemplateRepository.GetByIdsAsync`. Item ids come from `IItemIdAllocator` (`Guid.CreateVersion7()`), never from EF or the database (`ValueGeneratedNever`).
- **Memory is authoritative.** Change items only through `IInventoryService` and money only through `IWallet`, both from `ICharacterEconomy` in `Avalon.World/Inventory`. `ICharacterInventory` in World.Public is read-only apart from `Load`, which replaces a container's whole contents at character select and marks nothing. Tick thread only, all or nothing: adds fill existing Bag stacks, then the lowest free Bag slots, never Equipment or Bank; removal by template takes the highest Bag slot first. `IWallet.TryAddMoney` refuses past `Game:MaxMoney` and never wraps. A vendor trade goes through `ICharacterEconomy.VendorOf` (`VendorTrade`), which asks the pure `VendorRules` and applies the plan through these same two services.
- Each successful change marks `CharacterEntity.SaveState` (`New`/`Changed`/`Removed` per item and per slot, plus a money-dirty flag) and `CharacterEntity.ClientChanges`. **Writing a `CharacterInventoryContainer` directly, or calling `ICharacterInventory.Load` after select, skips both: the change is neither saved nor sent.** Character creation is not a save: `CharacterCreateHandler` writes the starting items and slots directly through `IItemInstanceRepository` and `ICharacterInventoryRepository`, because no entity exists yet.
- **Saves go through `ICharacterSaver`**: one Character-DB transaction (`ICharacterSaveRepository`) with the whole row plus only the non-`Unchanged` items and slots, and the character's `CharacterStats` row when its derived stats changed since the last save (`SaveState.StatsDirty`), as idempotent upserts and deletes. `CharacterSaver` chains saves per `CharacterId`, not per entity, so a relog's saves still queue behind the previous session's despawn save; `WhenIdle(id)` completes once every save queued for that character so far has finished, committed or failed, and `CharacterSelectHandler` waits on it (up to `SaveWaitLimit`, 5 s) before loading the character. **A select whose wait runs out reads nothing**: it logs a warning and cancels the select (`CancelSelect`), and the client can select again. Reading anyway would load the state from before the save still running, and the new session's first save would write it back over the committed one. `WhenAllIdle()` is the same for every character at once: `WorldServer.OnStoppingAsync` awaits it last, because a tick starts each despawn without waiting for it, so a despawn save begun on an earlier tick can still be writing when the host stops. That wait is bounded by the host's stop token and `WorldServer.SaveDrainLimit` (20 s), and logs an error if it gives up. Marks are acknowledged only when the commit's continuation runs on the tick thread; a failed save keeps them for the next one. The task a save returns never faults (it is `false` on failure), but the multi-character `Save(list)` throws `ArgumentException` synchronously, before queuing anything, if it names a character twice or one item under two characters.
- **One world session per account (#465, #474).** Two copies of a character would each hold their own inventory and money, and whichever saved last would write over the other, losing or duplicating items and gold; and the owner's rule is one character in the world per account. The auth server's `Online` flag cannot prevent it (a dropped auth connection clears it while the world session stays up), and the `inWorld` mutex only spans world select to key exchange, so the world server enforces it at select. `CharacterSelectHandler` asks `IWorldServer.SessionsOf(accountId, except)` for the account's other connections, which includes closed ones whose despawn the tick has not dequeued yet (a close enqueues its despawn before it leaves `Connections`). **Every one of them is kicked**, whatever it holds (the selected character, a different one, a select still under way, or nothing): the handler cancels its select if one is in progress, calls `World.DeSpawnPlayerAsync` for it right there on the tick, then `NotifyAndClose` with `DisconnectReason.DuplicateLogin` and "Your account has been logged in from another location.". The despawn runs in the handler rather than being left to the close, because a close is only despawned by a later tick, and a `WhenIdle` taken before then finds no logout save to wait on. `DeSpawnPlayerAsync` queues its save before its first await, so the save is already in the chain the new select waits on, and clears `connection.Character` in a `finally`, so the connection ends holding nothing on every path, throw or not, and the despawn the close queues later saves nothing. Its instance steps (lookup, `DropPlayerFromEncounter`, `RemoveCharacter`) are each contained and logged, and the save is queued whatever they did, so a throwing step costs neither the logout save nor the removal of the others; `MapInstance.RemoveCharacter` drops the character from its tick, broadcast and periodic-save membership before it tells its own creatures' scripts (`AiScript.OnCharacterLeft`, each call contained), so a script that throws cannot leave it live. Only a throw while taking the snapshot itself queues nothing. The kicked connection's continuations still run after it lets go: `EnterMapHandler` and `RespawnAtTownHandler` check that the connection still holds the character they started with and otherwise do nothing, and `ProcessContinuations` contains each callback, logging one that throws, so it cannot end the flush for the connections after it. The new select waits, before its first read, on one `Task.WhenAll` bounded by `SaveWaitLimit`: its own character's `WhenIdle`, the `WhenIdle` of every *different* character it kicked (taken after that character's despawn queued its save), and the select step each kicked mid-select connection still had in flight. If the wait runs out it reads nothing, as above. **A kicked select stops at its next step**: every step of the select chain goes through `CharacterSelectHandler.Step`, which records the step's task per connection (a `ConditionalWeakTable`, tick thread only) and runs the next step only if `OwnsSelect` holds, meaning the connection is still up, not closing (`IWorldConnection.IsClosing`, read-only, set the moment `Close` is called), and `SelectStartedTicks` still equals the value that select began with. A select from a closing connection is ignored at `Execute` too: a kicked connection stays `IsConnected` until its outbox flushes, so a select it had queued in the same tick would otherwise kick back the session that kicked it, leaving neither in the world. Cancelling the select (the kick, the chain's own give-up paths, or `CancelExpiredSelects`) or losing the connection therefore stops the chain before its row write, its inventory reads and its `SetPendingSpawn`; the one step already running cannot be called back, which is why the new select waits for it. Other accounts' sessions are never touched.
- **Change Character (#663).** `CMSG_CHARACTER_LEAVE` (`0x2016`, no fields, `CharacterLeaveHandler`) returns a player in the world to character selection on the same world connection; exactly one `SMSG_CHARACTER_LEAVE_RESULT` (`0x302B`, `CharacterLeaveResult`: `Left` 1, `NoCharacter` 2, `Selecting` 3 during a select or while the character waits on its load report, `AlreadyLeaving` 4; refusals change nothing) answers it, unless the connection is closed instead. The leave is a logout: `IWorld.LeaveWorldAsync` is `DeSpawnPlayerAsync` answering whether the logout save committed, and `Left` is sent only once it has, so the row is offline and a reselect of the character (which waits on `WhenIdle` anyway) reads what was saved. A save that fails, or a leave that throws, is never answered: the connection is closed with `DisconnectReason.CharacterSaveFailed` (5); one that drops or is kicked meanwhile is not answered. From the start of the leave until its answer, `IWorldConnection.LeaveInProgress` (read-only; set through the World-side `ICharacterLeaveControl`, with the target, last input sequence, respawn flag and conversation cleared) makes the list, select, create and delete handlers refuse as they do mid-select, by closing, and a second leave is `AlreadyLeaving` and saves nothing. The leave is accepted by `WorldSessionFilter` alone, whatever the connection holds, never by `MapSessionFilter`: it runs in the session pass, before any instance ticks, and in-map packets queued before it are handled by the map pass first. In-map packets queued behind it, meant for the character that left, would wedge the queue (neither filter accepts them without a character), so the session pass drops an in-map packet (`MapSessionFilter.IsMapPacket`) that reaches the head of the queue while the connection holds no character. A leave in combat is allowed, as a logout is. `docs/character-login-flow.md` has the exchange.
- **Character names (#757, owner decision).** A name is 3 to 12 ASCII letters (`CharacterName` in `Avalon.Domain.Characters`, the one rule), checked as sent, before anything is read or trimmed: `CharacterCreateHandler` answers `NameTooShort`, `NameTooLong` or, for anything else, `NameInvalid` (`SCharacterCreateResult` 8, appended; the full answer order is in `docs/character-login-flow.md`). It is stored, and shown to everyone, in one display form, first letter upper-case and the rest lower-case (`CharacterName.Display`: `kAELA` is `Kaela`). `Characters.NameKey` holds its key, the name with only its ASCII letters upper-cased and nothing trimmed (`CharacterName.Key`; setting `Character.Name` sets it); a unique index (`IX_Characters_NameKey`) makes "Bob" and "bob" one name per world, and a check constraint, `CK_Characters_NameKey` (`"NameKey" = upper("Name" COLLATE "C")` on Postgres, locale-independent and ASCII-only like the .NET fold; plain `upper("Name")` on the SQLite the tests use, which folds ASCII only, the model choosing by provider), holds every writer to it. A typed name is looked up by `CharacterName.LookupKey` (the key of it trimmed), so a dotless i never finds an I: the create's duplicate check and `ICharacterRepository.FindByNameAsync`, the ignore list's offline lookup (`FindCharacterByNameAsync`), `OnlineCharacters` (so `/w` and `/invite`), `Party.FindByName` (`/kick`, `/promote`), `IgnoreList.FindByName` (`/ignore`, `/unignore`) and the self checks (`CharacterName.Same`). **A name changes only by insert or by `ICharacterRepository.TryRenameAsync`:** `Name` and `NameKey` are insert-only to the change tracker (`PropertySaveBehavior.Ignore` after save), so no tracked update (the world's saves, the select-time write, the API's admin patch) ever writes them, and a world holding an older name in memory can neither write it back over a rename nor fail its saves on the unique index. `ICharacter.Name` on World.Public is get-only; `CharacterEntity.Name` (World-side) keeps a setter, which no production path uses. A race to the unique index is recognised only as that violation (`CharacterNameKeyViolation.Is`: SQLSTATE 23505 on `IX_Characters_NameKey` on Postgres, the UNIQUE failure on `Characters.NameKey` on SQLite); anything else is rethrown. A create that loses it is answered `NameAlreadyExists`. The migration that added the column (`AddCharacterNameKey`) fills it from `upper("Name" COLLATE "C")` before building the index and leaves every existing name as it is (owner guarantee: none breaks the rule or clashes by case); unlike the account username migration, it does not check for clashes. **REST renames** (`PATCH /world/{worldId}/character/{id}`, `CharacterService.UpdateCosmeticAsync` and `UpdateAnyAsync`, owner decision) follow the same rule and display form: a name that breaks it, an empty one included, is a 400 validation error (`CharacterNameRuleAttribute` on `CharacterPatchDto.Name`, the pattern in the OpenAPI schema, and again in the service as a 400 `BusinessException`, `CharacterName.Requirement`); a name another character holds by key is "Name already taken", and so is a rename that loses the race to the index; a character in the world is refused with 409 `CharacterOnlineException` "Character is online; rename it while logged out."; a character deleted between the endpoint's lookup and the rename (`CharacterRename.NotFound`) is 404, `CharacterNotFoundException`, written as MVC's own 404 client-error ProblemDetails, the endpoint's answer for a missing character (owner decision). A name that would not change writes nothing (a character may change the case of its own name), so an admin patch of other fields still applies while it is online. The rename is one conditional statement, `UPDATE ... SET Name, NameKey WHERE Id = @id AND NOT Online` (`TryRenameAsync`): the world marks the row online by writing it, so the row lock orders the two and the rename sees the flag or commits first. A rename landing between a select's read and its spawn (the row not yet online) is accepted; that session shows the old name until its next select, and since the world never writes the name, nothing reverts it.
- The save triggers: entering an instance (`World.SpawnInInstance`, which writes `Online = true`), map entry (`EnterMapHandler`), periodic (`CharacterSaveScheduler`, ticked from `MapInstance.Update`, every `Game:CharacterSaveInterval`, default 5 min, with each character's first save staggered across the interval by its id), and despawn (`SaveOnDespawnAsync`, every logout and disconnect). The despawn snapshot is taken on the tick; a dead logout's move to the respawn town needs a database lookup, so it is applied to the copied row inside the chained write. That lookup reads the World DB while the save writes the Character DB, so `World.MoveToRespawnTownAsync` never lets a failed lookup fail the save: it logs and falls back to town 1's default spawn, or, when map template 1 is not loaded, keeps the map and position the character died at. The select-time row update is still a plain `ICharacterRepository.UpdateAsync`, because nothing is loaded yet. The multi-character `Save(list)` is the one-transaction save for exchanges that must not half-happen (auction house, trade, mail); nothing calls it yet.
- **Client:** `SInventorySnapshotPacket` carries `Money` at login, and never the Bank. `SInventoryUpdatePacket` (`SMSG_INVENTORY_UPDATE`) carries absolute `{Container, Slot, Item?}` entries plus an optional `Money`, built at most once per tick per connection by `InventoryUpdateFlusher` in `WorldServer.Update`, after both passes. **Bank slots are sent only while the bank is open** (`BankAccess.IsOpen`): `InventoryClientChanges` records them like any slot, and the flusher drops them when it is closed. The client-to-server packets that change inventory are `CMSG_LOOT_PICKUP` (#460), `CMSG_ITEM_MOVE` and `CMSG_ITEM_DESTROY` (#463), the three vendor requests (#432), `CMSG_QUEST_TURN_IN` and `CMSG_QUEST_ABANDON` (#433), which take quest items and pay rewards, and `CMSG_ITEM_USE` (see Item use), which equips gear and spends what an item script consumes.
- **Item requests (#463).** `CMSG_ITEM_MOVE` (`0x2080`) and `CMSG_ITEM_DESTROY` (`0x2081`), both accepted by `MapSessionFilter`, address slots only (containers cross as numbers, 0 Equipment, 1 Bag, 2 Bank; never item ids), and each gets exactly one `SMSG_ITEM_RESULT` (`0x3090`): an `ItemRequestResult`, and on a refusal only, the current state of the slots it named (a Bank slot only while the bank is open). `InventoryMove` (`Avalon.World/Inventory`) is the pure rule table: from the two slots and the count the server derives Move, Split, Merge or Swap, checks equipment (slot, level, class, two-hander against the off hand) and the Bank, and changes nothing. Two whole copies of a non-stackable item swap rather than merge; no stack (count above 1), split or merge ever goes into Equipment (`NotStackable`); an item whose template is gone (a reload removed it) stacks to 1 and can be moved within the Bag and the Bank, taken off, and destroyed, but never equipped. `IInventoryService.TryMove`/`TryDestroy` apply its decision with the usual `SaveState`/`ClientChanges` marks; a split's new id comes from `IItemIdAllocator`. A dead character gets `Dead`; a handler exception is logged and answered `NotFound`.
- **Equipment slots** (`EquipmentSlots`, the one mapping): 0 Head, 1 Neck, 2 Shoulder, 3 Chest, 4 Hands, 5 Legs, 6 Feet, 7 and 8 Finger, 9 MainHand, 10 OffHand; 11-13 are reserved and every request naming one is refused. This is not `ItemSlotType`'s numbering (its `Gem` is 8, and a gem is never worn). A neck piece is `ItemSubClass.Amulet` (206, an Armor subclass, #433) with `Slot = Neck`, and a ring `ItemSubClass.Ring` (207, forest content pass) with `Slot = Finger`. Nothing starts in Equipment: creation puts every starting item in the Bag.
- **The bank.** Usable only at a banker, in an open conversation with it in which its `OpenBank` option was chosen, inside the dialogue leash. `BankAccess.TryUse` checks all of that on every request that touches the Bank, and ends the conversation when the banker is gone, dead, no longer a banker or past the leash. `CharacterEntity.OpenBankNpc` remembers who opened it, and the bank is open exactly while `CurrentDialogue` is still a conversation with that NPC, so every way a conversation ends closes it: talking to another NPC (`InteractHandler`), an instance transfer (`World.TransferPlayer`, which ends the conversation because the NPC stays behind), and despawn (`LeaveInstance` clears both). The first two send `SMSG_DIALOGUE_END`, the client's cue to hide the window. Opening sends every Bank slot in one `SInventoryUpdatePacket`, the only time the whole bank is sent.
- **Vendors (#432).** Stock is World DB data.
  - **Tables.** `VendorStocks` holds one row per line: creature template, `Sequence`, item, optional `MaxStock` + `RestockSeconds`, optional `PriceOverride`, and an optional quest requirement. `VendorStockCosts` holds the item costs per unit bought. Check constraints pair the optional columns both ways (both set or both null), and `(CreatureTemplateId, Sequence)` is unique.
  - **Catalog.** `VendorCatalog` (the Vendors reload area, `StaticData.Vendors`) validates every row. A bad row is refused with an error naming it, and the vendor still sells its other rows. Beyond the schema's pairings it refuses a missing item, a zero `MaxStock`, `RestockSeconds` or cost count, a cost on a missing item or one named twice, a `Sequence` the vendor already uses (the lower `Id` wins), and **a row whose effective price (`PriceOverride ?? BuyPrice`) is below the item's `SellPrice`**, because buying and selling it back would make gold. `VendorRules.UnitPrice` also floors the price at `SellPrice` at runtime, so the rule still holds after a `/reload items` changes a price.
  - **Live stock.** A `VendorStockState` per vendor creature holds the counts and restock timers, in a `VendorStocks` table on the town `MapInstance`. The instance reaches it through `IVendorHost` (not `IMapInstance`, the modding API). A state is created full the first time a shop opens there, and is reset only by a restart. `VendorStockState.Take` throws past the stock and on a limited row the state does not track, so a caller resolves its row from the state's own `Rows`.
    - The restock timer starts when a sale takes a full row below its maximum, and refills the row when it is due. Time is absolute (`TimeProvider`), so an instance that did not tick catches up. A reload clamps each count to the new `MaxStock`; a reload that raises `MaxStock` leaves the row owed a timer, which the next vendor pass starts, so the row refills without waiting for a sale.
    - `MapInstance.Update` runs the vendor pass right after the packet loop, on every tick while `Vendors.Count > 0`, whether or not a shop is open. It reconciles with the catalog, restocks, and sends each connection whose shop is open the one `SMSG_VENDOR_LIST` it is owed (a stock change, a restock, a reload, its own buyback, or, #738, a change to which quests it holds or has turned in since its last list: an accept, an abandon or a turn-in, `QuestLog.HeldVersion` against `CharacterEntity.VendorListQuestVersion`, so a turn-in that meets a gate shows the row at once). It then clears the change marks, and allocates nothing when nothing changed.
  - **Opening and closing.** The shop opens through the dialogue option action `OpenShop`, which sends the list, and it mirrors the bank exactly. `CharacterEntity.OpenShopNpc` records the NPC, `ShopAccess.IsOpen` means the conversation is still with it, and `ShopAccess.TryUse` re-checks the stock host, the NPC, alive, still a vendor, and the leash on every request, ending the conversation out loud when any fails. Every way a conversation ends closes it (`CloseNpcWindows`, which clears the bank and the shop together).
  - **Requests.** `CMSG_VENDOR_BUY` (`0x2090`), `CMSG_VENDOR_SELL` (`0x2091`) and `CMSG_VENDOR_BUYBACK` (`0x2092`), all accepted by `MapSessionFilter`, each get exactly one `SMSG_VENDOR_RESULT` (`0x30A1`) with a `VendorResult`. Gold and items leave in the tick's `SMSG_INVENTORY_UPDATE`.
    - **Buy** checks, in order: alive, open, row and quest gate, count (at most `MaxStackSize`), stock, gold, Bag-only cost items, room once the costs are out, unique.
    - **Sell** takes a Bag slot only, and refuses `NoSell`, a `SellPrice` of 0, a gone template, a damaged item (`Durability < ItemInstanceDefaults.FullDurability`), a bad count, and the money cap.
    - **Buyback** re-adds the exact instance under its own id (`IInventoryService.TryAddInstance`, so the save upserts it). It refuses a unique item already owned again, and answers `NotFound` for an item a `/reload items` has flagged `QuestItem` since it was sold, which the list leaves out too, the other sales keeping their index (#738).
    - A handler exception is logged at Error and answered `NotFound`. A dead character gets `Dead`, and its conversation is left alone. A connection with no character gets no reply at all.
    - **`VendorTrade` is not rolled back.** `VendorRules` checks every step first, and the apply order takes the player's costs, gold or item before anything is given, so a programmer bug can only lose one trade's value, never duplicate it; the handler logs it at Error.
  - **Buyback list.** `CharacterEntity.Buyback` holds the last 10 sales, newest first. It is cleared on despawn (`World.LeaveInstance`) and kept across an instance transfer, because the session goes on. A partial sale keeps a copy with a new id from `IItemIdAllocator` (`IInventoryService.TakeOut`).
  - **Quest gates.** They ask `IQuestProgress`; production's `QuestProgress` answers from the character's quest log (Active = held, Completed = turned in, #433); `NoQuestProgress` is only a handler's fallback when built without the container. No seeded row is gated. A gated row whose requirement is not met is hidden and cannot be bought, and no row may sell a `QuestItem` (a row whose item a `/reload items` made one is hidden and refused `NotFound` until `/reload vendors` drops it).
  - **Optional parameters.** `StaticData` and `World` take `IVendorStockRepository` as an optional last constructor parameter (an empty catalog without it), and `DialogueChooseHandler` takes `IQuestProgress` the same way. `WorldHostGraphShould` pins that production registers both, so a missing registration cannot silently leave every vendor empty.
  - **Seeds.** Garrick (12) sells the four Common starter weapons (items 32-35). Hilde (13) sells the four starter armour sets (36-55); each chest is limited to 2, restocking every 30 minutes. Tobin (14) sells items 1-3, the forest scrolls 9-11, and the Greater Health Potion (56: 25 gold plus 2 Health Potions, limited to 5, restocking every 10 minutes). Forest gear stays drop-only.
- **Character stats (#463, #434).** `CharacterStatsCalculator` (`Avalon.Combat`) derives `DerivedCharacterStats` from the seeded `ClassLevelStat` row (the only base-stat source; the old `CharacterStats.GetBase*` helpers are gone) and the stat pairs of the items worn in a slot that fits them. `CharacterStatsRefresh` runs it at create (level 1, nothing worn), at select (`EnterWorld`: nothing stores current health or power, so a character enters full, except that a Fury pool enters empty, #526), after every accepted request that changed Equipment (`KeepShare`: each pool keeps its share, never killing or reviving), and on level-up in `MapInstance.CreatureKilled` (`Refill`, or `KeepShare` when the member levelling is dead, so a level-up never refills a corpse; each eligible member of a party kill levels through this path on its own share). The highest level with a `CharacterLevelExperiences` row (15 today) is the cap, and a level before a gap in the rows stops a character the same way (`ExperienceAward.CanGainExperience`, #735): a character there gains no experience, while kills and quest turn-ins still pay copper and items. Select-time recalculation is also what corrects `CharacterStats` rows written before #463; there is no data migration, so a character that never logs in again keeps its old stored values. `CharacterEntity.ApplyStats` writes `Health`/`Power` (the stored and replicated maximums), the current pools, `Stamina`/`RegenStat`, and a stats mark in `SaveState` that makes the next save upsert the `CharacterStats` row. A class and level with no row keeps the stored maximums and logs a warning. The per-class factors come from `ClassStatFactors` (#506, the combat reload area), and the `Health`/`Power` setters clamp a total past `int.MaxValue`, the row's type, rather than wrapping it negative. Combat reads the damage stats, armour, block, dodge and crit (see the combat-formula bullet).
- **The character sheet (#506 slice C).** `SMSG_CHARACTER_STATS` (`SCharacterStatsPacket`, `0x302A`) carries Stamina, Strength, Agility, Intellect, Armor, AttackDamage, AbilityDamage, CritPct, DodgePct, BlockPct, WeaponMin, WeaponMax, HastePct (field 13, the effective haste) and MovementSpeed (field 14, m/s, the speed the server steps at) (#627), to the character's own connection only. The chances are effective: clamped to the current `CombatFormula`'s `CritCap`/`DodgeCap`/`BlockCap` by `HitResolver.EffectivePct`, the clamp every roll uses (`CharacterSheet.From`). `CharacterSheetFlusher` sends it from `WorldServer.Update`, right after `InventoryUpdateFlusher`, at most once per connection per tick, whenever the sheet differs from `CharacterEntity.SheetSent` (World-side, never saved): so on the tick the selected character enters the world (the readiness barrier puts it on the connection), after a stats refresh that changed a value it shows (a gear change, a level-up; an equip that changes nothing sends none), and after a `/reload combat` whose caps move a character's effective chance. New class factors reach it only at that character's next refresh, since a reload is forward-only. A character with no stats is sent none; a new session starts with no sheet sent, so it gets the whole sheet again.
- **Ability amounts (#669).** Each learned ability's per-hit amount, for client tooltips. `AbilityAmounts.For(caster.Combat, metadata)` (`Avalon.Combat`) runs, through `AbilityAmountMath` (`Avalon.Combat`) (the arithmetic, shared by world combat and the API: the character ability `amount` and the public ability tooltips, with a parity test), `HitResolver.AbilityBaseRange` (the ability's base, `EffectValue + ScalingCoefficient × stat + BaseDamageCoefficient × weapon roll`, through `AbilityBase` itself at the low and the high end of the inclusive main-hand roll) and floors each end as a normal hit does, before crit, dodge, block and armour: `HitResolver.NormalDamage` (minimum 1) for a Hostile ability, `NormalHeal` (no minimum) for an Ally one. Only the three shape scripts apply an amount directly, so any other `ScriptName` is `AbilityAmountKind.None` ("nothing to state", not 0); the ability catalog only accepts shape scripts today, so `None` is a safeguard. At select, `AbilityInfo` fields 18-20 (`AmountKind`, `AmountMin`, `AmountMax`) carry them, and `CharacterSelectHandler` records them (`CharacterEntity.AbilityAmountsSent`/`AbilityAmountsSentFor`, World-side, never saved). `AbilityAmountsFlusher`, called from `WorldServer.Update` right after `CharacterSheetFlusher`, works them out again only when `CharacterEntity.Combat` differs from the one last used, and sends `SMSG_CHARACTER_ABILITY_AMOUNTS` (`SCharacterAbilityAmountsPacket`, `0x302C`, every learned ability, whole) to the character's own connection only when an amount changed. `docs/client-combat-protocol-migration.md` has the contract.
- **Heal events (#506 slice C).** `SMSG_UNIT_HEALED` (`SUnitHealedPacket`, `0x310C`: Healer, Target, Amount, CurrentHealth, optional AbilityId, `HitResult` Result) is sent for every heal that restored more than 0 health: `CombatService.ApplyHeal` reports it through its instance (`ICombatOutcomes.UnitHealed`, #546), and `MapInstance` sends it to the healer, the target and every connection within `Game:InterestRadius` of the target (`EffectAudience`, #532), for a target in that instance only. `Amount` is the health restored, overheal left out; `Result` is `Crit` for a critical heal and otherwise None. A heal on a target at full health sends nothing.

## Item use

Right-clicking a Bag item uses it: gear is equipped into the slot it is worn in, any other item runs its item script. `docs/item-use-protocol.md` is the client contract.

- **Request and answer.** `CMSG_ITEM_USE` (`0x2082`, `CItemUsePacket`: `RequestId` 1, `Container` 2, `Slot` 3), accepted by `MapSessionFilter`, reaches `ItemUseHandler`, which hands it to `ItemUseService` (`Avalon.World/Items`, a DI singleton, tick thread only, no awaits). Each request gets **exactly one** `SMSG_ITEM_USE_RESULT` (`0x3091`, `SItemUseResultPacket`: `RequestId` echoed 1, `Result` 2, `CooldownMs` 3 only on `OnCooldown`, rounded up and at least 1, `Message` 4 only on `Refused`), to the requester only: at once for an equip or an instant use, when the cast ends for a cast-time use (its `SMSG_UNIT_START_CAST` is the acknowledgement meanwhile). A connection with no character gets nothing; an exception escaping the service is logged and answered `InternalError`. `ItemUseResult` is append-only from `Unknown = 0` (never sent): `Ok` 1, `NotFound` 2, `NotUsable` 3, `Dead` 4, `OnCooldown` 5, `AlreadyCasting` 6, `InCombat` 7 and `NotInCombat` 8 (reserved, nothing sends them), `WrongEquipSlot` 9, `LevelTooLow` 10, `WrongClass` 11, `TargetFull` 12, `Blocked` 13, `Interrupted` 14, `Refused` 15, `InternalError` 16.
- **Check order** (`ItemUseService.Begin`): dead (`Dead`, before anything else, so no hook, teleport or quest start runs for a dead user); the slot (a Bag slot in range holding an item, else `NotFound`); the template (gone: `NotUsable`); gear is equipped and nothing else is asked; otherwise a `UseScript` (none: `NotUsable`), an ability cast in progress (`Spells.IsCasting`: `AlreadyCasting`), the item's and its group's cooldown (`OnCooldown`), the script resolved and built (missing or unbuildable: `InternalError`), the user's instance (`IItemUseHost`, else `InternalError`), then the script's `CanUse` (a line: `Refused` with it). A use that passed every check ends the item cast running (answered `Interrupted`), then runs `OnUse` at once or starts its cast bar. Using another item, gear included, interrupts a running item cast, but only once that use has passed its checks (owner decision): an equip interrupts just before it moves anything, so the old use is answered `Interrupted` and the equip `Ok`, while a refused equip (`LevelTooLow`, `WrongClass`, ...) or a refused script use leaves the cast running. The per-request Error logs (a missing or unbuildable script type, a hook that throws, a completion that throws) are written at most once per script and step per `ThrottledErrorLog.Interval` (10 s), counting the ones left out.
- **Equipping** (`ItemEquip`): an item whose template `Slot` maps to an equipment slot (`EquipmentSlots.SlotsFor`: both fingers for a ring, none for a gem or no slot) goes through `IInventoryService.TryMove` from its Bag slot, the drag's `InventoryMove` rules and marks, then `CharacterStatsRefresh.AfterGearChange`. An occupied slot swaps its item into the clicked Bag slot; a ring takes the first empty finger, else finger 1 (slot 7); a two-hander with an off-hand item worn is first checked for wearing (`InventoryMove.CanWear`, so a refusal moves nothing), then the off-hand item goes to the lowest free Bag slot (none: `TargetFull`; the clicked slot is not free), then the weapon (a failure after the off-hand moved is logged and not rolled back). Every check runs before anything moves (`InventoryMove.Decide` for a plain equip), and the running item cast is interrupted only then. Move answers map to use answers (`ItemEquip.Map`): `NotFound`/`InvalidSlot` to `NotFound`, `NotStackable` (a stack of gear) to `NotUsable`, `BankClosed`, `CannotDestroy` and `InvalidCount` to `InternalError`, the rest by name.
- **Scripts.** `ItemScript` (`Avalon.World/Items`, World-side, never on `Avalon.World.Public`): `CanUse(ctx)` (null allows, a string refuses with that line; asked again when a cast completes), `OnUse(ctx)`, `OnCastStart(ctx)`, `OnInterrupted(ctx)`. `CanUse` is read only: effects belong in `OnUse`, a `Consume` made in `CanUse` is ignored, and every refusal belongs there, since an `OnUse` that returns without any effect still starts the cooldown. One instance per type, built through `QuestScriptServices` (loggers and `TimeProvider` only) and shared by every use, so it keeps no per-use state. Every hook is contained: a throw is logged at Error and answered `InternalError`, with nothing consumed and no cooldown; a throwing `OnCastStart` also ends the bar out loud (and is answered once: only when its own cancel ended the bar, not when the hook had already ended it), and a throwing `OnInterrupted` answers `InternalError` instead of `Interrupted`. Effects a hook applied before it threw stay applied. Scripts reach the world only through `IItemUseContext`.
- **The toolbox** (`IItemUseContext`, World-side, `ItemUseContext` built per hook call over the `ItemUseTools` singleton). Everything acts on the user, on units of the user's own instance, or on its party members in that instance, each change through the service that owns it, on the tick:
  - reads: name, level, class, health and power with their maximums, power type, position, map, `InTown`, `InCombat`, `InParty`, `ReturningToTown` (`RespawnInFlight`: a respawn, a party return, a scroll or a teleport under way), and the item's id, name, `UseValue`, stack count and configured cooldown.
  - `Consume(count)` marks part of the used stack spent (throws for 0 or past the stack); taken after `OnUse` returns. `HasBagRoom`/`GiveItem`/`TakeItem` go through `IInventoryService` (by template); `Money`, `GiveMoney` (false past `Game:MaxMoney`) and `TakeMoney` through `IWallet`.
  - `RestoreHealth` through `CombatService.RestoreHealth` (below); `RestorePower` through `CharacterEntity.GainPower` (capped, nothing for the dead or for a pool no cast spends).
  - `HostilesAround(radius)` lists living units of the instance hostile to the user (`Hostility.IsHostile`, so never the user, a party member or an unflagged player), nearest first; `Damage(target, amount)` is a raw hit on one of them through `CombatService.ApplyDamage(user, target, amount)`: dodge, crit, block and armour roll, the encounter forms, the creature gains threat, the user gets the kill's credit and loot. It answers true when the combat service took the hit (a dodge included); no self-damage, and a target the combat service ignores (an invulnerable creature, a corpse, a creature walking home, `CombatService.IgnoresHits`) or anything else answers false and does nothing.
  - `ReturnToTown()` starts `TownReturn` (`revive: false`, `dropEncounter: true`) to the town the current map's respawn resolves to; false in a town or while a move is under way. A reader who dies before arriving arrives in town revived, as a respawn would (owner decision). `Teleport(map, position?)` goes through `MapTeleport` and `World.TransferPlayer`: refused (false) for an unknown map, a level outside the map's band or a move under way; the instance is resolved as a portal resolves it (a town's shared one; in a party, the party's instance of a Normal map, re-checked on arrival as `EnterMapHandler` checks it: no longer in that party `MapNotFound`, full `InstanceFull`; otherwise the character's own); a given position is snapped to walkable ground with `IGroundNavigator.FindGround` inside the navigator's ground box (half-extents 2 m on X/Z and 4 m on Y, a 4 x 8 x 4 m box): X/Z kept with the mesh under it, the mesh's nearest point just beside it, kept as given on a map with no navmesh; no mesh in the box refuses the arrival with `MapTransitionResult.NoWalkableGround` (7), logged at Warning, nothing moved or saved; a destination instance whose build fails sends no `SMSG_MAP_TRANSITION` at all, as a portal entry or a respawn whose build fails does, and the item stays spent; with no position, the instance's entry spawn. A character that died while the instance built is not moved. The arrival drops the character from its encounter, sends the transition and the chunk layout (`MapArrival`), and saves the row's map, instance and position as a portal entry does (`ICharacterSaver.Save`). The item that started a move stays consumed whatever the arrival does (owner decision). While any move is under way (`RespawnInFlight`: a scroll return, an item teleport, a respawn or a party countdown return), `EnterMapHandler` refuses a portal entry with `MapTransitionResult.MoveInProgress` (8, owner decision), checked after the character and alive checks and before any lookup or build.
  - `CastAbility(id, free, point?)` through the cast system (`IItemUseHost.CastForItem`: `QueueAbility` for a cast time, `RunInstant` otherwise): an ability the user holds is cast as itself (its running cooldown refuses it, firing sets it); one it does not hold only from the catalog and only when instant; `free` skips the cost only; the global cooldown is neither checked nor started; refused while dead or while an ability is casting; a Cursor ability needs a finite `point`, toward which a Movement ability aims when given; an accepted cast marks the user in combat.
  - `GrantExperience` through `ExperienceAward.Grant` (the level cap applies). `StartQuest` through `QuestService.StartFromItem` (the accept's `QuestAvailability` rules, no giver, no conversation; `NotAvailable` for an unknown quest). `AdvanceQuest` through `QuestService.AdvanceFromItem`, for **Kill and Talk objectives only** of an Active quest's current stage, capped (`AddProgress`'s rules); Scripted objectives stay moved by the quest's own script, Collect by the Bag.
  - `SpawnCreature(template, distance, lifetime?)` through `ICreaturePlacementService.SpawnAt` (snapped to the ground as a procedural spawn is, #720, its AI script attached), 0 to 10 m in front of the user, never in a town, refused for a lifetime of 0 or less. `MapInstance` keeps each summon with the time it leaves (`IItemUseHost.DespawnAfter`, default 5 minutes, `ItemUseContext.DefaultSummonLifetime`, on the instance's `TimeProvider`) and on its tick drops a living summon whose time has come from its encounter and removes it (`RemoveCreature`), each summon contained on its own (a throw is logged at Error with the creature, and neither the tick nor the other summons pay for it); one killed first is the corpse removal's. An instance nobody is in does not tick, so its summons leave on its next occupied tick (owner decision). Loot, experience and quest credit are an ordinary creature's.
  - `PartyMembersHere()` lists the user's party members in the same instance by guid, the user excluded, alive or dead, at any distance; `RestoreHealthOf`/`RestorePowerOf` act only on a guid from that list (0 for anyone else), through `CombatService.RestoreHealth` (never the dead) and `GainPower`.
  - `Tell(line)` sends the user a system line; `Whisper(from, text)` a line on `ChatChannel.Whisper` with that sender name, to the user only; `from` is not checked against any character.
- **Cooldowns.** `CharacterEntity.ItemCooldowns` (`ItemCooldowns`, World-side, never saved, so a logout resets them): per item template and per `UseCooldownGroup` (ordinal; blank is none), absolute times on the container's `TimeProvider`, nothing ticks them; the time left is the longer of the two. Started for `UseCooldownMs` once `OnUse` returns, whatever it consumed; a refusal, an interrupt or a throw starts none. Independent of the ability global cooldown.
- **The cast bar.** `ItemUseCasts` (one per `MapInstance`, reached as `IItemUseHost.ItemUses`, at most one cast per character), ticked by `MapInstance.Update` right after the ability cast system. Its cast ids come from the instance's ability cast ids (`IAbilityCastSystem.TakeCastId`), so an item's cast and an ability's never share one. `SMSG_UNIT_START_CAST` with `AbilityId` 0, `ItemTemplateId` (field 6), the cast id and the cast time in seconds, then `SMSG_UNIT_FINISH_CAST` or `SMSG_INTERRUPTED_CAST` with the same cast id and `ItemTemplateId` (field 4), to every connection within `Game:InterestRadius` of the caster (`EffectAudience`). It ends early, out loud, when the character moves (any change of position from where it began) or dies (checked each tick; damage alone never ends it), leaves the instance (`MapInstance.RemoveCharacter` interrupts it, contained), uses another item (gear included) that passed its checks, or casts an ability `CastAbilityHandler` accepts (it interrupts after the cast system took the cast). At completion the same item instance must still be in the same Bag slot and the user alive (else `Interrupted`), and `CanUse` is asked again (a line: `Refused`). An interrupted use spends nothing and starts no cooldown. Every broadcast and callback is contained.
- **Consumption.** What `OnUse` marked with `Consume` is taken by instance id through `IInventoryService.TryRemove` after the hook returns, so it is saved and sent like any change (a removal that fails is logged at Error). A Town Portal Scroll is consumed once its return has started, though the move finishes later (owner decision).
- **Item heals.** `CombatService.RestoreHealth(healer, target, amount)` (World-side, not on `ICombatService`): a fixed amount, no stat scaling, no crit, never past the maximum and never lowering health above it (`HealRules.After`), never the dead; no heal threat and no encounter change; a heal that restored more than 0 is reported through `ICombatOutcomes.UnitHealed` and sent as `SMSG_UNIT_HEALED` with no ability id and `Result` None.
- **Data and the seeded items.** Nullable `ItemTemplate` columns `UseScript`, `UseCastTimeMs`, `UseCooldownMs`, `UseCooldownGroup`, `UseValue` (a whole percentage; `ItemUsePercent.Of` is `floor(maximum × UseValue / 100)`), migration `AddItemUse`, in the item schema and catalog (`useScript`, `useCastTimeMs`, `useCooldownMs`, `useCooldownGroup`, `useValue`) and editable through `PUT /world/{worldId}/item-template/{id}`, where a changed `useScript` must be a name in the world's published script catalog (`item`; an unchanged one, or a world that publishes no item list, is not checked), and a blank `useScript` or `useCooldownGroup` is stored as null (`TemplateFields`). `RestoreHealth` and `RestorePower` need `UseValue` set (the seed sets it): without it a potion restores nothing and is still spent. Seeded: Health Potion (1, `RestoreHealth`, 30) and Greater Health Potion (56, `RestoreHealth`, 60), refused at full health ("You are already at full health."); Mana Potion (2, `RestorePower`, 30, of Mana or Energy), refused for Fury and for no pool ("You cannot drink this.") and at full ("Your mana is already full." / "Your energy is already full."); the three share the `potion` group, 30 s. Town Portal Scroll (3, `TownPortalScroll`): a 3 s cast, then `ReturnToTown`, 30 s cooldown of its own, refused in a town ("You are already in town.") and while a move is under way ("You are already on your way to town."), usable in combat. Forest scrolls 9-11 have no script and answer `NotUsable`. `SeedIntegrityShould` pins them.

## Chat Commands

Commands live in `Avalon.World/Chat/` (the party commands in `Avalon.World/Parties/PartyCommands.cs`, the ignore commands in `Avalon.World/Social`). To add a new command:
1. Implement `ICommand`: `Name`, `Aliases[]`, optionally `RequiredAccess`, and `void Execute(CommandContext ctx, string[] args)`.
2. Register as `services.AddSingleton<ICommand, YourCommand>()` in `ServiceExtensions.AddWorldServices`.
3. `CommandDispatcher` resolves all `ICommand` registrations from DI automatically (name and aliases, case-insensitive).

**A command runs on the tick, to completion, and never awaits.** `ChatMessageHandler` calls `ICommandDispatcher.Dispatch(connection, packet)` synchronously on the tick for every `/`-prefixed message, with no continuation around it; `Dispatch` returns false for an unknown command or one the caller may not run, and the handler then answers "Unknown command.". `Execute` returns `void`, so `await` does not compile in it. `ctx.Reply(text)` sends the caller a system line. Work that cannot finish on the tick goes through `ctx.Then(task, callback)` (and `Then(Task, Action)`): the task is handed, settled so it never faults, to `IWorldConnection.EnqueueContinuation`, and the callback runs on a later tick, only once the task has succeeded. `/reload` and `/ignore` (for an offline name, #723) use it; `/godmode`, `/pvp`, `/w`, `/unignore`, `/ignorelist` and the party commands are plain synchronous. `CommandsNeverBlockTheTickShould` scans every `ICommand` in `Avalon.World` by reflection, nested types included (so lambdas and closures), and fails one with an async method or a call to `Task.Result`, `Task.Wait` or `GetAwaiter().GetResult()` (`TickBlockingScan`); it does not follow calls into other types or look for other blocking calls such as `Thread.Sleep`, so those stay the author's to avoid.

`ICommand.RequiredAccess` defaults to `AccessLevels.Player`, so a command that declares nothing stays runnable by any logged-in player — `Tournament` and `PTR` included: they are players with exactly the Player permission set, differing only in which worlds they may enter, and the API's Player policy lists them too; `ReloadCommand` is the one exception so far, declaring `AccessLevels.GameMaster`. `CommandDispatcher` checks `RequiredAccess.Allows(connection.AccessLevel)` — a mask test, not an ordinal one, because `AccountAccessLevel` is `[Flags]` and `Tournament`/`PTR` are not above `Admin`, so a `>=` comparison would let either through a `GameMaster` gate. A caller without access gets exactly "Unknown command.", the same as a caller who typed a command that doesn't exist — the dispatcher never reveals which commands are staff-only. `IWorldConnection.AccessLevel` has no setter: `Avalon.World.Public` is the future modding API, and a settable access level there would let a mod promote any player to GM. The server assigns it once, at character-select, through `IAccessLevelAssignable` in `Avalon.World`.

**Every failure is reported one way, synchronous or not.** A command that throws, a task handed to `ctx.Then` that faults or is cancelled, and a `Then` callback that throws all reach `CommandDispatcher.ReportFailure`: logged at Error with the command and account, and told only to a caller holding the `GameMaster` or `Admin` flag, as `Command /<name> failed: <ExceptionType>.` (the type name only, the message and stack stay in the log; a cancelled task reports `TaskCanceledException`, a task with several exceptions `AggregateException`). Everyone else, `Console` included, gets silence, because an error line would reveal that the command exists and what broke inside it. A command that throws still counts as dispatched, so nobody gets "Unknown command." for it.

**Chat channels.** `SChatMessagePacket.Channel` (field 6, `ChatChannel`: `Say` 0, `Party` 1, `System` 2, `Whisper` 3). A message without a `/` is said: `ChatMessageHandler` sends it on `Say` to every connection in the sender's `MapInstance`, the sender included (only to the sender when its instance cannot be found). There is no world-wide chat. `/p` goes to the sender's party on `Party` (see Parties). **Whispers (#717):** `/w <player> <message>` (`/whisper`, `WhisperCommand` in `Avalon.World/Chat`, Player access, synchronous) sends the text as typed after the name (trimmed at the ends; the command word and name found as `/p` finds its text, `CommandText`) to one online character, wherever it is on this world server, on `Whisper` with the sender's name; the sender gets an echo on `Whisper` with `SChatMessagePacket.TargetName` (field 7, set only on that echo) naming the recipient as it is spelled. Refusals are system lines to the sender only, nothing sent to anyone else, in this order: no name or no message, "Usage: /w <player> <message>"; the sender's own name (ignoring case), "You can't whisper yourself."; no online character with that name, offline and unknown alike, "No player named <name> is online." (the name as typed). Names are looked up in `OnlineCharacters` (`Avalon.World/Characters`, a World-side singleton, tick thread only): online characters by id and by name in any case, ignoring surrounding spaces (keyed by `CharacterName.LookupKey`, #757), fed from the world's online and offline hooks through `PartyService.CharacterOnline`/`CharacterOffline` (a stale connection's offline changes nothing) and read by the party invite and the whisper alike; `PartyService` takes it as an optional constructor parameter, and `WorldHostGraphShould` pins that production hands both the same instance. **Chat rate limit (#722):** `ChatRateLimiter` (`Avalon.World/Chat`, a DI singleton) gives each sending character one sliding 60 s budget of `Game:ChatMessagesPerMinute` messages (default 10 in `appsettings.json`, not in C#; 0 or below turns it off), shared by plain chat (`ChatMessageHandler`), `/p` (`PartyChatCommand`), `/w` (`WhisperCommand`) and `/ignore` (`IgnoreCommand`, #723, owner decision); no other command counts. Callers ask `Check(characterId, out retryAfter)` first, before any recipient or party lookup (so an over-limit sender learns nothing about who is online), and `Record(characterId)` only once the message is delivered, so a refusal (usage, self-whisper, no such player, not in a party) uses no budget. Over the limit the message is not delivered and the sender gets a system line, "You're sending messages too fast. Try again in {n}s." (n = seconds until the oldest counted message leaves the window, rounded up, at least 1). Timestamps come from the injected `TimeProvider` (a queue per sender, pruned on each call, no timers). Chat runs on the tick, so the service needs no concurrency, but every method takes one short lock because the shutdown despawn can reach `Forget` from another thread. `World.LeaveWorldAsync` calls `Forget(characterId)` (logout, leave to character selection, disconnect), so nothing is held for a character that left. **Ignore list (#723, owner design).** A character ignores other characters of its world by id, online or offline: `CharacterEntity.Ignores`, an `IgnoreList` (`Avalon.World/Social`, World-side, never on `ICharacter`, tick thread only; entries are id, name and when added, oldest first). Memory is authoritative and every check is `Ignoring.Hides(listener, senderId)`, with no database query per message: a whisper to a character ignoring the sender is not sent while the sender still gets its echo and the message counts against the rate limit as delivered; `ChatMessageHandler` and `/p` leave the line out for each listener or member that ignores the sender (the sender's own line always goes out); a party invite from an ignored character is answered `Ok` after every usual refusal, never sent, not answerable (`Respond` finds no invite) and kept by `PartyService` per (inviter, target) until it expires, when the inviter alone gets `InviteExpired` (and `InvitePending` meanwhile for a second invite to that target), or until the target goes offline (the inviter told `InviteExpired`) or the inviter does (ended silently). System lines are never filtered, and whispering a character you ignore is allowed. Commands (`IgnoreCommand`, `UnignoreCommand`, `IgnoreListCommand` in `Avalon.World/Social`, Player access, synchronous): `/ignore <name>` refuses, in order, without exactly one name ("Usage: /ignore <name>"), the caller's own name ("You can't ignore yourself."), a name already on the list ("X is already on your ignore list."), a full list (`Game:MaxIgnoredCharacters`, default 50, range 1-500, "Your ignore list is full (50/50)."), and over the chat rate limit (the limiter's own line; an `/ignore` past the four refusals before it spends one message of the budget whatever the lookup finds, while those four, `/unignore` and `/ignorelist` spend nothing), then finds the character in `OnlineCharacters` or, offline, through `ctx.Then(ICharacterIgnoreRepository.FindCharacterByNameAsync(...))` (by `NameKey`, so in any case; names are unique by key, so at most one character matches, #757), whose callback does nothing if the connection no longer holds that character and otherwise re-checks: no such character ("No character named X exists."), itself by id, already listed by id, full; an accepted one is "You are now ignoring X.", and an invite from that character the caller still holds then ends silently (`PartyService.HideInviteFrom`, owner decision: it becomes a dropped invite, so the caller can no longer accept it and the inviter is told nothing new and sees the usual expiry). `/unignore <name>` (by the name the list shows: "You are no longer ignoring X." or "X is not on your ignore list.") and `/ignorelist` ("Ignoring 2/50: A, B." or "You are not ignoring anyone.") never touch the database. `SMSG_IGNORE_LIST` (`SIgnoreListPacket`, 0x30D0: `Characters`, repeated `IgnoredCharacterDto` `CharacterId`, `Name`) is the whole list: sent by `CharacterSelectHandler` once the list is loaded (one more `Step` after the quest rows, before the pending spawn, empty too), after every change, and by `CharacterDeleteHandler` to each connection holding a loaded list that had the deleted one on it, in the world or selected and waiting to spawn (`IWorldServer.Connections`, `Character` or `PendingSpawn`; taken off in memory there; the rows cascade); a select whose rows were read before the delete committed but applied after keeps the entry until its next select, harmlessly. **Storage:** `CharacterIgnores` (Character DB, migration `AddCharacterIgnores`): `CharacterId`, `IgnoredCharacterId`, `CreatedAt`, key the pair, both foreign keys to `Characters` cascading, an index on `IgnoredCharacterId`. Every change marks `SaveStateTracker.IgnoreChanged(id)`, and the next save carries a `CharacterIgnoreWrite` (built in `CharacterSaveSnapshot`): each marked pair deleted, then inserted again while still on the list, one `INSERT ... SELECT` per entry from the ignored character's row, so a character deleted since it was ignored, or by a delete running alongside the save, skips its row and never fails the save (on Postgres the read takes `FOR KEY SHARE`: a delete committed first is seen, one still running waits for the save and then cascades the row; verified on Postgres 17). Select loads the names the rows hold now (`GetByCharacterIdAsync` joins `Characters`); a rename while the owner is online shows at its next select. `CharacterSelectHandler` takes the repository and `CharacterDeleteHandler` the `IWorldServer` optionally; `WorldHostGraphShould` pins that production hands them over. Command answers, "Unknown command." and every line the server speaks (party joins, leaves, leader and mode changes, leave countdowns, health scaling, quest milestones) are `SChatMessagePacket.System`: channel `System`, sender name "System", account and character 0.

## Live template editing

Admins edit item, ability and creature templates on a running world, and the world applies them without a restart.

- **Endpoints** (`[Authorize(Policy = AvalonRoles.Admin)]`, `[WorldScoped]`): `PUT /world/{worldId}/item-template/{id}`, `/ability-template/{id}` and `/creature-template/{id}`. The body is the read DTO minus `Id`, `Version` and `Editable`. The reads carry `version` (a lowercase hex SHA-256 of the row's stored values) and `editable`, and set `ETag: "<version>"`.
- **Editability is configuration, never code.** A world is editable only if its id is in `Application:Templates:EditableWorlds` (default empty; Helm `templates.editableWorlds`; the AppHost lists the local Development world). Anything else answers 403 `This world is not editable`, checked before the body is read. Production worlds stay out of the list. `Application:Templates:ReloadTimeout` (default `00:00:10`) bounds the wait for the world's answer.
- **If-Match and 409.** A `PUT` needs `If-Match: "<version>"`: missing gives 428, a stale one 409 `Changed since you opened it`. Other answers: 404 for an unknown id, 400 ValidationProblem keyed by camelCase field name. A `200` carries `{ template, reload: { status: "applied"|"failed"|"pending", summary } }`. The write is committed before the reload is requested, so `failed` and `pending` leave the saved row in place.
- **Reload over Redis.** After the commit the API publishes `{ requestId, areas }` on `world:{id}:reload` (`CacheKeys.WorldReloadChannel`); the world re-reads the areas (`Items`, `Abilities`, `Creatures`) through `IReferenceDataReloader`, the one `/reload` uses, and answers on `world:{id}:reload:result` (`CacheKeys.WorldReloadResultChannel`), matched by `requestId`. No answer within `ReloadTimeout` (world down, not yet subscribed: pub/sub is not queued) reports `pending`.
- **What players see.** A reload is forward-only, like `/reload`: new creature spawns use the edited template (live ones keep theirs), abilities are read at character select (a held ability keeps its old metadata until the next select), and items are read from the templates afterwards.
- **Caveat: a release that changes a template in code overwrites the live edit.** The templates are seeded from `WorldDbContext`, so a migration that changes that seed rewrites the row, edit included. Re-apply the edit after such a release.

## Balance Simulator

The simulator is a library with a thin tool on top. `Avalon.Balance.Core` (`src/Server/`) is the simulator, grader and
run contract; it references `Avalon.Combat` and `Avalon.Domain` only, no `Avalon.World`, no `Avalon.Database*`, no EF,
pinned by `BalanceCoreAssemblyShould`. `Avalon.Balance.Data` reads the seed and the files (`SeedSource`, `OverrideFiles`,
`ConfigFileStore`) and references Core and `Avalon.Database.World`. `tools/Avalon.Balance` references Core and Data
only: it parses options, loads, calls `Simulation.Run` and writes `balance/out/report.html` and `results.csv`
(gitignored). It simulates one player against packs of forest creatures and grades win rate, fight length, health left,
class parity, level curve, resource flow and levelling pace against `balance/targets.json`. Run
`dotnet run -c Release --project tools/Avalon.Balance` (`--class`, `--scenario`, `--runs`, `--seed`, `--overrides`,
`--out`); exit 0 no red, 1 red, 2 refused input.
`SeedSource.Load` reads the seed from `WorldDbContext`'s design-time model (`IDesignTimeModel`, `GetSeedData()`, Npgsql
with a placeholder string, never connected) into `SeedTables`; `balance/overrides.json` (`"Table.key.Column": value`)
is applied to a copy of it. It never copies a balance formula: stats, hits, Fury, haste, costs, power regen, power
gains and heal caps (`PowerRegen`, `PowerPool`, `HealRules`, see World Simulation) are `Avalon.Combat`, the code the
world server runs, and so are the checks that validate the data: `AbilityRules`, `CombatDataRules` and
`CreatureTemplateRules` (and `ClassPowerType`, `Fury.DefaultFromDamageTaken`) in `Avalon.Combat`, which the world's
`AbilityCatalog`, `CombatPatch.Build` and `CreaturesPatch.Validate` delegate to with their exact checks and messages.

The run contract: `Simulation.Run(seed, defaults, request, progress, ct)` returns a `RunResult` (`Status` Done,
Invalid or Cancelled; rows, grades, `CheckedRows`, summary, applied overrides, `Seed`, `RunsPerRow`). A `RunRequest`
carries optional overrides (a `JsonElement`), config, a `RunFilter` (classes, levels, gear, scenarios), runs per row
and seed. A refusal is data, never an exception: `Issue(Path, Message)`, the path naming where (`overrides.<Key>`,
`seed`, `scenarios`, `targets`, `rotations.<Class>`, `filter.levels`). The seed is never changed, so one loaded
`SeedTables` serves many runs. `IProgress<RunProgress>` reports one row at a time from worker threads, best-effort; a
cancelled token returns Cancelled with no rows. A filter only drops rows and never changes the seed of the rest, so the
same data, config and request always give the same rows. `Catalog.Describe(seed)` lists every tunable
(key, table, column, type, seed value) for an editor, from the same table map the overrides use.

Creature kits (basic, specials in rotation order, ranged-only specials) are a static table, `CreatureKits.ByScript`,
keyed by script type name; the world test `CreatureKitParityShould` keeps it equal to the scripts in `Avalon.World`.
The small cast-system bookkeeping the simulator mirrors (the cooldown set when a cast fires, a creature's swing
interval, a creature's level range) and the fight's event order are pinned by `SimulatorParityShould` against
`CombatService`, the cast system and `CharacterEntity.Update`. It steps at the server's tick (1/60 s) so cooldowns,
casts and the event order count as the server's do. Mana and Energy regenerate `stat x coefficient x dt` a tick with
the fraction of a point carried between ticks (`PowerRegen.Amount`, the caller owning the carry), dropped while a cast
suppresses regen or the pool cannot regenerate (full included).
`ConfigFiles.Save` writes `scenarios.json`, `targets.json` and `rotations.json` in one canonical JSON form
(`ConfigFileStore.Write`), and the checked-in files are in that form, so a parse and save round-trips byte for byte.
Balance tables change only through `HasData` plus a migration (see Commands); `ModelDriftShould` fails when `HasData`
changed without one. `balance/README.md` has the file formats and what is not modelled (everyone in melee, no
projectile travel time, continuous combat, wind-ups always land).

## Balance Service

`Avalon.Balance.Service` (`src/Server/`) is an in-cluster ASP.NET service that runs the simulator for the workbench.
It is never exposed outside the cluster: a ClusterIP Service, no ingress. `Avalon.Api` proxies the admin
`/balance/*` calls to it (`catalog`, `runs` POST / GET `{id}` / DELETE `{id}`, `exports`), each behind
`[Authorize(Policy = AvalonRoles.Admin)]`.

- **Endpoints:** `/catalog`, `/runs` (POST, GET `{id}`, DELETE `{id}`), `/exports`, plus `/health` and `/alive`.
  Only the last two skip the `X-Balance-Secret` check; every other request needs the header equal to
  `Balance:SharedSecret` (constant-time compare), else 401 with no detail. The secret is required at startup and
  at least 32 characters. Responses are camelCase JSON, enums as strings, gzip, no NaN or Infinity (`null`).
- **Limits:** one run executes at a time and 3 wait; one more gets 429. `runsPerRow` is at most 1000, overrides at
  most 500 keys, the request body at most 1 MiB (Kestrel, 413). A finished run is kept 1 hour, then 404, and at
  most 100 finished runs are retained. The queue is in memory, so the chart runs one replica.
- **Export** (`POST /exports`): branches `balance/<slug>-<yyyyMMdd-HHmm>` from the commit the service was built
  from, commits only the changed `balance/*.json` files in `ConfigFiles.Save` canonical form, and opens a draft PR
  against `main` titled `chore(balance): <title>` with a `Player note: No gameplay changes: balance tuning
  proposal.` line. It uses `Balance:GitHubToken`, a fine-grained token, never logged; without it exports answer
  503. The build commit is the `+<sha>` of `AssemblyInformationalVersion`, so CI publishes the service with
  `-p:SourceRevisionId="$(git rev-parse HEAD)"` (the checked-out commit, not `github.sha`, which is main's head on a manual release) on a publish that builds (no `--no-build`); without it exports answer 503.
- **Seed data:** read from `WorldDbContext`'s design-time model (`HasData`, no database); the `balance/*.json`
  files are copied next to the binary (`/app/balance` in the image) by the csproj.
- **API side:** `Application:Balance:Url` and `Application:Balance:SharedSecret`. Unconfigured (either empty) the
  `/balance/*` endpoints answer 503 ProblemDetails (`BalanceUnavailableException`) and the rest of the API is
  unaffected. The typed client removes the standard resilience handler, retries only GET (10 s an attempt) and gives
  POST and DELETE a single 60 s attempt with no retry, so a run or an export is never started twice. A 401 from the
  service maps to 502: it is our misconfiguration, not the caller's.
- **Deploy:** chart `avalon-balance` (image `ghcr.io/woozchucky/avalon-server/balance`), secret keys
  `balance-shared-secret` and optional `github-token`; the api chart takes `balance.url` and the same
  `balance-shared-secret` key. The homelab wiring is a separate change.
- **Local dev:** the Aspire AppHost (`src/Server/Avalon`) adds `balance` with a generated, persisted `balance-secret`
  parameter passed to both the service and the api, and sets the api's `Application__Balance__Url` from the
  service's endpoint (`http://localhost:5220`). Running the service alone needs `Balance__SharedSecret` (32+
  characters, e.g. in user-secrets or the environment).

## ValueObject Pattern

`ValueObject<TPrimitive>` (in `Avalon.Common`) wraps primitives like `AccountId`, `WorldId`, `CharacterId`. Fourteen of them, used across ~217 files.

**They live inside the server and stop at every boundary.** Each edge unwraps them explicitly rather than relying on automatic serialization:

| boundary | how |
|---|---|
| Database | EF `HasConversion`, ~42 registrations across the three DbContexts |
| Protobuf wire | packet contracts declare primitives; handlers pass `.Value` |
| REST JSON | DTOs declare primitives; mappers pass `.Value`. Enforced by `ApiContractShould` |

There is nothing on a value object making it serialize as its primitive automatically — no attribute, no global converter. `Avalon.Common.Converters.ValueObjectJsonConverterFactory` does it, but only for a `JsonSerializerOptions` that registers it, and its only caller is the item-catalog export, which serializes `ItemTemplate` entities directly. Serializing a value object without it yields `{"value":42}`.

The API deliberately registers neither that converter nor an OpenAPI schema transformer, because nothing on its surface is a value object. If a DTO ever needs to expose one, `ApiContractShould` fails and says so — that is the signal to register the converter and flatten the OpenAPI schema, not to delete the test.

## Testing Conventions

- Framework: **xUnit** + **NSubstitute** for mocks.
- Test files are named `<Subject>Should.cs`, methods follow `Should_<verb>_<condition>` or descriptive names.
- No integration test infrastructure (no real Redis/Postgres in unit tests) — all external dependencies are substituted.
- Auth handler tests construct handlers directly via `new CAuthHandler(...)` with `NullLoggerFactory` and `NSubstitute` fakes.
