### REST API signing key

`Avalon.Api` will not start without a JWT signing key, and none is committed (#482). The setting is `Application:Authentication:IssuerSigningKey` (environment variable `Application__Authentication__IssuerSigningKey`). `JwtSigningKey.Create` refuses a key that is missing, has leading or trailing whitespace, is under 32 bytes in UTF-8, or is on `JwtSigningKey.BlockedKeyHashes` (the SHA-256 of the one that used to sit in `appsettings.json`, public now), and the error names the setting. `AddAuth` registers the resulting `SymmetricSecurityKey` as a singleton, which `JwtUtils` signs with and the bearer handler validates with. Set it once per machine:

```bash
# Local runs (dotnet run, or the Aspire AppHost in src/Server/Avalon): Development loads user-secrets.
# Each line generates a key and stores it; run one from the repo root.
dotnet user-secrets set "Application:Authentication:IssuerSigningKey" "$(openssl rand -base64 48)" --project src/Server/Avalon.Api   # bash
$b = New-Object byte[] 48; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); dotnet user-secrets set "Application:Authentication:IssuerSigningKey" ([Convert]::ToBase64String($b)) --project src/Server/Avalon.Api   # PowerShell 5.1 or 7

# Containers and every non-Development host: the environment. Keep the key out of shell history:
# put it in a file (api.env is gitignored) holding the line Application__Authentication__IssuerSigningKey=<key> ...
docker run --env-file ./api.env ...
# ... or name the variable without a value, so docker passes it through from the current environment.
docker run -e Application__Authentication__IssuerSigningKey ...

# Helm: the chart reads every secret through a Kubernetes Secret (secretKeyRef), never a plain env value.
# Either name a Secret you manage (preferred; keys listed in values.yaml; leave the chart's own secret
# values empty, or it refuses to render) ...
helm install ... --set existingSecret=avalon-api-secrets
# ... or let the chart create it, passing the key from a file (a trailing newline is trimmed).
# Without one of the two, the chart refuses to render.
helm install ... --set-file authentication.issuerSigningKey=./jwt.key
```

Rotating the key: with a chart-managed Secret, `helm upgrade` with the new file restarts the pods (a checksum annotation). With `existingSecret`, the chart cannot see the change, so after updating the Secret run `kubectl rollout restart deployment/<release>-avalon-api` (the chart's fullname; the chart renders a Deployment).

`docker-compose.yml` runs only Redis and Postgres, so it needs no key. EF design-time commands (`dotnet ef migrations ...` with `--startup-project src/Server/Avalon.Api`) need no key either: they build each context through its `IDesignTimeDbContextFactory` and never run `AddAuth`. Tests never read one: `ApiAuthHost` and the other API tests make their own key in code. Changing the key invalidates every access token already issued; clients get a 401 and refresh.

## Architecture

Avalon is split into three independently deployable real-time servers plus a REST API:

| Component | Project | Role |
|---|---|---|
| REST API | `Avalon.Api` | HTTPS/JWT, account management, OpenAPI (Scalar UI at `/scalar`) |
| Auth Server | `Avalon.Server.Auth` | TCP login flow, MFA, world-key issuance |
| World Server | `Avalon.Server.World` | Game simulation loop, packet dispatch, world lifecycle |
| Core world | `Avalon.World` | Instanced maps, entities, spell/creature systems, chat commands |

Shared libraries under `src/Shared/`:
- `Avalon.Network.Tcp` / `.Packets` / `.Packets.Abstractions` — custom TCP server, packet protocol (Protobuf-net)
- `Avalon.Domain` — rich domain model (Account, Character, Spell, Creature, etc.)
- `Avalon.Common` — `ValueObject<T>`, utilities, JSON converters, math
- `Avalon.Configuration` — strongly-typed config binding classes
- `Avalon.Metrics` — OpenTelemetry integration

Infrastructure: `Avalon.Infrastructure` — `IReplicatedCache` (Redis wrapper), `IMFAHashService`, `CacheKeys` (all Redis key strings centralized here), `ISecureRandom`, and `Login/` (the login policy both the Auth server and the REST API run: `PasswordLoginPolicy`, `MfaLoginPolicy`, the budgets, `RemoteAddress`, `ILoginLimits`; #478).

Three separate Postgres DbContexts (via Npgsql EF Core): `AuthDbContext`, `CharacterDbContext`, `WorldDbContext`. Auth (and Redis) is shared; every world has its own world and characters database. A world server holds one pair (`Database:World`, `Database:Characters`); the REST API holds one pair per world under `Database:Worlds` (see "REST API Worlds"). Design-time factories in each `Avalon.Database.*` project enable `dotnet ef` without a running host; the World and Character ones read their string only from their project's user-secrets and then the environment, which wins (see Commands). Sensitive data logging (parameter values in EF's logs) is on only when the host environment is Development, whatever the configuration says (`AddAvalonDatabases`, #558), for every context, the API's per-world ones included; every `Microsoft.EntityFrameworkCore` category logs at Warning and above for every logging provider, OpenTelemetry's included (`AddCustomLogging`), and `docs/configuration-reference.md` says how to raise the command log in Development.

## Packet Protocol

All client↔server communication is custom TCP with Protobuf-net. Every packet wraps a `NetworkPacket` (header + payload). The header carries `NetworkPacketType` (opcode), `NetworkPacketFlags` (encryption/compression bitmask), `NetworkProtocol` (channel grouping), and `Version`.

**Adding a packet handler:**
1. Define the packet contract in `Avalon.Network.Packets` with a `NetworkPacketType` enum value.
2. For Auth: implement `IAuthPacketHandler<TPacket>` in `Avalon.Server.Auth/Handlers/`.
3. For World (server layer): implement `IWorldPacketHandler<TPacket>` in `Avalon.Server.World/Handlers/`, decorated with `[PacketHandler(NetworkPacketType.X)]` — handlers are registered via reflection scan in `WorldServer` constructor.
4. For World (core layer): implement `WorldPacketHandler<TPacket>` in `Avalon.World/Handlers/`, also discovered by attribute scan.

Auth handlers are registered in DI and resolved manually; World handlers use `ActivatorUtilities.CreateInstance` in `WorldServer`.

**A new client→server opcode also needs a session filter entry, or the handler never runs.** `MapSessionFilter` (in-map packets) or `WorldSessionFilter` (pre-character packets) must accept the opcode, not just a registered handler for it. `WorldConnection.OnReceive` only queues a packet if a filter accepts it at arrival; one no filter ever accepts skips the queue entirely and is dropped with a "could not find a handler" warning — a missing filter entry fails safe, so debug it by grepping the logs, not by hunting a frozen connection. The queue *can* wedge, but only for the narrower race where a packet's acceptance changes between arrival and dispatch (e.g. `CMSG_CHARACTER_LIST`/`CMSG_CHARACTER_LOADED` around a character spawn) — see `ProcessQueueWedgeShould.cs`.

**Reflection-bound registration — a reference grep proves nothing.** Packet handlers are discovered by attribute scan, and AI/ability scripts by type name: `ScriptManager` keys every `AiScript` subclass by `t.Name` (except those marked `[ChainedScript]`), and `ICreaturePlacementService.AttachScript` resolves `creature.ScriptName` from the DB and builds it with `ActivatorUtilities.CreateInstance(_sp, scriptType, creature, instance)`. So "nothing references this type" says nothing about whether it is used — and note that call site passes exactly two runtime arguments, so a script constructor needing anything beyond `(ILoggerFactory, ICreature, ISimulationContext)` will throw and be swallowed into a logged error. Check constructibility against that call site, not against grep — `AiScriptConstructibilityShould` does exactly that for every nameable script, against the production container. Ability scripts are bound the same way: `ScriptManager` keys every `AbilityScript` subclass by `t.Name`, `AbilityTemplate.SpellScript` names one, and `InstanceAbilityCastSystem` builds it with `ActivatorUtilities.CreateInstance(sp, type, ability, caster, aim, arena)` (an `AbilityAim` and the instance as `IAbilityArena`); `AbilityScriptConstructibilityShould` builds every seeded one that way.

## Auth Flow

```
CClientInfoPacket → SHandshakePacket → CHandshakePacket → SHandshakeResultPacket
→ CAuthPacket → SAuthResultPacket (per-source limit, per-username limit, lockout, BCrypt verify, then non-Active Status refused as BANNED/DEACTIVATED, then MFA check)
→ [MFA only] CMFAVerifyPacket → SAuthResultPacket (per-source limit, per-hash attempt limit, per-username limit, lockout, TOTP ±1 step, each step once; Status re-checked)
→ CWorldListPacket → SWorldListPacket
→ CWorldSelectPacket → SWorldSelectPacket (past the connection's select budget the connection is closed before any read, #574; non-Active Status closes the connection; an unknown world or one the account may not enter is answered WorldUnavailable, the same for both, with no key or mutex and the connection left open, #554; CSPRNG world key written to Redis, SETNX inWorld mutex)
→ [new TCP to World] CExchangeWorldKeyPacket → SExchangeWorldKeyPacket (key consumed from Redis, access re-checked, inWorld mutex cleared)
```

**World select is budgeted per connection** (#574). Every select reads the account and the world, and a refused one writes a warning, so repeated selects could flood the database and the logs. `CWorldSelectHandler` first takes a slot from the connection's own `WorldSelectBudget` (`IAuthConnection.WorldSelects`): at most `Application:MaxWorldSelectsPerMinute` (default 10, startup refuses one below 1) per window of one minute fixed from its first select, measured on `TimeProvider` timestamps, with no timer. The select past the cap closes the connection before `PostLoginGuard` or any other read, and its warning is written once per window, since selects already sent keep arriving until the connection is gone. The WorldUnavailable refusal is logged at Warning once per connection per window too, and at Debug after that. A select within the cap is answered as before. So a client should not retry `DuplicateSession` automatically (the inWorld slot lasts up to 5 minutes) and should back off after `WorldUnavailable`: every select, whatever its answer, counts against the budget, and the one past it closes the connection.

**Spending the world key** (`ExchangeWorldKeyHandler`): the `DEL` spends the key, not the `GET`. Two connections presenting the same key can both read it, so the handler goes on only when `RemoveAsync` reports it deleted the key — Redis tells exactly one caller that (#450). The key is spent before any other check, so a refused exchange cannot retry it. The handler then re-checks the account against a freshly read `World` row — `Status == Active` and the same `AccessLevels.ForWorld(...).Allows(...)` rule — because the key lives five minutes and the account may have been banned or demoted since it was issued. The `inWorld` mutex is cleared only once every check has passed; a refused exchange leaves it to expire on its TTL.

**Login throttling** (`CAuthHandler`, `CMFAVerifyHandler`, `SourceBudget`, #471). The rules in this paragraph and the next live in `Avalon.Infrastructure.Login` (`PasswordLoginPolicy`, `MfaLoginPolicy`), and the REST API runs them too, over the same keys (see "REST API Auth", #478). Every password or MFA-code attempt takes a slot from its source's budget *before* any work, by an atomic increment whose returned value decides: past `MaxFailedLoginsPerSource` inside `FailedLoginSourceWindowMinutes` it is answered `LOCKED` before any account is looked up, so parallel connections cannot all slip past a check made before the first is counted. A slot is given back (`DecrementFloorAsync`, only its own, never the whole count) only once an MFA hash is issued or a login completes, as the per-username budget below describes; every other attempt keeps its slot, a correct password refused on the way and an attempt on a locked account included. The source is the full IPv4 address, or the /64 prefix for IPv6 (IPv4-mapped addresses count as IPv4); `LastIp`/`LastAttemptIp` store the full address (`RemoteAddress`). An unknown username still costs one BCrypt verify, against `BCryptPasswordVerifier.UnknownAccountHash`, and a wrong password is answered *before* its write, so response time does not reveal which usernames exist.

**The account lock is a per-username budget** (`UsernameBudget`, #484), built on the same `AttemptBudget` mechanics as the source budget. Every password attempt takes a slot keyed by the username as it is looked up (trimmed, upper-cased, then SHA-256 in the key) *before* `FindByUserNameAsync`, from every source alike and whether or not an account has that username, and every MFA code takes one from its account's username before the code is checked. The count the increment returns is the attempt's place in the window (`LockoutDurationMinutes`, fixed from the first attempt), and it alone decides, never the row as read: past `MaxFailedLoginAttempts` the attempt is answered `LOCKED` before the lookup; a wrong password (or wrong code) in the last slot is answered `LOCKED`, locks the row, and holds the key with `HoldCounterAtLeastAsync`, one Lua script that raises the count to at least `MaxFailedLoginAttempts + 1` (`UsernameBudget.HeldValue`, one past anything a run of failures reaches, so the reset below can tell a held key apart) and restarts its expiry, recreating the key if it expired after the take (a plain `EXPIRE` did nothing then, and an unknown username went back to `INVALID_CREDENTIALS` while a known one's row stayed locked); `UsernameBudget.RecordFailureAsync` computes the row's `LockedUntil` before the hold, so it always ends first, catches and logs a hold error, writes the row anyway (with `CancellationToken.None` whenever it locks, so a closing connection never skips the lock), and only then rethrows, which closes the connection; an earlier one is answered `INVALID_CREDENTIALS` (`MFA_FAILED`). An unknown username goes through exactly the same steps, answers and expiry, minus the database write. Before it, the lock was decided from the row each request read before its BCrypt verify, so parallel guesses spread over sources got about ten verifies per lockout, and the right password, reaching its success write after the batch's failures had locked the row, was the one answered `LOCKED`. Slots are given back late: a correct password gives back its own source and username slots only when it issues an MFA hash (no reset there: each password login makes a fresh hash, so a reset would hand out a fresh set of code guesses per login), and otherwise only once `TryRecordLoginAsync` has recorded the login. A **completed** login (non-MFA once recorded; MFA once the code is accepted and the login recorded) gives the source its own slot back and deletes the username's key (`UsernameBudget.ResetAsync`, owner decision), so a player's own typos do not carry over. The delete is one script (`RemoveCounterIfBelowAsync(key, heldValue)`) that runs only while the count, which still includes the login's own slot, is below `HeldValue` (the limit + 1): four typos and a login leave five and the key goes, but a hold that a concurrent last-slot failure set (with its row lock) is not deleted by a reset. The MFA-hash give-back cannot bring a hold back within reach either: `UsernameBudget.GiveBackAsync` is its own script (`DecrementCounterIfAtMostAsync(key, limit)`) that decrements only while `0 < v <= limit`, so a held value is left alone (a plain floored `DECR` let a give-back lower six to five, after which a reset deleted it, or two give-backs reached four and the next guess was verified); `SourceBudget` keeps the floored `DECR`. Known edge case: an attempt refused past the budget that lands between a login's take and its reset raises the count to six or more, so the reset keeps the key and the player is answered `LOCKED` until the window ends, with no row lock behind it. It fails closed and needs a race of a few milliseconds. The source key is never reset. Known limit: the window is fixed, not sliding, so an attacker who stays one short of the limit, four guesses every 15 minutes, never locks the account: about 384 guesses a day per username (4 × 96 windows). A budget window longer than the lockout (say a day, with the refusal still ending when the row's lock does) would close that; the mechanism is unchanged for now. Failed logins are still counted in SQL (`IAccountRepository.RecordFailedLoginAsync`, one `UPDATE` whose right-hand sides all read the old row), never by writing back the row that was read, so concurrent failures are not lost; the caller passes `lockUntil` when the budget says the failure locks, and the row stays locked until `LockedUntil`. An expired lock is lifted there too, and by the success write, `TryRecordLoginAsync`, which refuses if the account is locked at write time, so a success can never write away a lock set after it read the row; that refusal is answered as a wrong password in the same slot would be (`INVALID_CREDENTIALS`/`MFA_FAILED`, or `LOCKED` in the last slot) and keeps both slots, so on the offline, Active, non-MFA path (and at MFA verify, the offline Active path) it does not single out the right password in a parallel batch. `MFA_REQUIRED`, `ALREADY_CONNECTED` and `BANNED`/`DEACTIVATED` do single out a correct password inside the budget, by design. A lock with `LockedUntil = null` never expires; the migration that added the column gave every earlier lock a 15-minute end. The row's lock check stays before the password (and code) check on purpose: after it, a locked account would still tell right from wrong passwords. Each MFA hash allows `MaxFailedMfaAttempts` codes, counted on the `auth:account:{accountId}:mfa` hash before the code is checked; the last failure deletes the hash, so the client must log in again, and a code whose hash is gone (no reverse key, or `attempts` of -1) is refused without being checked. All these settings are under `Application` in the Auth server's config, and again, with the same names, under `Application:Authentication` in the API's; the two must match, since both count on the same keys.

**Account rows are written by column, never whole** (#484). The auth server never calls `UpdateAsync(account)`: clearing a stale `Online` flag at login or MFA verify is `MarkOfflineAsync`, a disconnect is `MarkOfflineAsync` with the session's seconds added to `TotalTime` (`AuthConnection.RecordDisconnectAsync`), the start-up reset is one `MarkAllOfflineAsync`, and world select stores its key with `SetSessionKeyAsync`. Each is an `ExecuteUpdate` that never touches `Locked`, `LockedUntil`, `FailedLogins` or `Status`, so a ban or a lock written between the read and the write survives it.

**`Online` belongs to one connection (#487).** A TCP login (`TryRecordLoginAsync`) stores the logging-in connection's `Id` in `Accounts.OnlineSessionId` with `Online = true`. `MarkOfflineAsync(id, sessionId, seconds)` clears both only while `OnlineSessionId` still equals `sessionId`, in one statement, and adds the seconds to `TotalTime` either way, so a close that lands after a newer session of the account logged in leaves that session online. A disconnect passes its own connection id; the stale-flag clear at login or MFA verify passes the session id it read. **Exactly one auth server is supported:** the start-up `MarkAllOfflineAsync` clears every `Online` flag and session, and the `ALREADY_CONNECTED` check looks only at this server's connections, so a second server would break both (the Helm chart runs one replica). **A liveness sweep (#555)** relies on the same assumption: every `Application:OnlineSweepIntervalSeconds` (default 30, startup refuses below 1), `OnlineSweep`, run from `AuthServer.ExecuteAsync` on an absolute `TimeProvider` due time (a late pass sweeps once), reads only the online rows' id and session (`ListOnlineSessionsAsync`) and calls `MarkOfflineAsync(id, sessionId, 0)` for each whose session is none of this server's live connections, so a close whose write failed does not leave the account online until the next restart; the compare keeps a login that landed since, and a sweep that throws is logged and the next still runs. A half-open TCP connection is still live to it, so every socket the shared `ServerBase` accepts (auth and world) has TCP keepalive on (#571, `TcpKeepAlive`; `Hosting:TcpKeepAliveTimeSeconds`/`TcpKeepAliveIntervalSeconds`/`TcpKeepAliveRetryCount`, default 60/10/3, startup refuses below 1 or above the OS maximum), and the OS closes one within about 90 s, which runs the close path. **The accept loop (#578, #584)** is one awaited `AcceptTcpClientAsync` loop started by `ServerBase.StartAsync`: only a stop ends it (`StopAsync` cancels it and awaits it before `OnStoppingAsync`, and is idempotent); a failed accept outside a stop is counted (`avalon.tcp.accept.errors`), warned at most once per 10 s, and retried, at once for a peer reset and otherwise after a backoff of 100 ms doubling to 5 s. A client accepted once the stop began is closed, and a packet arriving then is dropped, not dispatched; the shutdown closes its connection.

**What a username may be (owner decision, #487 re-review):** 3 to 16 ASCII letters, digits or underscores (`UsernameRule`, `^[A-Za-z0-9_]{3,16}$`), checked as sent, before trimming or upper-casing. `POST /account/register` refuses anything else with a 400 validation error (`UsernameRuleAttribute` on `RegisterRequest.Username`, and again in `AccountService.Register`). A login with anything else (`PasswordLoginPolicy`, so TCP and REST alike) is answered exactly as an unknown username: both budgets, the lookup, one dummy verify, `INVALID_CREDENTIALS` or the generic 401, whatever row holds the normalised form. With ASCII letters only, .NET and Postgres upper-case alike, so the check constraint below cannot disagree with the code.

**One account per username (#487).** `Accounts.Username` has a unique index (`IX_Accounts_Username`). Usernames are stored trimmed and upper-cased, the form login looks up, so the index is on the normalised name. Registration still checks first; a registration that loses the race to the index gets the check's answer, "Username already exists". A check constraint, `CK_Accounts_Username_Normalised` (`"Username" = upper(trim("Username"))`), refuses a row that is not stored normalised, whoever writes it. The migration that added the index refuses to run, naming the accounts, when two accounts share a normalised username or a username is not stored normalised; it never deletes or rewrites a row.

**One account per email (#503).** `Accounts.Email` has a unique index (`IX_Accounts_Email`) and a check constraint, `CK_Accounts_Email_Normalised` (`"Email" = lower(trim("Email"))`). Emails are stored trimmed and with the whole address lower-cased, local part included (`AccountEmail.Normalise` in `Avalon.Domain.Auth`, chosen over folding the domain only), and `FindByEmailAsync` normalises what it is given, so `A@x.com` and `a@x.com` are one account. An email must be printable ASCII with exactly one `@`, neither first nor last (`AccountEmail.IsValid`; `[EmailAddress, AccountEmailRule]` on the request and again in the service, 400 otherwise): outside ASCII .NET and Postgres can lower-case differently, and the check constraint would refuse what the code stored. A check violation (SQLSTATE 23514) on `Accounts` that still reaches the API, direct or wrapped by SaveChanges, is a 400 (`ExceptionHandlerMiddleware`), not a 503. Registration and the start of an email change refuse a taken address as "Email already exists"; both take a slot of the source's budget before the lookup, kept on that answer, so it is never free; a registration or an email confirm that loses the race to the index gets the same answer. The migration that added the index refuses to run, naming the accounts, when two accounts share a normalised email or an email is not stored normalised; it never deletes or rewrites a row.

**TOTP codes are single-use** (`MFAService`, #471). `MfaSetups.LastAcceptedTotpStep` stores the step of the last accepted code, set at confirm and advanced by `TryAcceptTotpStepAsync`, which writes only when the new step is later. A code at or before that step is refused, and the window is ±1 step for both confirm and verify. A hash has one winner (#478): once a right code's step is accepted, the code spends the hash with `IMFAHashService.TryConsumeAsync`, and only the caller whose `DEL` removed the reverse key goes on, so two verifies of one hash with codes of adjacent steps cannot both pass. The step is accepted first on purpose: a replayed code (right, already used) is refused as `MfaCodeRefusal.Replayed` without spending the hash, and like a code that lost the hash (`HashSpent`) it is not a failed login: `MfaLoginPolicy` gives its slots back and writes nothing to the row. A replay also gives back the attempt it counted on the hash (`IMFAHashService.GiveBackAttemptAsync`, a script that decrements `attempts` only while the hash exists, never below zero); a code that lost the hash does not, since that per-account key may already hold the next login's hash.

**Every post-login auth handler starts with `PostLoginGuard.AccountOrCloseAsync`** (#495 review): MFA setup, confirm and reset, the world list and world select. It reads the account fresh and closes the connection unless it is logged in, the account exists, is `Active`, and is still at the `CredentialsVersion` this connection's login proved; so a session banned, deactivated or outdated by a credentials change since its login can neither change MFA nor get a world key. MFA confirm and reset also carry the session's version into their write (`IMFAService.ConfirmMFAAsync`/`ResetMFAAsync(accountId, credentialsVersion, ...)`): `MfaSetupRepository.TryConfirmAsync` and `ResetConfirmedAsync` start their transaction with `HoldCredentialsVersionAsync`, so a change committed between the guard and the write refuses it (`MfaSetupWrite.CredentialsChanged`, `CredentialsChanged` on the result); the TCP handler then closes the connection and the REST endpoint answers 401.

**World access** is decided by `AccessLevels.ForWorld(world.AccessLevelRequired).Allows(account.AccessLevel)`, the same test in `CWorldListHandler` (what is listed) and `CWorldSelectHandler` (what can be entered). A Player world admits every player, Tournament and PTR included; a Tournament or PTR world admits holders of that flag plus staff; a staff-gated world admits its staff mask. Never compare a world's level with `<=`: `AccountAccessLevel` is `[Flags]`, and PTR (32) and Tournament (16) are numerically above Admin (4), which is how PTR accounts used to reach the Admin-only world.

**Key Redis patterns** (all string literals in `CacheKeys`):
- `world:{worldId}:keys:{base64}` — one-time world entry token (5 min TTL)
- `account:{accountId}:inWorld` — duplicate session mutex via `SETNX` (5 min TTL)
- `auth:mfa:hash:{hash}` — an MFA hash's reverse key, `{accountId}:{credentialsVersion}` (#495), 2 min TTL; its `DEL` spends the hash
- `auth:account:{accountId}:mfa` — Redis Hash with MFA state (2 min TTL); its `attempts` field counts MFA codes tried against it (`HINCRBY`, only while the hash exists); a replayed right code gives its attempt back (one script: `HINCRBY -1` only while the hash exists and the field is above zero)
- `auth:source:{source}:failedLogins` — attempt budget per source (IPv4 address, or IPv6 /64 as `prefix::/64`), shared by the TCP login and the REST API (#478), `INCR` with the expiry set on the first attempt (fixed window, default 15 min); a correct password or MFA code gives its own slot back with a floored `DECR`
- `auth:source:{source}:accountsCreated` — accounts created by one source through `POST /account/register` (#495 review), `INCR` before the insert with the expiry set by the first (fixed window, default 60 min, cap default 5); given back only when no account is created
- `auth:emailChange:{sha256}` — a pending email change, keyed by the lowercase hex SHA-256 of its confirm token, never the token itself (#510 review); value `{accountId}|{credentialsVersion}|{email}`, 15 min TTL; the confirm hashes the presented token, and its `DEL` spends it
- `auth:account:{accountId}:emailChangePending` — the token hash of the account's one pending email change (15 min TTL). A start whose confirmation was sent swaps it in one script (`SwapAsync`: `GET` and `SET ... PX` together) and deletes the entry the old value names, so only the latest token confirms; a successful confirm deletes it only while it still names the confirmed token's hash (`RemoveIfEqualsAsync`, one script)
- `auth:account:{accountId}:emailChangeSends` and `auth:email:{sha256(normalised new email)}:emailChangeSends` — email-change confirmations sent per account and per new address (#510 review), `INCR` just before the send with the expiry set by the first (`Application:Authentication:EmailChangeSendWindowMinutes`, default 60; `MaxEmailChangeSendsPerAccount` and `MaxEmailChangeSendsPerAddress`, default 3 each, startup refuses below 1); never given back; past either, 429 `LOCKED` and nothing is stored or sent
- `auth:username:{sha256}:failedLogins` — attempt budget per username (lowercase hex SHA-256 of the trimmed, upper-cased username, whether or not an account has it), shared by password and MFA-code attempts from every source and by both servers (TCP and REST, #478); `INCR` with the expiry set on the first attempt (`LockoutDurationMinutes`, default 15 min); the failure that reaches `MaxFailedLoginAttempts` holds it with one script (raise to at least the limit + 1, `SET ... PX` the window, recreating an expired key); a correct password that issues an MFA hash gives its own slot back with one script that decrements only while `0 < v <= limit` (never lowering a held value); a completed login deletes it with one script, only while its value is below the held value, limit + 1 (so a reset never deletes a hold)
- `world:accounts:disconnect` — pub/sub, force-disconnect by accountId: published by the Auth server and the API (duplicate login, password change, MFA reset or removal, ban, email change, role change, refresh-token reuse); subscribed by the World server, which closes every connection of the account (`WorldServer.CloseAccountSessions`, #504 review; not only the first), and, since #495, by the Auth server, which closes that account's logged-in TCP connections with `DisconnectReason.Kicked` (`AuthServer.CloseAccountConnections`). The message is the bare id and cannot say why, so both servers tell the player the same neutral "Your session has ended. Please log in again." with `Kicked`; only the world server's own duplicate-login kick at character select says "logged in from another location". A TCP MFA reset therefore ends the connection that made it, too. The message is the bare account id the World server parses, so it carries no origin: before its own duplicate-login publish (`ALREADY_CONNECTED`) the auth server notes it (`NoteOwnDisconnectPublish`), and for `OwnPublishWindow` (10 s) a connection of that account that logged in after the note (`IAuthConnection.LoggedInAt`) is spared, so the retry that follows is not kicked by its own attempt (the note lasts its whole window, whatever messages arrive, because a ban and the echo cannot be told apart and a note consumed by the first let the second kick the retry; expired notes are dropped on read and pruned on every write, so the map holds only the last window's publishes); world select's version and status checks cover anything else that lands in that window. One connection that throws while closing is logged and the rest are still closed.
- `auth:accounts:online` — pub/sub: login event (reserved, no subscriber yet)
- `world:{worldId}:select` — pub/sub: world-select event (reserved, for future sharding)
- `world:{worldId}:presence` — one world's live presence snapshot (`WorldPresenceSnapshot`: its instances and the characters in them), written by that world server's `PresenceSnapshotService` about once a second with `CacheKeys.PresenceTtl` (5 s)
- `presence:world:{worldId}:character:{id}` — which instance of that world holds character `{id}` (`CharacterPresenceIndex`), same writer and TTL. It names the world because character ids are unique only per world (#556). A deploy that changed a presence key loses the entries under the old key; they expire within the TTL and each world server writes the new ones on its next capture, so nothing needs migrating

## REST API Auth

`Avalon.Api` takes two credentials:
- an access JWT, sent as `Authorization: Bearer` or in the `AVToken` cookie, and minted by `JwtUtils` at login, MFA verify and refresh;
- a personal access token, sent as `Authorization: Avalon avp_...` and read by `AvalonAuthenticationHandler`.

**Neither is believed on its own (#451, #480).** On every request both go through `AccountAccessCheck` (`Avalon.Api/Authentication`):
- the account is reloaded;
- a missing or non-Active one (Banned, Deactivated) is refused with 401;
- the request carries only `credential roles & account.AccessLevel` as `GroupSid` claims. That is a mask, never `>=`.

For a JWT this runs in `JwtBearerEvents.OnTokenValidated` (`JwtAccountRevalidation`), after the bearer handler has checked the signature (HS256 only, `ValidAlgorithms`), issuer, audience and lifetime. The loaded account is kept in `HttpContext.Items`, and `AvalonAuthHandler` (the default policy's requirement) reuses it rather than loading it again. A ban therefore takes effect on the next request. A role change, promotion or demotion, raises the credentials version (#504), so every token issued before it is refused and the account signs in again to get its new roles. A database failure during that lookup is a 503 (`ExceptionHandlerMiddleware` maps `DbException`), never a pass.

The JWT's lifetime is enforced: `ValidateLifetime = true`, with `AccessTokenLifetimeMinutes` (default 15) plus `ClockSkewInMinutes`. An expired JWT gets a 401, and the client renews it with `POST /account/refresh`. That endpoint is `[AllowAnonymous]` and reads only the HttpOnly refresh cookie, so an expired access token does not stand in its way.

**A refresh token rotates once (#495).** `RefreshTokenRepository.RotateAsync` revokes the parent with a conditional `UPDATE ... WHERE Id = @id AND NOT Revoked` and inserts the child, in one transaction, only when that write revoked the row: of two rotations of one token that both read it live, exactly one gets a child. The other (`RefreshRotation.ParentNotLive`) is answered as the same token presented a moment later would be. A revoked token presented within `RefreshTokenService.RotationGrace` (5 s) of the rotation that replaced it, while that rotation's child is still unused (not revoked, `Usages == 0`) and by the caller that rotated it (the child records its source, the login budget's IPv4 address or IPv6 /64, in `RotatedBySource`, and a SHA-256 of its User-Agent in `RotatedByAgentHash`; `RefreshCaller`; a caller whose address, after the forwarded-headers middleware, is still a trusted proxy (loopback or `Application:ForwardedHeaders` proxies and networks, i.e. a proxy that forwarded no client) gets no source and so never the grace, since everyone behind that proxy shares it), is two tabs or a client retry: 401 (`RefreshAlreadyRotatedException`), with the family, the refresh cookie and the account's sessions left alone. Anything else is a reuse: the family is revoked, `RefreshTheftException`, a world disconnect is published, the cookie is cleared and the caller gets 401.

**Nothing issues a credential to an account that is not Active** (`AccountAccessCheck.MayHoldSession`):
- password login (`AccountService.Authenticate`) checks after the BCrypt verify, and MFA verify after the code is accepted. Both throw `AccountInactiveException`, which `ExceptionHandlerMiddleware` answers as 403 ProblemDetails with `Detail` BANNED or DEACTIVATED, as the game client is told. A wrong password or bad code still gets the generic 401, whatever the status, so nothing about the account leaks before the proof;
- refresh revokes every refresh token the account holds, clears the cookie and returns 401.

**REST login and MFA verify run the game client's login policy (#478).** `AccountService.Authenticate` runs `PasswordLoginPolicy` and `MFAController.VerifyMFA` runs `MfaLoginPolicy`, the classes `CAuthHandler` and `CMFAVerifyHandler` run, in the same order: source slot, username slot before the lookup (a dummy BCrypt verify for an unknown username), the row's lock before the password or code, per-hash attempts (the last wrong code deletes the hash), failures counted with `RecordFailedLoginAsync` and locking in the budget's last slot, and on a completed login the source's slot back and the username's count cleared. The keys are the same on both servers, so a guess over REST and one over TCP spend one per-username budget and lock at one threshold; the per-source key is shared too, since that budget is per address across every account and a guesser must not get it twice by splitting guesses between servers. The API's source is `HttpContext.Connection.RemoteIpAddress` after `UseAvalonForwardedHeaders` (`Middlewares/ForwardedHeadersSetup.cs`), which believes `X-Forwarded-For` only from loopback and from `Application:ForwardedHeaders:{KnownProxies,KnownNetworks}` (with `ForwardLimit`, default 1; Helm `forwardedHeaders.*`). Behind an ingress not listed there every REST caller is one source, so outside Development the API warns at startup when none is configured, and it logs a header from an untrusted peer at most once a minute (`UntrustedForwardedHeaderLog`). An entry that does not parse, a trusted network wider than /8 (IPv4) or /32 (IPv6), `0.0.0.0/0` and `::/0` included, or a limit below 1 stops startup. A caller with no peer address has its `X-Forwarded-*` headers dropped before they are read, so it cannot name one, and is refused with 400 on every endpoint that spends a source budget (`BaseController.SourceAddress`), rather than sharing one `IPAddress.None` budget. A locked row pays the same dummy BCrypt verify as an unknown username, so it does not answer faster when its budget hold is gone. A refusal by a budget or a locked row, and the failure in the last slot, is **429** ProblemDetails with `Detail` `LOCKED` (`AccountLockedException`); a wrong password or code stays the generic 401, and 403 `BANNED`/`DEACTIVATED` still comes only after the proof (#480). HTTP cannot answer before its write, so an unknown username runs the same failure statements against `LoginPolicy.NoAccount` (id 0, which no account has). A REST login never touches `Online`, the game client's session flag: the success write is `TryRecordApiLoginAsync` (by column, refused while locked, answered as a wrong password in that slot). The limits are `Application:Authentication:{MaxFailedLoginAttempts,LockoutDurationMinutes,MaxFailedLoginsPerSource,FailedLoginSourceWindowMinutes,MaxFailedMfaAttempts}`, defaults equal to the Auth server's, which they must match; `AddInfrastructure` refuses one below 1, and both hosts log all five at Information at startup (`LoginLimitsValidation.LogAtStartup`) so a drift shows.

**Sensitive actions need the current password (#478, #483).** `IReauthentication.RequireCurrentPasswordAsync` runs `PasswordLoginPolicy` against the signed-in account, so a wrong current password is a failed login in every respect (both budgets, the row's count, the lock); a right one gives back only its own slots. It guards `POST /account/password`, the start of an email change (`InitiateEmailChangeAsync`, a `currentPassword` field, #503), `POST /mfa/setup` (was `GET`; body `SetupMFARequest { currentPassword }`), and `POST /pat` and `POST /pat/admin` (a `currentPassword` field; the admin route takes the admin's own, since it can mint for any account, the admin's included). Missing or wrong: 401 `Invalid current password`; budget spent or account locked: 429 `LOCKED`. New passwords are measured trimmed, the form they are hashed in: `POST /account/password` (`newPassword`) and `POST /account/register` (`password`, with `username` and `email` required) refuse one under 8 characters with a 400 validation error (`TrimmedMinLengthAttribute`).

**Every request is rate limited (#561)**, on top of the budgets above, which count attempts and are unchanged. `ApiRateLimiting` (`Middlewares/`) puts ASP.NET Core's limiter, a sliding window of one minute in six segments, in memory (one replica), after `UseAuthentication` and before the world routes and authorization. A request with a valid JWT (after its account revalidation) or personal access token (authenticated there, since it is not the default scheme, and only on an endpoint that requires authorization, while enabled, and while its source has failed fewer than `FailedPatLookupsPerMinute` (10) lookups and has fewer than 2 in flight, so made-up tokens cannot force a query per request; the handler's cached result is reused by authorization) counts against its account, `AuthenticatedPermitsPerMinute` (default 300); any other, an invalid token included, against its source, `RemoteAddress.SourceOf` after the forwarded headers (IPv4 address, IPv6 /64), `AnonymousPermitsPerMinute` (default 60); every caller with no peer address shares one "unknown" partition. `/health` and `/alive` are exempt (`DisableRateLimiting` in `MapDefaultEndpoints`). A refusal is 429 ProblemDetails `LOCKED` with `Retry-After` (a lower bound, one segment when the limiter gives no hint), alike for both partitions, and increments `avalon.api.rate_limit.rejections` (meter `avalon-api`, tag `partition`). Settings under `Application:RateLimiting` (`Enabled` too); a limit below 1 fails the startup validation `ApiStartup` runs, naming the setting.

**Registration is budgeted per source (#495).** `POST /account/register` still answers "Username already exists" and "Email already exists" (a registration form cannot hide a taken username, and merging the two answers would still reveal the email by pairing it with a fresh username), so it takes a slot from the source's budget (`SourceBudget`, the key TCP and REST logins spend) before any lookup; past the budget it is 429 `LOCKED`, whatever the name. A registration that creates its account gives the slot back; "already exists" and every other ending keep it. That budget alone does not bound account creation, since successes are refunded, so a second, separate cap counts created accounts per source: `Application:Authentication:MaxAccountsCreatedPerSource` (default 5) per `AccountCreationWindowMinutes` (default 60, fixed from the first), on `auth:source:{source}:accountsCreated`. Its slot is taken just before the insert and given back only when no account comes of it; past the cap the answer is 429 `LOCKED`. API only; startup refuses a value below 1. A caller with no peer address is refused with 400, as at login.

**A password change and an MFA reset revoke every token (#483).** `ChangePasswordAsync` writes the verifier by column (`AccountRepository.SetPasswordAsync`, a compare-and-set on the `CredentialsVersion` the current password was checked at, so of two changes that proved the same password only the first lands and the other is 401 `Credentials changed; sign in again`, #495 review) and revokes every refresh token and personal access token in one transaction; `MFAService.ResetMFAAsync` (both servers) deletes the confirmed row and revokes both kinds in one transaction (`MfaSetupRepository.ResetConfirmedAsync`, which also makes a concurrent second reset fail). Each then publishes the account on `world:accounts:disconnect`, best-effort, as the admin MFA removal (#475) and a ban do. `POST /mfa/reset` returns 204 and enrols nothing: the client enrols again with `POST /mfa/setup`, which needs the password, since recovery codes are not the password.

**A role change and an email change are credentials changes (#503, #504).** `AccountService.UpdateRolesAsync` (`PATCH /account/{id}/roles`, now with the admin as `actorId`) writes the level and raises the version in one statement (`AccountRepository.SetAccessLevelAsync(context, ...)`), and revokes every refresh token and personal access token in the same transaction; a promotion does it too, since only a new login gets the new roles onto the game client's TCP session. `ConfirmEmailChangeAsync` does the same with `AccountRepository.SetEmailAsync(context, ...)`, a compare-and-set on the version the current password was checked at when the change was started (the pending change in `auth:emailChange:{sha256(token)}` is `{accountId}|{version}|{email}`), so a credentials change in between voids it, answered "Invalid or expired token". Each then clears the account's pending MFA login state and publishes the account on `world:accounts:disconnect`, best-effort, as a password change does. **Email change is on only when `Application:Email:Sender` is configured (#510):** `ServiceRegistration.AddEmail` registers an `IEmailSender` (`Avalon.Api/Services/Email`) for a configured sender and none for `None`, the default, and `AccountController` takes it as an optional dependency: with none, `POST /account/email/change` and `POST /account/email/confirm` both answer 501 ProblemDetails "Email change is unavailable until email delivery exists" and never reach the service. `Pickup` (`PickupEmailSender`) writes each email as an RFC 5322 `.eml` file into `Application:Email:PickupDirectory` (default `avalon-mail` under `Environment.SpecialFolder.LocalApplicationData`, created 0700 on Unix), refuses a line break in the recipient or subject, and is Development-only: startup refuses it elsewhere, naming `Application:Email:Sender`, and refuses it without a bare-address `Application:Email:From`. With a sender, the start sends the confirm token to the **new** address and a notice with no token to the old one, and answers 202 with no body; the token is never in the response or a log (sender failures are logged by exception type and recipient domain only). Before anything is stored or sent, the start takes a slot of two send budgets that are never given back, per account and per new address (keys above; past either, 429 `LOCKED`). Accepted: the per-address send budget can be spent by any accounts, so three accounts can block an address as a change target for the window; account creation is capped per source, which keeps the impact small. Once its confirmation is sent, a new start deletes the account's earlier pending change, so only the latest token confirms; a start that could not send leaves the earlier one intact. Once the change is stored, each email is sent with its own `AccountService.EmailSendTimeout` (30 s) token, never the request's, so a caller dropping the connection cannot suppress the notice. A confirmation that cannot be sent deletes the pending change (a failed delete is logged by exception type, and the key expires on its TTL) and is 503 "Email could not be sent" (`EmailDeliveryException`), keeping the source slot and both send slots; a cancelled send is logged at Information, any other failure at Error. A failed notice is a Warning and the change still starts. No real provider exists yet; one goes behind the same interface. **For whoever adds one:** a sender that delivers the email and then throws (a timeout after the provider accepted it, say) leaves a delivered token whose pending change was deleted. That fails closed: the token answers "Invalid or expired token" and the player starts again, within the send budgets.

**Credentials version (#495).** `Accounts.CredentialsVersion` is an integer raised by one, as the first statement of the change's transaction, by every password change (`AccountRepository.SetPasswordAsync`), role change (`SetAccessLevelAsync`, #504), email change (`SetEmailAsync`, #503), owner MFA reset (`MfaSetupRepository.ResetConfirmedAsync`, both servers) and admin MFA removal (`AccountService.RemoveMfaAsync`, via `BumpCredentialsVersionAsync`). Whatever a proof of the credentials issues carries the version of the very row the proof was checked against, and every check is an equality with the account's current version: the access JWT's `cver` claim (`JwtUtils.CredentialsVersionClaim`; `JwtAccountRevalidation` refuses a missing, malformed or different one with 401); each refresh token's `CredentialsVersion` column, set when its family is opened and copied to every child (`IssueAsync(accountId, version)` at login, MFA verify and registration, and every rotation, refused when it no longer matches; the refresh endpoint also refuses when the account read after the rotation is at another version); the MFA hash's own reverse key, `auth:mfa:hash:{hash}` = `{accountId}:{version}` (`IMFAHashService.GetHashCredentialsVersionAsync(hash)`, -1 when absent; the presented hash's version, never the per-account record's, since two logins racing with the old and the new password share that record, #495 review; `MfaLoginPolicy` treats a mismatch as a hash that is gone, on both servers, checked before an attempt is counted so a stale presentation spends none of a newer login's tries, and `CleanupHash` deletes the per-account record only while its `hash` field is the hash being cleaned (`RemoveHashIfFieldEqualsAsync`, one Lua script), and a live hash is reused only at the same version); `Reauthenticated(AccountId, CredentialsVersion)` for a personal-access-token mint (the admin's own account on `POST /pat/admin`); and, on TCP, `IAuthConnection.CredentialsVersion`, set at login and MFA verify, checked by `PostLoginGuard` and stored in the world key's value (`CacheKeys.WorldKeyValue`, `{accountId}:{version}`), which `ExchangeWorldKeyHandler` checks against a fresh read. Issuing a refresh token, rotating one and minting a PAT each open their transaction with `AccountRepository.HoldCredentialsVersionAsync`, a no-op `UPDATE ... WHERE Id = @id AND CredentialsVersion = @v`: it takes the row lock, so a change that committed first refuses them, and one still in flight waits for them and then revokes what they issued. A password change also clears the account's pending MFA state in Redis, as an admin's MFA removal does. A refused refresh issue or PAT mint is 401 `Credentials changed; sign in again`.

**The API writes account rows by column (#478)**, as the Auth server has since #484: login and MFA verify `TryRecordApiLoginAsync`, password `SetPasswordAsync`, email `SetEmailAsync`, roles `SetAccessLevelAsync` (the last three on the context of the transaction that revokes the tokens). None writes back a row it read, so a ban or a lock written in between survives (`ApiWriteRaceShould`).

## REST API Worlds

A deployment runs any number of world servers, one per auth `Worlds` row, each with its own world and characters database (#523). The API reaches every configured world; adding one is configuration only.

- **Configuration:** `Database:Worlds:<id>:World:ConnectionString` and `...:Characters:ConnectionString` (environment `Database__Worlds__2__World__ConnectionString`), `<id>` the auth `Worlds` row's id. `WorldDatabaseSettings.Parse` reads it, and `WorldDatabaseSettings.TryParseWorldId` is the one parse of a world id, for the configuration keys and the route alike (ASCII digits, 1 to 65535, no sign, no leading zero: `01` is refused, never read as world 1). It is deliberately not an options validation: `ApiStartup.ValidateAndMigrateAsync` resolves `WorldDatabases` right after `IStartupValidator.Validate()` (which checks `Database:Auth:ConnectionString` through `ValidateDatabasesOnStart(DatabaseConnections.Auth)`), and that stops startup, naming the setting and never its value, for no world, an id not in that form, half a pair, or a blank string. OpenAPI generation starts the host but skips `ApiStartup`, and `WorldDatabases` is built only when first resolved, so generation needs no world. The API reads no singular `Database:World`/`Database:Characters`. `appsettings.json` lists no world, so the published image ships none; `appsettings.Development.json` holds world 1 (the docker compose databases) for local runs, and the Aspire AppHost sets the same pair through the environment.
- **Helm:** a `worlds` map keyed by world id (`worlds.<id>`), every string held in the Secret (`secretKeyRef`). Chart-managed Secret: give `worlds.<id>.world.connectionString` and `worlds.<id>.characters.connectionString` (`--set-file`), stored under `database-world-<id>-connection-string` and `database-characters-<id>-connection-string`. With `existingSecret`: give no strings; the Secret holds those default keys, or the names in `worlds.<id>.worldKey`/`charactersKey`, which are accepted only with `existingSecret`. The chart refuses to render with no world, a world id not in the API's form, half a pair (chart-managed), an inline string with `existingSecret`, a key that is not a valid Secret key name or that two settings would read (the chart's own keys included), and the removed `database.world`/`database.characters` values.
- **Per-request world:** repositories stay singletons over `IDbContextFactory<WorldDbContext>`/`<CharacterDbContext>`, which in the API are `CurrentWorldDbContextFactory<T>`: they read the request's scoped `ICurrentWorld` through `IHttpContextAccessor` and throw `InvalidOperationException` ("No world selected for this request") when there is none, never falling back to a world. Code that needs a named world uses `IWorldDbContextFactory` (`CreateWorld`/`CreateCharacters`, caller disposes) or `IWorldRepositories` (the same repositories over one world).
- **Routes:** world content and characters live under `/world/{worldId}/...` on controllers marked `[WorldScoped]` (character, map-template including `chunk-asset`, item-, ability- and creature-template, and `observability/character/{id}`); a test pins that a route names `{worldId}` exactly where `[WorldScoped]` is. `WorldRouteMiddleware`, between authentication and authorization, in order: a world endpoint that allows anonymous callers → 404 (fails closed; none does); it then authenticates through the default policy (so a PAT is checked like a JWT), and an unauthenticated caller passes on to the 401; a world id not in canonical form → 404 with nothing looked up; no auth row, `AccessLevels.ForWorld(world.AccessLevelRequired).Allows(caller)` fails, or not under `Database:Worlds` → the same empty 404 (the row is read before the configuration is asked, so an unconfigured world costs the same lookup as a restricted one, and a restricted world is never revealed, even while unavailable); unavailable → 503 ProblemDetails "World {id} is unavailable"; otherwise it selects the world and the endpoint's role policy decides. `GET /world/{id}` is the auth world lookup, not world-scoped.
- **Availability:** `ApiDatabaseMigrator`, called by `ApiStartup` after the checks above, migrates auth (a failure stops the API), then each world's World and Characters databases; a failure is logged with the world id and exception type only and marks the world `Unavailable` until the next restart. No retry; each unreachable world adds the driver's connect timeout to startup. `IWorldDatabases.IsAvailable` is the one test of "this API can serve that world". A database error mid-request is still a 503 through `ExceptionHandlerMiddleware`.
- **Cross-world views:** `GET /character` (`AccountCharactersController`) returns `{ characters, unavailableWorlds }` across every configured, available world the caller may enter, each `CharacterDto` carrying `worldId`/`worldName`; a world unavailable or whose read fails goes in `unavailableWorlds`, a world the caller may not enter appears nowhere. `GET /world` lists only permitted worlds, each with `configured`/`available`. Observability stays cross-world (Redis), shows only permitted worlds, and reads template names and layout staleness from each presence's own world, with its memo and pool cache keyed per world; a failed name lookup falls back to `#id`.
- **Character ids are unique only per world** (each world has its own characters database). Consumers key a character by `(worldId, id)`, never by `id` alone. The Redis presence keys are per world too (#556): `presence:world:{worldId}:character:{id}` (`CacheKeys.CharacterPresenceIndex(worldId, id)`), written by each world server with its own world id. One character's presence is `GET /world/{worldId}/observability/character/{id}` (`WorldObservabilityController`, `[WorldScoped]`, GameMaster), which reads only that world's keys and refuses an index entry naming another world. `GET /observability/online` and `GET /observability/instance/{instanceId}` stay cross-world: they read each permitted world's own snapshot, and instance ids are GUIDs (`Guid.NewGuid()` in `MapInstance`), so they cannot collide across worlds.
- The world servers are unchanged: each serves one world with its singular pair.

## World Simulation

`WorldServer` is an `IHostedService` that runs the tick loop at ~60 Hz (16.67ms intervals). On each tick it calls `World.Update(deltaTime)`, which ticks all active `MapInstance` objects via `IInstanceRegistry`.

**Two-pass tick architecture:** Each tick runs in two passes. Pass 1 — `WorldServer.Update` calls `connection.UpdateSession(deltaTime)` on every connected client, processing pre-character packets (`CMSG_PONG`, character list/select/create/delete) via `WorldSessionFilter`. Pass 2 — `World.Update → MapInstance.Update` calls `connection.UpdateMap(deltaTime)` on every in-map client, processing in-map packets (movement, attack, chat) via `MapSessionFilter`. `LockedQueue.Next(check)` uses peek-first semantics: a packet that fails the first-pass filter stays at the queue head and is picked up by the second pass. Both filter instances are stored on `WorldConnection` and reused each tick — no per-tick allocation.

- **MapInstance** (`Avalon.World/Instances/MapInstance.cs`) is the core simulation unit: manages entities in a flat tick context, runs `InstanceAbilityCastSystem`, creature AI scripts, broadcasts state to clients. Implements `ISimulationContext`. Holds a single `MapNavigator` (combined navmesh) and the `ChunkLayout` that produced it.
- **InstanceRegistry** (`Avalon.World/Instances/InstanceRegistry.cs`) owns all live instances. `GetOrCreateTownInstanceAsync` returns a shared persistent instance; `GetOrCreateNormalInstanceAsync` returns per-player instances with 15-min re-entry windows. `ProcessExpiredInstances` cleans up expired normal instances. Both creators dispatch to `ChunkLayoutInstanceFactory.BuildAsync` for actual instance construction. A build runs on the thread pool and the instance is registered only once it finishes, so each creator keeps its build in flight in a `Lazy<Task>` keyed by map (towns) or by character and map (normals): a caller arriving mid-build awaits that build instead of starting a second copy (#442). The entry is removed in a `finally` after registration, so a failed build is retried by the next caller rather than cached.
- **ChunkLayoutInstanceFactory** (`Avalon.World/ChunkLayouts/IChunkLayoutInstanceFactory.cs`) — single entry point that builds both town and procedural instances. `IChunkLayoutSourceResolver` picks `PredefinedChunkLayoutSource` (DB-backed `MapChunkPlacement` rows for towns) or `ProceduralChunkLayoutSource` (RNG + `ProceduralMapConfig`) per `MapType`. `ChunkLayoutNavmeshBuilder` stitches chunk objs → DotRecast bake → `MapNavigator`. Server emits `SChunkLayoutPacket` to clients on instance enter; client `ClientMapNavigator` bakes the same navmesh from the same chunk objs (deterministic mirror) for prediction parity. See `docs/map-generation.md` for the full pipeline.
- **Creature placement has two paths, and both run from `BuildAsync`.** `CreaturePlacementService.PlaceAsync` rolls a `SpawnTable` against chunk spawn slots and is procedural-only, because it needs a `ProceduralMapConfig` and slots. `PlaceAuthoredAsync` reads `MapCreatureSpawn` rows — hand-placed creature, map, offset from the map's entry spawn point, facing — and runs for every layout kind; it is the only path that puts a creature in a town. Offsets, not world coordinates: a town's coordinates fall out of its `MapChunkPlacement` rows and the cell size. `OffsetY` only centres the navmesh search box, and `SampleGroundHeight` decides the real height. Both paths wrap each creature in its own try/catch — placement runs inside `MapInstance` construction, so a throw would make the map unenterable for everyone.
- **Town NPCs are creatures.** Templates 1-3 (Uriel, Borin Stoutbeard, Innkeeper), 11 (Marta Ledgerwell, the banker, #463) and 12-14 (Garrick Emberforge, Hilde Brassbuckle and Tobin Marrowfield, the vendors, #432) are placed on map 1 by `MapCreatureSpawns`, carry `Invulnerable = true`, and run `TownNpcScript`. Each has a dialogue root (`DialogueNodes`, seeded in `WorldDbContext`), so a player can talk to them (#431, closed): `CMSG_INTERACT` (accepted by `MapSessionFilter`) reaches `InteractHandler`, which checks the target is a live creature in the instance, has a dialogue root and is within 5 m, then sends `SMSG_DIALOGUE_NODE`; `CMSG_DIALOGUE_CHOOSE` advances through `DialogueChooseHandler` and `SMSG_DIALOGUE_END` closes it. A rejected interact is a silent drop — a monster's interact gets no reply. `DialogueChooseHandler` drops most rejected choices silently too, but closes the window with `SMSG_DIALOGUE_END` when the NPC is gone or dead, the open node does not belong to it, or an option leads to an unknown node; it also sends it as the ordinary close when the chosen option ends the conversation. **Every choose re-checks range against the dialogue leash (#492)**: `NpcInteraction.IsWithinLeash`, `LeashRange = 15f`, inclusive, NaN counted as out of range. Past it the handler ends the conversation (clears `CurrentDialogue`, sends `SMSG_DIALOGUE_END`) and advances nothing. It is deliberately not the 5 m interact range, which still gates opening a conversation, because stepping back a metre mid-sentence must not close the window. It is checked only on choose, never on the tick. **Any handler that acts on an open NPC conversation must pass the same check** (a vendor, quest, payment or item effect, #432): `CurrentDialogue` lives until the connection leaves the instance, so an unchecked effect would work from anywhere on the map. A client must not re-check range itself; the server decides whether a conversation is open. Dialogue text lives in `IDialogueCatalog` and `ILocalizedTextCatalog` on `StaticData`, read in memory on the tick. Interacting with a different NPC mid-conversation always ends the old conversation out loud first (`SMSG_DIALOGUE_END` for the old NPC, then the new node); interacting with the same NPC again restarts at its root, and ends the old conversation out loud only when it had the bank or a shop open. A dialogue option can also carry an action (`DialogueOption.Action`, #463), indexed by `DialogueActions` on `StaticData` (rebuilt by `/reload dialogue`) and deliberately not on the World.Public `DialogueOptionView`, so the modding API cannot read or invent one: `DialogueChooseHandler` runs it after the leash check and only on an option that keeps the conversation open, so an `OpenBank` on an option that ends the conversation (or leads to an unknown node) opens nothing. The actions are `OpenBank` and `OpenShop` (#432, stored as 0 and 1, append-only). Each option on the wire carries `Kind` (`SDialogueOptionInfo` field 3): the action choosing it will actually run, or `Conversation` when it runs none, so a client can hide what it has not built; `DialogueOptionKinds` holds the rule for both handlers (#522). A creature whose dialogue offers `OpenBank` anywhere is a banker (`NpcInteraction.IsBanker`), and one that offers `OpenShop` anywhere is a vendor (`NpcInteraction.IsVendor`). `NpcInteraction.EndConversation` is the one way a conversation ends out loud; despawn clears it silently, because the client is gone. It calls `CharacterEntity.CloseNpcWindows()`, which closes the bank and the shop together. There is no quest interaction yet (#433).
- **`ObjectState.CanInteract` (field 20) tells a client whom it can talk to (#489).** It means "interacting with this will do something", so a client can offer an interact prompt without guessing. It is "the template has a dialogue root". A banker and a vendor are both reached through their dialogue, so neither changed it. The rule is one function, `NpcInteraction` (`Avalon.World/Dialogue/`): `InteractHandler` uses it to find the root it opens, and `CreatureSpawner.Spawn` uses it, over `world.Data.Dialogue` read once per call, to fix `Creature.CanInteract` at spawn — so the prompt the client shows and the interact the server accepts cannot drift apart. The value lives on the World-side `Creature`, init-only and deliberately not on `ICreature`, so no mod can make a creature advertise an interaction. `ObjectStateWriter.From(ICreature)` sends it on every creature state whatever is marked changed, like `CreatureMetadataId` and `Name`, and only as `true`: a monster leaves it out, and characters, portals and spells never carry it, so absent means false. It is fixed at spawn, so `/reload dialogue` reaches only creatures spawned afterwards; one already standing keeps the flag it spawned with, while `InteractHandler` still answers from the current catalog. Creatures never respawn and the town instance persists, so after a `/reload dialogue` a town NPC's flag stays stale until the server restarts. Any `ICreature` that is not the World-side `Creature` never advertises the flag: that fails safe, and the handler stays authoritative.
- **Every script resolvable by name must construct from `(creature, instance)` alone.** `AttachScript` builds it with `ActivatorUtilities.CreateInstance(sp, type, creature, instance)` — exactly two runtime arguments, anything else resolved from DI; a constructor wanting a plain `float` or array throws, and the throw is swallowed so the creature silently has no script. `ILoggerFactory` is fine (`AggroDefendScript` takes one). `AiScriptConstructibilityShould` builds every nameable script that way through the real World container. A component another script builds and chains with extra arguments (`CreatureRangeDetectorScript`, chained by `AggroDefendScript`) is marked `[ChainedScript]` (`Avalon.World.Public/Scripts`), and `ScriptManager` does not register it by name. `CreatureIdleScript` is gone (#437); use `TownNpcScript` for a passive creature.
- **Patrol paths are data, authored spawns only.** A `CreaturePath` (table `CreaturePaths`) holds ordered `CreaturePathPoint`s (`CreaturePathPoints`, keyed `(PathId, Sequence)`), each an offset from the map's entry spawn point plus a `WaitMs`; `MapCreatureSpawn.PathId` (nullable, shareable between spawns) names one. `PlaceAuthoredAsync` sets each point's height from the navmesh like the spawn itself (`SampleGroundHeight`; X and Z stay as authored) and sets `ICreature.PatrolPath` before attaching the script. `CreaturePatrolScript` walks it in a loop, standing at each point for its wait. **A patrolling creature fights, then resumes (#600):** the patrol chains a `CreatureCombatScript`, as `AggroDefendScript` does, and forwards `OnHit`, `Update` and `OnCharacterLeft` to it; a hit starts the fight under the normal combat rules (health, one kill with loot and experience, the leash). While the combat script's `State` is anything but `None` it drives the creature (the patrol stops its leg at the handover and then issues no `MoveTo`, `Stop` or `MoveState`) and the patrol's point and wait do not advance; once it is back to `None` (home after the leash, a lost, dead or unreachable target, or its target leaving), the patrol resumes at the path point nearest the creature and walks on in the path's order, dropping any interrupted wait. A hit that leaves it at 0 health stops the patrol for good. An invulnerable walker never fights: `CombatService` refuses the hit before any script hears of it. The path does not choose the AI: the template's `ScriptName` still does, and only a script reading `PatrolPath` walks it. No path is seeded, and procedural spawns never get one.
- **ISimulationContext** — minimal contract used by AI scripts, spell system, and respawner instead of the old `IChunk`. Exposes `Locomotion` and `MeleeSlots` to scripts.
- **Unit broadcasts go through the unit's own instance (#546); there are no static events.** Swings and cast finishes and interrupts are `ISimulationContext.BroadcastAttackAnimation`/`BroadcastFinishCast`/`BroadcastInterruptedCast` (the cast system calls them through its `IAbilityArena`), each sent only for a unit in that instance. A hit's outcome is reported by the instance's own `CombatService` right after the target's `OnHit` returns, through the World-side `ICombatOutcomes` that `MapInstance` implements: a living character's own `SCharacterDamagePacket` then the instance-wide hit (`CharacterDamaged`), and a creature brought from above 0 to 0 health killed once (`CreatureKilled`: corpse, loot, experience), before the encounter death and the death broadcast. `ICreature` has no `Died`, since the modding API must not grant a kill. A character leaving an instance is `AiScript.OnCharacterLeft`, called by `RemoveCharacter` on that instance's own creature scripts only and forwarded to chained scripts.
- **ICreatureLocomotion** (`Avalon.World.Public/Creatures/`) — the only thing that writes a creature's position. Scripts call `MoveTo` / `Stop` / `Teleport` / `HasArrived` and never touch `Position` themselves. `MapInstance` owns one, registers each creature in `AddCreature`, unregisters in `RemoveCreature`, and ticks it **after** the AI scripts — the scripts choose destinations, the locomotion consumes them, so the order matters and is pinned by a test. Two implementations in `Avalon.World/Creatures/Locomotion/`, selected by `GameConfiguration.CreatureLocomotion`: `WaypointLocomotion` (default; walks a navmesh path with no awareness of other agents) and `CrowdLocomotion` (DotRecast `DtCrowd`; agents steer around one another, and around players when `CrowdIncludesPlayers` is set). `Crowd` falls back to `Waypoint` with a warning on a map with no baked navmesh.
- **MeleeSlots** (`Avalon.World/Creatures/MeleeSlots.cs`) — hands each attacker a distinct standing position on a ring around its target so chasers surround rather than stack. Claims are keyed by target, world-fixed in angle (not facing-relative, which would churn every time the player turns), and handed out nearest the claimant's bearing. Attackers beyond `MeleeSlotCount` get no slot and stand off at attack range along their own bearing.
- **`CreatureCombatScript` gives up** and runs home at full health (slot released, target dropped) when a character target dies, the target leaves the instance, the creature is more than 40 m from where the fight began (its home, which may be any position, the origin included), or it has had no way to reach the target for more than 5 s in a row (#606: out of attack range while `ICreatureLocomotion.ResolvedDestination`, where its route really ends, is null or ends farther than attack range plus arrival tolerance from the target (a settled creature out of range re-plans every tick, so the route judged is fresh); never `HasArrived`, which flips while a creature stands at the end of a partial route; the count restarts on a tick that can reach and on a change of target). On the way home it ignores hits entirely (owner decision, #606; how, below under #610).
- **InstanceAbilityCastSystem** (`Avalon.World/Abilities/`, one per `MapInstance`) runs casts: `QueueAbility` for a cast-time cast, `RunInstant` for an instant one, and ticks the unfinished ability scripts (projectiles). The one power rule is `AbilityCost` (#521): the handler checks it and the cast system checks it again and pays it on both paths, only once the cast is accepted (for a queued cast, once its script is built and the queue has taken it), so a refused cast spends nothing. A character leaving an instance (`MapInstance.RemoveCharacter`) has its queued casts interrupted (`CancelCasts`) and its still-running scripts dropped (`CancelScriptsOf`, #541), so a projectile in flight never lands for a caster who is gone: no damage, threat, credit or loot; it leaves the next tick's world objects, so every watcher gets one remove. A script whose `Prepare` or `Update` throws is contained (#530): logged at Error with the ability and caster, dropped (a projectile gets its remove the same way), and its caster sent the interrupt (`SCharacterInterruptedCastPacket`, broadcast to the instance); the other scripts in that tick still run, and what the cast spent stays spent.
- **`AiScript` hot reload** — `IScriptHotReloader` (`Avalon.World.Scripts.Abstractions`) reloads only `AiScript` types from compiled script assemblies; `World.Update` polls it every `Game:ScriptHotReloadIntervalSeconds` (default 5) and applies the reload on the tick thread. `AbilityScript` types are not hot-reloaded: `ScriptManager` finds them once, at `Load()`.
- **Skills aim; they do not target (#164).** A cast carries an `AbilityAim` captured at cast start: the caster's facing (a Movement skill) or the cursor's ground point (a Cursor skill; `CCastAbilityPacket.GroundPos`, refused as `NoAimPoint` when missing or non-finite). `TargetGuid` is ignored. The ability's `Shape` decides who is affected, through one generic script per shape: `CircleAbilityScript` (on the caster, or on the aim point clamped to `Reach` and pulled back from walls by `RaycastWalkable`), `ConeAbilityScript` (never clipped by walls), and `ProjectileAbilityScript`: a world object (`ObjectType.SpellProjectile`, replicated through the world-state add, update and remove packets like any entity, drawn `HeightOffset` 0.5 m above the ground it flies along) spawned at the caster and flying flat toward the aim point at `ProjectileSpeed` metres per second. Each tick it sweeps its whole step, capped at the `Reach` left and cut by `RaycastWalkable`, so a long tick tunnels through nothing; it ends at `Reach`, at a wall (a caster off the navmesh ends it on the first tick), or on its first qualifying hit, where it stops at the point of its step nearest the unit's centre, while with `Pierce` it hits each unit once and flies on. A finished projectile is never ticked again and stays a world object until its final state (where it stopped, zero velocity) has been taken for a broadcast; `InstanceAbilityCastSystem` removes it on a later update, so a client sees every projectile's add, final update and remove, even one that ended on the tick it was first seen. An instance nobody is in drops its finished projectiles at once (`IAbilityCastSystem.DropFinished`, on `MapInstance.Update`'s empty-instance return), since nobody is there to send them to, so the next player to enter never sees one frozen where it stopped. The shapes ask `IAbilityArena.Hits` (`IHitQuery`, World-side, implemented by `MapInstance` over its characters and creatures) for living units whose body circle (`IUnit.BodyRadius`: `CreatureTemplate.BodyRadius`, characters a fixed 0.5 m) overlaps the shape on X/Z, nearest-first, and each unit is affected at most once per cast (`AbilityEffect`). `Hostility` decides: a creature is hostile to a player unless `Invulnerable`; two players only when both are PvP-flagged and the map is not a town; `Affects = Ally` heals the caster and every player not hostile to it through `ApplyHeal`, which restores health. Heal threat counts the health actually restored, so overheal adds none, and a heal that restores nothing does not add the healer to the encounter (#531). A skill that affects nobody still spends its cost and cooldown. Circles and cones broadcast `SMSG_ABILITY_FIRED` (`SAbilityFiredPacket`: caster, ability, origin, and a circle's centre or a cone's direction); hits arrive as the usual damage packets, and `SCharacterDamagePacket.AbilityId` is filled. A shape script reads the caster's position when it fires (`Prepare`), never in its constructor, because a queued cast's script is built when the cast starts. `AbilityCatalog` (the Abilities reload area) refuses an invalid shape row, or one whose `ThreatMultiplier` or `HealThreatPerHp` is not finite and 0 or more (#529, also a database check), with an error naming it.
- **PvP is a flag on the character row (#164).** `Characters.PvpEnabled` and `PvpOffAt` (UTC; null means no timer) are read World-side through `CharacterEntity` and written only by `PvpToggle` (`Avalon.World/Pvp`), never through the modding API. `CMSG_PVP_TOGGLE` (`MapSessionFilter` entry, `PvpToggleHandler`) and `/pvp` (`PvpCommand`, Player access) both call `PvpToggle.Toggle`: off turns on at once; on with no timer starts `Game:PvpOffDelay` (default 5 min), during which the player stays hostile; on with a timer cancels it. Each is answered with `SMSG_PVP_STATE { Enabled, OffInMs }`, which is also sent when the timer turns the flag off (checked each tick in `MapInstance` against the container's `TimeProvider`) and when a character enters an instance. Every player-on-player hit that deals damage to a living player (`CombatService.ApplyDamage` between two `CharacterEntity`) restarts both players' running timers, and the countdown is re-sent when a hit moves the deadline by more than a second (`PvpToggle.CountdownOwed` against `CharacterEntity.PvpOffAtTold`, World-side and never saved), so the client's countdown is exact; the reset does not re-check the town rule itself, relying on `AbilityEffect` checking `Hostility` first. A timer that ran out while the player was offline is expired on entry, before the state is sent. A dead character may toggle. Towns never allow player hostility whatever the flags. The flag is replicated as `ObjectState.PvpEnabled` on every character state, only as true, and saved with the row by every save (`SaveStateTracker.PvpChanged` marks it).
- **The seeded starter kit** (migrations `SeedStarterSkillKit`, World, and `GrantStarterSkillKit`, Character): three skills per class, ids 200-202 Warrior, 210-212 Wizard, 220-222 Hunter, 230-232 Healer, each with `AllowedClasses` its class and one of the three shape scripts; `CharacterCreateInfos.StartingSpells` grants them, and the Character migration replaced every existing character's abilities with its class's three. The retired abilities 1, 2 and 100-103, and the two scripts they ran, are gone, and their ids are never reused. 232 Mending Circle is the only ally heal. Every kit cost is payable from its class's pool (`ClassPowerType`: Warrior Fury, Wizard and Healer Mana, Hunter Energy). `SeedIntegrityShould` pins it.
- **Every refused `CMSG_CAST_ABILITY` is answered (#512).** `CastAbilityHandler` sends exactly one `SAbilityNotReadyPacket` per refusal, carrying a `CastRejectReason` (`Gcd`, `Cooldown`, `RequiresOutOfCombat`, `RequiresInCombat`, `NotEnoughPower`, `Dead`, `NotOwned`, `InternalError`, `NoAimPoint`, `AlreadyCasting`; `Unknown = 0` is only what a payload without the field decodes as). `OutOfRange`, `TargetNotFound` and `NotFacing` stay in the enum (append-only) but are no longer sent. `CooldownMs` is the time left for `Gcd` and `Cooldown`, rounded up so it is at least 1, and 0 for every other reason. The one silent path is a connection with no character. A cast the cast system refuses (`QueueAbility` or `RunInstantAbility` returning false: a missing script, or one that cannot be built) is `InternalError` and starts no global cooldown. `CombatConfig` is registered with its defaults and not bound from configuration.
- **Casts aim, they do not target (#164).** `CastAbilityHandler` ignores `CCastAbilityPacket.TargetGuid` and does no range or facing check; there is no facing cone any more, and `AbilityInfo.FacingAngle` is never set. At cast start it captures an `AbilityAim`: the caster's facing from its yaw (`AbilityAim.FacingFromYaw`, a non-finite yaw aims along +Z) and, for a `Cursor` skill, the ground point (`GroundPos`, missing or with a non-finite component is `NoAimPoint`). A cast-time cast fires with the aim it started with. A cast while `Spells.IsCasting` is `AlreadyCasting` (#521). Scripts are `AbilityScript(IAbility, IUnit caster, AbilityAim aim)` and are built by `InstanceAbilityCastSystem` with `ActivatorUtilities.CreateInstance(sp, type, ability, caster, aim, arena)`, where the arena is the `MapInstance` as `IAbilityArena` (World-side, not the modding API). **One power rule on both paths (#521):** `AbilityCost.Check`/`Pay`; a cost above 0 needs a pool the cast spends (Mana, Energy or Fury) holding at least the cost, and `PowerType.None` with a cost is `InternalError`. Fury is spent like the others but nothing generates it yet (#526). The cast system sets `Casting` and pays only once the queue took the cast, builds a queued cast's script when it is queued, before paying (a script that is missing or cannot be built is refused and costs nothing, and the prebuilt script fires at completion with the aim captured at cast start), drops a cast whose caster died before it completed (clearing `Casting`, and broadcasting the interrupt, so every client's cast bar for it ends, #530), removes finished and interrupted casts after the loop, and keeps only unfinished scripts (projectiles) ticking. `SUnitStartCastPacket` carries the `AbilityId` (#521 item 9).
- **ICorpseRemover** / **CreatureCorpseRemover** — removes a dead creature's corpse from the instance after `ICreatureMetadata.BodyRemoveTimer`. Creatures do not respawn on a timer; the time-based respawn scheduler was removed deliberately.
- **Ground loot (#460)** lives in `Avalon.World/Loot/`. `CreatureTemplate.LootTableId` (nullable) names a `LootTable`; its `LootTableEntry` rows each drop an item or roll another table, exactly one of the two (a check constraint enforces it). Ungrouped entries roll on their own against `Chance` (a percentage); entries sharing a `GroupId` always drop exactly one of them, weighted by `Chance`, so a group that should not drop on every kill belongs in its own table, referenced at the chance it should drop with. `MinGold`/`MaxGold` are **copper** and make one pile. Tables load as the `/reload loot` area into `StaticData.Loot`, a `LootCatalog` that refuses a bad table (a reference cycle, a missing reference, both targets or neither, counts out of order or above 1000, a chance outside 0-100) with an error naming it, and keeps the rest. `MapInstance.CreatureKilled` rolls on the tick (`ILootRoller`), asks `ILootAllocator` for an owner (the only implementation gives everything to the instance owner, free for all after `GameConfiguration.LootGracePeriod`; groups will replace it), places each drop on a ring around the corpse snapped to the navmesh, keeps them in the instance's `GroundLootStore`, and broadcasts `SLootSpawnedPacket`. A character entering an instance gets the drops already there at the start of the instance's next tick, after the map transition packets. Drops are never persisted and never despawn on a timer: they leave when picked up, or when the instance is disposed. `CMSG_LOOT_PICKUP` (`LootPickupHandler`, with its `MapSessionFilter` entry) runs its checks in a fixed order in `LootPickup.TryPickUp` and answers with `SLootPickupResultPacket`; a dead character gets no answer.
- **EntityTrackingSystem** tracks which objects each client sees. `CharacterCharacterGameState` feeds it only what `Interest.IsVisible` accepts (#593). Your own character is always visible. Other characters, creatures and projectiles are added within `Game:InterestRadius` (60 m) and removed beyond it plus `Game:InterestRemoveMargin` (10 m), on X/Z, so an object at the edge doesn't flicker. Leaving view is a remove, and coming back is a fresh add with full state. Loot, chat, PvP state and threat are still instance-wide. **The replication state is World-side (#612)**: `CharacterEntity.CharacterGameState` (a `CharacterCharacterGameState`), not on `ICharacter`, and World.Public has no `ICharacterGameState`, so no mod can drive what a client is told it sees; `MapInstance` replicates only to characters that are `CharacterEntity`. **Changing instance starts replication over (#611).** The client (`AvalonSession`'s world-object table) keeps every object until a remove names it, even across a map transition, so `MapInstance.AddCharacter` resets the arriving character's state (`Reset`, which forgets everything without raising removes) and sends, at once and only when it had any, one `SMSG_WORLD_STATE_REMOVE` naming everything the client knew in the instance left, its own character included; that goes out ahead of the map transition the handler sends next. The first tick in the new instance then adds, in full, the character itself and everything in view there, a character that crossed just before it included. Every move between instances (map entry, respawn at town, a transfer into the instance the character is already in) goes through `World.TransferPlayer` and so through `AddCharacter` (`InstanceTransferReplicationShould`). Portals are not replicated as world objects: a client gets them with the map, in `SChunkLayoutPacket.Portals`.
- **Effect broadcasts are local (#532).** `MapInstance`'s one-shot effect broadcasts (unit hit, start, finish and interrupted cast, ability fired, attack animation, death, revive) go only to connections within `Game:InterestRadius` (default 60 m, X/Z, inclusive) of the effect or involved in it (`EffectAudience`).
- **CreatureStatDeriver** (`Avalon.World/Creatures/`) — turns a creature template plus a rolled level into the stats it spawns with: `CreatureBaseStats` by level, scaled by the template's modifiers and its `CreatureRarity` via `CreatureRarityModifiers`. It lives on `StaticData` (`StaticData.CreatureStats`), and `CreatureSpawner.Spawn` reads it, together with the templates, off `world.Data.Creatures` once per call; before it existed every creature spawned as level 1 with 100 health whatever its template said. `CreatureTemplate.Exp` overrides the derived experience when set — `null` means derive.
- **`/reload <area>`** (`Avalon.World/Chat/ReloadCommand.cs`, game-master only) drives `IReferenceDataReloader` to apply changed dialogue, creature, ability, item, progression, loot, or vendor rows without a restart. Forward-only: `StaticData.PrepareAsync` reads the database and builds a whole `StaticDataPatch` off the tick thread; `ApplyOnNextTickAsync` queues it, and `World.Update` applies every queued patch at the top of `World.Update`, before the map pass and any instance ticks (the session pass — character create/select — runs earlier, in `WorldServer.Update`, so it sees a reload one tick later) — so nothing already spawned or already built is touched, only what gets built afterward. Each area is published as a single immutable `volatile` reference to its patch, because instance construction — and therefore `CreatureSpawner.Spawn` — runs on the thread pool, not the tick thread; a reader that needs more than one creature-area property together must take the `StaticData.Creatures` snapshot once rather than chain two property reads, or a reload landing in between could pair a new template with an old deriver. Maps and chunk layouts are excluded: live instances have already baked a navmesh from them, and the client mirrors that bake, so a change needs a restart. Spawn tables and town spawns need no reload of their own — `CreaturePlacementService` reads `ISpawnTableRepository`/`IMapCreatureSpawnRepository` straight from the database on every instance build, never from `StaticData`. `/reload vendors` rebuilds the `VendorCatalog` from `VendorStocks`, validating it against the item templates it reads in the same prepare. On their next vendor pass, the town instances carry each live stock count over by row id, and every open shop hears the new list.
- **The seeded loot** (migration `SeedForestLoot`): hostile templates 4-10 each name their own table (2-8) and a copper range; the town NPCs (1-3) name none. Loot tables are generic, and shared tables are pools. Each creature table rolls a Health Potion and a Mana Potion on their own, then references the pools: table 1 "Forest common", table 9 "Forest weapons" at 2 % (a group of one weapon per class, items 5-8), table 10 "Forest scrolls" at 10 % (a group of three collectible scrolls, items 9-11, which do nothing when used yet), and table 11 "Forest armour" at 100 % (20 Uncommon pieces, items 12-31, one per class in each of five slots, each its own entry at 2 %). So a kill drops at most one weapon and at most one scroll. Item 4, the Rusted Sword, is left as it is (it may become a starting item) and is in no table. Items 5-31 can be sold (no `NoSell`). Every armour piece carries Armor, cloth (Wizard, Healer) below leather (Hunter) below plate (Warrior) in each slot. Potion and common-table chances rise with the creature's rarity; the pool references are the same for every creature. `SeedIntegrityShould` pins all of it.
- `CreatureTemplate.Invulnerable` **is** read — `CreatureSpawner` copies it onto the creature and `CombatService.ApplyDamageCore` returns early on it, ahead of `ResolveOrSpawn`, so an invulnerable target also creates no encounter and does not combat-tag its attacker.
- **A creature walking home ignores hits entirely (#610).** Once its `CreatureCombatScript` is `Returning` (after the leash or a lost target), `ApplyDamageCore` returns early beside the invulnerable and corpse checks: no encounter, no threat, no `OnHit`, no broadcast, no combat tag, and `ApplyHeal` gives it no heal threat (splitting it across the hostiles still fighting), so nothing from the walk home outlives the reset at home. It asks `IReturningHome` (`Avalon.World/Scripts/Creatures`), internal and read-only: `CreatureCombatScript` answers it, and a script that chains one (`AggroDefendScript`, `CreaturePatrolScript`) must forward it, or its creature takes hits on the way home. Being internal, no mod or script can declare it directly, so none can make a creature unhittable on its own; a subclass of `CreatureCombatScript` (hot-reloaded or not) inherits it, with its behaviour. `ApplyTaunt` and `EnterCombat` do nothing on a returning creature either (#614). **Home and reset, a creature leaves its encounter** (#614): `ResetToIdleAtSpawn`, the one place `Returning` goes back to `None`, clears the creature's taunt (`TauntedBy`, `TauntExpiresAt`) and calls `IHostileEncounterExit.DropHostileFromEncounter` (`Avalon.World/Combat`, internal, implemented by `CombatService` and deliberately not on the modding API's `ICombatService`, where a mod could call it every tick to keep a creature from ever holding threat), which removes the creature and its threat list (`Encounter.RemoveHostile`) and leaves the players in the encounter with their threat on every other hostile; an encounter left with no hostile ends after its grace, as after a kill. So no threat from before the leash, not even a seed from a player it swung at, and no old taunter steers its next fight. **Combat runs on the container's clock** (#610, #614): `CreatureCombatScript` times taunts by `TimeProvider` (an optional constructor parameter, resolved from DI by `AttachScript` and passed down by the chaining scripts), and `MapInstance` hands its own `TimeProvider` to `EncounterRegistry` (and so every `Encounter`: last damage and the end grace), `CombatService` (a taunt's end) and `ThreatBroadcastService` (the broadcast throttle), and uses the same clock for `LastEmptyAt` (instance expiry). `CharacterEntity` takes the container's `TimeProvider` (an optional constructor parameter, passed by `CharacterSelectHandler`) for the combat tag (`MarkCombat`/`IsInCombat`, so `RequiresOutOfCombat` and in-combat regen) and the cast-regen suppression. Threat decay itself runs on the tick's delta.
- Deliberately still unread on `CreatureTemplate`: `ArmorModifier` (no mitigation step exists in `CombatService.ApplyDamage`), `ManaModifier` (creatures cannot cast), `RegenHealth`, `BaseAttackTime` (cadence is `CreatureCombatScript.AttackCooldown`), and `RespawnTimerSecs`. Do not assume any of them work.

**Two contracts worth knowing before touching creature movement or AI scripts:**
- The calling script owns the *moving* `MoveState` and `Speed`; a locomotion writes `MoveState` only when a creature comes to rest, setting `Idle` and zeroing `Velocity`. A locomotion that writes a moving value stomps the script every tick.
- `HasArrived` means "no further destination", which includes *no destination was reachable*. Treating it as "arrived successfully" turns a pathing failure into a silent success.
- `Velocity` is metres per second in both locomotions, the same as a character's, and zero at rest (#424). The client extrapolates by `position + Velocity * secondsSinceUpdate`, so a bare unit direction would move every creature at 1 m/s between broadcasts. `LocomotionVelocityUnitsShould` pins it for both. The same rule holds for every `IWorldObject.Velocity` writer — characters publish the step `PlayerInputHandler` actually took (zero against a wall, zero once dead), a projectile its flight speed (`ProjectileSpeed`) — and the rule is listed per writer on that property.

## Inventory, Gold and Character Saves

- **Everything a player owns lives in the Character DB**: `Character.Money` (the character's gold balance, in copper, a `ulong`), `ItemInstance`, and `CharacterInventory`, whose `ItemId` is a real FK to `ItemInstance` (cascade). `ItemInstance.CharacterId` is a real FK to `Characters` (cascade), so the hard delete in `CharacterDeleteHandler` takes the character's items with it, as it already did its slots. The World DB holds reference data only; `ItemInstance.TemplateId` points into it with no FK, and the REST API looks templates up with `IItemTemplateRepository.GetByIdsAsync`. Item ids come from `IItemIdAllocator` (`Guid.CreateVersion7()`), never from EF or the database (`ValueGeneratedNever`).
- **Memory is authoritative.** Change items only through `IInventoryService` and money only through `IWallet`, both from `ICharacterEconomy` in `Avalon.World/Inventory`. `ICharacterInventory` in World.Public is read-only apart from `Load`, which replaces a container's whole contents at character select and marks nothing. Tick thread only, all or nothing: adds fill existing Bag stacks, then the lowest free Bag slots, never Equipment or Bank; removal by template takes the highest Bag slot first. `IWallet.TryAddMoney` refuses past `Game:MaxMoney` and never wraps. A vendor trade goes through `ICharacterEconomy.VendorOf` (`VendorTrade`), which asks the pure `VendorRules` and applies the plan through these same two services.
- Each successful change marks `CharacterEntity.SaveState` (`New`/`Changed`/`Removed` per item and per slot, plus a money-dirty flag) and `CharacterEntity.ClientChanges`. **Writing a `CharacterInventoryContainer` directly, or calling `ICharacterInventory.Load` after select, skips both: the change is neither saved nor sent.** Character creation is not a save: `CharacterCreateHandler` writes the starting items and slots directly through `IItemInstanceRepository` and `ICharacterInventoryRepository`, because no entity exists yet.
- **Saves go through `ICharacterSaver`**: one Character-DB transaction (`ICharacterSaveRepository`) with the whole row plus only the non-`Unchanged` items and slots, and the character's `CharacterStats` row when its derived stats changed since the last save (`SaveState.StatsDirty`), as idempotent upserts and deletes. `CharacterSaver` chains saves per `CharacterId`, not per entity, so a relog's saves still queue behind the previous session's despawn save; `WhenIdle(id)` completes once every save queued for that character so far has finished, committed or failed, and `CharacterSelectHandler` waits on it (up to `SaveWaitLimit`, 5 s) before loading the character. **A select whose wait runs out reads nothing**: it logs a warning and cancels the select (`CancelSelect`), and the client can select again. Reading anyway would load the state from before the save still running, and the new session's first save would write it back over the committed one. `WhenAllIdle()` is the same for every character at once: `WorldServer.OnStoppingAsync` awaits it last, because a tick starts each despawn without waiting for it, so a despawn save begun on an earlier tick can still be writing when the host stops. That wait is bounded by the host's stop token and `WorldServer.SaveDrainLimit` (20 s), and logs an error if it gives up. Marks are acknowledged only when the commit's continuation runs on the tick thread; a failed save keeps them for the next one. The task a save returns never faults (it is `false` on failure), but the multi-character `Save(list)` throws `ArgumentException` synchronously, before queuing anything, if it names a character twice or one item under two characters.
- **One world session per account (#465, #474).** Two copies of a character would each hold their own inventory and money, and whichever saved last would write over the other, losing or duplicating items and gold; and the owner's rule is one character in the world per account. The auth server's `Online` flag cannot prevent it (a dropped auth connection clears it while the world session stays up), and the `inWorld` mutex only spans world select to key exchange, so the world server enforces it at select. `CharacterSelectHandler` asks `IWorldServer.SessionsOf(accountId, except)` for the account's other connections, which includes closed ones whose despawn the tick has not dequeued yet (a close enqueues its despawn before it leaves `Connections`). **Every one of them is kicked**, whatever it holds (the selected character, a different one, a select still under way, or nothing): the handler cancels its select if one is in progress, calls `World.DeSpawnPlayerAsync` for it right there on the tick, then `NotifyAndClose` with `DisconnectReason.DuplicateLogin` and "Your account has been logged in from another location.". The despawn runs in the handler rather than being left to the close, because a close is only despawned by a later tick, and a `WhenIdle` taken before then finds no logout save to wait on. `DeSpawnPlayerAsync` queues its save before its first await, so the save is already in the chain the new select waits on, and clears `connection.Character` in a `finally`, so the connection ends holding nothing on every path, throw or not, and the despawn the close queues later saves nothing. Its instance steps (lookup, `DropPlayerFromEncounter`, `RemoveCharacter`) are each contained and logged, and the save is queued whatever they did, so a throwing step costs neither the logout save nor the removal of the others; `MapInstance.RemoveCharacter` drops the character from its tick, broadcast and periodic-save membership before it tells its own creatures' scripts (`AiScript.OnCharacterLeft`, each call contained), so a script that throws cannot leave it live. Only a throw while taking the snapshot itself queues nothing. The kicked connection's continuations still run after it lets go: `EnterMapHandler` and `RespawnAtTownHandler` check that the connection still holds the character they started with and otherwise do nothing, and `ProcessContinuations` contains each callback, logging one that throws, so it cannot end the flush for the connections after it. The new select waits, before its first read, on one `Task.WhenAll` bounded by `SaveWaitLimit`: its own character's `WhenIdle`, the `WhenIdle` of every *different* character it kicked (taken after that character's despawn queued its save), and the select step each kicked mid-select connection still had in flight. If the wait runs out it reads nothing, as above. **A kicked select stops at its next step**: every step of the select chain goes through `CharacterSelectHandler.Step`, which records the step's task per connection (a `ConditionalWeakTable`, tick thread only) and runs the next step only if `OwnsSelect` holds, meaning the connection is still up, not closing (`IWorldConnection.IsClosing`, read-only, set the moment `Close` is called), and `SelectStartedTicks` still equals the value that select began with. A select from a closing connection is ignored at `Execute` too: a kicked connection stays `IsConnected` until its outbox flushes, so a select it had queued in the same tick would otherwise kick back the session that kicked it, leaving neither in the world. Cancelling the select (the kick, the chain's own give-up paths, or `CancelExpiredSelects`) or losing the connection therefore stops the chain before its row write, its inventory reads and its `SetPendingSpawn`; the one step already running cannot be called back, which is why the new select waits for it. Other accounts' sessions are never touched.
- The save triggers: entering an instance (`World.SpawnInInstance`, which writes `Online = true`), map entry (`EnterMapHandler`), periodic (`CharacterSaveScheduler`, ticked from `MapInstance.Update`, every `Game:CharacterSaveInterval`, default 5 min, with each character's first save staggered across the interval by its id), and despawn (`SaveOnDespawnAsync`, every logout and disconnect). The despawn snapshot is taken on the tick; a dead logout's move to the respawn town needs a database lookup, so it is applied to the copied row inside the chained write. That lookup reads the World DB while the save writes the Character DB, so `World.MoveToRespawnTownAsync` never lets a failed lookup fail the save: it logs and falls back to town 1's default spawn, or, when map template 1 is not loaded, keeps the map and position the character died at. The select-time row update is still a plain `ICharacterRepository.UpdateAsync`, because nothing is loaded yet. The multi-character `Save(list)` is the one-transaction save for exchanges that must not half-happen (auction house, trade, mail); nothing calls it yet.
- **Client:** `SInventorySnapshotPacket` carries `Money` at login, and never the Bank. `SInventoryUpdatePacket` (`SMSG_INVENTORY_UPDATE`) carries absolute `{Container, Slot, Item?}` entries plus an optional `Money`, built at most once per tick per connection by `InventoryUpdateFlusher` in `WorldServer.Update`, after both passes. **Bank slots are sent only while the bank is open** (`BankAccess.IsOpen`): `InventoryClientChanges` records them like any slot, and the flusher drops them when it is closed. The client-to-server packets that change inventory are `CMSG_LOOT_PICKUP` (#460), `CMSG_ITEM_MOVE` and `CMSG_ITEM_DESTROY` (#463), and the three vendor requests (#432).
- **Item requests (#463).** `CMSG_ITEM_MOVE` (`0x2080`) and `CMSG_ITEM_DESTROY` (`0x2081`), both accepted by `MapSessionFilter`, address slots only (containers cross as numbers, 0 Equipment, 1 Bag, 2 Bank; never item ids), and each gets exactly one `SMSG_ITEM_RESULT` (`0x3090`): an `ItemRequestResult`, and on a refusal only, the current state of the slots it named (a Bank slot only while the bank is open). `InventoryMove` (`Avalon.World/Inventory`) is the pure rule table: from the two slots and the count the server derives Move, Split, Merge or Swap, checks equipment (slot, level, class, two-hander against the off hand) and the Bank, and changes nothing. Two whole copies of a non-stackable item swap rather than merge; no stack (count above 1), split or merge ever goes into Equipment (`NotStackable`); an item whose template is gone (a reload removed it) stacks to 1 and can be moved within the Bag and the Bank, taken off, and destroyed, but never equipped. `IInventoryService.TryMove`/`TryDestroy` apply its decision with the usual `SaveState`/`ClientChanges` marks; a split's new id comes from `IItemIdAllocator`. A dead character gets `Dead`; a handler exception is logged and answered `NotFound`.
- **Equipment slots** (`EquipmentSlots`, the one mapping): 0 Head, 1 Neck, 2 Shoulder, 3 Chest, 4 Hands, 5 Legs, 6 Feet, 7 and 8 Finger, 9 MainHand, 10 OffHand; 11-13 are reserved and every request naming one is refused. This is not `ItemSlotType`'s numbering (its `Gem` is 8, and a gem is never worn). Nothing starts in Equipment: creation puts every starting item in the Bag.
- **The bank.** Usable only at a banker, in an open conversation with it in which its `OpenBank` option was chosen, inside the dialogue leash. `BankAccess.TryUse` checks all of that on every request that touches the Bank, and ends the conversation when the banker is gone, dead, no longer a banker or past the leash. `CharacterEntity.OpenBankNpc` remembers who opened it, and the bank is open exactly while `CurrentDialogue` is still a conversation with that NPC, so every way a conversation ends closes it: talking to another NPC (`InteractHandler`), an instance transfer (`World.TransferPlayer`, which ends the conversation because the NPC stays behind), and despawn (`LeaveInstance` clears both). The first two send `SMSG_DIALOGUE_END`, the client's cue to hide the window. Opening sends every Bank slot in one `SInventoryUpdatePacket`, the only time the whole bank is sent.
- **Vendors (#432).** Stock is World DB data.
  - **Tables.** `VendorStocks` holds one row per line: creature template, `Sequence`, item, optional `MaxStock` + `RestockSeconds`, optional `PriceOverride`, and an optional quest requirement. `VendorStockCosts` holds the item costs per unit bought. Check constraints pair the optional columns both ways (both set or both null), and `(CreatureTemplateId, Sequence)` is unique.
  - **Catalog.** `VendorCatalog` (the Vendors reload area, `StaticData.Vendors`) validates every row. A bad row is refused with an error naming it, and the vendor still sells its other rows. Beyond the schema's pairings it refuses a missing item, a zero `MaxStock`, `RestockSeconds` or cost count, a cost on a missing item or one named twice, a `Sequence` the vendor already uses (the lower `Id` wins), and **a row whose effective price (`PriceOverride ?? BuyPrice`) is below the item's `SellPrice`**, because buying and selling it back would make gold. `VendorRules.UnitPrice` also floors the price at `SellPrice` at runtime, so the rule still holds after a `/reload items` changes a price.
  - **Live stock.** A `VendorStockState` per vendor creature holds the counts and restock timers, in a `VendorStocks` table on the town `MapInstance`. The instance reaches it through `IVendorHost` (not `IMapInstance`, the modding API). A state is created full the first time a shop opens there, and is reset only by a restart. `VendorStockState.Take` throws past the stock and on a limited row the state does not track, so a caller resolves its row from the state's own `Rows`.
    - The restock timer starts when a sale takes a full row below its maximum, and refills the row when it is due. Time is absolute (`TimeProvider`), so an instance that did not tick catches up. A reload clamps each count to the new `MaxStock`; a reload that raises `MaxStock` leaves the row owed a timer, which the next vendor pass starts, so the row refills without waiting for a sale.
    - `MapInstance.Update` runs the vendor pass right after the packet loop, on every tick while `Vendors.Count > 0`, whether or not a shop is open. It reconciles with the catalog, restocks, and sends each connection whose shop is open the one `SMSG_VENDOR_LIST` it is owed (a stock change, a restock, a reload, or its own buyback). It then clears the change marks, and allocates nothing when nothing changed.
  - **Opening and closing.** The shop opens through the dialogue option action `OpenShop`, which sends the list, and it mirrors the bank exactly. `CharacterEntity.OpenShopNpc` records the NPC, `ShopAccess.IsOpen` means the conversation is still with it, and `ShopAccess.TryUse` re-checks the stock host, the NPC, alive, still a vendor, and the leash on every request, ending the conversation out loud when any fails. Every way a conversation ends closes it (`CloseNpcWindows`, which clears the bank and the shop together).
  - **Requests.** `CMSG_VENDOR_BUY` (`0x2090`), `CMSG_VENDOR_SELL` (`0x2091`) and `CMSG_VENDOR_BUYBACK` (`0x2092`), all accepted by `MapSessionFilter`, each get exactly one `SMSG_VENDOR_RESULT` (`0x30A1`) with a `VendorResult`. Gold and items leave in the tick's `SMSG_INVENTORY_UPDATE`.
    - **Buy** checks, in order: alive, open, row and quest gate, count (at most `MaxStackSize`), stock, gold, Bag-only cost items, room once the costs are out, unique.
    - **Sell** takes a Bag slot only, and refuses `NoSell`, a `SellPrice` of 0, a gone template, a damaged item (`Durability < ItemInstanceDefaults.FullDurability`), a bad count, and the money cap.
    - **Buyback** re-adds the exact instance under its own id (`IInventoryService.TryAddInstance`, so the save upserts it). It refuses a unique item already owned again.
    - A handler exception is logged at Error and answered `NotFound`. A dead character gets `Dead`, and its conversation is left alone. A connection with no character gets no reply at all.
    - **`VendorTrade` is not rolled back.** `VendorRules` checks every step first, and the apply order takes the player's costs, gold or item before anything is given, so a programmer bug can only lose one trade's value, never duplicate it; the handler logs it at Error.
  - **Buyback list.** `CharacterEntity.Buyback` holds the last 10 sales, newest first. It is cleared on despawn (`World.LeaveInstance`) and kept across an instance transfer, because the session goes on. A partial sale keeps a copy with a new id from `IItemIdAllocator` (`IInventoryService.TakeOut`).
  - **Quest gates.** They ask `IQuestProgress`, whose only implementation, `NoQuestProgress`, answers false until #433, so a gated row is hidden and cannot be bought.
  - **Optional parameters.** `StaticData` and `World` take `IVendorStockRepository` as an optional last constructor parameter (an empty catalog without it), and `DialogueChooseHandler` takes `IQuestProgress` the same way. `WorldHostGraphShould` pins that production registers both, so a missing registration cannot silently leave every vendor empty.
  - **Seeds.** Garrick (12) sells the four Common starter weapons (items 32-35). Hilde (13) sells the four starter armour sets (36-55); each chest is limited to 2, restocking every 30 minutes. Tobin (14) sells items 1-3, the forest scrolls 9-11, and the Greater Health Potion (56: 25 gold plus 2 Health Potions, limited to 5, restocking every 10 minutes). Forest gear stays drop-only.
- **Character stats (#463, #434).** `CharacterStatsCalculator` (`Avalon.World/Characters`) derives `DerivedCharacterStats` from the seeded `ClassLevelStat` row (the only base-stat source; the old `CharacterStats.GetBase*` helpers are gone) and the stat pairs of the items worn in a slot that fits them. `CharacterStatsRefresh` runs it at create (level 1, nothing worn), at select (`Refill`: nothing stores current health or power, so a character enters full), after every accepted request that changed Equipment (`KeepShare`: each pool keeps its share, never killing or reviving), and on level-up in `MapInstance.CreatureKilled` (`Refill`, or `KeepShare` when the killer is dead, so a level-up never refills a corpse). Select-time recalculation is also what corrects `CharacterStats` rows written before #463; there is no data migration, so a character that never logs in again keeps its old stored values. `CharacterEntity.ApplyStats` writes `Health`/`Power` (the stored and replicated maximums), the current pools, `Stamina`/`RegenStat`, and a stats mark in `SaveState` that makes the next save upsert the `CharacterStats` row. A class and level with no row keeps the stored maximums and logs a warning. Combat reads none of the attributes, armour or damage values yet, and they are not replicated (#506).

## Chat Commands

Commands live in `Avalon.World/Chat/`. To add a new command:
1. Implement `ICommand` (has `Name`, `Aliases[]`, `ExecuteAsync`).
2. Register as `services.AddSingleton<ICommand, YourCommand>()` in `ServiceExtensions.AddWorldServices`.
3. `CommandDispatcher` resolves all `ICommand` registrations from DI automatically.

`ChatMessageHandler` routes `/`-prefixed messages to `ICommandDispatcher`; unknown commands reply with "Unknown command." Non-slash messages broadcast to the current `MapInstance`.

`ICommand.RequiredAccess` defaults to `AccessLevels.Player`, so a command that declares nothing stays runnable by any logged-in player — `Tournament` and `PTR` included: they are players with exactly the Player permission set, differing only in which worlds they may enter, and the API's Player policy lists them too; `ReloadCommand` is the one exception so far, declaring `AccessLevels.GameMaster`. `CommandDispatcher` checks `RequiredAccess.Allows(connection.AccessLevel)` — a mask test, not an ordinal one, because `AccountAccessLevel` is `[Flags]` and `Tournament`/`PTR` are not above `Admin`, so a `>=` comparison would let either through a `GameMaster` gate. A caller without access gets exactly "Unknown command.", the same as a caller who typed a command that doesn't exist — the dispatcher never reveals which commands are staff-only. `IWorldConnection.AccessLevel` has no setter: `Avalon.World.Public` is the future modding API, and a settable access level there would let a mod promote any player to GM. The server assigns it once, at character-select, through `IAccessLevelAssignable` in `Avalon.World`.

A command that throws is caught by `CommandDispatcher`, logged at Error, and still counts as dispatched — so nobody gets "Unknown command." for it. Only a caller holding the `GameMaster` or `Admin` flag is told, as `Command /<name> failed: <ExceptionType>.` — the type name only; the message and stack stay in the log. Everyone else, `Console` included, gets silence, because an error line would reveal that the command exists and what broke inside it. The catch has to live in the dispatcher: `WorldConnection.ProcessContinuations` logs a faulted continuation and drops its callback, so an exception that escapes leaves the caller with no reply at all.

## ValueObject Pattern

`ValueObject<TPrimitive>` (in `Avalon.Common`) wraps primitives like `AccountId`, `WorldId`, `CharacterId`. Fourteen of them, used across ~217 files.

**They live inside the server and stop at every boundary.** Each edge unwraps them explicitly rather than relying on automatic serialization:

| boundary | how |
|---|---|
| Database | EF `HasConversion`, ~42 registrations across the three DbContexts |
| Protobuf wire | packet contracts declare primitives; handlers pass `.Value` |
| REST JSON | DTOs declare primitives; mappers pass `.Value`. Enforced by `ApiContractShould` |

There is nothing on a value object making it serialize as its primitive automatically — no attribute, no global converter. `Avalon.Common.Converters.ValueObjectJsonConverterFactory` does it, but only for a `JsonSerializerOptions` that registers it, and its only caller is the item-catalog export, which serializes `ItemTemplate` entities directly. Serializing a value object without it yields `{"value":42}`.

The API deliberately registers neither that converter nor an OpenAPI schema transformer, because nothing on its surface is a value object. If a DTO ever needs to expose one, `ApiContractShould` fails and says so — that is the signal to register the converter and flatten the OpenAPI schema, not to delete the test.

## Testing Conventions

- Framework: **xUnit** + **NSubstitute** for mocks.
- Test files are named `<Subject>Should.cs`, methods follow `Should_<verb>_<condition>` or descriptive names.
- No integration test infrastructure (no real Redis/Postgres in unit tests) — all external dependencies are substituted.
- Auth handler tests construct handlers directly via `new CAuthHandler(...)` with `NullLoggerFactory` and `NSubstitute` fakes.
