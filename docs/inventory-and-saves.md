# Inventory, gold, vendors and character saves

Ownership of items and gold, the inventory and wallet services, character saves, one world session per account, Change Character, character names, item requests, equipment, the bank, vendors, character stats and the character sheet.

## Inventory, Gold and Character Saves

- **Everything a player owns lives in the Character DB**: `Character.Gold` (the character's gold balance, a `ulong`; gold is the one currency, #1173, and the column was `Money` until migration `RenameMoneyToGold`), `ItemInstance`, and `CharacterInventory`, whose `ItemId` is a real FK to `ItemInstance` (cascade). `ItemInstance.CharacterId` is a real FK to `Characters` (cascade), so the hard delete of a character (`ICharacterRepository.DeleteForGameplayAsync`, from the `CMSG_CHARACTER_DELETE` handler) takes the character's items with it, as it already did its slots. The World DB holds reference data only; `ItemInstance.TemplateId` points into it with no FK, and the REST API looks templates up with `IItemTemplateRepository.GetByIdsAsync`. Item ids come from `IItemIdAllocator` (`Guid.CreateVersion7()`), never from EF or the database (`ValueGeneratedNever`). Since Character migration `AddItemInstanceModifiers` (#1179) every `ItemInstances` row also carries its `Rarity` (`smallint`, `CK_ItemInstances_Rarity`: 0 to 3) and `ItemLevel` (`smallint`, `CK_ItemInstances_ItemLevel`: above 0), and its modifiers are child rows: `ItemInstanceModifiers` (`Id` `uuid`, from the server like an item id; `ItemInstanceId`, a foreign key to `ItemInstances`, cascade, indexed; `ModifierId` `integer` (widened from `smallint` by migration `WidenModifierIds`, so the catalog never runs out of ids), naming a catalog modifier in the World DB (`ItemModifiers`, [item modifiers](item-modifiers.md)) with no foreign key, as `TemplateId` does; `Ordinal` `smallint`, its place among the item's modifiers, with no unique index, so a reorder saved row by row never trips one) and `ItemInstanceModifierValues` (`ItemInstanceModifierId`, a foreign key to `ItemInstanceModifiers`, cascade, and `Index` `smallint`, the key; `Stat` `smallint`, a `StatType`; `Value` `integer`; `Value2` `integer`, null except on an "adds X to Y" line, its high end, `CK_ItemInstanceModifierValues_Range`). The stat is stored on the value row, so a catalog edit never changes an item that exists. Deleting an item takes its modifiers and their values with it. Since Character migration `AddItemIdentified` (#1179, part C) every `ItemInstances` row also carries `Identified` (`boolean NOT NULL`, no default), held by `CK_ItemInstances_Identified` (`"Rarity" <> 0 OR "Identified"`: a common copy is always identified), and so does every `TradeRecordItems` row (`CK_TradeRecordItems_Identified`, the same rule); the migration filled the rows that existed as identified and then dropped the column's default, so every insert writes the value its entity holds ([identification](#identification-at-the-resonance-workbench-1179)).
- **Memory is authoritative.** Change items only through `IInventoryService` and gold only through `IWallet`, both from `ICharacterEconomy` in `Avalon.World/Inventory` (the inventory service is made once per character and kept on it, `CharacterEntity.EconomyInventory`, so asking for it per request costs nothing; it holds no state of its own and reads the item templates as they are at each call, #883). `ICharacterInventory` in World.Public is read-only apart from `Load`, which replaces a container's whole contents at character select and marks nothing. Tick thread only, all or nothing: adds fill existing Bag stacks, then the lowest free Bag slots, never Equipment or Bank; removal by template takes the highest Bag slot first. `IWallet.TryAddGold` refuses past `Game:MaxGold` and never wraps. A vendor trade goes through `ICharacterEconomy.VendorOf` (`VendorTrade`), which asks the pure `VendorRules` and applies the plan through these same two services. **Locked items and reservations (#1175, [trading](trading.md#locks-and-reservations)):** an item offered in a face-to-face trade stays in the Bag but is locked, and offered gold stays in the balance but is held (`CharacterEntity.Locks`, an `InventoryLocks`, World-side, never saved). Adds never fill a locked stack and removals by template never see it; `TryRemove` of a locked instance is `InventoryRemoveResult.Locked`; `IWallet.TrySpend` spends only the balance less the held gold. While a trade completes, the receiver's destination Bag slots are reserved, so every add but the trade's own (`TryAddInstanceAt`) treats them as taken, and the copies and gold it is about to receive count toward Unique and `Game:MaxGold` (`TryAddGold` included), so loot, a quest reward or a purchase in that window may be refused. Every check asks `InventoryLocks.Any` first, one bool read, so nothing changes or allocates while nothing is offered.
- **Bases and instances (#1179).** Equipment is made of bases (World migration `ReplaceItemsWithBases`, `ItemBaseSeed`). An `ItemTemplate` is `Common` or `Unique` (`ItemRarity` in `Avalon.Common`: `Common` 0, `Magic` 1, `Rare` 2, `Unique` 3; `CK_ItemTemplates_Rarity` allows 0 and 3, since Magic and Rare exist only on a copy), names its `BaseKind` (`ItemBaseKind`, 1-27: plate, leather and cloth in head, shoulders, chest, hands, legs and feet, then sword, mace, staff, bow, shield, caster off-hand, amulet, ring and trinket; null for a consumable or a quest item; `CK_ItemTemplates_BaseKind`), lists no classes, and asks an attribute instead: none, 30 or 45 at base tiers T9, T8 and T7 (required levels 1, 5 and 10; plate, swords and shields Strength; leather and bows Agility; cloth, staves and caster off-hands Intellect), a mace Strength or Intellect (`RequiresAnyAttribute`: at least one set requirement met, `ItemTemplate.MeetsAttributes`); ring and amulet bases ask no attribute, only their tier's level, and come in lines of three tiers, one line per implicit (nine ring lines and seven amulet lines; a drop draws its line, [item modifiers](item-modifiers.md#drops)), and the two trinket bases (150, 151) exist only for the trinket uniques to name. A base carries no stat line: its defence (plate armour, leather evasion, cloth ward; a shield's armour and block, a caster off-hand's ward) and a weapon's damage range and attack time are its **base stats** (#1179, part B2), ranges on the template (`ItemTemplateBaseStats`) within which every copy rolls its own values (`ItemInstanceBaseStats`, [item modifiers](item-modifiers.md#base-stats)); a weapon's template names only the type of its damage (`DamageType`). Every base also links one themed implicit at its tier, which every copy rolls after its base stats ([implicits](item-modifiers.md#implicits)); jewellery and trinket bases have no base stats, only their implicit. The five uniques (58, 64, 65, 66, 67) are seeded with no stat lines and no base stats: each names its base (`ItemTemplates.BaseTemplateId`, set on every Unique template and on no other, `CK_ItemTemplates_BaseTemplate`), and a copy rolls that base's base stats and implicit, then the unique's own modifier, when it drops; only the elite and boss loot tables name them (World migration `SeedUniqueAndBossDrops`, [world simulation](world-simulation.md)), and no vendor or quest does. `ItemTemplateFlags.Unique` (own one copy) is a different thing, set on no base. The `ItemPower` column is gone: a copy's item level replaces it. **A copy carries its own facts:** `InventoryItem` (World.Public) has `Rarity` and `ItemLevel`, read-only, as it has count and flags; a copy made from a template outright (a vendor sale, an item script's add, a quest reward, a pickup of a drop that did not roll, creation) takes the template's rarity, and its required level as item level, at least 1 (`ItemInstanceDefaults.InitialItemLevel`), and rolls its base stats, each uniform within its range in `ItemBaseStat` order, then the modifiers its template links in the current catalog (a base's implicit) as it is made, a unique its base's base stats and implicit (`ItemsPatch.BaseOf`), then its own modifier: `IInventoryService.TryAdd` and `CharacterCreateHandler` make it through `IItemRoller.RollPlain` (`Avalon.World/Loot`, a singleton over `ILootRandom` and `IItemIdAllocator`, which hands out the copy's id and each modifier's id, `NextModifierId`), one modifier per link, ordinals from 0, each value uniform within its line's range. So a vendor's copy, an item script's, a quest reward that is not a base and a starting item each roll their base stats too. A template with neither makes a copy with none, allocating no rows. **A drop's copy is made when it drops** (#1179, [world simulation](world-simulation.md)): the ground drop holds it whole, and `IInventoryService.TryAddRolled` puts exactly that copy (its id, rarity, item level, rare name, base stats and modifier list, count 1, its template's initial durability, never merged) in the lowest free Bag slot outside a trade's reservations, handing its base stats and modifier list to the store and marking them and the item for the next save; it answers `InventoryFull`, `UniqueAlreadyOwned` (as `TryAddInstance` does) or `UnknownTemplate` and changes nothing then, so a refused pickup leaves the drop as it lay. **Whether a copy is identified (#1179, part C)** is stated by every path that makes it (`InventoryItem.Identified`, World.Public, read-only, a positional member with no default, so no path can leave it out): a copy `TryAddRolled` adds (a drop's pickup, a quest reward that rolled) is identified exactly when it is Common (`ItemVisibility.IdentifiedWhenRolled`, the rule the ground shows it by), so a magic, rare or unique drop and a Magic quest reward arrive unidentified; a copy `TryAdd` makes (a vendor purchase, an item script's add, a unique included, a quest reward that is not a base) and every starting item arrive identified. A move, split, buyback, trade, save and reload carry the value unchanged (`InventoryAssembler` reads it, `CharacterSaveSnapshot` writes it, a trade record keeps it); only `IInventoryService.TryIdentify` sets it. **A rare copy's name** is the two words its roll gave it, kept on the copy (`ItemInstances.RareName`, `varchar(32)`, Character migration `AddRareName`; `CK_ItemInstances_RareName` holds it set exactly on a Rare copy) so a change to the word lists never renames an item a player holds; `InventoryItem.RareName` (World.Public, read-only) mirrors it, the save writes it, and a trade record keeps it (`TradeRecordItems.RareName`, held by `CK_TradeRecordItems_RareName` to the same rule). `TryAdd` makes one copy per slot of a template that rolls (it has base-stat ranges or links modifiers), whatever its `MaxStackSize`, since such a copy is one of a kind. **Owned equipment was wiped for base stats** (#1179, part B2, owner, 2026-10-24, as part A's `WipeOwnedEquipment` did): Character migration `WipeOwnedEquipmentForBaseStats`, the first of that part and before `AddItemInstanceBaseStats`, deletes every owned copy of the 79 equipment templates of the time (the 74 bases and 5 uniques: 5-8, 12-26, 32-50, 58 and 64-103, written out in the migration), in bags, banks and worn slots, its slot rows, modifiers and their values going by cascade; consumables, scrolls and quest items stay, and trade records keep naming the wiped copies as history. Its Down restores nothing. So no copy made before base stats existed is converted, and part B's backfill of implicits on owned copies (`AddImplicitsToOwnedItems`) is history. A later item patch keeps owned copies' rolled values and rescales them by a migration only when it needs to; this part wiped instead because it changed the item model under every copy. **Rolled rows stay World-side:** `ItemModifierStore` (`CharacterEntity.ItemModifiers`, one per character, tick thread only, keyed by item id) holds the modifiers and base stats of every item the character's containers hold, an entry for each copy that has either. It is loaded at select (modifiers in ordinal order, values in index order, base stats read from their rows) and otherwise written only by `CharacterInventoryService`, beside the container it changes, so an entry lives exactly as long as its item is held; the modding API never reaches it. In memory a copy's base stats are one value, `ItemBaseStats` (`Avalon.Domain.World`: a nullable number per `ItemBaseStat`, null where the copy has no row, never 0), so they travel by copy through the roll, the store, `CarriedItem`, a save, a trade, the buyback and the stats fold, with no allocation or deep copy, and turn into rows only at load and at write. An item outside every container (taken out for a sale and kept for buyback, or planned into a trade) travels as a `CarriedItem(InventoryItem Item, ItemBaseStats BaseStats, IReadOnlyList<ItemInstanceModifier> Modifiers)`. `ItemInstanceModifier` and `ItemInstanceModifierValue` (`Avalon.Domain.World`) are the one model for memory, saves and the API: the world keeps the objects it loaded, and every save copies them on the tick, each row and each value row of its own (`ItemInstanceModifier.CopyRow`, `ItemInstanceModifierValue.Copy`). An item with modifiers or base stats is one of a kind (`ItemModifierStore.IsOneOfAKind`): it neither splits nor merges, nothing merges into it (`InventoryMove`), and it is sold whole; every base has `MaxStackSize` 1 anyway. The client gets each slot's rarity, item level, modifiers, base stats and whether it is identified as `ItemSlotDto` fields 8, 9, 10, 12 and 13 ([character login flow](character-login-flow.md#sinventorysnapshotpacket)), a trade window as `TradeItemDto` fields 5, 6, 7, 9 and 10, and the REST inventory read as the item's `rarity`, `itemLevel`, `modifiers`, `baseStats` and `identified` ([multi-world API](api-worlds.md#routes)); an unidentified copy's modifiers are its implicit lines only, on every path ([identification](#identification-at-the-resonance-workbench-1179)). **A copy's name** (`ItemNames.Display`, [item modifiers](item-modifiers.md#naming)) is worked out at the copy's first describe in an items generation and held beside its modifiers (`DescribedName`, on its `ItemModifierStore` entry), so describing it again builds nothing: an identified magic copy's prefix and suffix names around its template's, an identified rare copy's stored two words, and null for a common or unique copy, whose template's name is the item's, and for every unidentified copy, whose held name is then neither read nor filled (`ItemModifierStore.Describe`), so the first describe after it is identified works the name out; it goes out as `ItemSlotDto.Name` (field 11), `TradeItemDto.Name` (8) and the REST inventory item's `name`. A drop on the ground sends no name (`LootDropDto` has no name field since #1179, part C): every copy that would have one lies there unidentified.
- Each successful change marks `CharacterEntity.SaveState` (`New`/`Changed`/`Removed` per item and per slot, plus a gold-dirty flag) and `CharacterEntity.ClientChanges`. An item's mark (`SaveMark(State, Version, Modifiers)`) also carries a rolled-rows flag (#1179, still named for the modifiers, which it covers with the base stats): `SaveStateTracker.ItemModifiersChanged` marks the item `Changed` (or keeps it `New`) and sets the flag, and every later mark of the item keeps the flag until a save that carried it is acknowledged; `ItemHandedOver` forgets the whole mark, flag and all. `TryAdd` and `TryAddRolled` set it on every copy that rolled base stats or modifiers, so the save that inserts the copy writes them, and `TryAddInstance` (a buyback) for an item with either, because the sale may have been saved since, deleting its rows; a later change to an item's modifiers sets it the same way. **Writing a `CharacterInventoryContainer` directly, or calling `ICharacterInventory.Load` after select, skips both: the change is neither saved nor sent.** Character creation is not a save: `CharacterCreateHandler` builds the character row, its stats (no abilities: a character's come from the talent tree at every select, #1181), its starting items (each made through `IItemRoller.RollPlain`, as any copy is, and identified: its id, its template's rarity and item level, its base stats and the modifiers its template links, inserted with it as its `ItemInstance.BaseStats` and `ItemInstance.Modifiers`; a full stack of a stackable template that rolls neither, one of anything else) and their Bag slots (each `CharacterCreateItems` row names its class's template and Bag slot; a template that no longer exists is skipped with a warning), and `ICharacterRepository.CreateForGameplayAsync` writes them all in one transaction under the account's gameplay guard, with the character-count check, because no entity exists yet.
- **Saves go through `ICharacterSaver`**: one Character-DB transaction (`ICharacterSaveRepository`), under the account's gameplay guard (a save from a session that no longer holds the account's lease is refused, [game server admission](steam-authentication-workloads.md)), with the whole row plus only the non-`Unchanged` items and slots, the rolled rows (modifiers and base stats) of each upserted item whose mark carries the rolled-rows flag (below), and the character's `CharacterStats` row when its derived stats changed since the last save (`SaveState.StatsDirty`), as idempotent upserts and deletes, and the character's `CharacterAuras` rows whenever it holds an aura or one changed (auras; each with its snapshot, the damage type and the caster's crit multiplier bonus included, #1178), all deleted and inserted again, and the character's `CharacterTalents` row of every node the talent tree marked (#1181: each marked node's row deleted, and inserted again while the node is still held, so a retry writes the same rows; [talents](talents.md#saved-talents)). **The rolled-rows write (#1179).** The snapshot (`CharacterSaveSnapshot.Take`, on the tick) adds an item's whole current modifier set, as fresh deep copies, and its base stats, as fresh rows, only when the item is upserted and its mark carries the flag, as the batch's `ItemModifierWrite(Items, Modifiers, Values, BaseStats)`, flat rows; a flagged item the save deletes writes none, its rows going with the item's. The repository, in the save's one transaction, deletes every base-stat row of those items and every modifier of theirs whose id is not in the set (its values by cascade), deletes the value rows of the modifiers in the set, upserts each modifier by id (one query for which exist; update when it does, insert otherwise), and inserts their value rows and the base-stat rows; the one `SaveChanges` orders item, modifier, value and base-stat inserts by foreign key. So a modifier changed, removed or added on an item already saved leaves exactly the current rows, a kept one updated in place under the same id, and the item's base-stat rows are exactly its current base stats. The fence refuses a write naming an item its own batch does not upsert, a modifier or a base-stat row on an item the write does not name and a value row for a modifier the write does not carry; the write itself (`UpsertModifiersAsync`) refuses a modifier id already stored under another item, so a modifier never moves between items. One mark per item keeps an item and its rolled rows in the same save, and a flag or count change never rewrites them. **A batch and its modifier write are single use:** while the write tracks them, EF's fix-up adds the rows to the batch's navigations, and a second write of the same objects would reach them twice, which the repository refuses; the snapshot builds fresh rows for every save. `CharacterSaver` chains saves per `CharacterId`, not per entity, so a relog's saves still queue behind the previous session's despawn save; `WhenIdle(id)` completes once every save queued for that character so far has finished, committed or failed, and `CharacterSelectHandler` waits on it (up to `SaveWaitLimit`, 5 s) before loading the character. **A select whose wait runs out reads nothing**: it logs a warning and cancels the select (`CancelSelect`), and the client can select again. Reading anyway would load the state from before the save still running, and the new session's first save would write it back over the committed one. `WhenAllIdle()` is the same for every character at once: `WorldServer.OnStoppingAsync` awaits it last, because a tick starts each despawn without waiting for it, so a despawn save begun on an earlier tick can still be writing when the host stops. That wait is bounded by the host's stop token and `WorldServer.SaveDrainLimit` (20 s), and logs an error if it gives up. Marks are acknowledged only when the commit's continuation runs on the tick thread; a failed save keeps them for the next one. The task a save returns never faults (it is `false` on failure), but the multi-character `Save(list)` throws `ArgumentException` synchronously, before queuing anything, if it names a character twice or one item under two characters. **Every save write reports an exception from the commit itself, or after it, as `SaveOutcomeUnknownException` (#1175):** `ICharacterSaveRepository.WriteAsync` and `WriteTradeAsync` mark the work done after the one `SaveChanges` and the lease deadline check, and the transaction runner's only step after that is the commit, so such an exception means the write may or may not have committed; any other exception came before the commit and rolled it back. An ordinary save treats it as a failure (`false`, its marks kept for the next save, whose upserts and deletes write the same values again); only a trade tells the two apart. **The trade hold:** while a trade's paired save holds a character (`SaveTrade`, below), its `Save` and `SaveOnDespawnAsync` take no snapshot and are snapshotted and chained only at `ReleaseHold`, its `WhenIdle` completes only after the release and every save the hold kept waiting, and `WhenAllIdle` waits for every hold; with a trade still unsettled at shutdown, the despawn wait and this final wait get only what is left of the `SaveDrainLimit` window ([trading](trading.md#completion-save-first-then-swap)).
- **One world session per account (#465, #474).** Two copies of a character would each hold their own inventory and gold, and whichever saved last would write over the other, losing or duplicating items and gold; and the owner's rule is one character in the world per account. The retained `Accounts.Online` and `OnlineSessionId` columns are not current game-session ownership or presence signals. The game admission holds one session per account (a join ticket is refused while another session's lease is live, unless the client confirms the takeover, and saves are fenced), and the world server also enforces it at select. `CharacterSelectHandler` asks `IWorldServer.SessionsOf(accountId, except)` for the account's other connections, which includes closed ones whose despawn the tick has not dequeued yet (a close enqueues its despawn before it leaves `Connections`). **Every one of them is kicked**, whatever it holds (the selected character, a different one, a select still under way, or nothing): the handler cancels its select if one is in progress, calls `World.DeSpawnPlayerAsync` for it right there on the tick, then `NotifyAndClose` with `DisconnectReason.DuplicateLogin` and "Your account has been logged in from another location.". The despawn runs in the handler rather than being left to the close, because a close is only despawned by a later tick, and a `WhenIdle` taken before then finds no logout save to wait on. `DeSpawnPlayerAsync` queues its save before its first await, so the save is already in the chain the new select waits on, and clears `connection.Character` in a `finally`, so the connection ends holding nothing on every path, throw or not, and the despawn the close queues later saves nothing. Its instance steps (lookup, `DropPlayerFromEncounter`, `RemoveCharacter`) are each contained and logged, and the save is queued whatever they did, so a throwing step costs neither the logout save nor the removal of the others; `MapInstance.RemoveCharacter` drops the character from its tick, broadcast and periodic-save membership before it tells its own creatures' scripts (`AiScript.OnCharacterLeft`, each call contained), so a script that throws cannot leave it live. Only a throw while taking the snapshot itself queues nothing. The kicked connection's continuations still run after it lets go: `EnterMapHandler` and `RespawnAtTownHandler` check that the connection still holds the character they started with and otherwise do nothing, and `ProcessContinuations` contains each callback, logging one that throws, so it cannot end the flush for the connections after it. The new select waits, before its first read, on one `Task.WhenAll` bounded by `SaveWaitLimit`: its own character's `WhenIdle`, the `WhenIdle` of every *different* character it kicked (taken after that character's despawn queued its save), and the select step each kicked mid-select connection still had in flight. If the wait runs out it reads nothing, as above. **A kicked select stops at its next step**: every step of the select chain goes through `CharacterSelectHandler.Step`, which records the step's task per connection (a `ConditionalWeakTable`, tick thread only) and runs the next step only if `OwnsSelect` holds, meaning the connection is still up, not closing (`IWorldConnection.IsClosing`, read-only, set the moment `Close` is called), and `SelectStartedTicks` still equals the value that select began with. A select from a closing connection is ignored at `Execute` too: a kicked connection stays `IsConnected` until its outbox flushes, so a select it had queued in the same tick would otherwise kick back the session that kicked it, leaving neither in the world. Cancelling the select (the kick, the chain's own give-up paths, or `CancelExpiredSelects`) or losing the connection therefore stops the chain before its row write, its inventory reads and its `SetPendingSpawn`; the one step already running cannot be called back, which is why the new select waits for it. Other accounts' sessions are never touched.
- **Change Character (#663).** `CMSG_CHARACTER_LEAVE` (`0x2016`, no fields, `CharacterLeaveHandler`) returns a player in the world to character selection on the same world connection; exactly one `SMSG_CHARACTER_LEAVE_RESULT` (`0x302B`, `CharacterLeaveResult`: `Left` 1, `NoCharacter` 2, `Selecting` 3 during a select or while the character waits on its load report, `AlreadyLeaving` 4; refusals change nothing) answers it, unless the connection is closed instead. The leave is a logout: `IWorld.LeaveWorldAsync` is `DeSpawnPlayerAsync` answering whether the logout save committed, and `Left` is sent only once it has, so the row is offline and a reselect of the character (which waits on `WhenIdle` anyway) reads what was saved. A save that fails, or a leave that throws, is never answered: the connection is closed with `DisconnectReason.CharacterSaveFailed` (5); one that drops or is kicked meanwhile is not answered. From the start of the leave until its answer, `IWorldConnection.LeaveInProgress` (read-only; set through the World-side `ICharacterLeaveControl`, with the target, last input sequence, respawn flag and conversation cleared) makes the list, select, create and delete handlers refuse as they do mid-select, by closing, and a second leave is `AlreadyLeaving` and saves nothing. The leave is accepted by `WorldSessionFilter` alone, whatever the connection holds, never by `MapSessionFilter`: it runs in the session pass, before any instance ticks, and in-map packets queued before it are handled by the map pass first. In-map packets queued behind it, meant for the character that left, would wedge the queue (neither filter accepts them without a character), so the session pass drops an in-map packet (`MapSessionFilter.IsMapPacket`) that reaches the head of the queue while the connection holds no character. A leave in combat is allowed, as a logout is. `docs/character-login-flow.md` has the exchange.
- **Character names (#757, owner decision).** A name is 3 to 12 ASCII letters (`CharacterName` in `Avalon.Domain.Characters`, the one rule), checked as sent, before anything is read or trimmed: `CharacterCreateHandler` answers `NameTooShort`, `NameTooLong` or, for anything else, `NameInvalid` (`SCharacterCreateResult` 8, appended; the full answer order is in `docs/character-login-flow.md`). It is stored, and shown to everyone, in one display form, first letter upper-case and the rest lower-case (`CharacterName.Display`: `kAELA` is `Kaela`). `Characters.NameKey` holds its key, the name with only its ASCII letters upper-cased and nothing trimmed (`CharacterName.Key`; setting `Character.Name` sets it); a unique index (`IX_Characters_NameKey`) makes "Bob" and "bob" one name per world, and a check constraint, `CK_Characters_NameKey` (`"NameKey" = upper("Name" COLLATE "C")` on Postgres, locale-independent and ASCII-only like the .NET fold; plain `upper("Name")` on the SQLite the tests use, which folds ASCII only, the model choosing by provider), holds every writer to it. **The name itself is pinned too (#944):** a second check constraint, `CK_Characters_NameRule`, refuses any row whose name breaks the rule, on insert and on rename alike (`TryRenameAsync` writes the name as given), because whisper, invite and ignore by name refuse anything that is not a name (#936) and could never reach such a row. On Postgres it is `"Name" COLLATE "C" ~ '^[A-Za-z]{3,12}$'` (`CharacterName.Pattern`; the "C" collation keeps the letter ranges ASCII whatever the database's locale, and `$` matches only at the very end, so a trailing newline is refused); on SQLite, which has no regular expressions of its own, `length("Name") BETWEEN 3 AND 12 AND "Name" NOT GLOB '*[^A-Za-z]*'` (GLOB is case-sensitive and compares code points). It pins letters only, not the display case: creation and the REST rename both write `CharacterName.Display`, but the names stored before #757 were left as they were, and only the letters-only form was checked against every live world (2026-10-15, after the one PTR name that broke it, `golfinho2`, was renamed). Its migration, `PinCharacterNameRule`, only adds the constraint, which Postgres checks against every existing row: it fails, and adds nothing, on a database holding a name outside the rule, so a world restored from an older backup needs its offending names renamed first. A typed name is looked up by `CharacterName.LookupKey` (the key of it trimmed), so a dotless i never finds an I: `ICharacterRepository.FindByNameAsync`, the ignore list's offline lookup (`FindCharacterByNameAsync`), `OnlineCharacters` (so `/w` and `/invite`), `Party.FindByName` (`/kick`, `/promote`), `IgnoreList.FindByName` (`/ignore`, `/unignore`) and the self checks (`CharacterName.Same`); in memory the last four compare in place, as the key compares, and make no key (`CharacterName.Same` and `CharacterName.KeyComparer`, #973). **A name changes only by insert or by `ICharacterRepository.TryRenameAsync`:** `Name` and `NameKey` are insert-only to the change tracker (`PropertySaveBehavior.Ignore` after save), so no tracked update (the world's saves, the select-time write, the API's admin patch) ever writes them, and a world holding an older name in memory can neither write it back over a rename nor fail its saves on the unique index. `ICharacter.Name` on World.Public is get-only; `CharacterEntity.Name` (World-side) keeps a setter, which no production path uses. A race to the unique index is recognised only as that violation (`CharacterNameKeyViolation.Is`: SQLSTATE 23505 on `IX_Characters_NameKey` on Postgres, the UNIQUE failure on `Characters.NameKey` on SQLite); anything else is rethrown. A create has no lookup of its own: the index refuses a taken name inside the create's transaction, answered `NameAlreadyExists`. The migration that added the column (`AddCharacterNameKey`) fills it from `upper("Name" COLLATE "C")` before building the index and leaves every existing name as it is (owner guarantee: none breaks the rule or clashes by case); unlike the account username migration, it does not check for clashes. **REST renames** (`PATCH /world/{worldId}/character/{id}`, `CharacterService.UpdateCosmeticAsync` and `UpdateAnyAsync`, owner decision) follow the same rule and display form: a name that breaks it, an empty one included, is a 400 validation error (`CharacterNameRuleAttribute` on `CharacterPatchDto.Name`, the pattern in the OpenAPI schema, and again in the service as a 400 `BusinessException`, `CharacterName.Requirement`); a name another character holds by key is "Name already taken", and so is a rename that loses the race to the index; a character in the world is refused with 409 `CharacterOnlineException` "Character is online; rename it while logged out."; a character deleted between the endpoint's lookup and the rename (`CharacterRename.NotFound`) is 404, `CharacterNotFoundException`, written as MVC's own 404 client-error ProblemDetails, the endpoint's answer for a missing character (owner decision). A name that would not change writes nothing (a character may change the case of its own name), so an admin patch of other fields still applies while it is online. The rename is one conditional statement, `UPDATE ... SET Name, NameKey WHERE Id = @id AND NOT Online` (`TryRenameAsync`): the world marks the row online by writing it, so the row lock orders the two and the rename sees the flag or commits first. A rename landing between a select's read and its spawn (the row not yet online) is accepted; that session shows the old name until its next select, and since the world never writes the name, nothing reverts it.
- The save triggers: entering an instance (`World.SpawnInInstance`, which writes `Online = true`), map entry (`EnterMapHandler`), periodic (`CharacterSaveScheduler`, ticked from `MapInstance.Update`, every `Game:CharacterSaveInterval`, default 5 min, with each character's first save staggered across the interval by its id), and despawn (`SaveOnDespawnAsync`, every logout and disconnect). The despawn snapshot is taken on the tick; a dead logout's move to the respawn town needs a database lookup, so it is applied to the copied row inside the chained write. That lookup reads the World DB while the save writes the Character DB, so `World.MoveToRespawnTownAsync` never lets a failed lookup fail the save: it logs and falls back to town 1's default spawn, or, when map template 1 is not loaded, keeps the map and position the character died at. The select-time row update is `ICharacterRepository.UpdateForGameplayAsync`, under the same guard, not a save, because nothing is loaded yet. The multi-character `Save(list)` is the one-transaction save for exchanges that must not half-happen; nothing calls it with more than one character. **Trades (#1175) save through `ICharacterSaver.SaveTrade`**, the same one-transaction write chained behind both characters' saves, for their paired save: each character is snapshotted with its side of the trade applied (`TradeSaveBatch.Apply`: an outgoing item is never deleted, since a trade changes its owner, #1179: the giver's batch drops its slot row and whatever its snapshot held for the item, row or modifier write; each incoming item is upserted as the receiver's, an update of `CharacterId` when the row exists, with its slot and its whole modifier set; the row is a copy with the gold given and received), and both are written with the trade's `TradeRecord` (and its `TradeRecordItem` rows, each with its own copy of the item's rarity, item level, `Identified` and modifiers) in one transaction (`WriteTradeAsync`), so the record exists exactly when the trade committed. Its task is a `SaveOutcome`: `Committed`, `Refused` (nothing written) or `Unknown` (a `SaveOutcomeUnknownException`: the record is then looked up with `TradeCommittedAsync`, under both accounts' fence locks, within `CharacterSaver.TradeLookupDeadline`, 5 s, and retried until it answers). Memory changes only after a commit (save first, then swap), and the trade holds both characters' other saves until it has applied the outcome (above). The swap's `TakeOut` is followed by `SaveState.ItemHandedOver`, which forgets the giver's whole mark for an item the paired save already wrote as the receiver's, modifiers included, since the fence refuses a save that names an item another character owns. [Trading](trading.md#the-trade-record) has the record's tables, the lookup and how to read the history.
- **Client:** `SInventorySnapshotPacket` carries `Gold` at login, and never the Bank. `SInventoryUpdatePacket` (`SMSG_INVENTORY_UPDATE`) carries absolute `{Container, Slot, Item?}` entries, ordered by container and then by slot, plus an optional `Gold`, built at most once per tick per connection by `InventoryUpdateFlusher` in `WorldServer.Update`, after both passes. An entry's modifiers and base stats (#1179) are taken from a pool on the tick (`ItemModifierDtoPool`: the flush's is `WorldServer`'s, an item request's refusal, the bank snapshot and the select snapshot each use their handler's) and given back once the packet is encoded, which its `Create` does before it returns, so describing held items makes no modifier or base-stat garbage. **Bank slots are sent only while the bank is open** (`BankAccess.IsOpen`): `InventoryClientChanges` records them like any slot, and the flusher drops them when it is closed. The client-to-server packets that change inventory are `CMSG_LOOT_PICKUP` (#460), `CMSG_ITEM_MOVE` and `CMSG_ITEM_DESTROY` (#463), the three vendor requests (#432), `CMSG_QUEST_TURN_IN` and `CMSG_QUEST_ABANDON` (#433), which take quest items and pay rewards, `CMSG_ITEM_USE` (see Item use), which equips gear, takes a worn item off to the Bag, and spends what an item script consumes, `CMSG_ITEM_IDENTIFY` (#1179, [identification](#identification-at-the-resonance-workbench-1179)), which identifies a Bag item, and `CMSG_TRADE_CONFIRM` (#1175, [trading](trading.md)), whose completed trade moves items and gold between two characters.
- **Item requests (#463).** `CMSG_ITEM_MOVE` (`0x2080`) and `CMSG_ITEM_DESTROY` (`0x2081`), both accepted by `MapSessionFilter`, address slots only (a container is the wire enum `InventoryType` of `Avalon.Common`, 0 Equipment, 1 Bag, 2 Bank, declared in the exported schema, #913; never item ids), and each gets exactly one `SMSG_ITEM_RESULT` (`0x3090`): an `ItemRequestResult`, and on a refusal only, the current state of the slots it named (a Bank slot only while the bank is open). A protobuf enum member carries any number, so `SlotRef.TryParse` still checks the container of every request: one that is no member is answered `InvalidSlot` (`CMSG_ITEM_USE`: `NotFound`), while one past 255 does not fit the enum's type (a `byte`, owner decision, #913; the `CharacterInventory.Container` column is a `smallint`), fails the packet's decode and closes the connection, as any payload that cannot be read does. A slot number is a `byte` the same way, on the wire and in the server (no container has 255 slots: Equipment 14, Bag and Bank 30; the `CharacterInventory.Slot` column is a `smallint`, #921): a slot the container does not have is refused where it is read (`InvalidSlot`; `CMSG_ITEM_USE` and `CMSG_VENDOR_SELL`: `NotFound`), and one past 255 fails the decode and closes the connection. `InventoryMove` (`Avalon.World/Inventory`) is the pure rule table: from the two slots and the count the server derives Move, Split, Merge or Swap, checks equipment (an identified item only, #1179: an unidentified one going into Equipment by a move, a swap with the worn item or a two-hander over a worn off hand is `ItemRequestResult.Unidentified` 17, asked right after `NotStackable` and before the level, class and attributes, and through `CMSG_ITEM_USE` `ItemUseResult.Unidentified` 21, so nothing moves; a move to the Bag or the Bank is not asked, so an unidentified item can be banked; slot, level, class, two-hander against the off hand, where `ItemTemplate.IsTwoHanded` counts a two-handed or a ranged weapon, so a bow leaves the off hand empty too, #1179; the class check is `ItemTemplate.AllowsClass`: an empty `AllowedClasses` lets every class wear the item, and an item lists classes only when it is restricted to some of them, #1171; then the attribute requirements, #1178: `RequiredStrength`, `RequiredAgility` and `RequiredIntellect` against the attributes of the character's last stats refresh, gear worn and auras included, so the item a swap takes off still counts, refused as `ItemRequestResult.AttributesTooLow` 15 and through `CMSG_ITEM_USE` as `ItemUseResult.AttributesTooLow` 19; only a move into Equipment is checked, and worn gear whose requirement stops being met keeps working; and, #1179, one worn copy of an `ItemTemplateFlags.UniqueEquipped` template: a move into Equipment while another slot wears a copy is `ItemRequestResult.UniqueEquipped` 16, through `CMSG_ITEM_USE` `ItemUseResult.UniqueEquipped` 20 only when no swap avoids it, since a use of a second copy takes the slot wearing the first and swaps it out ([item use](item-use.md)), while moving the worn copy to another slot or swapping it for another copy is allowed; two copies of any other template may be worn, and `ItemTemplateFlags.Unique` limits owning, not wearing) and the Bank, and changes nothing. Two whole copies of a non-stackable item swap rather than merge; no stack (count above 1), split or merge ever goes into Equipment (`NotStackable`); an item whose template is gone (a reload removed it) stacks to 1 and can be moved within the Bag and the Bank, taken off, and destroyed, but never equipped. `IInventoryService.TryMove`/`TryDestroy` apply its decision with the usual `SaveState`/`ClientChanges` marks; a split's new id comes from `IItemIdAllocator`. A dead character gets `Dead`, and a stunned one `Stunned` (#770) for a move or a destroy that touches Equipment or the Bank (Bag moves and destroying a Bag item still go); a handler exception is logged and answered `NotFound`. A move, split, merge or swap whose source item or target item is offered in a trade, or whose target is a Bag slot a completing trade reserved, and a destroy of an offered item, are `ItemRequestResult.Locked` (14, appended, #1175), checked right after `NotFound`. An accepted move that touches Equipment (an equip or unequip by drag) refreshes the stats and ends the character's [arrival protection](auras.md#arrival-protection-1088), as an equip through `CMSG_ITEM_USE` does.
- **Equipment slots** (`EquipmentSlots`, the one mapping): 0 Head, 1 Neck, 2 Shoulder, 3 Chest, 4 Hands, 5 Legs, 6 Feet, 7 and 8 Finger, 9 MainHand, 10 OffHand, 11 and 12 Trinket (#1179); 13 is reserved and every request naming it is refused. This is not `ItemSlotType`'s numbering (its `Gem` is 8, and a gem is never worn). A neck piece is `ItemSubClass.Amulet` (206, an Armor subclass, #433) with `Slot = Neck`, and a ring `ItemSubClass.Ring` (207, forest content pass) with `Slot = Finger`. #1179 appends `ItemSubClass.Shoulders` (208), `CasterOffHand` (209) and `Trinket` (210), and `ItemSlotType.Trinket` (11): a shield is `ItemClass.Armor`/`Shield` and a caster off-hand `ItemClass.Armor`/`CasterOffHand`, both worn in the off hand, and a trinket goes in either trinket slot. Nothing starts in Equipment: creation puts every starting item in the Bag.
- **The bank.** Usable only at a banker, in an open conversation with it in which its `OpenBank` option was chosen, inside the dialogue leash. `BankAccess.TryUse` checks all of that on every request that touches the Bank, and ends the conversation when the banker is gone, dead, no longer a banker or past the leash. `CharacterEntity.OpenBankNpc` remembers who opened it, and the bank is open exactly while `CurrentDialogue` is still a conversation with that NPC, so every way a conversation ends closes it: talking to another NPC (`InteractHandler`), an instance transfer (`World.TransferPlayer`, which ends the conversation because the NPC stays behind), and despawn (`LeaveInstance` clears both). The first two send `SMSG_DIALOGUE_END`, the client's cue to hide the window. Opening sends every Bank slot in one `SInventoryUpdatePacket`, the only time the whole bank is sent.
- **Vendors (#432).** Stock is World DB data.
  - **Tables.** `VendorStocks` holds one row per line: creature template, `Sequence`, item, optional `MaxStock` + `RestockSeconds`, optional `PriceOverride`, and an optional quest requirement. `VendorStockCosts` holds the item costs per unit bought. Check constraints pair the optional columns both ways (both set or both null), and `(CreatureTemplateId, Sequence)` is unique.
  - **Catalog.** `VendorCatalog` (the Vendors reload area, `StaticData.Vendors`) validates every row. A bad row is refused with an error naming it, and the vendor still sells its other rows. Beyond the schema's pairings it refuses a missing item, a zero `MaxStock`, `RestockSeconds` or cost count, a cost on a missing item or one named twice, a `Sequence` the vendor already uses (the lower `Id` wins), **a row whose effective price (`PriceOverride ?? BuyPrice`) is below the item's `SellPrice`**, because buying and selling it back would make gold, and a row whose item is not `Common` (#1179: a vendor sells commons only; a unique comes only from a drop). A `/reload items` that makes a stocked item Unique without a vendor reload hides its row and refuses a buy of it (`NotFound`, `VendorRules.IsSoldNew`) until `/reload vendors` drops the row, as for one flagged `QuestItem`; buying back a unique sold to the vendor stays allowed. These item rules (`ItemUseRules.VendorStockProblem`) are the ones the API's item edit checks, so an edit making a stocked item a quest item or Unique is refused there. `VendorRules.UnitPrice` also floors the price at `SellPrice` at runtime, so the rule still holds after a `/reload items` changes a price.
  - **Live stock.** A `VendorStockState` per vendor creature holds the counts and restock timers, in a `VendorStocks` table on the town `MapInstance`. The instance reaches it through `IVendorHost` (not `IMapInstance`, the modding API). A state is created full the first time a shop opens there, and is reset only by a restart. `VendorStockState.Take` throws past the stock and on a limited row the state does not track, so a caller resolves its row from the state's own `Rows`.
    - The restock timer starts when a sale takes a full row below its maximum, and refills the row when it is due. Time is absolute (`TimeProvider`), so an instance that did not tick catches up. A reload clamps each count to the new `MaxStock`; a reload that raises `MaxStock` leaves the row owed a timer, which the next vendor pass starts, so the row refills without waiting for a sale.
    - `MapInstance.Update` runs the vendor pass right after the packet loop, on every tick while `Vendors.Count > 0`, whether or not a shop is open. It reconciles with the catalog, restocks, and sends each connection whose shop is open the one `SMSG_VENDOR_LIST` it is owed (a stock change, a restock, a reload, its own buyback, or, #738, a change to which quests it holds or has turned in since its last list: an accept, an abandon or a turn-in, `QuestLog.HeldVersion` against `CharacterEntity.VendorListQuestVersion`, so a turn-in that meets a gate shows the row at once). It then clears the change marks, and allocates nothing when nothing changed.
  - **Opening and closing.** The shop opens through the dialogue option action `OpenShop`, which sends the list, and it mirrors the bank exactly. `CharacterEntity.OpenShopNpc` records the NPC, `ShopAccess.IsOpen` means the conversation is still with it, and `ShopAccess.TryUse` re-checks the stock host, the NPC, alive, still a vendor, and the leash on every request, ending the conversation out loud when any fails. Every way a conversation ends closes it (`CloseNpcWindows`, which clears the bank and the shop together).
  - **Requests.** `CMSG_VENDOR_BUY` (`0x2090`), `CMSG_VENDOR_SELL` (`0x2091`) and `CMSG_VENDOR_BUYBACK` (`0x2092`), all accepted by `MapSessionFilter`, each get exactly one `SMSG_VENDOR_RESULT` (`0x30A1`) with a `VendorResult`. Gold and items leave in the tick's `SMSG_INVENTORY_UPDATE`.
    - **Buy** checks, in order: alive, not stunned (#770), open, row and quest gate, count (at most `MaxStackSize`), stock, gold, Bag-only cost items, room once the costs are out, unique. A trade's locks and reservations (#1175) apply: gold held for a trade pays for nothing, a stack offered in a trade is no cost and no room, a slot a completing trade reserved is no room, and copies it is about to add count toward unique; buyback alike.
    - **Sell** takes a Bag slot only, and refuses an item offered in a trade (`VendorResult.Locked`, 14, #1175), `NoSell`, a `SellPrice` of 0, a gone template, a damaged item (`Durability < ItemInstanceDefaults.FullDurability`), a bad count, and the gold cap (counting gold a completing trade is about to pay). **It pays by the copy's rarity** (#1179): `SellPrice` times `Game:Items:SellFactor` for `InventoryItem.Rarity` (`Magic` 2, `Rare` 4, `Unique` 6 by default, each at least 1, validated at startup; `Common` 1), for an unidentified copy (#1179, part C) times `Game:Items:UnidentifiedSellPercent` (default 50, 0-100, validated at startup) over 100 and rounded down, worked out in 128 bits so it never overflows, then times the count (an unidentified copy is one of a kind, so 1), and the buyback costs exactly what the sale paid. An unidentified item can be sold, and its buyback returns it unidentified. Buy prices and the catalog's price floor are unchanged: a vendor sells only `Common` items, whose factor is 1.
    - **Buyback** re-adds the exact instance under its own id, with its rarity, item level, whether it is identified, base stats and modifiers (`IInventoryService.TryAddInstance` with the sale's `CarriedItem`, so the save upserts it and, when it has base stats or modifiers, writes them again, since a saved sale deleted its rows, #1179). It refuses a unique item already owned again, and answers `NotFound` for an item a `/reload items` has flagged `QuestItem` since it was sold, which the list leaves out too, the other sales keeping their index (#738).
    - A handler exception is logged at Error and answered `NotFound`. A dead character gets `Dead`, and a stunned one `Stunned` (#770, buy, sell and buyback alike, asked before the leash), and either's conversation is left alone. A connection with no character gets no reply at all.
    - **`VendorTrade` is not rolled back.** `VendorRules` checks every step first, and the apply order takes the player's costs, gold or item before anything is given, so a programmer bug can only lose one trade's value, never duplicate it; the handler logs it at Error.
  - **Buyback list.** `CharacterEntity.Buyback` holds the last 10 sales, newest first. It is cleared on despawn (`World.LeaveInstance`) and kept across an instance transfer, because the session goes on. Each entry is a `BuybackEntry(CarriedItem Item, ulong Price)`: a whole-stack sale keeps the instance itself with the modifiers that left the store with it (`IInventoryService.TakeOut`), a partial sale a copy with a new id from `IItemIdAllocator` and no modifiers (an item carrying modifiers is one of a kind: `VendorRules.DecideSell` refuses part of it with `InvalidCount`, and `TakeOut` throws on one, as the move rules refuse to split or merge it).
  - **Quest gates.** They ask `IQuestProgress`; production's `QuestProgress` answers from the character's quest log (Active = held, Completed = turned in, #433); `NoQuestProgress` is only a handler's fallback when built without the container. No seeded row is gated. A gated row whose requirement is not met is hidden and cannot be bought, and no row may sell a `QuestItem` (a row whose item a `/reload items` made one is hidden and refused `NotFound` until `/reload vendors` drops it).
  - **Optional parameters.** `StaticData` and `World` take `IVendorStockRepository` as an optional last constructor parameter (an empty catalog without it), and `DialogueChooseHandler` takes `IQuestProgress` the same way. `WorldHostGraphShould` pins that production registers both, so a missing registration cannot silently leave every vendor empty.
  - **Seeds.** Garrick (12) sells the six T9 weapon and off-hand bases (#1179, rows 32-37: the Ironwood Sword 32, the Oak Mace 35, the Ash Staff 33, the Hunter's Shortbow 34, the Oak Buckler 70 and the Ash Focus 73), unlimited. Hilde (13) sells the 18 T9 armour bases (rows 38-55: plate 36-40 and 76, leather 46-50 and 77, cloth 41-45 and 78, each family in head, chest, legs, hands, feet and shoulders); each chest (37, 47, 42) is limited to 2, restocking every 30 minutes. Tobin (14) sells items 1-3, the forest scrolls 9-11, and the Greater Health Potion (56: 25 gold plus 2 Health Potions, limited to 5, restocking every 10 minutes). The T8 and T7 bases and the jewellery bases are not sold, and no vendor sells a unique.
- **Character stats (#463, #434).** `CharacterStatsCalculator` (`Avalon.Combat`) derives `DerivedCharacterStats` from the seeded `ClassLevelStat` row (the only base-stat source; the old `CharacterStats.GetBase*` helpers are gone) and the items worn in a slot that fits them, each as a `WornItem(Template, BaseStats, Modifiers, DamageType)`: its template's stat pairs, read from the current template, the base stats and modifiers that copy rolled, and the damage type its base gives it (a unique weapon's is its named base's) (#1179, `CharacterEntity.ItemModifiers`, which a template edit never touches, so an edit of a base's ranges reaches only copies made afterwards). Every line of a worn item counts (its template's pairs, then each modifier's values, through `ItemLines`, read by index, allocating nothing; an "adds X to Y" line reads `Min = Value`, `Max = Value2`), and its base stats are read in place, with one rule for what is local to an item: an item's armour is `round((its base Armour + its Armor lines) x max(0, 1 + its LocalIncreasedArmor / 100))`, half away from zero, and the same for evasion and ward, so increased armour on a helmet never scales the chest; a copy's base block chance adds to block unscaled; the main hand's damage range and attack time are its copy's base stats (`WeaponDamage.Of`; with no main hand, or one that rolled no damage above 0, the formula's unarmed range and pace), its added damage by type goes to its `WeaponDamage.Added`, its local increased physical damage scales each end of its physical range and of its added physical damage, and its local attack speed makes its attack time `round(time / (1 + sum / 100))` (a sum of 0 or below is none), all worked out in whole numbers; local lines on any other item add nothing. A base's template carries no defence or damage line (#1179): its defence and its weapon numbers are its copy's base stats, and its implicit is read like any other modifier. Added damage to attacks and to spells sums over every worn item into `AddedToAttacks` and `AddedToSpells` on the attacker, beside the offence block (`DerivedCharacterStats`, `AttackerCombat`; each a `DamageRanges` whose mask names the types that add anything, so a hit reads one byte when none does) ([the skill system](spell-system.md#4-hit-resolution) has the roll order). The fold runs once per stats refresh, never per hit or per tick. **The talent tree folds in the same calculation (#1181)**: the held nodes' lines, summed once per change of what the character holds (`TalentAllocation.Totals`, a `TalentTotals`), count as a worn item's global lines do. The offence sums and both added-damage ranges start at the tree's; its attributes join the gear's before the conversions; its flat life and mana, and its increased maximum life and mana, join the gear's, and its more life and mana then multiply the maximums; its flat armour, evasion and ward join the gear's and the attributes' before the global increases (the gear's and the tree's `IncreasedArmor`, `IncreasedEvasion` and `IncreasedWard`, `StatType` 56-58, which scale the whole rating); and its block, crit, movement, resistances and increased mana regeneration add to the gear's ([talents](talents.md#the-stats-fold)). `CharacterStatsRefresh` runs it at create (level 1, nothing worn), at select (`EnterWorld`: nothing stores current health or power, so a character enters with every pool full, health, mana and the ward; every class is on mana since #1181; the saved talents are checked against the live tree and summed first), after every accepted request that changed Equipment (`KeepShare`: each pool keeps its share, never killing or reviving), after every accepted talent allocation (`KeepShare`, `TalentChange.Apply`), and on level-up in `MapInstance.CreatureKilled` (`Refill`, or `KeepShare` when the member levelling is dead, so a level-up never refills a corpse; each eligible member of a party kill levels through this path on its own share). The highest level with a `CharacterLevelExperiences` row (15 today) is the cap, and a level before a gap in the rows stops a character the same way (`ExperienceAward.CanGainExperience`, #735): a character there gains no experience, while kills and quest turn-ins still pay gold and items. Select-time recalculation is also what corrects `CharacterStats` rows written before #463; there is no data migration, so a character that never logs in again keeps its old stored values. `CharacterEntity.ApplyStats` writes `Health`/`Power` (the stored and replicated maximums), the current pools, `Stamina`, the two mana regeneration rates (`ManaRegen`, `ManaRegenRates.Of` over the stored maximum and the gear's increased mana regeneration, see "Regeneration carries the fraction of a point" in [World simulation](world-simulation.md)), and a stats mark in `SaveState` that makes the next save upsert the `CharacterStats` row. A class and level with no row keeps the stored maximums, regenerates no mana and logs a warning; at select its pace falls back to the bare hand's (`CharacterEntity.UseBareHandPace`: the formula's `UnarmedAttackTimeMs`, no speed, #1178), so its basic attack is never free. Every class reads one `CombatFormula` (the combat reload area; the per-class `ClassStatFactors` table and `ClassLevelStats.BaseMana` were dropped by the World migration `ManaFormula`, #1181). The maximum mana is `ManaBase + ManaPerLevel x (level - 1) + Intellect x ManaPerIntellect` (seeded 100, 8 and 4; the Intellect product truncated once) plus the gear's flat `Power`, that sum scaled by the gear's `IncreasedMaximumMana` (`StatType` 54, as increased maximum life scales life; auras fold after it): 180 for a level 1 Warrior or Hunter and 192 for a Wizard or Cleric with nothing worn. The gear's `IncreasedManaRegeneration` (`StatType` 55) scales both regeneration rates (`DerivedCharacterStats.IncreasedManaRegenPct`, not saved); no seeded item carries either stat yet. Health and crit are class-neutral (#1178): the maximum health is `BaseHp + Stamina x LifePerStamina` plus the gear's `Health`, that sum scaled by the gear's `IncreasedMaximumLife` (#1179: `round(sum x max(0, 1 + x / 100))`, whole numbers, half away from zero; auras fold after it, so an aura's flat health is not scaled by it and an aura's increased or more health multiplies the scaled total), and crit `BaseCritPct` plus the gear's (`CombatFormula`, seeded 5 and 5), each class's `BaseHp` rebalanced so health with nothing worn is what its own rate gave; and the `Health`/`Power` setters clamp a total past `int.MaxValue`, the row's type, rather than wrapping it negative; the calculator's scaled products (an item's defence and a weapon end by their local increases, the flat life by increased maximum life, Stamina's life, the flat mana by increased maximum mana and Intellect's mana, #1181) and each item's defence summed into the total saturate at a long's range rather than wrapping (`LocalScaling`), so no authored gear wraps a stat. Combat reads the weapon and the offence block (#1178), armour, evasion, block, crit, the four resistances and the maximum ward (see "Combat reads the derived stats" in [World simulation](world-simulation.md)). The defences are class-neutral (#1178): armour is the gear's plus `Strength x ArmorPerStrength`, the evasion rating the gear's (`StatType.Evasion`) plus `Agility x EvasionPerAgility`, the maximum ward the gear's (`StatType.Ward`) plus `Intellect x WardPerIntellect` (each product truncated once; `CombatFormula`, seeded 0.1, 1.125 and 0.25), block the gear's alone, and the four resistances the gear's (`StatType.FireResistance` to `BlightResistance`), auras folded on top. The `CharacterStats` row saves `Evasion`, `MaxWard` and the four resistances; its retired `DodgePct`, `AttackDamage` and `AbilityDamage` columns were dropped (#1178), and the weapon and offence block are not saved: select derives them again. The current ward is not saved, as current health is not. The same walk counts the worn items' Resonance themes (#1180, [item modifiers](item-modifiers.md#resonance-themes)) into the character's reused `CharacterEntity.Resonance` buffer (see "Resonance counts" in [World simulation](world-simulation.md)); the counts are not saved either, and a select counts them again.
- **The character sheet (#506 slice C).** `SMSG_CHARACTER_STATS` (`SCharacterStatsPacket`, `0x302A`) carries Stamina, Strength, Agility, Intellect, Armor, CritPct, BlockPct, WeaponMin, WeaponMax and MovementSpeed (field 14, m/s, the speed the server steps at) (#627), and since #1178 `Evasion` (15, the rating), `EvasionPct` (16, the chance it gives against an attacker of the character's own level, `HitResolver.EvasionChance`, in percentage points), `MaxWard` (17), the four effective resistances (18-21, `FireResistance`, `ColdResistance`, `LightningResistance`, `BlightResistance`, capped as a hit caps them, `HitResolver.EffectiveResistance`), `CritMultiplier` (22, `HitResolver.CritMultiplier`), the three effective speeds from `CharacterEntity.Pace` (23-25, `AttackSpeedPct`, `CastSpeedPct`, `CooldownRecoveryPct`, each from 0 to its cap), `AttackTimeMs` (26, the main hand's or the bare hand's, before attack speed), `IncreasedPct` (27, the offence block's increased points, indexed by `OffenceStat`), since #1180 `Resonance` (28, a list of `ResonanceDto { ThemeId, Count }`: each Resonance theme at least one worn item carries, with how many do, by the table's slot order; a theme at 0 is not listed, and the list is empty or absent when there is none; the client finds a theme's name in its vendored `item-modifier-catalog-v1.json`) and, since #1181, `ManaRegenInCombat` (29) and `ManaRegenOutOfCombat` (30), the mana regained a second in and out of combat (`CharacterEntity.ManaRegen`, through `CharacterSheet.From`), to the character's own connection only; the retired fields 6, 7, 9 and 13 were deleted. The crit and block chances are effective: clamped to the current `CombatFormula`'s `CritCap`/`BlockCap` by `HitResolver.EffectivePct`, the clamp every roll uses (`CharacterSheet.From`). `CharacterSheetFlusher` sends it from `WorldServer.Update`, right after `InventoryUpdateFlusher`, at most once per connection per tick, whenever the sheet differs from `CharacterEntity.SheetSent` or the Resonance counts differ from `CharacterEntity.ResonanceSent`, the counts the last sheet carried (#1180; `CharacterSheet` keeps no counts, it writes the character's live buffer into the packet, `CharacterSheet.ToPacket`, through the tick thread's one reused list and DTOs; both World-side, never saved; it rebuilds the sheet only when a stats refresh, the level, the movement speed or the combat generation moved since the last one, `CharacterEntity.SheetInputs`, #1178): so on the tick the selected character enters the world (the readiness barrier puts it on the connection), after a stats refresh that changed a value it shows (a gear change, a level-up; an equip that changes nothing sends none, and the sheet keeps only what it sends, `IncreasedPoints` of the offence block rather than the block, so a more, which the sheet does not show, sends none either), and after a `/reload combat` whose caps or evasion terms move a character's effective chance or resistance. A new formula's mana terms reach it only at that character's next refresh, since a reload is forward-only. A character with no stats is sent none; a new session starts with no sheet sent, so it gets the whole sheet again. A refresh that moves only a Resonance count (an equip that changes no shown value but adds or removes a theme) sends a sheet too; a `/reload items` gives the next refresh a new table, so that refresh sends one sheet for a character holding any count, even when none moved. The counts change only in a stats refresh: anything that changes them elsewhere (#1180's later parts) must go through a refresh, or the client hears of it only at the next one. **REST** (#1180): `GET /world/{worldId}/character/{id}/stats` returns `resonance`, a list of `{ themeId, count }` counted from the saved inventory through the same per-item step (`CharacterStatsCalculator.CountResonance` over the worn items in a slot that fits them and the catalog rows they carry; not saved, a theme at 0 not listed), and the inventory read gives each modifier line its `themeId` (null on an implicit or unique line, or when the catalog no longer holds the modifier); an unidentified copy shows only its implicit lines, so it names no theme ([multi-world API](api-worlds.md#routes)).
- **Ability amounts (#669).** Each learned ability's per-hit amount, for client tooltips, and since #1178 its damage types and pace: `CooldownMs` and `CastTimeMs` through `AbilityPace` over `CharacterEntity.Pace`, rounded to the nearest millisecond, so a client never applies the speed rules. `AbilityAmounts.For(caster.Combat, metadata, pace)` (`Avalon.Combat`) runs the very arithmetic a hit uses (#1178): the base (`OffenceMath.DirectBase` for damage, `OffenceMath.HealBase` for a heal; see [the skill system](spell-system.md#4-hit-resolution)) with every roll at the low and then the high end of its inclusive range (`RollEnds`: the weapon or the spell base, and any added damage), and floors each end as a normal hit does, before evasion, crit, block and mitigation, through `AbilityAmountMath` (`Avalon.Combat`, shared with the API's character ability `amount` and public ability tooltips): `HitResolver.NormalDamage` (minimum 1) for a Hostile ability, `NormalHeal` (no minimum) for an Ally one. Damage is typed as a hit reports its types, every type with a part at the high end (`AmountTypes`). The worlds service advertises the same amounts for a saved character: it builds the attacker through the same entry points, from the saved attributes, the items worn in a slot that fits them with their saved base stats and modifiers (#1179: `ItemInstance.BaseStats`, `ItemInstance.Modifiers` and their values, loaded with the instances, so its main hand rolls the damage range and attack time its copy rolled) the held talent nodes' lines (#1181, a `TalentTotals` from the saved `CharacterTalents` rows and the World database's tree) and the world's `CombatFormula` row (`CharacterOffence.Of`, `WeaponDamage.Of`), without auras (an offline character's are stale), and a parity test holds the two together. Only the three shape scripts apply an amount directly, so any other `ScriptName` is `AbilityAmountKind.None` ("nothing to state", not 0), and so is an ability whose `Effects` give it no direct amount (one that only applies an aura, see Auras); the ability catalog only accepts shape scripts today, so `None` is a safeguard. In `SMSG_CHARACTER_ABILITIES`, at select and after a talent allocation that changed the abilities held (#1181), `AbilityInfo` fields 18-24 (`AmountKind`, `AmountMin`, `AmountMax`, `Tags`, `AmountTypes`, `CooldownMs`, `CastTimeMs`) carry them, and `CharacterAbilitiesSender` records them (`CharacterEntity.AbilityAmountsSent`/`AbilityAmountsSentFor`/`AbilityAmountsInputs`, World-side, never saved). `AbilityAmountsFlusher`, called from `WorldServer.Update` right after `CharacterSheetFlusher` and `TalentFlusher`, compares only the stats refresh count and the level the amounts were last checked at on a tick where neither moved (`AbilityAmountsInputs`, #1178), and once one moved works the amounts out again only when `CharacterEntity.Combat` or `CharacterEntity.Pace` differs from the one last used, and sends `SMSG_CHARACTER_ABILITY_AMOUNTS` (`SCharacterAbilityAmountsPacket`, `0x302C`, every learned ability, whole) to the character's own connection only when an amount or a pace changed. `docs/client-combat-protocol-migration.md` has the contract.
- **Heal events (#506 slice C).** `SMSG_UNIT_HEALED` (`SUnitHealedPacket`, `0x310C`: Healer, Target, Amount, CurrentHealth, optional AbilityId, `HitResult` Result) is sent for every heal that restored more than 0 health: `CombatService.ApplyHeal` reports it through its instance (`ICombatOutcomes.UnitHealed`, #546), and `MapInstance` sends it to the healer, the target and every connection within `Game:InterestRadius` of the target (`EffectAudience`, #532), for a target in that instance only. `Amount` is the health restored, overheal left out; `Result` is `Crit` for a critical heal and otherwise None. A heal on a target at full health sends nothing.

## Identification at the Resonance Workbench (#1179)

- **What an unidentified copy shows.** A magic, rare or unique copy that drops or that a quest pays as a rolled reward
  arrives unidentified (above). Until it is identified, the server sends its template, rarity, item level, base stats
  and implicit lines, and never its prefixes, suffixes, a unique's own line or a generated name, on any path: the login
  snapshot and every inventory update, the bank, the vendor buyback list, an item request's refusal echo, a trade window
  (one entry serves both sides), the ground, and the REST inventory read for every caller, staff included. The rule is
  one, `ItemVisibility` (`Avalon.Domain.World`): an identified copy shows every modifier with no lookup, and an
  unidentified one keeps a modifier only when its catalog row's kind is `Implicit` (`ShowsUnidentified`; an id the
  catalog no longer holds is hidden), by kind, never by ordinal. The world's messages apply it in
  `ItemModifierDtoMapper.ToDtos` and `ItemModifierDtoPool.Rent`/`Refill` (the kept list is sized by what is kept, and is
  null, its list back in the pool, when nothing is), the REST read in `CharacterService`. Names follow it too
  (`ItemVisibility.NameShown`, only once identified): `ItemModifierStore.Describe`, the buyback's carried-item mapping
  and `CharacterService` ask it before working a name out, so none names an unidentified copy. An unidentified unique
  shows its template, its base's base stats (none on today's jewellery and trinkets) and its base's implicit. `ItemSlotDto.Identified` (13) and
  `TradeItemDto.Identified` (10) tell the client which it is; a drop on the ground is identified exactly when its
  `Rarity` is Common, so `LootDropDto` needs no field for it.
- **What it can do.** It cannot be worn (`ItemRequestResult.Unidentified` 17, `ItemUseResult.Unidentified` 21: a drag,
  a swap with the worn item, an item use, a two-hander over a worn off hand, a second copy of a UniqueEquipped
  template), and it can be moved in the Bag, banked, traded, destroyed and sold (for `Game:Items:UnidentifiedSellPercent`
  of its price, [vendors](#inventory-gold-and-character-saves)).
- **The Workbench.** The Resonance Workbench is doodad template 7, the one seeded doodad whose `Service` is `Workbench`,
  placed in Glimmerdell's market (`MapDoodadSpawns` row 2, [doodads](doodads.md)). A click on it goes through
  `CMSG_INTERACT` and `DoodadUseService` like any click (it ends the user's casts and arrival protection) and does
  nothing else on the server: the client opens its Workbench window when the player clicks a doodad whose catalog
  `service` is 1. No window state is held: each request names the Workbench and is checked against it on its own.
- **The request.** `CMSG_ITEM_IDENTIFY` (`0x2083`, `CItemIdentifyPacket`: `RequestId`, `WorkbenchGuid`, `BagSlot`),
  accepted by `MapSessionFilter`, identifies one Bag item; an "identify all" is the client sending one request per item.
  `ItemIdentifyHandler` answers each with exactly one `SMSG_ITEM_IDENTIFY_RESULT` (`0x3092`,
  `SItemIdentifyResultPacket`: `RequestId`, `ItemIdentifyResult`), and a connection with no character gets nothing
  (logged at Debug). `IdentifyRules.Decide`, which reads and never changes, asks in this order, its first four the
  Workbench's shared prefix (`WorkbenchRules.Access`, which extraction and imprinting ask too, #1180 part C): `Dead`
  (1); `Stunned` (2, `ControlGates.CanAct`); `NotFound` (3: no instance, no doodad of that guid in it, a despawned one,
  or one whose template's service is not Workbench); `TooFar` (4: beyond the Workbench's `InteractionRange`, 5 m, written so a
  position that is not a number is beyond it; a doodad has no conversation to leash, so walking away after opening the
  window is caught by the next request); `NoItem` (5: nothing in that Bag slot, a slot past the Bag included);
  `AlreadyIdentified` (6); `Locked` (7: the item is offered in a trade); `NotEnoughGold` (8: only when the cost is above
  0, through `IWallet.CanSpend`, which leaves out gold a trade holds). Any answer but `Ok` (0) and `InternalError` (9)
  changes nothing. On `Ok`
  the handler spends `Game:Items:IdentifyCost` through `IWallet.TrySpend` (nothing when it is 0, the default), then calls
  `IInventoryService.TryIdentify(bagSlot)`, which replaces the Bag item with the same instance identified (marked
  `Changed` for the save, its slot recorded for the client; its rolled rows do not change, so they are not marked).
  Gold goes before the item, so a failure after the rules allowed it (a bug, logged at Error and answered
  `InternalError`, 9) loses value and never makes it: the gold of a cost above 0 may be spent and is not given back.
  The revealed item, with its name and every modifier, and the gold reach the client in the tick's
  `SMSG_INVENTORY_UPDATE`.

## Awakening (#1180)

What a sealed affix is, which rares carry one, its bar and its wake are in [item modifiers](item-modifiers.md#awakening);
this section is how the world holds, saves, sends and wakes it.

- **The seal is one column on the modifier row.** `ItemInstanceModifiers.SealProgress` (`integer NULL`,
  Character DB, migration `AddModifierSeals`) is set exactly on a sealed affix, the points its bar holds, and null on
  every awake one; in the domain, `ItemInstanceModifier.SealProgress` (`int?`) with `Sealed` (whether it is set, not a
  column of its own). One nullable column and not a flag beside a bar: a bar that is `NOT NULL` would need a value on
  every awake row that means "not applicable", and null already says that, as `ItemInstances.RareName` does. The
  database holds the rest: `CK_ItemInstanceModifiers_SealProgress` (`"SealProgress" IS NULL OR "SealProgress" >= 0`)
  and the partial unique index `IX_ItemInstanceModifiers_Sealed` (`ItemInstanceId` where it is set), so an item carries
  at most one seal. The bar never passes its threshold, which the settle (below) holds.
- **The bar travels with the copy.** It is on the row, so it goes wherever the row goes, with no path of its own:
  `ItemInstanceModifier.CopyRow` copies it, so every save (`CharacterSaveSnapshot`) and a trade's paired save
  (`TradeSaveBatch`) write it; the trade record keeps it (`TradeRecordItemModifiers.SealProgress`, the same check, no
  index: the record is history); a sale keeps it in the buyback list's carried rows, which the buyback writes again;
  the bank keeps the rows where they are. A new owner goes on from the same point when it wears the item.
- **The meter, and the one in-place write.** Each character has an `AwakeningMeter` (`CharacterEntity.Awakening`,
  World-side and `internal`, never on `ICharacter`, never saved): `SealedWorn`, the sealed rows `Awakening.Fills`
  accepts (a seal on an identified copy that is not Tainted, `ItemModification.Allowed`, #1180 part C) on the items in the Equipment container, counted again by every stats refresh
  that counts Resonance again (an item put on or taken off, a wake, a reload), with the Equipment slots they are in,
  kept so the settle, the wake check and the progress packet visit only those (found again after an Equipment change);
  `PendingMilli`, the points earned and not yet settled, in thousandths; and two bits, `Due` (the tick's flush must
  settle and look for a full bar) and `Unsent` (progress moved since the client was told). Setting either queues the
  character, once, on the world's `AwakeningQueue` while it is in the world ([world simulation](world-simulation.md),
  Awakening). A recount that finds no seal worn drops the pending fraction; one that finds any sets `Due`, so a seal
  worn again with a full bar, or at login, wakes at the next flush. A hit or a kill only adds to
  `PendingMilli` ([world simulation](world-simulation.md), Awakening): no row, no save mark, no client change.
  `Awakening.Settle` moves the whole points into each worn row `Fills` accepts, **in place on the store's row**, each
  capped at its item's threshold, and keeps the fraction pending; it marks each item whose bar moved for the next save
  (`SaveState.ItemModifiersChanged`), sets `Due` and `Unsent`, records no client slot and never wakes anything. This is
  the one field written inside a held modifier list: the bar feeds no stat, no Resonance count and no name, so nothing
  that caches a list by reference needs to see it. A fraction of a point left at a logout is lost.
- **The settle points.** Before every save (`CharacterSaveSnapshot.Take`, its first statement: the periodic save, the
  logout and despawn save, a trade's save), so damage dealt with no kill, a fight that ends in a logout, is written;
  before every inventory change that touches the Equipment (`CharacterInventoryService`: `TryMove` on either side,
  `TryDestroy`, `TakeOut` and `TryRemove` of a worn item), so an item taken off keeps what it earned and one put on gets
  nothing earned before it; and in the tick's Awakening flush.
- **The wake, through `IInventoryService.TryAwaken(equipmentSlot)`.** Only the tick's flush calls it, and only for a
  worn item. It answers null and changes nothing unless the slot holds an item with a row `Awakening.ReadyToWake`
  accepts (it fills and its bar is at its threshold). Otherwise `IItemRoller.Awaken` makes the woken row, a new object
  with the sealed row's id, item and ordinal, no seal and a values list of its own; a new list, the old one with the
  woken row in the sealed one's place, **replaces** the item's (`ItemModifierStore.ReplaceModifiers`, which refuses the
  list the item already holds); the rows are marked for the save; and the item becomes **Attuned** (replaced with
  `ItemInstanceFlags.Attuned` set, marked `Changed`, its slot recorded for the client), or, already attuned, has its
  slot recorded. It never writes a field inside the old list: a stats refresh counts Resonance again only for a worn
  list it has not seen, by reference, so the woken affix counts because its list is new. It answers
  `AwakenedItem(EquipmentSlot, ModifierId, Outcome)` and does not refresh stats: the flush does, after its wakes
  (`CharacterStatsRefresh.AfterGearChange`). An item taken off in the very tick its bar filled wakes when it is next
  worn.
- **Attuned.** `ItemInstanceFlags.Attuned` (1, in `ItemInstances.Flags`) is the one binding bit: a wake sets it, and
  nothing clears it. It reaches the client in `ItemSlotDto.Flags` (7) and the REST read as `attuned`. An attuned copy
  is refused in a face-to-face trade ([trading](trading.md)); it can still be banked, sold, bought back as itself and
  destroyed. The template attunement flags are unchanged: public tooltips show them, and no rule reads them.
- **The messages.** `ItemModifierDto.SealProgress` (3) and `SealThreshold` (4, `ItemAwakening.Threshold` of the copy's
  item level), both `uint?`, are set exactly on a sealed modifier of an identified copy the client is shown, on every
  path an item's modifiers travel (the login snapshot, inventory updates, item replies, the bank, the buyback, the trade
  window), and null otherwise; a reused pooled entry is always overwritten. An unidentified copy shows no affix, and no
  line it shows carries a seal, so nothing says it has one. Progress itself is never sent by rebuilding an item entry:
  - `SMSG_AWAKENING_PROGRESS` (`0x3093`, `SAwakeningProgressPacket`: `Items` 1, a list of `AwakeningProgressDto`
    with `EquipmentSlot` 1, `Progress` 2 and `ItemInstanceId` 3, the item's instance id as `ItemSlotDto` carries it),
    to the owner only, at most once a tick and only on a tick its progress moved: every worn sealed affix, in Equipment
    slot order (a woken one is no longer sealed, so it is not listed), from entries the flusher reuses. The stage runs
    before the inventory flush, so the slots are the ones this tick's `SMSG_INVENTORY_UPDATE` leaves; a client applies
    each bar to the item its instance id names, so a same-tick swap never shows one item's bar on another;
  - `SMSG_ITEM_AWAKENED` (`0x3094`, `SItemAwakenedPacket`: `EquipmentSlot` 1, `ModifierId` 2, the catalog modifier it
    woke as, and `Outcome` 3), to the owner only, once per wake. The item itself, attuned and with its woken modifier,
    arrives in the same tick's `SMSG_INVENTORY_UPDATE`, whose flush runs after the Awakening stage.
  - `AwakeningOutcome`, an append-only wire enum (`Avalon.Network.Packets.Items`): `Woken` 0 (the same tier and
    values), `TierRaised` 1 (one tier better, values rolled anew), `Polished` 2 (the same tier, each line the better of
    old and new).

  Both are server to client only, so no session filter lists them.
- **REST.** The inventory read (`GET /world/{worldId}/character/{id}/inventory`) gives each modifier line it shows its
  `sealProgress` and `sealThreshold` (both null on an awake line, and on every line of an unidentified copy), the bar
  as the character's last save left it, and each item `attuned`. `/stats` leaves a sealed affix out of the stats and the Resonance counts, through the same `ItemLines`
  and per-item count the world uses ([multi-world API](api-worlds.md)).

## Extraction and imprinting (#1180 part C)

What can be extracted, what a glyph is, the imprint rules, instability, the brick and Tainted items are in [item
modifiers](item-modifiers.md#extraction); this section is how the world decides, applies, holds, saves and sends them.

- **The Workbench's three requests.** Identification, extraction and imprinting are all requests at the Resonance
  Workbench, each in `MapSessionFilter`, handled on the tick in the map pass, each answered with exactly one result
  (a connection with no character gets nothing, logged at Debug), and none holding window state. Each first passes the
  Workbench's shared prefix, `WorkbenchRules.Access` (`WorkbenchAccess`, World-side and not on the wire: `Dead`;
  `Stunned`, `ControlGates.CanAct`; `NotFound`, no instance, no doodad of that guid in it, a despawned one or one whose
  service is not `Workbench`; `TooFar`, beyond its `InteractionRange`, a distance that is not a number included), which
  each request's rules map to its own result with a `switch`. Then its own rules, which read and never change. **A
  refusal changes nothing and allocates nothing** beyond its pooled reply
  (`InventoryAllocationShould.Answer_workbench_requests_allocating_nothing`, and `WorkbenchRequestBenchmarks`,
  [benchmarks](benchmarks.md)).
- **Extract.** `CMSG_ITEM_EXTRACT` (`0x2084`, `CItemExtractPacket`: `RequestId` 1, `WorkbenchGuid` 2, `BagSlot` 3,
  `ModifierId` 4, the catalog modifier of the affix to keep), answered by `ItemExtractHandler` with
  `SMSG_ITEM_EXTRACT_RESULT` (`0x3095`, `SItemExtractResultPacket`: `RequestId`, `ItemExtractResult`).
  `ExtractRules.Decide` asks, in order: the prefix, `Dead` 1, `Stunned` 2, `NotFound` 3, `TooFar` 4; `NoItem` 5 (nothing
  in that Bag slot, a slot past the Bag included); `Unidentified` 6; `Locked` 7 (offered in a trade); `Tainted` 8;
  `NotExtractable` 9, for any of: its template is gone or is not a rolled base (`ItemRoller.IsRolledBase`, which leaves
  out uniques and glyphs), the copy is not Magic or Rare, the template is `NoDestroy`, the item carries no row of that
  modifier (an id above `int.MaxValue` names none), the row's catalog modifier is gone or is not a prefix or suffix, the
  row is sealed, or the items patch holds no Glyph template. It costs no gold. On `Ok` (0) the handler calls
  `IInventoryService.TryExtract(bagSlot, modifierId)`; a failure after the rules allowed it is a bug, logged at Error
  and answered `InternalError` (10), and leaves the item as it was.
- **`TryExtract`.** It answers false and changes nothing unless the Bag slot holds an item `ItemModification.Allowed`
  accepts (identified and not Tainted), not offered in a trade (it asks `Locks` itself, as every removal by id does,
  whoever calls it), carrying an awake prefix or suffix row of that modifier in the current catalog
  (`ExtractRules.ExtractableRow`, the rules' own check, which also hands back the catalog row), and the patch holds a
  Glyph template. It builds the glyph in full first (a new item id; the affix's row copied by
  `ItemInstanceModifier.CopyAs` under a new row id from `IItemIdAllocator.NextModifierId`, ordinal 0, unsealed, not
  imprinted; the copy Magic, identified, `Attuned`, count 1, its template's initial durability, its item level the
  modifier's `RequiredItemLevel`), so whatever throws leaves the item as it was. Then it deletes the item (marked
  Removed, its store entry taken: rows, base stats, instability and all), puts the glyph's row in the store (`PutMade`,
  marked for the save) and creates the glyph **in the same Bag slot**: no free slot is needed, the slot's save mark nets
  to Changed, and the cascade from the old item's delete makes the slot's upsert an insert. The glyph reaches the client
  in the tick's `SMSG_INVENTORY_UPDATE`.
- **Imprint.** `CMSG_ITEM_IMPRINT` (`0x2085`, `CItemImprintPacket`: `RequestId` 1, `WorkbenchGuid` 2, `GlyphBagSlot` 3,
  `TargetBagSlot` 4), answered by `ItemImprintHandler` with `SMSG_ITEM_IMPRINT_RESULT` (`0x3096`,
  `SItemImprintResultPacket`: `RequestId`, `ItemImprintResult`). `ImprintRules.Decide` asks, in order: the prefix,
  `Dead` 1, `Stunned` 2, `NotFound` 3, `TooFar` 4; `NoGlyph` 5 (the glyph slot is empty or past the Bag, its template is
  gone or not a glyph, it holds other than exactly one row, or that row's catalog modifier is gone, untiered, or not a
  prefix or suffix); `NoItem` 6 (the target slot is empty or past the Bag); `Locked` 7 (the target is offered in a
  trade); `Unidentified` 8; `WrongRarity` 9 (not Magic or Rare, or its template is gone or not a rolled base, which
  catches a glyph as the target, and so the glyph's own slot); `Tainted` 10; `NoRoom` 11 (the target's rows of the
  glyph's kind, counted through the catalog with a sealed affix included, already fill its rarity's room, Magic 1,
  Rare 3); `GroupTaken` 12 (it carries an affix row of the glyph modifier's group); `WrongSlot` 13 (the glyph's modifier
  never rolls on the target's base kind, `ItemModifierCatalog.RollsOn`); `ItemLevelTooLow` 14 (the target's item level
  is below the glyph modifier's `RequiredItemLevel`); `InternalError` 17 when `Game:Items:ImprintCost` holds no cost for
  the glyph modifier's tier (a reload added a tier with no configuration), which the handler logs at Error as "the
  glyph's tier has no Game:Items:ImprintCost", before any gold; `NotEnoughGold` 15 (the cost is above 0 and
  `IWallet.CanSpend` refuses it; the wallet leaves out gold a trade holds). Rows the catalog no longer holds count toward
  neither room nor group. **No rule reads instability**, so no refusal says anything of it. On `Ok` the handler spends
  the cost through `IWallet.TrySpend` (nothing at 0), then calls `IInventoryService.TryImprint(glyphSlot, targetSlot)`
  and answers what it returns, `Ok` (0) or `Bricked` (16), a success too. An imprint is all or nothing. When
  `TryImprint` answers null or throws after the rules allowed it, it has written nothing (it throws only before its
  first write, below), and the handler catches the throw, gives the cost back through `IWallet.TryAddGold`, logs at
  Error (generated `[LoggerMessage]` methods, naming the request, the cost and the refund's result, and the exception
  for a throw, never the total) and answers `InternalError` 17, its one reply: the request changed nothing, gold
  included. A brick that finds an affix offered no tier is such a throw.
- **`TryImprint`.** It answers null and changes nothing unless both slots are held and differ, the glyph is a glyph
  holding one row of a tiered prefix or suffix the catalog holds (`ImprintRules.GlyphAffix`, the rules' own check), and
  the target is an item `ItemModification.Allowed` accepts of a rolled base, carrying rolled rows (an entry in the
  store, which every rolled base has). Otherwise `IItemRoller.Imprint` makes the target's new modifier list (its rows,
  then the glyph's row copied by `CopyAs` under a new row id at the next ordinal after the highest, flagged
  `Imprinted`), draws the instability and, when the total bricks the item, rerolls its affixes as new row objects ([item
  modifiers](item-modifiers.md#extraction)); neither the held list nor any row in it is written. The item's new flags
  are made too: a bricked item `Tainted` with `Attuned` cleared; any other `Attuned`, or, already attuned, unchanged.
  These rolls and builds are the only steps that may throw, so any throw comes before the first write. Only then does it
  write, and no write can throw: the new list and total **replace** the item's
  (`ItemModifierStore.ReplaceModifiers(item, list, instability)`, whose refusals, an item without an entry and the list
  it holds, are ruled out) and, in the same step with nothing between them that can throw, the item is replaced with its
  new flags (an unchanged one only has its slot recorded for the client), so no item ever holds a bricking total
  untainted (the container's `Put` refuses only a slot past its end, and this one was just found held); the item is
  marked for the save (dictionary writes), and last the glyph is deleted (marked Removed), from a slot just found held.
  It answers `Bricked` or `Ok`. It never logs, and never throws with the total in a message. The item, the emptied glyph
  slot and the gold reach the client in the tick's `SMSG_INVENTORY_UPDATE`; the brick itself is told only by the
  `Bricked` answer.
- **The columns** (Character migration `AddImprintsAndInstability`). `ItemInstances.Instability` (`smallint NOT NULL`,
  `ushort` in the domain as `ItemLevel` is; `CK_ItemInstances_Instability`: `"Instability" >= 0`), the hidden running
  total; `ItemInstances.Tainted` (`boolean NOT NULL`), held equal to the brick by `CK_ItemInstances_Tainted`:
  `"Tainted" = ("Instability" >= 100)` (100 is `ItemInstability.BrickAt`); and `ItemInstanceModifiers.Imprinted`
  (`boolean NOT NULL`, no index: nothing counts imprints). The trade record mirrors all three
  (`TradeRecordItems.Instability` and `Tainted`, `required` on the record as `Identified` is, with
  `CK_TradeRecordItems_Instability` and `CK_TradeRecordItems_Tainted`, and `TradeRecordItemModifiers.Imprinted`). The
  migration adds each with a default of 0 or false, which only fills the rows that exist, and then drops the defaults,
  as the model declares none, so no insert can leave a column out. The total cannot pass 199: a total below
  100 plus one draw of at most 100, after which a Tainted item is never imprinted again.
- **Where instability lives in memory.** Only World-side: on the item's `ItemModifierStore` entry, beside its rolled
  rows (`InstabilityOf(item)`, 0 for an item without an entry; `Load` reads the column; `Put` takes it; both throw for a
  total above 0 with no rolled rows, since an imprinted item always carries its imprint, rather than drop a total every
  later save would need; `Take` returns it), and on `CarriedItem` (its fourth member, `Instability`, with no default, so
  no path drops it silently) while the item is out of every container: taken out for a sale and kept for the buyback, or
  planned into a trade (`TradeRules.ItemsInPlace`, `TradeService.Completion`). It is never on `InventoryItem`, the
  modding API's view. `Tainted` is a visible fact of the copy, on `InventoryItem` (World.Public, read-only, a positional
  member with no default, so every copy built states it and none rebuilt untaints an item), which `InventoryAssembler`
  reads from the row. So both travel with the copy wherever `Identified` does: a save writes them
  (`CharacterSaveSnapshot.ItemRow`, with the store's total), a trade's paired save (`TradeSaveBatch`, from the carried
  item) and its record (`TradeService.AddItems`) keep them and each row's `Imprinted` (`CopyRow` copies it), a sale and
  its buyback carry them, and the bank moves the copy within the character, so its store entry never leaves.
- **A seal that moves is cleared first.** No part C path moves a seal (a brick keeps every row's id and progress, and
  an imprinted or glyph row is never sealed), but the save is made safe for a later one: `CharacterSaveRepository`'s
  rewrite pass, for each batch with modifier writes, first clears the stored seals in its own statement
  (`ExecuteUpdateAsync`, `SealProgress = NULL` on stored rows whose id the batch writes unsealed and whose stored seal
  is set, of the items whose new rows hold a seal), before the tracked updates set any new seal, so a seal moving
  between two rows of one item never meets the one-seal index twice. One statement per batch, and only when an item
  whose new rows hold a seal also has a row written unsealed: a seal on a row outside the new set went with the deletes
  before it, and an item that keeps no seal has its rows written null by the tracked updates alone.
- **The messages.** `ItemSlotDto.Tainted` (14) and `TradeItemDto.Tainted` (11) say whether a copy is Tainted, on every
  path an item travels (the login snapshot, inventory updates, item replies, the bank, the buyback list, the trade
  window). `ItemModifierDto.Imprinted` (5) is set on an imprinted line of an identified copy the client is shown, and
  false otherwise; a reused pooled entry always overwrites it. A ground drop is a fresh roll, never Tainted or
  imprinted. Nothing on the wire carries the total.
- **REST.** The inventory read gives each item `tainted` and each modifier line it shows `imprinted` (false on every
  line of an unidentified copy), as the character's last save left them ([multi-world API](api-worlds.md#routes)). The
  read loads the `ItemInstance` entity, `Instability` included, and maps none of it: no DTO carries the total, for any
  caller, staff included. `ApiContractShould.Name_instability_on_no_client_facing_type` holds that no packet, REST
  contract or modding-API type names it.
