# Inventory, gold, vendors and character saves

Ownership of items and gold, the inventory and wallet services, character saves, one world session per account, Change Character, character names, item requests, equipment, the bank, vendors, character stats and the character sheet.

## Inventory, Gold and Character Saves

- **Everything a player owns lives in the Character DB**: `Character.Money` (the character's gold balance, in copper, a `ulong`), `ItemInstance`, and `CharacterInventory`, whose `ItemId` is a real FK to `ItemInstance` (cascade). `ItemInstance.CharacterId` is a real FK to `Characters` (cascade), so the hard delete in `CharacterDeleteHandler` takes the character's items with it, as it already did its slots. The World DB holds reference data only; `ItemInstance.TemplateId` points into it with no FK, and the REST API looks templates up with `IItemTemplateRepository.GetByIdsAsync`. Item ids come from `IItemIdAllocator` (`Guid.CreateVersion7()`), never from EF or the database (`ValueGeneratedNever`).
- **Memory is authoritative.** Change items only through `IInventoryService` and money only through `IWallet`, both from `ICharacterEconomy` in `Avalon.World/Inventory`. `ICharacterInventory` in World.Public is read-only apart from `Load`, which replaces a container's whole contents at character select and marks nothing. Tick thread only, all or nothing: adds fill existing Bag stacks, then the lowest free Bag slots, never Equipment or Bank; removal by template takes the highest Bag slot first. `IWallet.TryAddMoney` refuses past `Game:MaxMoney` and never wraps. A vendor trade goes through `ICharacterEconomy.VendorOf` (`VendorTrade`), which asks the pure `VendorRules` and applies the plan through these same two services.
- Each successful change marks `CharacterEntity.SaveState` (`New`/`Changed`/`Removed` per item and per slot, plus a money-dirty flag) and `CharacterEntity.ClientChanges`. **Writing a `CharacterInventoryContainer` directly, or calling `ICharacterInventory.Load` after select, skips both: the change is neither saved nor sent.** Character creation is not a save: `CharacterCreateHandler` writes the starting items and slots directly through `IItemInstanceRepository` and `ICharacterInventoryRepository`, because no entity exists yet.
- **Saves go through `ICharacterSaver`**: one Character-DB transaction (`ICharacterSaveRepository`) with the whole row plus only the non-`Unchanged` items and slots, and the character's `CharacterStats` row when its derived stats changed since the last save (`SaveState.StatsDirty`), as idempotent upserts and deletes, and the character's `CharacterAuras` rows whenever it holds an aura or one changed (auras), all deleted and inserted again. `CharacterSaver` chains saves per `CharacterId`, not per entity, so a relog's saves still queue behind the previous session's despawn save; `WhenIdle(id)` completes once every save queued for that character so far has finished, committed or failed, and `CharacterSelectHandler` waits on it (up to `SaveWaitLimit`, 5 s) before loading the character. **A select whose wait runs out reads nothing**: it logs a warning and cancels the select (`CancelSelect`), and the client can select again. Reading anyway would load the state from before the save still running, and the new session's first save would write it back over the committed one. `WhenAllIdle()` is the same for every character at once: `WorldServer.OnStoppingAsync` awaits it last, because a tick starts each despawn without waiting for it, so a despawn save begun on an earlier tick can still be writing when the host stops. That wait is bounded by the host's stop token and `WorldServer.SaveDrainLimit` (20 s), and logs an error if it gives up. Marks are acknowledged only when the commit's continuation runs on the tick thread; a failed save keeps them for the next one. The task a save returns never faults (it is `false` on failure), but the multi-character `Save(list)` throws `ArgumentException` synchronously, before queuing anything, if it names a character twice or one item under two characters.
- **One world session per account (#465, #474).** Two copies of a character would each hold their own inventory and money, and whichever saved last would write over the other, losing or duplicating items and gold; and the owner's rule is one character in the world per account. The auth server's `Online` flag cannot prevent it (a dropped auth connection clears it while the world session stays up), and the `inWorld` mutex only spans world select to key exchange, so the world server enforces it at select. `CharacterSelectHandler` asks `IWorldServer.SessionsOf(accountId, except)` for the account's other connections, which includes closed ones whose despawn the tick has not dequeued yet (a close enqueues its despawn before it leaves `Connections`). **Every one of them is kicked**, whatever it holds (the selected character, a different one, a select still under way, or nothing): the handler cancels its select if one is in progress, calls `World.DeSpawnPlayerAsync` for it right there on the tick, then `NotifyAndClose` with `DisconnectReason.DuplicateLogin` and "Your account has been logged in from another location.". The despawn runs in the handler rather than being left to the close, because a close is only despawned by a later tick, and a `WhenIdle` taken before then finds no logout save to wait on. `DeSpawnPlayerAsync` queues its save before its first await, so the save is already in the chain the new select waits on, and clears `connection.Character` in a `finally`, so the connection ends holding nothing on every path, throw or not, and the despawn the close queues later saves nothing. Its instance steps (lookup, `DropPlayerFromEncounter`, `RemoveCharacter`) are each contained and logged, and the save is queued whatever they did, so a throwing step costs neither the logout save nor the removal of the others; `MapInstance.RemoveCharacter` drops the character from its tick, broadcast and periodic-save membership before it tells its own creatures' scripts (`AiScript.OnCharacterLeft`, each call contained), so a script that throws cannot leave it live. Only a throw while taking the snapshot itself queues nothing. The kicked connection's continuations still run after it lets go: `EnterMapHandler` and `RespawnAtTownHandler` check that the connection still holds the character they started with and otherwise do nothing, and `ProcessContinuations` contains each callback, logging one that throws, so it cannot end the flush for the connections after it. The new select waits, before its first read, on one `Task.WhenAll` bounded by `SaveWaitLimit`: its own character's `WhenIdle`, the `WhenIdle` of every *different* character it kicked (taken after that character's despawn queued its save), and the select step each kicked mid-select connection still had in flight. If the wait runs out it reads nothing, as above. **A kicked select stops at its next step**: every step of the select chain goes through `CharacterSelectHandler.Step`, which records the step's task per connection (a `ConditionalWeakTable`, tick thread only) and runs the next step only if `OwnsSelect` holds, meaning the connection is still up, not closing (`IWorldConnection.IsClosing`, read-only, set the moment `Close` is called), and `SelectStartedTicks` still equals the value that select began with. A select from a closing connection is ignored at `Execute` too: a kicked connection stays `IsConnected` until its outbox flushes, so a select it had queued in the same tick would otherwise kick back the session that kicked it, leaving neither in the world. Cancelling the select (the kick, the chain's own give-up paths, or `CancelExpiredSelects`) or losing the connection therefore stops the chain before its row write, its inventory reads and its `SetPendingSpawn`; the one step already running cannot be called back, which is why the new select waits for it. Other accounts' sessions are never touched.
- **Change Character (#663).** `CMSG_CHARACTER_LEAVE` (`0x2016`, no fields, `CharacterLeaveHandler`) returns a player in the world to character selection on the same world connection; exactly one `SMSG_CHARACTER_LEAVE_RESULT` (`0x302B`, `CharacterLeaveResult`: `Left` 1, `NoCharacter` 2, `Selecting` 3 during a select or while the character waits on its load report, `AlreadyLeaving` 4; refusals change nothing) answers it, unless the connection is closed instead. The leave is a logout: `IWorld.LeaveWorldAsync` is `DeSpawnPlayerAsync` answering whether the logout save committed, and `Left` is sent only once it has, so the row is offline and a reselect of the character (which waits on `WhenIdle` anyway) reads what was saved. A save that fails, or a leave that throws, is never answered: the connection is closed with `DisconnectReason.CharacterSaveFailed` (5); one that drops or is kicked meanwhile is not answered. From the start of the leave until its answer, `IWorldConnection.LeaveInProgress` (read-only; set through the World-side `ICharacterLeaveControl`, with the target, last input sequence, respawn flag and conversation cleared) makes the list, select, create and delete handlers refuse as they do mid-select, by closing, and a second leave is `AlreadyLeaving` and saves nothing. The leave is accepted by `WorldSessionFilter` alone, whatever the connection holds, never by `MapSessionFilter`: it runs in the session pass, before any instance ticks, and in-map packets queued before it are handled by the map pass first. In-map packets queued behind it, meant for the character that left, would wedge the queue (neither filter accepts them without a character), so the session pass drops an in-map packet (`MapSessionFilter.IsMapPacket`) that reaches the head of the queue while the connection holds no character. A leave in combat is allowed, as a logout is. `docs/character-login-flow.md` has the exchange.
- **Character names (#757, owner decision).** A name is 3 to 12 ASCII letters (`CharacterName` in `Avalon.Domain.Characters`, the one rule), checked as sent, before anything is read or trimmed: `CharacterCreateHandler` answers `NameTooShort`, `NameTooLong` or, for anything else, `NameInvalid` (`SCharacterCreateResult` 8, appended; the full answer order is in `docs/character-login-flow.md`). It is stored, and shown to everyone, in one display form, first letter upper-case and the rest lower-case (`CharacterName.Display`: `kAELA` is `Kaela`). `Characters.NameKey` holds its key, the name with only its ASCII letters upper-cased and nothing trimmed (`CharacterName.Key`; setting `Character.Name` sets it); a unique index (`IX_Characters_NameKey`) makes "Bob" and "bob" one name per world, and a check constraint, `CK_Characters_NameKey` (`"NameKey" = upper("Name" COLLATE "C")` on Postgres, locale-independent and ASCII-only like the .NET fold; plain `upper("Name")` on the SQLite the tests use, which folds ASCII only, the model choosing by provider), holds every writer to it. A typed name is looked up by `CharacterName.LookupKey` (the key of it trimmed), so a dotless i never finds an I: the create's duplicate check and `ICharacterRepository.FindByNameAsync`, the ignore list's offline lookup (`FindCharacterByNameAsync`), `OnlineCharacters` (so `/w` and `/invite`), `Party.FindByName` (`/kick`, `/promote`), `IgnoreList.FindByName` (`/ignore`, `/unignore`) and the self checks (`CharacterName.Same`). **A name changes only by insert or by `ICharacterRepository.TryRenameAsync`:** `Name` and `NameKey` are insert-only to the change tracker (`PropertySaveBehavior.Ignore` after save), so no tracked update (the world's saves, the select-time write, the API's admin patch) ever writes them, and a world holding an older name in memory can neither write it back over a rename nor fail its saves on the unique index. `ICharacter.Name` on World.Public is get-only; `CharacterEntity.Name` (World-side) keeps a setter, which no production path uses. A race to the unique index is recognised only as that violation (`CharacterNameKeyViolation.Is`: SQLSTATE 23505 on `IX_Characters_NameKey` on Postgres, the UNIQUE failure on `Characters.NameKey` on SQLite); anything else is rethrown. A create that loses it is answered `NameAlreadyExists`. The migration that added the column (`AddCharacterNameKey`) fills it from `upper("Name" COLLATE "C")` before building the index and leaves every existing name as it is (owner guarantee: none breaks the rule or clashes by case); unlike the account username migration, it does not check for clashes. **REST renames** (`PATCH /world/{worldId}/character/{id}`, `CharacterService.UpdateCosmeticAsync` and `UpdateAnyAsync`, owner decision) follow the same rule and display form: a name that breaks it, an empty one included, is a 400 validation error (`CharacterNameRuleAttribute` on `CharacterPatchDto.Name`, the pattern in the OpenAPI schema, and again in the service as a 400 `BusinessException`, `CharacterName.Requirement`); a name another character holds by key is "Name already taken", and so is a rename that loses the race to the index; a character in the world is refused with 409 `CharacterOnlineException` "Character is online; rename it while logged out."; a character deleted between the endpoint's lookup and the rename (`CharacterRename.NotFound`) is 404, `CharacterNotFoundException`, written as MVC's own 404 client-error ProblemDetails, the endpoint's answer for a missing character (owner decision). A name that would not change writes nothing (a character may change the case of its own name), so an admin patch of other fields still applies while it is online. The rename is one conditional statement, `UPDATE ... SET Name, NameKey WHERE Id = @id AND NOT Online` (`TryRenameAsync`): the world marks the row online by writing it, so the row lock orders the two and the rename sees the flag or commits first. A rename landing between a select's read and its spawn (the row not yet online) is accepted; that session shows the old name until its next select, and since the world never writes the name, nothing reverts it.
- The save triggers: entering an instance (`World.SpawnInInstance`, which writes `Online = true`), map entry (`EnterMapHandler`), periodic (`CharacterSaveScheduler`, ticked from `MapInstance.Update`, every `Game:CharacterSaveInterval`, default 5 min, with each character's first save staggered across the interval by its id), and despawn (`SaveOnDespawnAsync`, every logout and disconnect). The despawn snapshot is taken on the tick; a dead logout's move to the respawn town needs a database lookup, so it is applied to the copied row inside the chained write. That lookup reads the World DB while the save writes the Character DB, so `World.MoveToRespawnTownAsync` never lets a failed lookup fail the save: it logs and falls back to town 1's default spawn, or, when map template 1 is not loaded, keeps the map and position the character died at. The select-time row update is still a plain `ICharacterRepository.UpdateAsync`, because nothing is loaded yet. The multi-character `Save(list)` is the one-transaction save for exchanges that must not half-happen (auction house, trade, mail); nothing calls it yet.
- **Client:** `SInventorySnapshotPacket` carries `Money` at login, and never the Bank. `SInventoryUpdatePacket` (`SMSG_INVENTORY_UPDATE`) carries absolute `{Container, Slot, Item?}` entries plus an optional `Money`, built at most once per tick per connection by `InventoryUpdateFlusher` in `WorldServer.Update`, after both passes. **Bank slots are sent only while the bank is open** (`BankAccess.IsOpen`): `InventoryClientChanges` records them like any slot, and the flusher drops them when it is closed. The client-to-server packets that change inventory are `CMSG_LOOT_PICKUP` (#460), `CMSG_ITEM_MOVE` and `CMSG_ITEM_DESTROY` (#463), the three vendor requests (#432), `CMSG_QUEST_TURN_IN` and `CMSG_QUEST_ABANDON` (#433), which take quest items and pay rewards, and `CMSG_ITEM_USE` (see Item use), which equips gear and spends what an item script consumes.
- **Item requests (#463).** `CMSG_ITEM_MOVE` (`0x2080`) and `CMSG_ITEM_DESTROY` (`0x2081`), both accepted by `MapSessionFilter`, address slots only (containers cross as numbers, 0 Equipment, 1 Bag, 2 Bank; never item ids), and each gets exactly one `SMSG_ITEM_RESULT` (`0x3090`): an `ItemRequestResult`, and on a refusal only, the current state of the slots it named (a Bank slot only while the bank is open). `InventoryMove` (`Avalon.World/Inventory`) is the pure rule table: from the two slots and the count the server derives Move, Split, Merge or Swap, checks equipment (slot, level, class, two-hander against the off hand) and the Bank, and changes nothing. Two whole copies of a non-stackable item swap rather than merge; no stack (count above 1), split or merge ever goes into Equipment (`NotStackable`); an item whose template is gone (a reload removed it) stacks to 1 and can be moved within the Bag and the Bank, taken off, and destroyed, but never equipped. `IInventoryService.TryMove`/`TryDestroy` apply its decision with the usual `SaveState`/`ClientChanges` marks; a split's new id comes from `IItemIdAllocator`. A dead character gets `Dead`; a handler exception is logged and answered `NotFound`.
- **Equipment slots** (`EquipmentSlots`, the one mapping): 0 Head, 1 Neck, 2 Shoulder, 3 Chest, 4 Hands, 5 Legs, 6 Feet, 7 and 8 Finger, 9 MainHand, 10 OffHand; 11-13 are reserved and every request naming one is refused. This is not `ItemSlotType`'s numbering (its `Gem` is 8, and a gem is never worn). A neck piece is `ItemSubClass.Amulet` (206, an Armor subclass, #433) with `Slot = Neck`, and a ring `ItemSubClass.Ring` (207, forest content pass) with `Slot = Finger`. Nothing starts in Equipment: creation puts every starting item in the Bag.
- **The bank.** Usable only at a banker, in an open conversation with it in which its `OpenBank` option was chosen, inside the dialogue leash. `BankAccess.TryUse` checks all of that on every request that touches the Bank, and ends the conversation when the banker is gone, dead, no longer a banker or past the leash. `CharacterEntity.OpenBankNpc` remembers who opened it, and the bank is open exactly while `CurrentDialogue` is still a conversation with that NPC, so every way a conversation ends closes it: talking to another NPC (`InteractHandler`), an instance transfer (`World.TransferPlayer`, which ends the conversation because the NPC stays behind), and despawn (`LeaveInstance` clears both). The first two send `SMSG_DIALOGUE_END`, the client's cue to hide the window. Opening sends every Bank slot in one `SInventoryUpdatePacket`, the only time the whole bank is sent.
- **Vendors (#432).** Stock is World DB data.
  - **Tables.** `VendorStocks` holds one row per line: creature template, `Sequence`, item, optional `MaxStock` + `RestockSeconds`, optional `PriceOverride`, and an optional quest requirement. `VendorStockCosts` holds the item costs per unit bought. Check constraints pair the optional columns both ways (both set or both null), and `(CreatureTemplateId, Sequence)` is unique.
  - **Catalog.** `VendorCatalog` (the Vendors reload area, `StaticData.Vendors`) validates every row. A bad row is refused with an error naming it, and the vendor still sells its other rows. Beyond the schema's pairings it refuses a missing item, a zero `MaxStock`, `RestockSeconds` or cost count, a cost on a missing item or one named twice, a `Sequence` the vendor already uses (the lower `Id` wins), and **a row whose effective price (`PriceOverride ?? BuyPrice`) is below the item's `SellPrice`**, because buying and selling it back would make gold. `VendorRules.UnitPrice` also floors the price at `SellPrice` at runtime, so the rule still holds after a `/reload items` changes a price.
  - **Live stock.** A `VendorStockState` per vendor creature holds the counts and restock timers, in a `VendorStocks` table on the town `MapInstance`. The instance reaches it through `IVendorHost` (not `IMapInstance`, the modding API). A state is created full the first time a shop opens there, and is reset only by a restart. `VendorStockState.Take` throws past the stock and on a limited row the state does not track, so a caller resolves its row from the state's own `Rows`.
    - The restock timer starts when a sale takes a full row below its maximum, and refills the row when it is due. Time is absolute (`TimeProvider`), so an instance that did not tick catches up. A reload clamps each count to the new `MaxStock`; a reload that raises `MaxStock` leaves the row owed a timer, which the next vendor pass starts, so the row refills without waiting for a sale.
    - `MapInstance.Update` runs the vendor pass right after the packet loop, on every tick while `Vendors.Count > 0`, whether or not a shop is open. It reconciles with the catalog, restocks, and sends each connection whose shop is open the one `SMSG_VENDOR_LIST` it is owed (a stock change, a restock, a reload, its own buyback, or, #738, a change to which quests it holds or has turned in since its last list: an accept, an abandon or a turn-in, `QuestLog.HeldVersion` against `CharacterEntity.VendorListQuestVersion`, so a turn-in that meets a gate shows the row at once). It then clears the change marks, and allocates nothing when nothing changed.
  - **Opening and closing.** The shop opens through the dialogue option action `OpenShop`, which sends the list, and it mirrors the bank exactly. `CharacterEntity.OpenShopNpc` records the NPC, `ShopAccess.IsOpen` means the conversation is still with it, and `ShopAccess.TryUse` re-checks the stock host, the NPC, alive, still a vendor, and the leash on every request, ending the conversation out loud when any fails. Every way a conversation ends closes it (`CloseNpcWindows`, which clears the bank and the shop together).
  - **Requests.** `CMSG_VENDOR_BUY` (`0x2090`), `CMSG_VENDOR_SELL` (`0x2091`) and `CMSG_VENDOR_BUYBACK` (`0x2092`), all accepted by `MapSessionFilter`, each get exactly one `SMSG_VENDOR_RESULT` (`0x30A1`) with a `VendorResult`. Gold and items leave in the tick's `SMSG_INVENTORY_UPDATE`.
    - **Buy** checks, in order: alive, open, row and quest gate, count (at most `MaxStackSize`), stock, gold, Bag-only cost items, room once the costs are out, unique.
    - **Sell** takes a Bag slot only, and refuses `NoSell`, a `SellPrice` of 0, a gone template, a damaged item (`Durability < ItemInstanceDefaults.FullDurability`), a bad count, and the money cap.
    - **Buyback** re-adds the exact instance under its own id (`IInventoryService.TryAddInstance`, so the save upserts it). It refuses a unique item already owned again, and answers `NotFound` for an item a `/reload items` has flagged `QuestItem` since it was sold, which the list leaves out too, the other sales keeping their index (#738).
    - A handler exception is logged at Error and answered `NotFound`. A dead character gets `Dead`, and its conversation is left alone. A connection with no character gets no reply at all.
    - **`VendorTrade` is not rolled back.** `VendorRules` checks every step first, and the apply order takes the player's costs, gold or item before anything is given, so a programmer bug can only lose one trade's value, never duplicate it; the handler logs it at Error.
  - **Buyback list.** `CharacterEntity.Buyback` holds the last 10 sales, newest first. It is cleared on despawn (`World.LeaveInstance`) and kept across an instance transfer, because the session goes on. A partial sale keeps a copy with a new id from `IItemIdAllocator` (`IInventoryService.TakeOut`).
  - **Quest gates.** They ask `IQuestProgress`; production's `QuestProgress` answers from the character's quest log (Active = held, Completed = turned in, #433); `NoQuestProgress` is only a handler's fallback when built without the container. No seeded row is gated. A gated row whose requirement is not met is hidden and cannot be bought, and no row may sell a `QuestItem` (a row whose item a `/reload items` made one is hidden and refused `NotFound` until `/reload vendors` drops it).
  - **Optional parameters.** `StaticData` and `World` take `IVendorStockRepository` as an optional last constructor parameter (an empty catalog without it), and `DialogueChooseHandler` takes `IQuestProgress` the same way. `WorldHostGraphShould` pins that production registers both, so a missing registration cannot silently leave every vendor empty.
  - **Seeds.** Garrick (12) sells the four Common starter weapons (items 32-35). Hilde (13) sells the four starter armour sets (36-55); each chest is limited to 2, restocking every 30 minutes. Tobin (14) sells items 1-3, the forest scrolls 9-11, and the Greater Health Potion (56: 25 gold plus 2 Health Potions, limited to 5, restocking every 10 minutes). Forest gear stays drop-only.
- **Character stats (#463, #434).** `CharacterStatsCalculator` (`Avalon.Combat`) derives `DerivedCharacterStats` from the seeded `ClassLevelStat` row (the only base-stat source; the old `CharacterStats.GetBase*` helpers are gone) and the stat pairs of the items worn in a slot that fits them. `CharacterStatsRefresh` runs it at create (level 1, nothing worn), at select (`EnterWorld`: nothing stores current health or power, so a character enters full, except that a Fury pool enters empty, #526), after every accepted request that changed Equipment (`KeepShare`: each pool keeps its share, never killing or reviving), and on level-up in `MapInstance.CreatureKilled` (`Refill`, or `KeepShare` when the member levelling is dead, so a level-up never refills a corpse; each eligible member of a party kill levels through this path on its own share). The highest level with a `CharacterLevelExperiences` row (15 today) is the cap, and a level before a gap in the rows stops a character the same way (`ExperienceAward.CanGainExperience`, #735): a character there gains no experience, while kills and quest turn-ins still pay copper and items. Select-time recalculation is also what corrects `CharacterStats` rows written before #463; there is no data migration, so a character that never logs in again keeps its old stored values. `CharacterEntity.ApplyStats` writes `Health`/`Power` (the stored and replicated maximums), the current pools, `Stamina`/`RegenStat`, and a stats mark in `SaveState` that makes the next save upsert the `CharacterStats` row. A class and level with no row keeps the stored maximums and logs a warning. The per-class factors come from `ClassStatFactors` (#506, the combat reload area), and the `Health`/`Power` setters clamp a total past `int.MaxValue`, the row's type, rather than wrapping it negative. Combat reads the damage stats, armour, block, dodge and crit (see the combat-formula bullet).
- **The character sheet (#506 slice C).** `SMSG_CHARACTER_STATS` (`SCharacterStatsPacket`, `0x302A`) carries Stamina, Strength, Agility, Intellect, Armor, AttackDamage, AbilityDamage, CritPct, DodgePct, BlockPct, WeaponMin, WeaponMax, HastePct (field 13, the effective haste) and MovementSpeed (field 14, m/s, the speed the server steps at) (#627), to the character's own connection only. The chances are effective: clamped to the current `CombatFormula`'s `CritCap`/`DodgeCap`/`BlockCap` by `HitResolver.EffectivePct`, the clamp every roll uses (`CharacterSheet.From`). `CharacterSheetFlusher` sends it from `WorldServer.Update`, right after `InventoryUpdateFlusher`, at most once per connection per tick, whenever the sheet differs from `CharacterEntity.SheetSent` (World-side, never saved): so on the tick the selected character enters the world (the readiness barrier puts it on the connection), after a stats refresh that changed a value it shows (a gear change, a level-up; an equip that changes nothing sends none), and after a `/reload combat` whose caps move a character's effective chance. New class factors reach it only at that character's next refresh, since a reload is forward-only. A character with no stats is sent none; a new session starts with no sheet sent, so it gets the whole sheet again.
- **Ability amounts (#669).** Each learned ability's per-hit amount, for client tooltips. `AbilityAmounts.For(caster.Combat, metadata)` (`Avalon.Combat`) runs, through `AbilityAmountMath` (`Avalon.Combat`) (the arithmetic, shared by world combat and the API: the character ability `amount` and the public ability tooltips, with a parity test), `HitResolver.AbilityBaseRange` (the ability's base, `EffectValue + ScalingCoefficient × stat + BaseDamageCoefficient × weapon roll`, through `AbilityBase` itself at the low and the high end of the inclusive main-hand roll) and floors each end as a normal hit does, before crit, dodge, block and armour: `HitResolver.NormalDamage` (minimum 1) for a Hostile ability, `NormalHeal` (no minimum) for an Ally one. Only the three shape scripts apply an amount directly, so any other `ScriptName` is `AbilityAmountKind.None` ("nothing to state", not 0), and so is an ability whose `Effects` give it no direct amount (one that only applies an aura, see Auras); the ability catalog only accepts shape scripts today, so `None` is a safeguard. At select, `AbilityInfo` fields 18-20 (`AmountKind`, `AmountMin`, `AmountMax`) carry them, and `CharacterSelectHandler` records them (`CharacterEntity.AbilityAmountsSent`/`AbilityAmountsSentFor`, World-side, never saved). `AbilityAmountsFlusher`, called from `WorldServer.Update` right after `CharacterSheetFlusher`, works them out again only when `CharacterEntity.Combat` differs from the one last used, and sends `SMSG_CHARACTER_ABILITY_AMOUNTS` (`SCharacterAbilityAmountsPacket`, `0x302C`, every learned ability, whole) to the character's own connection only when an amount changed. `docs/client-combat-protocol-migration.md` has the contract.
- **Heal events (#506 slice C).** `SMSG_UNIT_HEALED` (`SUnitHealedPacket`, `0x310C`: Healer, Target, Amount, CurrentHealth, optional AbilityId, `HitResult` Result) is sent for every heal that restored more than 0 health: `CombatService.ApplyHeal` reports it through its instance (`ICombatOutcomes.UnitHealed`, #546), and `MapInstance` sends it to the healer, the target and every connection within `Game:InterestRadius` of the target (`EffectAudience`, #532), for a target in that instance only. `Amount` is the health restored, overheal left out; `Result` is `Crit` for a critical heal and otherwise None. A heal on a target at full health sends nothing.
