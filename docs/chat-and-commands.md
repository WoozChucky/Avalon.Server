# Chat and commands

Chat commands (how to add one, access levels, failure reporting), the length of a message, the names a player sends, chat channels, whispers, the chat rate limit and the ignore list.

## Chat Commands

Commands live in `Avalon.World/Chat/` (the party commands in `Avalon.World/Parties/PartyCommands.cs`, the ignore commands in `Avalon.World/Social`). To add a new command:
1. Implement `ICommand`: `Name`, `Aliases[]`, optionally `RequiredAccess` and `ReadsRawText`, and `void Execute(CommandContext ctx, string[] args)`. A command that reads its text from the message as typed (`CommandText`: the text after the command word, or its first word and the rest, as slices of the message) and never its arguments declares `ReadsRawText => true`: the dispatcher then hands it an empty array instead of a string for every word (#973); `/p` and `/w` do. Every other command gets its arguments, as before.
2. Register as `services.AddSingleton<ICommand, YourCommand>()` in `ServiceExtensions.AddWorldServices`.
3. `CommandDispatcher` resolves all `ICommand` registrations from DI automatically (name and aliases, case-insensitive).

**A command runs on the tick, to completion, and never awaits.** `ChatMessageHandler` calls `ICommandDispatcher.Dispatch(connection, packet)` synchronously on the tick for every `/`-prefixed message within the length rule below, with no continuation around it; `Dispatch` returns false for an unknown command or one the caller may not run, and the handler then answers "Unknown command.". `Execute` returns `void`, so `await` does not compile in it. `ctx.Reply(text)` sends the caller a system line. Work that cannot finish on the tick goes through `ctx.Then(task, callback)` (and `Then(Task, Action)`): the task is handed, settled so it never faults, to `IWorldConnection.EnqueueContinuation`, and the callback runs on a later tick, only once the task has succeeded. `/reload` and `/ignore` (for an offline name, #723) use it; `/godmode`, `/pvp`, `/w`, `/unignore`, `/ignorelist` and the party commands are plain synchronous. `CommandsNeverBlockTheTickShould` scans every `ICommand` in `Avalon.World` by reflection, nested types included (so lambdas and closures), and fails one with an async method or a call to `Task.Result`, `Task.Wait` or `GetAwaiter().GetResult()` (`TickBlockingScan`); it does not follow calls into other types or look for other blocking calls such as `Thread.Sleep`, so those stay the author's to avoid.

`ICommand.RequiredAccess` defaults to `AccessLevels.Player`, so a command that declares nothing stays runnable by any logged-in player — `Tournament` and `PTR` included: they are players with exactly the Player permission set, differing only in which worlds they may enter, and the API's Player policy lists them too; the staff commands declare more: `/reload`, `/god` and `/spawn` `AccessLevels.GameMaster`, `/maintenance` `AccountAccessLevel.Admin`. `CommandDispatcher` reads a message by dropping every leading slash and cutting it at spaces (the space character only, empty pieces left out, nothing quoted): the first piece is the command word, in any case, and the rest are the arguments as typed (`CommandDispatcherShould`). The word is looked up as a slice of the message, so a message that names no command, or one the caller may not run, allocates nothing, and a command that runs is given a context and its arguments and nothing else is made (#883); one that declares `ReadsRawText` is given no arguments, so `/p` and `/w` make only the context and the one string of the text they send on (#973). `CommandDispatcher` checks `RequiredAccess.Allows(connection.AccessLevel)` — a mask test, not an ordinal one, because `AccountAccessLevel` is `[Flags]` and `Tournament`/`PTR` are not above `Admin`, so a `>=` comparison would let either through a `GameMaster` gate. A caller without access gets exactly "Unknown command.", the same as a caller who typed a command that doesn't exist — the dispatcher never reveals which commands are staff-only. `IWorldConnection.AccessLevel` has no setter: `Avalon.World.Public` is the future modding API, and a settable access level there would let a mod promote any player to GM. The server assigns it through `IAccessLevelAssignable` in `Avalon.World`, once, when the connection is admitted (`WorldConnection.PublishAdmission`, from the level the API read when it activated the game session, before `AccountId` is published, so the maintenance cutoff can tell an Admin waiting at character selection and leave it connected). Every session heartbeat (15 s) compares the account's level and credentials version with the admitted ones, and a change revokes the lease and ends the connection, so a promotion or demotion takes effect through a new admission. Do not drop the admission assignment: without it every Admin still at character selection is closed at the maintenance deadline.

**`/spawn` (GameMaster, a testing tool).** `/spawn <creature> [count] [radius] [idle]` (`SpawnCommand` in `Avalon.World/Chat`, synchronous) spawns `count` creatures of one template (1 to 50, default 1) over a disc of `radius` metres around the caller (1 to 40, default 10, inside the 60 m interest radius so every spawn reaches the caller's client; a decimal is read with a dot on any culture), in the caller's instance, towns included. The creature is a template id, or a name: every word before the first number or `idle` (chat splits on spaces), matched ignoring case, a name equal to it first, else the one name containing it; several answer "'<text>' matches several: <id> <name>, ..." (at most five), none "No creature template matches '<text>'.", and anything else malformed the usage line. The points are a golden-angle spiral, so any count covers the disc without clumping; each goes through `ICreaturePlacementService.SpawnAt`, which snaps it to the navmesh, and a point with no ground is skipped and counted. `idle` spawns them without their AI script (`SpawnAt(..., withScript: false)`), standing where they are placed; without it they behave as their template says. Each spawn leaves after 10 minutes through the instance's summon expiry (`IItemUseHost.DespawnAfter`, as item summons do) and dies and is removed like any creature; nothing respawns or is saved. The answer is one line: "Spawned 20 Grey Fen Wolf (idle).", "Spawned 18 Grey Fen Wolf; 2 found no ground." or "No Grey Fen Wolf could be placed: no ground nearby.". It exists so a scene with a known number of creatures can be built on any generated layout (the game client measures its per-creature costs with it).

**Every failure is reported one way, synchronous or not.** A command that throws, a task handed to `ctx.Then` that faults or is cancelled, and a `Then` callback that throws all reach `CommandDispatcher.ReportFailure`: logged at Error with the command and account, and told only to a caller holding the `GameMaster` or `Admin` flag, as `Command /<name> failed: <ExceptionType>.` (the type name only, the message and stack stay in the log; a cancelled task reports `TaskCanceledException`, a task with several exceptions `AggregateException`). Everyone else, `Console` included, gets silence, because an error line would reveal that the command exists and what broke inside it. A command that throws still counts as dispatched, so nobody gets "Unknown command." for it.

**Message length (#936, owner decision).** A chat message is at most 511 bytes: the whole `CChatMessagePacket.Message` as sent, command word, name and text together, counted as UTF-8 (`ChatMessageLimit.MaxBytes` in `Avalon.World/Chat`). That is the game client's own bound, so a client that follows it is never refused: its chat box takes 255 bytes, and the longest message it builds is a whisper typed after `/w Name`, sent as `/w `, a name of at most 252 bytes, a space and 255 bytes of text. A client that sends more must have the constant raised with it. A longer message is refused whole, never cut. `ChatMessageHandler` checks it first, before it looks for a `/`: nothing is said, no command is dispatched (so no command parses it, looks anything up or answers), the rate limit is neither asked nor spent, and the sender alone gets the system line "Your message is too long and was not sent." (`ChatMessageLimit.TooLong`). No path escapes it: `ChatMessageHandler` is the only handler of `CMSG_CHAT_MESSAGE` and the only caller of `ICommandDispatcher.Dispatch`, every command reads its text from that same packet, and no other client packet carries text into chat or a command. The count allocates nothing for the text a packet decodes to: a message of at most 170 UTF-16 units is within the limit and one of more than 511 is over it without counting, and the rest go through `Encoding.UTF8.GetByteCount`. The decoder turns malformed UTF-8 into replacement characters (three bytes each), so such a message is counted as what it would be sent on as, and can count for more than it took on the wire. A packet with no `Message` field says nothing and gets no answer.

**What a line may carry (#944, owner decision).** A said, party or whispered line goes out without the code points of the Unicode categories Control, Format, LineSeparator and ParagraphSeparator: C0 and C1 controls (tab, carriage return and line feed included), bidirectional overrides, isolates and marks, zero-width characters (the zero-width joiner included, so a joined emoji goes out as its parts), the byte order mark, U+2028 and U+2029, and the format characters past the first plane (the tag characters among them), read as whole surrogate pairs. Everything else goes out as sent, emoji and their variation selectors included, and a surrogate pair is never split. The text is then trimmed at both ends. One function does it for the three (`ChatText` in `Avalon.World/Chat`: `SaysNothing` and `Clean`), so they cannot drift. It runs after the length rule, which counts the message as sent: a message that is too long is refused on what the client sent, never on what stripping would leave of it: the limit bounds what a client may send and the server reads, and stripping only ever shortens a line. **A message that says nothing once stripped and trimmed is no message:** said, it is dropped, nobody hears it and nobody is told; `/p` and `/w` answer their usage line, as they always did for no text; none of them asks or spends the rate limit. A said line is now sent trimmed, as `/p` and `/w` always were. Clean text costs nothing: `SaysNothing` allocates nothing, a said message with nothing to strip or trim goes out as the very string the packet decoded to, and only text that changes is copied, once (on the stack while it is built). Nothing else is stripped: a name typed after `/w` or `/invite` is checked as sent (below), a refusal that repeats it goes to the sender alone, and no server log carries a line's text.

**Names a player sends (#936).** A name that is not a character name (`CharacterName.IsValid`: 3 to 12 ASCII letters, checked as sent, see [inventory and saves](inventory-and-saves.md)) is treated as nobody's, so it is answered as an unknown name and nothing is looked up for it. The database enforces only the name key, not the rule: creation and renames have enforced the rule since #757, and the migration left older names as they were on the owner's word that none breaks it, so a character whose stored name does not follow the rule (none is known) could not be whispered, invited or ignored by name. The four places: `CMSG_PARTY_INVITE` (`PartyInviteHandler`: `NotFound`, and the name is not sent back, so surrounding spaces are no longer ignored there), `/invite` (`NotFound` and "Could not find X."), `/w` ("No player named X is online.", in its usual place after the usage, self and rate-limit refusals) and `/ignore` ("No character named X exists.", in the lookup's place: after the refusals made in memory and the rate limit, which it spends as any lookup does; neither `OnlineCharacters` nor the database is asked). `PartyService.Invite` itself does not check the rule: its two callers do. `/kick`, `/promote` and `/unignore` compare the name with the caller's own party or ignore list only, ask nothing else, and are unchanged.

**Chat channels.** `SChatMessagePacket.Channel` (field 6, `ChatChannel`: `Say` 0, `Party` 1, `System` 2, `Whisper` 3). A message without a `/` is said: `ChatMessageHandler` sends it, stripped and trimmed (above), on `Say` to every connection in the sender's `MapInstance`, the sender included (only to the sender when its instance cannot be found). There is no world-wide chat. `/p` goes to the sender's party on `Party` (see Parties). **Sender's class (#763):** `SChatMessagePacket.CharacterClass` (field 8, the wire enum `CharacterClass`, as the party roster sends it, #922) is the sending character's class on said, party and whispered lines, the whisper's echo included (both copies name the sender in `CharacterName`; the recipient's class is not sent), so a client can colour the name; it is `None` (0) on System lines and on a script's line (`ItemUseContext.Whisper`), which no character sent, and a payload from before it reads as `None`. **Whispers (#717):** `/w <player> <message>` (`/whisper`, `WhisperCommand` in `Avalon.World/Chat`, Player access, synchronous) sends the text as typed after the name (stripped and trimmed, see above; the command word and name found as `/p` finds its text, `CommandText`) to one online character, wherever it is on this world server, on `Whisper` with the sender's name; the sender gets an echo on `Whisper` with `SChatMessagePacket.TargetName` (field 7, set only on that echo) naming the recipient as it is spelled. Refusals are system lines to the sender only, nothing sent to anyone else, in this order: no name or no message (a text that says nothing once stripped and trimmed is none), "Usage: /w <player> <message>"; the sender's own name (ignoring case), "You can't whisper yourself."; no online character with that name, offline and unknown alike, "No player named <name> is online." (the name as typed). Names are looked up in `OnlineCharacters` (`Avalon.World/Characters`, a World-side singleton, tick thread only): online characters by id and by name in any case, ignoring surrounding spaces, as `CharacterName.LookupKey` compares them (#757), but in place: the names are held under `CharacterName.KeyComparer`, which compares two names as their keys compare (ASCII letters in any case, every other character as it is), and are looked up by a slice of what was typed, so a lookup makes no key (#973), fed from the world's online and offline hooks through `PartyService.CharacterOnline`/`CharacterOffline` (a stale connection's offline changes nothing) and read by the party invite and the whisper alike; `PartyService` takes it as an optional constructor parameter, and `WorldHostGraphShould` pins that production hands both the same instance. **Chat rate limit (#722):** `ChatRateLimiter` (`Avalon.World/Chat`, a DI singleton; its refusal line for each whole second of the window is written once, so refusing a message allocates nothing, #883) gives each sending character one sliding 60 s budget of `Game:ChatMessagesPerMinute` messages (default 10 in `appsettings.json`, not in C#; 0 or below turns it off), shared by plain chat (`ChatMessageHandler`), `/p` (`PartyChatCommand`), `/w` (`WhisperCommand`) and `/ignore` (`IgnoreCommand`, #723, owner decision); no other command counts (party invites, `/invite` included, have their own budget of the same kind, `Game:PartyInvitesPerMinute`, see [parties](parties.md), #944). The window is `CharacterRateBudget`, which both use. Callers ask `Check(characterId, out retryAfter)` first, before any recipient or party lookup (so an over-limit sender learns nothing about who is online), and `Record(characterId)` only once the message is delivered, so a refusal (usage, self-whisper, no such player, not in a party) uses no budget. Over the limit the message is not delivered and the sender gets a system line, "You're sending messages too fast. Try again in {n}s." (n = seconds until the oldest counted message leaves the window, rounded up, at least 1). Timestamps come from the injected `TimeProvider` (a queue per sender, pruned on each call, no timers). Chat runs on the tick, so the service needs no concurrency, but every method takes one short lock because the shutdown despawn can reach `Forget` from another thread. `World.LeaveWorldAsync` calls `Forget(characterId)` (logout, leave to character selection, disconnect), so nothing is held for a character that left. **Ignore list (#723, owner design).** A character ignores other characters of its world by id, online or offline: `CharacterEntity.Ignores`, an `IgnoreList` (`Avalon.World/Social`, World-side, never on `ICharacter`, tick thread only; entries are id, name and when added, oldest first). Memory is authoritative and every check is `Ignoring.Hides(listener, senderId)`, with no database query per message: a whisper to a character ignoring the sender is not sent while the sender still gets its echo and the message counts against the rate limit as delivered; `ChatMessageHandler` and `/p` leave the line out for each listener or member that ignores the sender (the sender's own line always goes out); a party invite from an ignored character is answered `Ok` after every usual refusal, never sent, not answerable (`Respond` finds no invite) and kept by `PartyService` per (inviter, target) until it expires, when the inviter alone gets `InviteExpired` (and `InvitePending` meanwhile for a second invite to that target), or until the target goes offline (the inviter told `InviteExpired`) or the inviter does (ended silently). System lines are never filtered, and whispering a character you ignore is allowed. Commands (`IgnoreCommand`, `UnignoreCommand`, `IgnoreListCommand` in `Avalon.World/Social`, Player access, synchronous): `/ignore <name>` refuses, in order, without exactly one name ("Usage: /ignore <name>"), the caller's own name ("You can't ignore yourself."), a name already on the list ("X is already on your ignore list."), a full list (`Game:MaxIgnoredCharacters`, default 50, range 1-500, "Your ignore list is full (50/50)."), and over the chat rate limit (the limiter's own line; an `/ignore` past the four refusals before it spends one message of the budget whatever the lookup finds, while those four, `/unignore` and `/ignorelist` spend nothing), then finds the character in `OnlineCharacters` or, offline, through `ctx.Then(ICharacterIgnoreRepository.FindCharacterByNameAsync(...))` (by `NameKey`, so in any case; names are unique by key, so at most one character matches, #757), whose callback does nothing if the connection no longer holds that character and otherwise re-checks: no such character ("No character named X exists."), itself by id, already listed by id, full; an accepted one is "You are now ignoring X.", and an invite from that character the caller still holds then ends silently (`PartyService.HideInviteFrom`, owner decision: it becomes a dropped invite, so the caller can no longer accept it and the inviter is told nothing new and sees the usual expiry). `/unignore <name>` (by the name the list shows: "You are no longer ignoring X." or "X is not on your ignore list.") and `/ignorelist` ("Ignoring 2/50: A, B." or "You are not ignoring anyone.") never touch the database. `SMSG_IGNORE_LIST` (`SIgnoreListPacket`, 0x30D0: `Characters`, repeated `IgnoredCharacterDto` `CharacterId`, `Name`) is the whole list: sent by `CharacterSelectHandler` once the list is loaded (one more `Step` after the quest rows, before the pending spawn, empty too), after every change, and by the `CMSG_CHARACTER_DELETE` handler (`src/Server/Avalon.World/Handlers/CharacterDeleteHandler.cs`) to each connection holding a loaded list that had the deleted one on it, in the world or selected and waiting to spawn (`IWorldServer.Connections`, `Character` or `PendingSpawn`; taken off in memory there; the rows cascade); a select whose rows were read before the delete committed but applied after keeps the entry until its next select, harmlessly. **Storage:** `CharacterIgnores` (Character DB, migration `AddCharacterIgnores`): `CharacterId`, `IgnoredCharacterId`, `CreatedAt`, key the pair, both foreign keys to `Characters` cascading, an index on `IgnoredCharacterId`. Every change marks `SaveStateTracker.IgnoreChanged(id)`, and the next save carries a `CharacterIgnoreWrite` (built in `CharacterSaveSnapshot`): each marked pair deleted, then inserted again while still on the list, one `INSERT ... SELECT` per entry from the ignored character's row, so a character deleted since it was ignored, or by a delete running alongside the save, skips its row and never fails the save (on Postgres the read takes `FOR KEY SHARE`: a delete committed first is seen, one still running waits for the save and then cascades the row; verified on Postgres 17). Select loads the names the rows hold now (`GetByCharacterIdAsync` joins `Characters`); a rename while the owner is online shows at its next select. `CharacterSelectHandler` takes the repository and the delete handler the `IWorldServer` optionally; `WorldHostGraphShould` pins that production hands them over. **Timestamps (#944).** Every `SChatMessagePacket.DateTime` is the server's clock in UTC when the line is sent (the container's `TimeProvider`: `ChatMessageHandler` and `CommandDispatcher` take it, and a command stamps with `CommandContext.Now`), never the time a client put on its `CChatMessagePacket`, which nothing reads ([packet protocol](networking-packet-protocol.md#open-defect--a-datetime-loses-its-kind)). Command answers, "Unknown command." and every line the server speaks (party joins, leaves, leader and mode changes, leave countdowns, health scaling, quest milestones) are `SChatMessagePacket.System`: channel `System`, sender name "System", account and character 0.
