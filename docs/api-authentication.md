# REST API authentication

How the REST API authenticates callers (access JWTs and personal access tokens), revalidates accounts on every request, rotates refresh tokens, rate limits, and handles credential changes. It runs the same login policy as the TCP auth server ([Auth server](auth-server.md)).

The API runs as four services from one binary (#794, [API services](api-services.md)). Only identity (`Avalon.Api.Identity`) issues credentials: login, MFA, refresh, launcher sign-in, personal access tokens, registration, and every credentials change below. Every service validates a credential itself, with the shared code in `Avalon.Api.Hosting/Authentication` (the bearer handler and its revalidation, the personal access token scheme, the policies), against the one auth database, and never asks another service; production still runs all four in one process until #802.

## REST API Auth

Every API service takes two credentials:
- an access JWT, sent as `Authorization: Bearer` or in the `AVToken` cookie, and minted by identity's `JwtUtils` (ES256, #801) at login, MFA verify and refresh;
- a personal access token, sent as `Authorization: Avalon avp_...` and read by `AvalonAuthenticationHandler`.

**Neither is believed on its own (#451, #480).** On every request both go through `AccountAccessCheck` (`Avalon.Api.Hosting/Authentication`):
- the account is reloaded;
- a missing or non-Active one (Banned, Deactivated) is refused with 401;
- the request carries only `credential roles & account.AccessLevel` as `GroupSid` claims. That is a mask, never `>=`.

For a JWT this runs in `JwtBearerEvents.OnTokenValidated` (`JwtAccountRevalidation`), after the bearer handler has checked the signature, issuer, audience and lifetime. The signature is ES256 (#801): identity signs with its private key under a key id (`Application:Authentication:SigningKey`, `SigningKeyId`), which only a process running identity may hold, and every service checks a token with the public key its key id names (`Application:Authentication:ValidationKeys`; identity knows its own). `ValidAlgorithms` is ES256 alone, and `JwtKeys.Resolve` hands a key only to an ES256 token, the public key its key id names, so an HS256 token (as every token before #801 was), a token naming an unknown key id, an HMAC keyed with a public key, or one with no signature finds none. HS256 is refused whatever is configured: `Application:Authentication:IssuerSigningKey`, the HS256 key of before, is ignored, and a process that still has it warns at startup. The keys and their rotation: [Configuration Reference](configuration-reference.md#rest-api-jwt-signing-key). The loaded account is kept in `HttpContext.Items`, and `AvalonAuthHandler` (the default policy's requirement) reuses it rather than loading it again. A ban therefore takes effect on the next request. A role change, promotion or demotion, raises the credentials version (#504), so every token issued before it is refused and the account signs in again to get its new roles. A database failure during that lookup is a 503 (`ExceptionHandlerMiddleware` maps `DbException`), never a pass.

The JWT's lifetime is enforced: `ValidateLifetime = true`, with `AccessTokenLifetimeMinutes` (default 15) plus `ClockSkewInMinutes`. An expired JWT gets a 401, and the client renews it with `POST /account/refresh`. That endpoint is `[AllowAnonymous]` and reads only the HttpOnly refresh cookie, so an expired access token does not stand in its way.

**A refresh token rotates once (#495).** `RefreshTokenRepository.RotateAsync` revokes the parent with a conditional `UPDATE ... WHERE Id = @id AND NOT Revoked` and inserts the child, in one transaction, only when that write revoked the row: of two rotations of one token that both read it live, exactly one gets a child. The other (`RefreshRotation.ParentNotLive`) is answered as the same token presented a moment later would be. A revoked token presented within `RefreshTokenService.RotationGrace` (5 s) of the rotation that replaced it, while that rotation's child is still unused (not revoked, `Usages == 0`) and by the caller that rotated it (the child records its source, the login budget's IPv4 address or IPv6 /64, in `RotatedBySource`, and a SHA-256 of its User-Agent in `RotatedByAgentHash`; `RefreshCaller`; a caller whose address, after the forwarded-headers middleware, is still a trusted proxy (loopback or `Application:ForwardedHeaders` proxies and networks, i.e. a proxy that forwarded no client) gets no source and so never the grace, since everyone behind that proxy shares it), is two tabs or a client retry: 401 (`RefreshAlreadyRotatedException`), with the family, the refresh cookie and the account's sessions left alone. Anything else is a reuse: the family is revoked, `RefreshTheftException`, a world disconnect is published, the cookie is cleared and the caller gets 401. A reuse is logged at Warning with the account, the family and which condition of the grace it missed (no successor, successor revoked or used, after the grace, caller without a source, another caller), never the caller's address or the token, so a session ended by two tabs refreshing at once can be told from a sign-out.

**Nothing issues a credential to an account that is not Active** (`AccountAccessCheck.MayHoldSession`):
- password login (`AccountService.Authenticate`) checks after the BCrypt verify, and MFA verify after the code is accepted. Both throw `AccountInactiveException`, which `ExceptionHandlerMiddleware` answers as 403 ProblemDetails with `Detail` BANNED or DEACTIVATED, as the game client is told. A wrong password or bad code still gets the generic 401, whatever the status, so nothing about the account leaks before the proof;
- refresh revokes every refresh token the account holds, clears the cookie and returns 401.

**REST login and MFA verify run the game client's login policy (#478).** `AccountService.Authenticate` runs `PasswordLoginPolicy` and `MFAController.VerifyMFA` runs `MfaLoginPolicy`, the classes `CAuthHandler` and `CMFAVerifyHandler` run, in the same order: source slot, username slot before the lookup (a dummy BCrypt verify for an unknown username), the row's lock before the password or code, per-hash attempts (the last wrong code deletes the hash), failures counted with `RecordFailedLoginAsync` and locking in the budget's last slot, and on a completed login the source's slot back and the username's count cleared. The keys are the same on both servers, so a guess over REST and one over TCP spend one per-username budget and lock at one threshold; the per-source key is shared too, since that budget is per address across every account and a guesser must not get it twice by splitting guesses between servers. The API's source is `HttpContext.Connection.RemoteIpAddress` after `UseAvalonForwardedHeaders` (`Avalon.Api.Hosting/Middlewares/ForwardedHeadersSetup.cs`), which believes `X-Forwarded-For` only from loopback and from `Application:ForwardedHeaders:{KnownProxies,KnownNetworks}` (with `ForwardLimit`, default 1; Helm `forwardedHeaders.*`). Behind an ingress not listed there every REST caller is one source, so outside Development the API warns at startup when none is configured, and it logs a header from an untrusted peer at most once a minute (`UntrustedForwardedHeaderLog`). An entry that does not parse, a trusted network wider than /8 (IPv4) or /32 (IPv6), `0.0.0.0/0` and `::/0` included, or a limit below 1 stops startup. A caller with no peer address has its `X-Forwarded-*` headers dropped before they are read, so it cannot name one, and is refused with 400 on every endpoint that spends a source budget (`BaseController.SourceAddress`), rather than sharing one `IPAddress.None` budget. A locked row pays the same dummy BCrypt verify as an unknown username, so it does not answer faster when its budget hold is gone. A refusal by a budget or a locked row, and the failure in the last slot, is **429** ProblemDetails with `Detail` `LOCKED` (`AccountLockedException`); a wrong password or code stays the generic 401, and 403 `BANNED`/`DEACTIVATED` still comes only after the proof (#480). HTTP cannot answer before its write, so an unknown username runs the same failure statements against `LoginPolicy.NoAccount` (id 0, which no account has). A REST login never touches `Online`, the game client's session flag: the success write is `TryRecordApiLoginAsync` (by column, refused while locked, answered as a wrong password in that slot). The limits are `Application:Authentication:{MaxFailedLoginAttempts,LockoutDurationMinutes,MaxFailedLoginsPerSource,FailedLoginSourceWindowMinutes,MaxFailedMfaAttempts}`, read by identity, defaults equal to the Auth server's, which they must match; identity's registration (`AddIdentity`, `LoginLimitsValidation.Validate`) refuses one below 1, and the Auth server and every API process running identity log all five at Information at startup (`LoginLimitsValidation.LogAtStartup`) so a drift shows.

**Sensitive actions need the current password (#478, #483).** `IReauthentication.RequireCurrentPasswordAsync` runs `PasswordLoginPolicy` against the signed-in account, so a wrong current password is a failed login in every respect (both budgets, the row's count, the lock); a right one gives back only its own slots. It guards `POST /account/password`, the start of an email change (`InitiateEmailChangeAsync`, a `currentPassword` field, #503), `POST /mfa/setup` (was `GET`; body `SetupMFARequest { currentPassword }`), and `POST /pat` and `POST /pat/admin` (a `currentPassword` field; the admin route takes the admin's own, since it can mint for any account, the admin's included). Missing or wrong: 401 `Invalid current password`; budget spent or account locked: 429 `LOCKED`. New passwords are measured trimmed, the form they are hashed in: `POST /account/password` (`newPassword`) and `POST /account/register` (`password`, with `username` and `email` required) refuse one under 8 characters with a 400 validation error (`TrimmedMinLengthAttribute`).

**Every request is rate limited (#561)**, on top of the budgets above, which count attempts and are unchanged. `ApiRateLimiting` (`Avalon.Api.Hosting/Middlewares`) puts ASP.NET Core's limiter, a sliding window of one minute in six segments, in memory, after `UseAuthentication` and before the world routes and authorization. Each API process counts only the requests it serves: one process today, and once the services run apart one budget per service process (and per replica), while the attempt budgets above stay in Redis, shared. A request with a valid JWT (after its account revalidation) or personal access token (authenticated there, since it is not the default scheme, and only on an endpoint that requires authorization, while enabled, and while its source has failed fewer than `FailedPatLookupsPerMinute` (10) lookups and has fewer than 2 in flight, so made-up tokens cannot force a query per request; the handler's cached result is reused by authorization) counts against its account, `AuthenticatedPermitsPerMinute` (default 300); any other, an invalid token included, against its source, `RemoteAddress.SourceOf` after the forwarded headers (IPv4 address, IPv6 /64), `AnonymousPermitsPerMinute` (default 60), and so does a PAT on the public endpoints (`/public/...` have no `IAuthorizeData`, so it is not identified before the limiter; it counts against its source's anonymous budget, and `PublicCaller` looks it up afterwards, outside the `FailedPatLookupsPerMinute` budget); every caller with no peer address shares one "unknown" partition. `/health` and `/alive` are exempt (`DisableRateLimiting` in `MapDefaultEndpoints`). A refusal is 429 ProblemDetails `LOCKED` with `Retry-After` (a lower bound, one segment when the limiter gives no hint), alike for both partitions, and increments `avalon.api.rate_limit.rejections` (meter `avalon-api`, tag `partition`). Settings under `Application:RateLimiting` (`Enabled` too); a limit below 1 fails the startup validation `ApiStartup` runs, naming the setting.

**Registration is budgeted per source (#495).** `POST /account/register` still answers "Username already exists" and "Email already exists" (a registration form cannot hide a taken username, and merging the two answers would still reveal the email by pairing it with a fresh username), so it takes a slot from the source's budget (`SourceBudget`, the key TCP and REST logins spend) before any lookup; past the budget it is 429 `LOCKED`, whatever the name. A registration that creates its account gives the slot back; "already exists" and every other ending keep it. That budget alone does not bound account creation, since successes are refunded, so a second, separate cap counts created accounts per source: `Application:Authentication:MaxAccountsCreatedPerSource` (default 5) per `AccountCreationWindowMinutes` (default 60, fixed from the first), on `auth:source:{source}:accountsCreated`. Its slot is taken just before the insert and given back only when no account comes of it; past the cap the answer is 429 `LOCKED`. API only; startup refuses a value below 1. A caller with no peer address is refused with 400, as at login.

**A password change and an MFA reset revoke every token (#483).** `ChangePasswordAsync` writes the verifier by column (`AccountRepository.SetPasswordAsync`, a compare-and-set on the `CredentialsVersion` the current password was checked at, so of two changes that proved the same password only the first lands and the other is 401 `Credentials changed; sign in again`, #495 review) and revokes every refresh token and personal access token in one transaction; `MFAService.ResetMFAAsync` (both servers) deletes the confirmed row and revokes both kinds in one transaction (`MfaSetupRepository.ResetConfirmedAsync`, which also makes a concurrent second reset fail). Each then publishes the account on `world:accounts:disconnect`, best-effort, as the admin MFA removal (#475) and a ban do. `POST /mfa/reset` returns 204 and enrols nothing: the client enrols again with `POST /mfa/setup`, which needs the password, since recovery codes are not the password.

**A role change and an email change are credentials changes (#503, #504).** `AccountService.UpdateRolesAsync` (`PATCH /account/{id}/roles`, now with the admin as `actorId`) writes the level and raises the version in one statement (`AccountRepository.SetAccessLevelAsync(context, ...)`), and revokes every refresh token and personal access token in the same transaction; a promotion does it too, since only a new login gets the new roles onto the game client's TCP session. `ConfirmEmailChangeAsync` does the same with `AccountRepository.SetConfirmedEmailAsync(context, ...)`, which also records the new address as verified (`EmailVerifiedAt`, since the confirmation proved it), a compare-and-set on the version the current password was checked at when the change was started (the pending change in `auth:emailChange:{sha256(token)}` is `{accountId}|{version}|{email}`), so a credentials change in between voids it, answered "Invalid or expired token". Each then clears the account's pending MFA login state and publishes the account on `world:accounts:disconnect`, best-effort, as a password change does. **Email change is on only when `Application:Email:Sender` is configured (#510):** identity's `IdentityServiceRegistration.AddEmail` registers an `IEmailSender` (`Avalon.Api.Identity/Services/Email`) for a configured sender, `Pickup` or `Resend`, and none for `None`, the default, and `AccountController` takes it as an optional dependency: with none, `POST /account/email/change` and `POST /account/email/confirm` both answer 501 ProblemDetails "Email change is unavailable until email delivery exists" and never reach the service. `Pickup` (`PickupEmailSender`) writes each email as an RFC 5322 `.eml` file into `Application:Email:PickupDirectory` (default `avalon-mail` under `Environment.SpecialFolder.LocalApplicationData`, created 0700 on Unix), refuses a line break in the recipient or subject, and is Development-only: startup refuses it elsewhere, naming `Application:Email:Sender`, and refuses it without a bare-address `Application:Email:From`. With a sender, the start sends the confirm token to the **new** address and a notice with no token to the old one, and answers 202 with no body; the token is never in the response or a log (sender failures are logged by exception type and recipient domain only). Before anything is stored or sent, the start takes a slot of two send budgets that are never given back, per account and per new address (keys above; past either, 429 `LOCKED`). Accepted: the per-address send budget can be spent by any accounts, so three accounts can block an address as a change target for the window; account creation is capped per source, which keeps the impact small. Once its confirmation is sent, a new start deletes the account's earlier pending change, so only the latest token confirms; a start that could not send leaves the earlier one intact. Once the change is stored, each email is sent with its own `AccountService.EmailSendTimeout` (30 s) token, never the request's, so a caller dropping the connection cannot suppress the notice. A confirmation that cannot be sent deletes the pending change (a failed delete is logged by exception type, and the key expires on its TTL) and is 503 "Email could not be sent" (`EmailDeliveryException`), keeping the source slot and both send slots; a cancelled send is logged at Information, any other failure at Error. A failed notice is a Warning and the change still starts. `Resend` (`ResendEmailSender`) is the one real provider: it sends plain text through Resend's HTTP API with `Application:Email:ResendApiKey` and a bare `Application:Email:From` (and an optional `FromName`), once, with a 30 s timeout and no retry, since a send whose outcome is unknown must not be repeated; startup refuses it without a key or a valid `From`. A sender that delivers the email and then throws (a timeout after the provider accepted it, say) leaves a delivered token whose pending change was deleted. That fails closed: the token answers "Invalid or expired token" and the player starts again, within the send budgets.

**Credentials version (#495).** `Accounts.CredentialsVersion` is an integer raised by one, as the first statement of the change's transaction, by every password change (`AccountRepository.SetPasswordAsync`), role change (`SetAccessLevelAsync`, #504), email change (`SetConfirmedEmailAsync`, #503), owner MFA reset (`MfaSetupRepository.ResetConfirmedAsync`, both servers) and admin MFA removal (`AccountService.RemoveMfaAsync`, via `BumpCredentialsVersionAsync`). Whatever a proof of the credentials issues carries the version of the very row the proof was checked against, and every check is an equality with the account's current version: the access JWT's `cver` claim (`JwtUtils.CredentialsVersionClaim`; `JwtAccountRevalidation` refuses a missing, malformed or different one with 401); each refresh token's `CredentialsVersion` column, set when its family is opened and copied to every child (`IssueAsync(accountId, version)` at login, MFA verify and registration, and every rotation, refused when it no longer matches; the refresh endpoint also refuses when the account read after the rotation is at another version); the MFA hash's own reverse key, `auth:mfa:hash:{hash}` = `{accountId}:{version}` (`IMFAHashService.GetHashCredentialsVersionAsync(hash)`, -1 when absent; the presented hash's version, never the per-account record's, since two logins racing with the old and the new password share that record, #495 review; `MfaLoginPolicy` treats a mismatch as a hash that is gone, on both servers, checked before an attempt is counted so a stale presentation spends none of a newer login's tries, and `CleanupHash` deletes the per-account record only while its `hash` field is the hash being cleaned (`RemoveHashIfFieldEqualsAsync`, one Lua script), and a live hash is reused only at the same version); `Reauthenticated(AccountId, CredentialsVersion)` for a personal-access-token mint (the admin's own account on `POST /pat/admin`); and, on TCP, `IAuthConnection.CredentialsVersion`, set at login and MFA verify and checked by `PostLoginGuard`; for world entry, the game context's version, which a join ticket carries and which its issue, its redemption and every game-session heartbeat check against the account, so a game session ends at its next heartbeat once the version moves. Issuing a refresh token, rotating one and minting a PAT each open their transaction with `AccountRepository.HoldCredentialsVersionAsync`, a no-op `UPDATE ... WHERE Id = @id AND CredentialsVersion = @v`: it takes the row lock, so a change that committed first refuses them, and one still in flight waits for them and then revokes what they issued. A password change also clears the account's pending MFA state in Redis, as an admin's MFA removal does. A refused refresh issue or PAT mint is 401 `Credentials changed; sign in again`.

**The API writes account rows by column (#478)**, as the Auth server has since #484: login and MFA verify `TryRecordApiLoginAsync`, password `SetPasswordAsync`, email `SetConfirmedEmailAsync`, roles `SetAccessLevelAsync` (the last three on the context of the transaction that revokes the tokens). None writes back a row it read, so a ban or a lock written in between survives (`ApiWriteRaceShould`).
