# Quests (server design)

Server-side rules for quests. The client contract is [Quest protocol](quest-protocol.md).

## Quests

Quests (#433): NPCs offer and take back quests through their dialogue; kills, conversations, collected items and quest scripts move a quest through its ordered stages; a turn-in pays experience, gold and items. `docs/quest-protocol.md` is the client contract.

- **Data** (World DB reference data, migrations `ReshapeQuests`, `SeedQuestStoryline`, `AddUseDoodadObjectives`, `SeedBoarCullDaily` and `AddQuestChoiceRewards`): `QuestTemplates` (title, description and completion texts as `LocalizedTextId`s, giver and ender creature templates, `LevelRequirement`, nullable `ClassRequirement`, one nullable `RequiredQuestId`, `RewardExperience`, `RewardGold` (`RewardMoney` until migration `RenameRewardMoneyToRewardGold`, #1173), `RewardTalentPoints` (#1181, migration `AddTalentTree`: the talent points a turn-in pays, 0 by default, `CK_QuestTemplates_RewardTalentPoints` at least 0; 1 on quests 3, 7 and 8; `QuestView.RewardTalentPoints`), nullable `ScriptName`; `Environment`, `Type` and `Rarity` are kept but unread; `IsRepeatable` and nullable `RepeatFrequency` (`None` 0, `Daily` 1, `Weekly` 2, `Monthly` 3) are read as one repeat kind, `QuestView.Repeat` (#710): `Once` when not repeatable, `Repeatable` (again at once) for a null or `None` frequency, else `Daily`, `Weekly` or `Monthly`; the catalog refuses a frequency on a quest that is not repeatable, a frequency value it does not know, and a repeatable quest that pays talent points (#1181: so each point is earned once)), `QuestStages` (keyed `(QuestId, Sequence)`, an optional description text; `CK_QuestStages_Sequence`), `QuestObjectives` (an id set in the data, unique across quests; its stage, type `Kill` 1, `Collect` 2, `Talk` 3, `Scripted` 4 or `UseDoodad` 5, a creature, item or doodad template target (`DoodadTemplateId`, a `Restrict` foreign key to `DoodadTemplates`), `Count`, a description text; `CK_QuestObjectives_TargetFitsType` pins exactly one target per type, Kill and Talk a creature, Collect an item, UseDoodad a doodad template, Scripted none; `CK_QuestObjectives_CountPositive`), `QuestItemRewards` (fixed items, every one paid), `QuestItemChoices` (#711: the choose-one set, of which a turn-in pays exactly the one item the player picks; shaped as `QuestItemRewards`, keyed `(QuestId, ItemTemplateId)`, a `Count`, a `Restrict` foreign key to `ItemTemplates`, `CK_QuestItemChoices_CountPositive`; a separate table rather than a flag on the fixed rows, so fixed and choice cannot be confused; a quest has fixed items, a choice set, both or neither) and `QuestItemDrops` (a Collect objective's item from a creature at `Chance` percent; `CK_QuestItemDrops_Chance`). The old `QuestRewards`/`QuestRewardTemplates` tables are gone. `ItemTemplateFlags.QuestItem` (2048) marks a quest item, and `ItemSubClass.Amulet` (206, an Armor subclass, worn in Neck) was added for the storyline's pendant; both are in the API contract enums too.
- **Catalog.** `QuestCatalog` (`Avalon.World/Quests`; the Quests reload area, `StaticData.Quests`, empty before the first load) validates every quest against the creature, item and doodad templates read in the same prepare, refuses a bad one with an Error naming it (`QuestRefusal`), and loads every other. It refuses an id of 0 or above `int.MaxValue` (quest options carry it negated), a repeat frequency on a quest that is not repeatable or a frequency value it does not know (#710), talent points below 0 or a repeatable quest that pays any (#1181, `a repeatable quest pays no talent points`), a missing giver or ender, a quest that is its own prerequisite, no stages, stages not numbered 0..n, a stage with no objectives or more than 4 (`MaxObjectivesPerStage`), an objective naming a stage the quest lacks, a count of 0, a target that does not fit the type, a missing creature or item, a missing doodad template or one whose `Interaction` is not `Click` (nobody could use it), a Collect item that is not a `QuestItem`, one quest collecting an item twice, drops on an objective that is not Collect (no check constraint can say it), a drop from a missing creature or outside 0-100, a missing or zero-count reward item, one flagged `Unique` (own one copy), or one of `Unique` rarity (#1179: a unique's stats are its unique modifier, rolled per copy, so no quest pays one; `ItemUseRules.QuestRewardProblem`, which the API's live item edit also applies to a template a quest names), a choice set (#711) of other than 2 to 6 items (`MinItemChoices`, `MaxItemChoices`: one would be a fixed reward in disguise, more than six is more than a client lays out well in one offer; none is fine), an item both a fixed reward and a choice of the same quest (the pick would be ambiguous to read), a missing, zero-count or `Unique` choice item (the fixed reward's checks), a `Scripted` objective on a quest with no `ScriptName` (only its script can move it), and a `ScriptName` that is not a loaded `QuestScript` (`IScriptManager.GetQuestScript`). It also refuses a giver, an ender or a Talk objective's creature whose template has no dialogue root (#737, `has no dialogue root`), against the `DialogueNodes` read in the same prepare, startup included, since `InteractHandler` opens a conversation only at a root and such a quest could never be accepted, handed in or finished. The other direction refuses nothing: applying a dialogue patch, or a quests patch (whose prepare may have read other roots than the ones live), logs one Error per loaded quest whose giver, ender or Talk target has no root in the live dialogue, listing its problems (`QuestCatalog.NpcsWithoutDialogue`, from `StaticData.Apply`), and the quest stays loaded until a `/reload quests` refuses it. In the same way, applying a doodads patch or a quests patch logs one Error per loaded quest with a UseDoodad objective whose template the live `DoodadCatalog` lacks (refused, or gone) or is not `Click` there (`QuestCatalog.DoodadObjectivesNotUsable`, from `StaticData.Apply`; `StaticDataReloadShould`), since the quests prepare checks the doodad rows it reads, not the catalog they become; the quest stays loaded and refuses nothing. Markers are unchanged, still built from the catalog. Then, to a fixed point, a quest whose prerequisite is in a cycle, missing or refused, and, by id, every later quest collecting an item an earlier surviving quest collects, so a drop or a pickup credits exactly one quest. A `QuestView` lists its fixed items (`ItemRewards`) and its choice set (`ItemChoices`, empty when none) by item template id, so every consumer shows the same order. `GivenBy` (by level then id), `EndedBy` (by id), `DropsFrom` and `IsQuestNpc` are its lookups. `/reload quests` rebuilds it, effective from the next tick; characters keep the quests they hold, and a held quest the catalog no longer has is left out of the log, counts nothing, and can still be abandoned. **Every held quest is settled once against a new catalog (#738)**: `QuestFlusher`'s first step, `QuestService.SettleAfterReload`, compares `QuestLog.SettledCatalog` (never saved; set by the select recount) with the catalog by reference and, once per reload, caps each count above its objective's count, recounts the current stage's Collect objectives, sends a `ReadyToTurnIn` quest back to `Active` ("X: no longer ready to turn in.") when its stage is no longer the last or a Collect objective of its last stage is short in the Bag, and settles the stages (so a stage added after the last starts), with the usual lines and updates. `TurnIn` and `DialogueOptionsFor` run the same check first (one reference compare), so a turn-in or an NPC's options on the reload tick, before the flush, see settled quests. The select recount (`RecountAtSelect`) does the same settle quietly, so a reload while a character was offline is settled at login. A quest whose current stage a reload removed is left as it is (abandon still works) and logged at Warning, at most once per quest per 10 s; a ready quest whose Kill or Talk count a reload raised stays ready.
- **`QuestService`** (`Avalon.World/Quests`, a DI singleton, World-side): everything a quest does at run time. **Tick thread only**, no timers and no awaits: its callers are the three quest handlers, `InteractHandler`, `DialogueChooseHandler`, `LootPickupHandler`, `MapInstance.CreatureKilled`, `DoodadUseService`, `CharacterSelectHandler` and `QuestFlusher`; the clock is read only to stamp accept and completion times and the lines, and to build the service's own reset clock (`QuestService.Resets`) when the container hands it none (production injects the `QuestResetClock` singleton). It changes a character only through its `QuestLog`, `IInventoryService` and `IWallet`. Its walks over a character's quests that can settle one or run a script's hook (the kill credit, a conversation, a doodad use, the Bag recount) go over a copy the log keeps for the walk (`QuestLog.BeginWalk`, given back with `EndWalk` in a `finally`; one list per walk in progress, emptied when it ends), so the walk covers the quests held when it began, each once, whatever a hook does to the log meanwhile; a kill, a doodad use, a Bag change or a pickup that moves no quest allocates nothing, and a quest without a script costs its hooks nothing (#883, `QuestAllocationShould`; the doodad use, `QuestDoodadCreditShould`). `MapInstance`, `WorldServer` and every handler but the three quest handlers take it as an optional dependency; `WorldHostGraphShould` pins that production registers it, `QuestProgress` and `ICharacterQuestRepository`, and that `InteractHandler`, `DialogueChooseHandler`, `CharacterSelectHandler` (with the repository too) and `LootPickupHandler` receive it (`Hand_the_quest_service_to_the_handlers`).
- **Availability** (`QuestAvailability.Check`, pure but for the reset clock's boundaries, in this order): not held, and never turned in or available again by its repeat kind (#710: `Once` never; `Repeatable` at once; `Daily`, `Weekly` and `Monthly` when the quest's last turn-in is before the latest boundary of its frequency in `QuestService.Resets`, the world's `QuestResetClock`, so a turn-in exactly at a boundary counts as after it), the prerequisite turned in at least once (a reset never locks a quest behind a repeatable again; vendor gates, `QuestRequirementState.Completed`, likewise mean "at least once"), `Level >= LevelRequirement`, the class when one is required, the script's `CanAccept`, then room in the log (`Game:MaxActiveQuests`, default 20, range 1-100). All but the last answer `NotAvailable`; a full log answers `LogFull`, and a quest refused only by a full log is still offered and still marked available, so the accept can say why.
- **Dialogue.** `QuestService.DialogueOptionsFor` adds quest options only at the NPC's root: one `QuestTurnIn` per quest this NPC ends that the character holds `ReadyToTurnIn` (by id), then one `QuestOffer` per quest it gives that is `Ok` or `LogFull` (by level, then id); `InteractHandler.Send` puts them before the node's own options. An option's id is the quest id negated, and `SDialogueOptionInfo.QuestId` (field 4) names the quest. `DialogueChooseHandler` hands a negative option id, after its usual checks (alive, the NPC there and alive, the leash, the node), to `QuestService.TryChoose`, which sends `SMSG_QUEST_OFFER` only for an option this character is offered at this node now (anything else is logged and ignored) and leaves the conversation where it is. `InteractHandler` contains the options and the talk credit: a quest that throws loses them, and the NPC still opens.
- **Accept, abandon, turn-in.** `Accept` and `TurnIn` first check the conversation: the character alive and `CurrentDialogue` with that NPC (else `NoConversation`), the NPC in the instance and alive (else `NoConversation`, ending the conversation out loud), inside `NpcInteraction.IsWithinLeash` (else `TooFar`, ending it), as the dialogue leash rule above requires. **Accept:** the quest known and this NPC its giver (else `NotAvailable`), then availability; it starts at stage 0 with every count 0 ("Quest accepted: X."), runs the script's `OnAccepted` then stage 0's start, settles, and re-sends the NPC's root. **Abandon**, anywhere in a map: `NotActive` unless held; every copy of the quest's Collect items leaves the Bag and the Bank, but a stack offered in a face-to-face trade (#1175, [trading](trading.md#locks-and-reservations)), which stays where it is, the quest and its progress are dropped ("Quest abandoned: X.", "#id" for a quest the catalog lacks), and it can be accepted again. **Turn-in, all or nothing:** held and known (else `NotActive`), this NPC its ender (else `NoConversation`), the Bag recounted as it is now, then `QuestTurnInRules.Decide`, pure: `ReadyToTurnIn` and the last stage's Collect items all in the Bag, counting only stacks not offered in a trade (#1175: a locked Collect stack makes the turn-in `NotReady`), the pick (#711, `CQuestTurnInPacket.ChoiceItemTemplateId`, an item template id, 0 for none) one of the quest's choice set, or 0 for a quest without one (else `InvalidChoice`: a missing pick, a pick outside the set, or any pick on a quest without a set, refused rather than ignored so a client bug shows; `QuestTurnInRules.Choice` walks `ItemChoices` by index and allocates nothing; the pick names a template, not a place in the list, so a `/reload` that changed the set between offer and turn-in cannot turn it into another item), every reward template, the fixed ones and the pick, known, and the template it is paid as (`QuestTurnInRules.PaidAs`, #1179: a base's best tier at the quest's level, else itself) one a quest may pay (`ItemUseRules.QuestRewardProblem`: not flagged `Unique`, not of `Unique` rarity; else `Error`, logged at Error naming the quest and the template, since a reload made it unpayable), the fixed rewards plus the pick, as paid, fit the Bag as it will be once the quest items have left (`Fits`, stacking as `TryAdd` does: a locked stack stays and is not filled, a slot a completing trade reserved is not free, and a rolled base is one copy per slot whatever it stacks to; else `BagFull`), the gold under `Game:MaxGold`, counting gold a completing trade is about to pay (else `GoldCap`). Only then are the quest items taken (Bag and Bank), the experience granted, gold and items (the fixed ones, then the pick) paid, the quest completed ("Quest completed: X."), a quest paying talent points says so ("You gained 1 talent point." or "You gained N talent points.", #1181) and owes the talent window its state, which the tick's `TalentFlusher` sends ([talents](talents.md)), and the root re-sent. A step refusing after the checks passed is logged at Error and not rolled back (the `VendorTrade` stance). The root re-sent after an accept or turn-in is contained: a throw there is logged at Error, throttled per quest, and the request is still answered `Ok`, since it has happened. A repeatable quest may be accepted again once availability allows it (#710); its accept is a first accept, and its turn-in updates its completion record (below). A choice set is offered whole to every class (owner decision: a Wizard may pick the Warrior's sword; equipping it still checks its level and attribute requirements, `RequiredLevel` and `ItemTemplate.MeetsAttributes`, #1179), and a repeatable quest with one asks for a pick at every turn-in: nothing remembers the last.
- **Progress.** `AddProgress` adds to one objective of an Active quest's current stage, capped at its count; it refuses 0, a quest not Active, an objective outside the current stage, and any Collect objective. **Kill:** `MapInstance.CreatureKilled` calls `QuestService.CreatureKilled` (`CreditQuests`, contained) with the kill's `PartyEligibility` list, before the drops and the experience: every eligible character (the killer alone outside a party; dead members included) gets +1 on each Kill objective for that creature template in the current stage of each Active quest, wherever the kill happens. **Talk:** `InteractHandler`, for an interact it accepted (alive, within 5 m, an NPC with a dialogue root), calls `Interacted` before building the node, which meets every Talk objective for that template in the current stage, so a quest made ready by the conversation already shows its turn-in. A Talk target therefore needs a dialogue root, which the catalog checks (#737, see Catalog). **Collect** counts the item in the **Bag only** (`QuestService.HeldInBag`), capped, for the current stage of every held quest (`RecountCollect`): from `QuestFlusher` on a tick whose inventory changes touched a Bag slot (so every path counts: a pickup, a move, a destroy, a vendor), at each stage start, at turn-in, and at select (`RecountAtSelect`, which then drops the lines and updates it queued, since the log already shows the counts). **Use doodad:** `DoodadUseService`, once a use completes (instantly or at the end of its cast bar) and the doodad script's `OnUse` did not throw, calls `QuestService.DoodadUsed` (contained, before the doodad is spent): **the user alone** (never its party: each player on the step uses the doodad for their own credit; a use credits only its user) gets +1, capped, on each UseDoodad objective for that doodad template in the current stage of each Active quest, settled as a kill is; a use that moves no quest allocates nothing (`QuestDoodadCreditShould`). A credit raises the user's `QuestLog.GateVersion`, so a doodad's `OnObjective` gate on that objective closes for the user at its next view decision once the count fills ([doodads](doodads.md)). Item use and quest scripts cannot move a UseDoodad objective. **Scripted** objectives move only through the quest's script (`IQuestContext.Advance`).
- **Stages.** `Settle` runs after each change: while every objective of the current stage is met, the next stage starts ("X: stage complete.", its Collect objectives counted from the Bag, then the script's `OnStageStarted`), or after the last the quest becomes `ReadyToTurnIn` ("X: ready to turn in."). A Collect recount that leaves a ready quest short sends it back to `Active` ("X: no longer ready to turn in."); nothing else does. A count change says "<objective text>: n/m". A stage-start hook that advances its own quest is settled by the loop already running for it; any other quest settles at once.
- **Quest drops and items.** In `MapInstance.DropLoot`, `RollQuestDrops` (contained) rolls each of the creature's quest drop rows once for each eligible character with an Active quest whose current stage has that Collect objective and fewer of the item in the Bag than its count (`StillNeeds`, the one rule the pickup shares), at `Chance` percent through `ILootRandom`; each success is one item, owned by that character with `FreeForAllAt = DateTime.MaxValue`, placed in the same ring as the table drops (a creature without a loot table can still drop quest items). `LootPickup.TryPickUp` refuses, with `NotYours`, a quest item the picker no longer needs (`QuestService.MayPickUp`, by the Bag; a throw refuses too), its owner included, and the drop stays. Drops on the ground do not count, so an owner short of its count may see more drops than it can take. Quest items are never sold: `VendorRules` refuses selling one (`NotSellable`) and `VendorCatalog` refuses a stock row of one; a stocked item that a `/reload items` flags `QuestItem` is hidden from the list and its buy answered `NotFound` at once (`VendorRules.IsStockable`), as the price floor holds, and so is a buyback of one sold before the flag (#738). Turn-in and abandon take every copy from the Bag and the Bank but a stack offered in a trade (quest items cannot be offered, but a `/reload items` can make an offered item one); equipped copies are not searched (quest items have no slot).
- **Experience** (owner decision): `ExperienceAward.Grant` (`Avalon.World/Characters`) gives a character experience its caller worked out and levels it past **every** requirement the total covers, carrying the rest; each new level refreshes the stats (`Refill`, or `KeepShare` for a dead character), and the party roster is resent (`LevelChanged`). A character can gain experience only while its level and the next both have a `CharacterLevelExperiences` row (`ExperienceAward.CanGainExperience`, the one rule the award and the party split share, never a constant, #735). So at the maximum level (the highest row, 15 today), and on a level whose next level is missing (a gap, treated exactly like the maximum, owner decision), a character gains no experience from any source (kill, party kill, quest), and an award that levels a character onto such a level stops there, the rest discarded, so it arrives with 0; nothing is logged for either. A character whose current level has no row is awarded nothing and a warning is logged. A quest's `RewardExperience` is personal: no party split, no level gap, no map band. Kills use it too, after `PartyExperience.Fill` and `ScaledExperience`, so one kill's share can now raise several levels, where it raised one before.
- **The quest log and saves.** `CharacterEntity.Quests` is a `QuestLog` (World-side, never on `ICharacter`): the `ActiveQuest`s (state `Active` 1 or `ReadyToTurnIn` 2, stage, the counts above 0, the accept time) and the completed quests, each a `QuestCompletion` (#710: first turn-in time, last turn-in time and count; a later turn-in keeps the first time, moves the last and adds one; `Completions` walks them with the dictionary's struct enumerator). Only `QuestService` calls its mutators; each marks `SaveStateTracker.QuestChanged(questId)` and the client change for that quest, and raises `Version`. The next save carries a `CharacterQuestWrite` (built in `CharacterSaveSnapshot`) in the same transaction as the rest: for each marked quest its `CharacterQuests` row and `CharacterQuestObjectives` rows are deleted and, for a quest still held, the current ones inserted; for a quest turned in at least once, its `CharacterCompletedQuests` row is inserted when missing, else its `LastCompletedAt` and `CompletionCount` are updated by column (the first time, `CompletedAt`, stays), absolute values so a retried save writes the same. The completion row is written independently of the active row, so a repeatable turned in and accepted again within one save window saves both, and abandoning it afterwards keeps the completion (migration `AddCharacterQuests`; all three cascade from `Characters`, the objectives from their quest row; migration `TrackRepeatedQuestCompletions` added the two columns, back-filling `LastCompletedAt = CompletedAt` and `CompletionCount = 1`). Memory is authoritative, as for the inventory. Select loads the rows (`ICharacterQuestRepository.GetByCharacterIdAsync`, one more `CharacterSelectHandler.Step` after the abilities), copies the connection's locale for the lines (an account lookup that lands later sets it too) and runs `RecountAtSelect`, contained.
- **Vendor quest gates** ask `IQuestProgress`; production's `QuestProgress` answers from the quest log (`Active` = held, active or ready; `Completed` = turned in). An open shop's list is sent again on the vendor pass after an accept, an abandon or a turn-in (#738); progress alone sends none. `NoQuestProgress` is only a handler's fallback when built without the container. No seeded row is gated.
- **Quest scripts.** A `QuestScript` (`Avalon.World.Public/Scripts`) is named by `QuestTemplate.ScriptName` and found by type name: `ScriptManager` keys every subclass by `t.Name`, once, at `Load()` (never hot-reloaded, like `AbilityScript`). `QuestService` builds one per quest with `ActivatorUtilities.CreateInstance`, **no runtime arguments**, over `QuestScriptServices` (`Avalon.World/Quests`, #738), a provider over the world's container that hands over **only `ILoggerFactory`, `ILogger<T>` and `TimeProvider`** and answers null for everything else, the provider itself included, so no script can obtain `QuestService`, `IWorld` or any other service that writes; the one instance serves every character, so it keeps no per-character state. One whose constructor asks for anything else (or otherwise cannot be built) is logged at Error once and its quest cannot be accepted; a reload pointing the quest at another type builds that one. `QuestScriptConstructibilityShould` builds every shipped one through the production container wrapped in `QuestScriptServices` (none is seeded yet), and pins that a script asking for `QuestService`, `IWorld` or `IServiceProvider` builds from the bare container but not through it. AI scripts are unchanged: still built from the full container. The modding surface is `QuestScript`, `IQuestContext`, `IQuestCharacter` (id, name, level, class) and the read-only snapshots `QuestCreatureView` and `QuestInstanceView`, nothing else: a hook reads the world only through them, and its one write, enforced by what its constructor can receive, is `IQuestContext.Advance`, which adds to one of **its own quest's Scripted objectives in the current stage**, judged by the live catalog, while the character still holds that very copy and it is Active; anything else returns false, changes nothing and is logged at Warning, at most once per quest per 10 s. Hooks: `CanAccept(character)` (can only narrow availability), `OnAccepted`, `OnStageStarted(stage)` (stage 0 right after `OnAccepted`, then each stage as it starts, each once and in order; also for a character still being selected when its select recount completes a stage), `OnCreatureKilled` (the character shared the kill), `OnInteract` (it opened a conversation) and `OnEnterInstance`. Each runs contained: a throw is logged at Error with the quest, the hook and the character, at most once per quest per `ThrottledErrorLog.Interval` (10 s, counting the throws left out), and the quest, the kill, the conversation, the accept or the select goes on; a `CanAccept` that throws refuses. **For script authors:** hooks run only while the quest is Active, so a kill or a talk that made it ready reaches no hook and a ready quest hears nothing; `OnCreatureKilled` after a kill that changed the stage gets the new stage's context (`Stage`, `ProgressOf`); `OnEnterInstance` fires on each arrival in an instance other than the one it last ran for, checked by `QuestFlusher` every tick once the character stands in a live instance, after every login too (the memo, `QuestLog.ScriptsInstance`, is never saved); the memo is per character, not per quest, so a quest accepted while already inside an instance, or one going from ready back to Active, hears it only on the next arrival.
- **Flush.** `QuestFlusher.Flush` runs from `WorldServer.Update` after both passes and **before** `InventoryUpdateFlusher`, whose slot changes it reads, each step contained on its own (`QuestService.FlushStepFailed`, a `ThrottledErrorLog` per step, so a recount that throws every tick still lets the log, updates, lines and markers out), for a connection holding a `CharacterEntity`: a daily, weekly or monthly reset that passed since the session last looked (#710, `QuestService.ApplyResets`, below), the settle after a `/reload quests` (#738), the Collect recount if the Bag was touched, `EnteredInstanceIfChanged`, `FlushClient` (the whole `SMSG_QUEST_LOG` the first time, `QuestLog.LogSent`, which carries every change already; afterwards one `SMSG_QUEST_UPDATE` per changed quest in id order; then the milestone lines, `SChatMessagePacket.System`), then `FlushMarkers`. **A connection with nothing to flush is skipped (#977)**: the flush runs for every connection on every tick, and almost every tick changes no one's quests, so it first asks `QuestLog.FlushOwed`, a flag every input of its steps that belongs to the character sets: each mutator of the log (`Start`, `SetProgress`, `SetStage`, `SetState`, `Remove`, `Complete`, so a kill credit, a conversation, a stage advance, a recount that moved a count, an accept, an abandon and a turn-in), each milestone line (`Say`), a `Load`, and `CharacterEntity`'s `Level` and `InstanceId` setters (the markers' and the enter-instance hooks' inputs), set to begin with so a session's first flush sends the log. What comes from elsewhere it checks itself: the catalog generation, against the one the log was settled and its markers worked out with (a `/reload quests` swaps it for every character at once), the reset generation, against `QuestLog.ResetGeneration` (never saved, 0 for a new session; one `int` comparison), and whether the tick's inventory changes touched the Bag. With the flag clear, the same catalog, the same reset generation and the Bag untouched, every step would have had nothing to do, and none runs. After a flush the flag stays set while a step still has something left (the log, an update or a line unsent after a throw, or the hooks and markers waiting for a live instance), so that step is tried again on the next tick as before. A level or an instance written to the character's row directly, not through the entity, is not seen (nothing in the server does that). So within a tick a quest's update and lines precede the inventory update: a turn-in's `Completed` arrives before its reward items and gold. A quest whose log entry or update cannot be built is left out and logged at Error, throttled per quest. **Markers:** `SMSG_QUEST_MARKERS` lists every quest NPC (`IsQuestNpc`) in the character's instance, with no interest radius, with `MarkerFor` (highest first: `ReadyToTurnIn` for a once-only quest ready to turn in, `RepeatableReadyToTurnIn` for a repeatable one, `Available` for a once-only quest offered, `RepeatableAvailable` for a repeatable one, else `None`: a turn-in before an offer, a story quest before a repeatable one within each, #710); worked out again only when the instance, the level, the log's `MarkerVersion` (raised by an accept, an abandon, a turn-in, a load, a held quest's state change and a reset that made a completion available again, never by a count or a stage alone, which no marker reads, #973) or the catalog generation changed, and sent only when the list differs from the last one sent. **A reset while online (#710):** `WorldServer` advances the `QuestResetClock` once per tick before the flushes (`Advance(now)`, two comparisons, before the next daily boundary and not before the latest one, until one fails, contained; a clock stepped back before the latest daily boundary, a corrected host clock, takes the boundaries back with it and raises the generation as a crossing does, so a turn-in made after the earlier boundary is not offered again in the meantime, `QuestResetScheduleShould`); a flush that sees a generation other than `QuestLog.ResetGeneration` first runs `ApplyResets`, which notes the generation and, when the character holds a completion of a daily, weekly or monthly quest whose frequency rolled since (`QuestResetClock.RolledAt`), calls `QuestLog.ResetPassed` (raises `MarkerVersion` and `GateVersion`): its markers turn blue again on that tick and its doodad gates are asked again at the next view decision (the following tick: view decisions run inside the instances' update, before this post-update stage), without a relog. Anyone else is left untouched; at most once per character per reset, and allocation-free (`QuestAllocationShould`, `RepeatableQuestsShould`). The reset tick is the one tick on which every connection skips the #977 early exit; measured with every character holding a rolled daily completion in a town with its seven NPCs, so every one's markers are worked out again and sent (`QuestFlushBenchmarks.ResetPassed`), it costs about 0.7 µs per connection, about 1.25 ms at 1,800 connections, allocating nothing, once per reset, so it is not spread over several ticks. The doodad gates it reopens are asked again in the following tick's view decisions, so that figure leaves them out. An NPC conversation already open is not refreshed; reopening it offers the quest. A quest NPC spawned or removed later is not noticed until one of those changes (the seeded ones are town NPCs, which stay). **Doodad gates** read the log too, through `QuestLog.GateVersion`, raised by every change a gate can see (a load, an accept, a count that changed, a stage, a state, an abandon, a turn-in, a reset that made a completion available again): a view decision asks a gated doodad's rules again only when it moved (docs/world-simulation.md).
- **Protocol** (`Avalon.Network.Packets/Quest`): `CMSG_QUEST_ACCEPT` (0x20C0, `QuestId`, `NpcGuid`), `CMSG_QUEST_TURN_IN` (0x20C1, the same, and field 3 `ChoiceItemTemplateId`, the item picked from the choice set, 0 for none, #711) and `CMSG_QUEST_ABANDON` (0x20C2, `QuestId`), each with a `MapSessionFilter` entry and a handler in `Avalon.World/Handlers` running through `QuestReplies.Handle` (the service and the packet handed through as state to a static lambda, as for parties, so a request allocates nothing of its own): **exactly one** `SMSG_QUEST_RESULT` (0x30C1, `QuestResult`: `Ok` 1, `NotAvailable` 2, `NotActive` 3, `NotReady` 4, `LogFull` 5, `BagFull` 6, `GoldCap` 7, `TooFar` 8, `NoConversation` 9, `Error` 10, `Stunned` 11 (#770: a stunned character accepts and turns in nothing, the conversation left open), `InvalidChoice` 12 (#711: a missing or foreign pick, or a pick on a quest without a choice set), append-only), sent after any dialogue node the request caused and before its updates; a throw is logged at Error and answered `Error`; a connection with no character gets nothing. `SMSG_QUEST_OFFER` (0x30C0), `SMSG_QUEST_LOG` (0x30C2), `SMSG_QUEST_UPDATE` (0x30C3: `Accepted` with the display, `Progress`, `Removed`, `Completed`; at most one per quest per tick, an accept staying `Accepted` for its tick, except a repeatable turned in and accepted again in one tick, which sends `Completed` then `Accepted` (#710)) and `SMSG_QUEST_MARKERS` (0x30C4) are self-describing: `QuestDisplayDto` (`QuestDisplay.Build`) carries every text resolved in the character's language, the stages, objectives and rewards (`QuestRewardsDto`: experience, gold, the fixed `Items` and, field 4, the choice set `Choices`, by item id, #711; field 5, `TalentPoints`, the talent points the turn-in pays, #1181; each `QuestRewardItemDto` its template id, count and, field 3, `Rarity`, #1179: `Magic` for a Common base the turn-in rolls, else the template's rarity), so the client needs no quest catalog. `DialogueOptionKind` gained `QuestOffer` 3 and `QuestTurnIn` 4.
- **Read-only outside the world server (#714).** `GET /world/{worldId}/quest-template` (paged by id, page size at most 50) and `/{id}` (`QuestTemplateController`, `[WorldScoped]`, **GameMaster** policy, since stages, drops and scripts are the storyline ahead of a player; 404 for an unknown id) return `QuestTemplateDto`: the header (title, description and completion text each resolved to the base-locale (enUS) wording of `LocalizedTexts`, beside its text id, an id with no row reading as an empty string, placeholders such as `{name}` left as stored), giver and ender creature template ids, level, class and prerequisite requirements, script name, experience, gold and the talent points the turn-in pays (`RewardTalentPoints`, #1181), the stages in order with their objectives by id (type as the string enum `Avalon.Api.Contract.QuestObjectiveType`, creature, item or doodad template target, count, text), the fixed item rewards (`ItemRewards`) and the choice set (`ItemChoices`, #711, empty when none), each by item template id, and every Collect objective's drops (`IQuestRepository.PaginateAsync`/`FindByIdAsync`, `ILocalizedTextRepository.GetByIdsAsync`); `IsRepeatable` and `RepeatFrequency` as the template stores them (#710: the frequency as the string enum `Avalon.Api.Contract.QuestRepeatFrequency`, `Daily`, `Weekly` or `Monthly`, and null for a stored null, `None` or unknown value, so a repeatable quest with a null frequency is one done again at once; mapped by an explicit switch, the contract enum having no `None`); `Environment`, `Type` and `Rarity` are left out, being unread. `tools/Avalon.Exporter -- quest-catalog` writes `schema/quests/quest-catalog-v1.json` (`QuestCatalogExport`, pinned by `QuestCatalogExportShould`, which also fails when the committed file differs from the seed rendered, so a seed change needs a re-export): per quest the id, the enUS title, the repeat kind (`repeat`, the wire's `QuestRepeatKind` number: 1 once, 2 repeatable, 3 daily, 4 weekly, 5 monthly, 0 for a frequency it does not know), the stages with each objective's id, type (as its number, the wire's `QuestObjectiveKind`), target id (a creature, item or doodad template; 0 for Scripted) and count, and the rewards (experience, gold, `talentPoints` (#1181), the fixed `items` and the `choices` the player picks one of, #711, each by item id, `choices` empty when the quest has none); for tooling only, the client needs none of it; like `ability-catalog` it needs a World database and is reviewed as a data diff. A character's quest log is `GET /world/{worldId}/character/{id}/quests` (`CharacterController.GetQuests`, the owner or a game master, as the other character sub-resources; 404 for an unknown character): `CharacterQuestLogDto`, the held quests by id (state as the string enum `Avalon.Api.Contract.CharacterQuestState`, stage, accept time, and the saved objective counts by objective id, **an objective with no entry standing at 0**, since only counts above 0 are saved) and the turned-in quests with their first completion time (`CompletedAt`), their last (`LastCompletedAt`) and how many times each was turned in (`CompletionCount`, #710), as the world server last saved them (`ICharacterQuestRepository`, no World DB lookup, no titles).
