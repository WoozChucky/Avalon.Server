# Packet handlers, session filters and reflection-bound registration

How a packet reaches its handler, the session filters that gate it, the rule for retired opcodes, and why a reference grep proves nothing for handlers and scripts. The wire format itself is in [Packet protocol](networking-packet-protocol.md).

## Packet Protocol

All client↔server communication is custom TCP, inside TLS, with Protobuf-net. Every packet wraps a `NetworkPacket` (header + payload). The header carries `NetworkPacketType` (opcode), `NetworkPacketFlags` (encryption/compression bitmask), `NetworkProtocol` (channel grouping), and `Version`.

**Adding a packet handler:**
1. Define the packet contract in `Avalon.Network.Packets` with a `NetworkPacketType` enum value.
2. For Auth: implement `IAuthPacketHandler<TPacket>` in `Avalon.Server.Auth/Handlers/`.
3. For World, the connection layer (admission and the version handshake, before any gameplay): implement the generic `IWorldPacketHandler<TPacket>` (`Avalon.World/WorldPacketHandler.cs`) in `Avalon.Server.World/Handlers/`, as `GameAdmissionHandler` and `WorldHandshakeHandler` do.
4. For World, the game layer (everything a character does): implement `WorldPacketHandler<TPacket>` in `Avalon.World/Handlers/`, decorated with `[PacketHandler(NetworkPacketType.X)]`, and give the opcode a session filter entry (below).

Auth handlers and the World connection-layer handlers are found by `PacketManager` (`AddCoreServices`): each packet type marked for the server (`[Packet(HandleOn = ...)]`) maps to the class implementing `IPacketHandlerNew` for it (by the interface's type argument; when two do, the last by ordinal full name wins, #793). `PacketManager` builds each handler's `ActivatorUtilities.CreateFactory` factory once, at startup, into the packet's `PacketInfo`, and only reads its map afterwards; `ServerBase.CallListener` builds one handler per packet from that factory, in a new DI scope, and awaits it as the packet arrives. Nothing on the dispatch path is filled lazily: a handler cache written on a type's first dispatch was corrupted by connections sending their first packets at once (#866, `ServerBaseShould.Dispatch_the_first_packets_of_a_type_from_many_connections_at_once`). The game-layer handlers are found by the attribute scan in the `WorldServer` constructor and built once with `ActivatorUtilities.CreateInstance` (given the server itself when a constructor asks for `IWorldServer`); their packets are queued per connection and run on the tick. At startup `PacketManager` warns "Packet ... does not have a handler" only for a packet neither layer serves: the World registers its game layer as an `IPacketHandlerLayer` (`GamePacketHandlerLayer`, which shares the `WorldServer` constructor's attribute scan), and a packet a layer serves is noted at Debug instead. That changes only the startup log: such a packet still gets no `PacketManager` entry, so `ServerBase` dispatches only `IPacketHandlerNew` handlers, as before. `WorldHostGraphShould.Serve_every_world_packet_by_exactly_one_handler_layer` fails when a World packet is served by neither layer or by both. A World connection drops every packet but `CMSG_GAME_ADMISSION`, and `CMSG_WORLD_HANDSHAKE` once admitted, until it is admitted and its version handshake accepted (`WorldConnection.IsGameplayAuthorized`). Those two are the only packets a World connection hands to `ServerBase.CallListener`, which runs a handler on the receive path, off the tick: once admitted, every other packet is either queued for the tick or dropped at arrival (#861, below).

**A retired opcode is deleted, not kept (owner decision, #697).** `NetworkPacketType` holds only opcodes in use: one that nothing sends or handles any more is deleted, with its packet class, and the wire schema re-exported (`tools/Avalon.Exporter -- proto opcodes corpus`). Its number may be reused once clients have re-vendored the schema without it. Nothing in `NetworkPacketType` is `[Obsolete]`. The unused chat-window packets (`CMSG_CHAT_OPEN` 0x2008, `CMSG_CHAT_CLOSE` 0x2009, `SMSG_CHAT_OPEN` 0x300A, `SMSG_CHAT_CLOSE` 0x300B) and the retired group opcodes went this way. The unused quest requests (`CMSG_QUEST_STATUS` 0x2040, `CMSG_QUEST_LIST` 0x2041, `CMSG_QUEST_QUERY_AVAILABLE` 0x2042) went this way with #433.

**A new client→server opcode also needs a session filter entry, or the handler never runs.** `MapSessionFilter` (in-map packets) or `WorldSessionFilter` (pre-character packets) must accept the opcode, not just a registered handler for it. `WorldConnection.OnReceive` only queues a packet if a filter accepts it at arrival; any other is dropped right there (#861), never handed to `CallListener`, so a game handler cannot run off the tick. One no filter accepts in any state (`WorldSessionFilter.IsSessionPacket`, `MapSessionFilter.IsMapPacket`) is logged with a "Could not find a handler for packet" warning, the first on each connection (later ones at Debug, so a client cannot flood the log) — a missing filter entry fails safe, so debug it by grepping the logs, not by hunting a frozen connection. One a filter accepts in another state is expected and logged at Debug only: the client sends `CMSG_PLAYER_INPUT` at 60 Hz from the moment it enters, so every login drops the inputs sent between the select and the spawn, and a select-phase packet sent once in the world is dropped the same way (`CMSG_PLAYER_INPUT` at Trace, as the receive loop's "IN:" line skips it). If a handler never runs and nothing is warned, enable Debug (Trace for input) for `Avalon.World.WorldConnection` and look for "Dropped … not accepted in the connection's current state". The drop allocates nothing (generated log methods that check the level first). `WorldHostGraphShould.Serve_every_world_packet_by_exactly_one_handler_layer` fails when a `[PacketHandler]` opcode has no entry in either filter. The queue *can* wedge, but only for the narrower race where a packet's acceptance changes between arrival and dispatch (e.g. `CMSG_CHARACTER_LIST`/`CMSG_CHARACTER_LOADED` around a character spawn) — see `ProcessQueueWedgeShould.cs`. The one case the queue clears by itself is an in-map packet left behind by a character that has gone (a Change Character leave, #663): the session pass drops it while the connection holds no character (`CharacterLeaveQueueShould`).

**Reflection-bound registration — a reference grep proves nothing.** Packet handlers are discovered by attribute scan, and AI/ability scripts by type name: `ScriptManager` keys every `AiScript` subclass by `t.Name` (except those marked `[ChainedScript]`), and `ICreaturePlacementService.AttachScript` resolves `creature.ScriptName` from the DB and builds it with `ActivatorUtilities.CreateInstance(_sp, scriptType, creature, instance)`. So "nothing references this type" says nothing about whether it is used — and note that call site passes exactly two runtime arguments, so a script constructor needing anything beyond `(ILoggerFactory, ICreature, ISimulationContext)` will throw and be swallowed into a logged error. Check constructibility against that call site, not against grep — `AiScriptConstructibilityShould` does exactly that for every nameable script, against the production container. Ability scripts are bound the same way: `ScriptManager` keys every `AbilityScript` subclass by `t.Name`, `AbilityTemplate.ScriptName` names one (the column was `SpellScript` until #163), and `InstanceAbilityCastSystem` builds it with `ActivatorUtilities.CreateInstance(sp, type, ability, caster, aim, arena)` (an `AbilityAim` and the instance as `IAbilityArena`); `AbilityScriptConstructibilityShould` builds every seeded one that way. Quest scripts too (#433): `ScriptManager` keys every `QuestScript` subclass by `t.Name`, `QuestTemplate.ScriptName` names one, and `QuestService` builds it with `ActivatorUtilities.CreateInstance(new QuestScriptServices(services), type)`, no runtime arguments, from a provider that hands over only `ILoggerFactory`, `ILogger<T>` and `TimeProvider` (#738); `QuestScriptConstructibilityShould` builds every shipped one that way (see Quests). Item scripts too (see Item use): `ScriptManager` keys every `ItemScript` subclass (`Avalon.World/Items`, World-side) by `t.Name`, once, at `Load()`; `ItemTemplate.UseScript` names one; `ItemUseService` builds it once per type with `ActivatorUtilities.CreateInstance(new QuestScriptServices(services), type)`, no runtime arguments; `ItemScriptConstructibilityShould` builds every shipped and every seeded one that way. The world publishes their names in its script catalog (`item`), and an item template save checks `useScript` against it. Aura scripts too (see Auras): `ScriptManager` keys every `AuraScript` subclass (`Avalon.World/Auras`, World-side) by `t.Name`, once, at `Load()`; `AuraTemplate.ScriptName` names one; `AuraScripts` builds it once per type with `ActivatorUtilities.CreateInstance(new QuestScriptServices(services), type)`, no runtime arguments; `AuraScriptConstructibilityShould` builds every shipped and seeded one that way (none is shipped or seeded yet). The world publishes their names in its script catalog (`aura`), and an aura template save checks `scriptName` against it. Packet handlers themselves (#822): `WorldHostGraphShould.Build_every_packet_handler_from_the_production_container` builds every `[PacketHandler]` type in `Avalon.World` from the production World container as the `WorldServer` constructor does (handing the world server to a handler that names it), and every `IPacketHandlerNew` type in `Avalon.Server.World` as `ServerBase` does per packet (`ActivatorUtilities.CreateFactory` with no runtime arguments, over a scope), and fails naming each handler and the service it could not get.
