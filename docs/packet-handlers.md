# Packet handlers, session filters and reflection-bound registration

How a packet reaches its handler, the session filters that gate it, the rule for retired opcodes, and why a reference grep proves nothing for handlers and scripts. The wire format itself is in [Packet protocol](networking-packet-protocol.md).

## Packet Protocol

World gameplay communication is custom TCP, inside TLS, with Protobuf-net. Every packet wraps a `NetworkPacket` (header + payload). The header carries `NetworkPacketType` (opcode), `NetworkPacketFlags` (of which only `Encrypted` is read: the payload is sealed), `NetworkProtocol` (always `Tcp`, read by nothing), and `Version` (always 0, read by nothing).

**Adding a packet handler:**
1. Define the packet contract in `Avalon.Network.Packets`, deriving from `Packet`, with a new `NetworkPacketType` enum value in a `public static NetworkPacketType PacketType` field (what identifies the packet) and `[Packet(HandleOn = ComponentType.World)]` for the world server (what gives that server a decoder for it).
2. For World, the connection layer (admission and the version handshake, before any gameplay): implement the generic `IWorldPacketHandler<TPacket>` (`Avalon.World/WorldPacketHandler.cs`) in `Avalon.Server.World/Handlers/`, as `GameAdmissionHandler` and `WorldHandshakeHandler` do.
3. For World, the game layer (everything a character does): implement `WorldPacketHandler<TPacket>` in `Avalon.World/Handlers/`, decorated with `[PacketHandler(NetworkPacketType.X)]`, and give the opcode a session filter entry (below).

The World connection-layer handlers are found by `PacketManager` (`AddCoreServices`): each packet type marked for the server (`[Packet(HandleOn = ...)]`) maps to the class implementing `IPacketHandlerNew` for it (by the interface's type argument; when two do, the last by ordinal full name wins, #793). `PacketManager` builds each handler's `ActivatorUtilities.CreateFactory` factory once, at startup, into the packet's `PacketInfo`, and only reads its map afterwards; `ServerBase.CallListener` builds one handler per packet from that factory, in a new DI scope, and awaits it as the packet arrives. Nothing on the dispatch path is filled lazily: a handler cache written on a type's first dispatch was corrupted by connections sending their first packets at once (#866, `ServerBaseShould.Dispatch_the_first_packets_of_a_type_from_many_connections_at_once`). The game-layer handlers are found by the attribute scan in the `WorldServer` constructor and built once with `ActivatorUtilities.CreateInstance` (given the server itself when a constructor asks for `IWorldServer`); their packets are queued per connection and run on the tick. At startup `PacketManager` warns "Packet ... does not have a handler" only for a packet neither layer serves: the World registers its game layer as an `IPacketHandlerLayer` (`GamePacketHandlerLayer`, which shares the `WorldServer` constructor's attribute scan), and a packet a layer serves is noted at Debug instead. That changes only the startup log: such a packet still gets no `PacketManager` entry, so `ServerBase` dispatches only `IPacketHandlerNew` handlers, as before. `WorldHostGraphShould.Serve_every_world_packet_by_exactly_one_handler_layer` fails when a World packet is served by neither layer or by both. A World connection drops every packet but `CMSG_GAME_ADMISSION`, and `CMSG_WORLD_HANDSHAKE` once admitted, until it is admitted and its version handshake accepted (`WorldConnection.IsGameplayAuthorized`). Those two are the only packets a World connection hands to `ServerBase.CallListener`, which runs a handler on the receive path, off the tick: once admitted, every other packet is either queued for the tick or dropped at arrival (#861, below).

**A retired opcode is deleted, not kept (owner decision, #697).** The auth process retirement (#1097) has not yet retired its shared packet classes or opcodes; that wire-contract decision remains separate. For an opcode explicitly retired, `NetworkPacketType` holds only opcodes in use: one that nothing sends or handles any more is deleted, with its packet class, and the wire schema re-exported (`tools/Avalon.Exporter -- proto opcodes corpus`). Its number may be reused once clients have re-vendored the schema without it. Nothing in `NetworkPacketType` is `[Obsolete]`. The unused chat-window packets (`CMSG_CHAT_OPEN` 0x2008, `CMSG_CHAT_CLOSE` 0x2009, `SMSG_CHAT_OPEN` 0x300A, `SMSG_CHAT_CLOSE` 0x300B) and the retired group opcodes went this way. The unused quest requests (`CMSG_QUEST_STATUS` 0x2040, `CMSG_QUEST_LIST` 0x2041, `CMSG_QUEST_QUERY_AVAILABLE` 0x2042) went this way with #433. The audio record pair (`CMSG_AUDIO_RECORD` 0x2050, `SMSG_AUDIO_RECORD` 0x3050), which nothing ever handled or sent, went this way with #937. The logout pair (`CMSG_LOGOUT` 0x2002, `SMSG_LOGOUT` 0x3011, with its `LogoutResult` enum) and the character presence pair (`SMSG_CHARACTER_CONNECTED` 0x3020, `SMSG_CHARACTER_DISCONNECTED` 0x3021), which nothing handled or sent, went this way with #941: leaving the world is a character leave (`CMSG_CHARACTER_LEAVE`) or a disconnect, and a character appearing or going is told through object state (`SMSG_WORLD_STATE_ADD`, `SMSG_WORLD_STATE_REMOVE`).

**A new client→server opcode also needs a session filter entry, or the handler never runs.** `MapSessionFilter` (in-map packets) or `WorldSessionFilter` (pre-character packets) must accept the opcode, not just a registered handler for it. `WorldConnection.OnReceive` only queues a packet if a filter accepts it at arrival; any other is dropped right there (#861), never handed to `CallListener`, so a game handler cannot run off the tick. At dispatch the tick asks again: the filter's state rules (`Accepts`) and the connection's authorization, the lease judged at the tick's time rather than by a clock read per packet (#977, [game server admission](steam-authentication-workloads.md)); the filters' `CanProcess`, which the read loop asks, reads the clock. With `Network:PacketEncryption` on, a plain packet that a filter names in any state, other than the pong, or a plain version handshake, closes the connection before the filters are asked (#875). One no filter accepts in any state (`WorldSessionFilter.IsSessionPacket`, `MapSessionFilter.IsMapPacket`) is logged with a "Could not find a handler for packet" warning, the first on each connection (later ones at Debug, which a world does not write at the level it ships with, so a client cannot flood the log; an opcode the world has no packet type for never gets this far, and is dropped by the read loop under a once of its own, below) — a missing filter entry fails safe, so debug it by grepping the logs, not by hunting a frozen connection. One a filter accepts in another state is expected and logged at Debug only: the client sends `CMSG_PLAYER_INPUT` at 60 Hz from the moment it enters, so every login drops the inputs sent between the select and the spawn, and a select-phase packet sent once in the world is dropped the same way (`CMSG_PLAYER_INPUT` at Trace, as the receive loop's "IN:" line skips it). If a handler never runs and nothing is warned, enable Debug (Trace for input) for `Avalon.World.WorldConnection` and look for "Dropped … not accepted in the connection's current state". The drop allocates nothing (generated log methods that check the level first). `WorldHostGraphShould.Serve_every_world_packet_by_exactly_one_handler_layer` fails when a `[PacketHandler]` opcode has no entry in either filter. The queue *can* wedge, but only for the narrower race where a packet's acceptance changes between arrival and dispatch (e.g. `CMSG_CHARACTER_LIST`/`CMSG_CHARACTER_LOADED` around a character spawn) — see `ProcessQueueWedgeShould.cs`. A wedged connection no longer grows without limit: what the client goes on sending fills the queue to its cap, and the connection is closed there (below). The one case the queue clears by itself is an in-map packet left behind by a character that has gone (a Change Character leave, #663): the session pass drops it while the connection holds no character (`CharacterLeaveQueueShould`). That drop is logged as an arrival drop is, at Debug and input at Trace, by generated log methods, so it allocates nothing either (#883: its line cost an argument array and a boxed opcode, 56 B, for every packet dropped, with Debug off; `ReceiveQueueAllocationShould`).

**Item identification (#1179) is one in-map request.** `CMSG_ITEM_IDENTIFY` (`0x2083`, `CItemIdentifyPacket`: `RequestId`, `WorkbenchGuid`, `BagSlot`) is in `MapSessionFilter.IsMapPacket` beside the other item requests, and `ItemIdentifyHandler` answers each with exactly one `SMSG_ITEM_IDENTIFY_RESULT` (`0x3092`, `SItemIdentifyResultPacket`: `RequestId`, `ItemIdentifyResult`); a connection with no character gets nothing (`HandlerGuardsShould`). The refusals are asked in this order: `Dead` 1, `Stunned` 2, `NotFound` 3, `TooFar` 4, `NoItem` 5, `AlreadyIdentified` 6, `Locked` 7, `NotEnoughGold` 8 (`IdentifyRules.Decide`; `Ok` is 0, and a fault is logged at Error and answered `InternalError` 9, the gold of a cost above 0 possibly already spent). [Inventory and saves](inventory-and-saves.md#identification-at-the-resonance-workbench-1179) has what each means.

**Awakening (#1180) adds two server-to-client opcodes and no request**, so no session filter lists them and no handler exists: `SMSG_AWAKENING_PROGRESS` (`0x3093`, `SAwakeningProgressPacket`: `Items`, each `EquipmentSlot`, `Progress` and `ItemInstanceId`, the item a client applies the bar to), at most once a tick to a character whose worn sealed affixes' bars moved, and `SMSG_ITEM_AWAKENED` (`0x3094`, `SItemAwakenedPacket`: `EquipmentSlot`, `ModifierId`, `Outcome`, the append-only `AwakeningOutcome`: `Woken` 0, `TierRaised` 1, `Polished` 2), once per wake. Both are sent by the tick's Awakening stage (`AwakeningFlusher`); [inventory and saves](inventory-and-saves.md#awakening-1180) has what each carries.

**The goodbye is noted on arrival (#967).** `CMSG_LEAVE_WORLD` is in `WorldSessionFilter`'s every-state list, beside the
pong, the load report and the character leave, so it is accepted before a character and in a map, and never by the map
filter. Its handler only closes the connection. What it means, a session ended as a `logout`, is noted by the read loop
as the packet arrives (`WorldConnection.OnReceive`, one comparison per received packet, after the authorization check
and before the pong credit and the depth cap), because the client closes right after it: the close queues the despawn,
the tick drains disconnects before its session pass, and a closed connection's queued packets are never dispatched, so
a goodbye left to its handler would end every quit as a drop. The first reason noted wins
([world player limit](world-player-limit.md#the-goodbye)); `LeaveWorldShould` holds both paths.

**What the read loop does with a frame it does not take (#897).** Before any filter or handler, the world connection read loop (`Connection.ExecuteAsync`) frames what a peer sends, parses each frame's header, opens a payload flagged `Encrypted`, and decodes it as its opcode's packet (`PacketReader`). Any peer that completes TLS reaches all of it, before it is admitted, and can reconnect to reach it again; the handshake before it, the table's first row, is reached by any peer at all. So no case below writes more than one line at Warning per connection, and none writes an exception, a stack trace or anything the peer chose but its opcode. The Warnings that close a connection also say how many packets it had delivered before the frame, and its account once it has one (the account a world connection was admitted as): a count of 0 or 1 is a peer that is no client or a client that never agreed with the server, and a large one is a session that worked and then received a bad frame. The lines are generated log methods that check the level first, and the catches and the one flag behind them cost nothing until a frame is refused.

| The frame | The connection | Logged (the connection's logger) | Counted |
|---|---|---|---|
| never comes: the TLS handshake fails (a peer that does not speak TLS) or does not finish within the world's five seconds | dropped | one Debug line | `network.in.handshake_failures`, `reason` `failed` or `timeout` |
| declares more than `Hosting:MaxInboundFrameSize`, or its length prefix is no length (#927) | closed | one Debug line | `network.in.frame_kicks` |
| is started and not complete within `Hosting:InboundFrameTimeoutSeconds` of its first byte: the peer stopped, or trickles it (#938, [packet protocol](networking-packet-protocol.md#the-inbound-frame-deadline)) | closed | one Warning | `network.in.protocol_kicks`, `reason` `frame_timeout` |
| is not a `NetworkPacket`: its header, or a length in it, does not parse (`InboundPacketFrame.ParseFrame`) | closed | one Warning | `network.in.protocol_kicks`, `reason` `malformed_frame` |
| is flagged `Encrypted` and arrives before the connection's session has its keys, or on a connection that has no session (a world with `Network:PacketEncryption` off runs no key exchange, #878) | closed | one Warning naming the opcode | `reason` `sealed_before_key` |
| is flagged `Encrypted` and does not open under the session's key: it does not authenticate, or is shorter than a nonce and a tag | closed | one Warning naming the opcode | `reason` `seal_not_authentic` |
| carries a payload that is not an encoding of its opcode's packet (cut short, a wrong wire type, a length past its end, nesting more than 32 deep) | closed | one Warning naming the opcode | `reason` `undecodable_payload` |
| carries an opcode this server has no packet type for (one a newer server retired, one meant for the other server) | stays open; the frame is counted as received and dropped, and no filter or handler sees it | "Unknown packet type": a Warning for the first packet the connection sends that the server does not serve, Trace after that | nothing more |
| arrives while the connection is closing | [read and discarded undecoded](networking-graceful-shutdown.md#what-a-closing-connection-reads) | nothing | its bytes |

Every close in the table is without a notice to the peer, as when a peer goes away, and is the connection's normal close. A failed handshake was an Error, "Failed to establish connection", with the exception and its stack trace, for every HTTP probe or port scan that reached the port; so was a handshake cut short by the server stopping, which is now one Debug line and is not counted as a peer's. Each of the four `protocol_kicks` cases before the frame deadline was an Error, "Failed to read from stream", with the exception and its stack trace, on every connection that sent one; a payload nested past the decoder's depth made that one line about 59 KB. (A payload cut short was the exception: its `EndOfStreamException` is an `IOException`, so it was reported at Debug as the peer having closed the connection.) An unknown opcode was a Warning per frame from `PacketReader`, with the connection left open. The connection stays open for an unknown opcode because an older client may still send an opcode a newer server has retired (above); an unknown opcode flagged `Encrypted` is not opened at all. Repeats are at Trace, so they do not flood logs when Debug is enabled. One line still is: the read loop names every frame's opcode at Debug before it reads it ("IN:", skipped only for the pong and player input), on any server whose level is Debug.

**What stays an Error.** "Failed to read from stream" keeps its exception for everything that is not the peer's doing, and the two are told apart where the failure happens, not by a type a handler could also throw. `PacketReader.Read` wraps the peer's cases in a `PacketReadException`, which the read loop catches, and lets the rest through: a session that refuses to open because its send counter is spent (a plain `InvalidOperationException`; the refusal of a session with no exchange completed, none yet or one that failed on the peer's key, is the peer's, and has its own type, `CryptoSessionNotInitializedException`, #878); a cipher that fails on a packet long enough to be sealed (a `CryptographicException` that is not the platform's `AuthenticationTagMismatchException`); and anything a decode throws that is not one of the five types protobuf-net throws for malformed bytes. Those were measured over every client packet with mutated, truncated, random and deeply nested payloads: `ProtoException`, `EndOfStreamException`, `OverflowException`, `InvalidOperationException` and `ArgumentOutOfRangeException` (a date out of range). The decode is classified by those types and by nothing finer, so the Error is kept only for what throws another type: a packet class whose own code threw one of the five during a decode would be taken for a bad payload and closed with the Warning. No packet class runs code of its own in a decode today (they are plain members, with no callbacks). `ConnectionReadLoopShould` holds each row above but the frame deadline's, and the Error; `PacketStreamShould` and `InboundFrameDeadlineShould` hold the deadline.

**A contract that cannot be decoded stops the server from starting (#897).** protobuf-net builds a type's decoder on its first use, and reports a contract it cannot build as an `InvalidOperationException`, on every decode: left to the first frame, that server defect would close every client that sends the opcode with "does not decode" and blame the client. So `PacketReader` decodes an empty payload with every packet type it is given as it is built, and a failure there stops it from being built, naming the type (`PacketReaderShould`). The world server builds its reader at startup, off the tick and before its port opens (`WorldStartup.PrepareAsync`, ahead of `PacketEncoder.PrepareServerPackets`); left to the container it was built by the first connection accepted. That also moves the build of every decoder from the read loop that received the first packet of a type to startup: a millisecond or two a type and some seventy more for the first in a process, which was the first packet any client sent. Measured in a new process on a loaded machine, the world's 35 packet types take 127 to 166 ms.

**What a server sends is built at startup too (#883).** protobuf-net builds a type's serializer on its first use as well, and the runtime compiles it as it first runs: the first packet of each type a server sent paid for it, which on a world is on the tick. Over the 67 server packets that was 156 to 214 ms in all, a millisecond or two for most and 14 to 32 ms for the quest log, which nests five messages. `PacketEncoder.PrepareServerPackets`, which the world server runs at startup after it has built its reader, now writes every server packet once, as a message with something in every member (`SampleMessage`): a value that is not the member's default, one element in each list and a message, filled the same way, in each member that holds one. A new message would not do: a member left at its default is skipped, and what would have written it, a nested message's serializer above all, is built by the first packet that sets it (writing new messages left 49 ms of the 156 to the first sends, and writing a new message of every nested type as well still left 7 to 10 ms). After it the first sends of all 67 types take about half a millisecond together, 79 µs at most for one. It costs the world server about 0.2 s of startup ([benchmarks](benchmarks.md#results--the-network-path-883-2026-10-13)). The world prepares all server packet contracts, including retained legacy contracts; nothing in a contract says which server sends it. What stays for a thread's first packet of a type is that thread's own scratch message, one object.

A server packet that cannot be prepared stops the start, naming the packet, whatever inside it is at fault: one whose contract protobuf-net cannot build, which left to the first send would fail every send of the type on the tick, and one `SampleMessage` cannot write in full, since what it left out would be built by a first send after all. That is a member of a shape it has no value for, a message it cannot create (it uses a constructor without parameters, public or not, as protobuf-net does), a setter that refuses the value it is given, and a message that declares subtypes (`[ProtoInclude]`), which would be written as the base alone. No shipped contract has any of these. A new shape in a contract therefore fails `PacketEncoderScratchShould.Prepare_every_server_packet_at_startup` until `SampleMessage` is taught it. `PacketEncoderPrepareShould` holds the refusals, and that a prepared type's first packet allocates nothing (the fewest bytes of three types' first packets, since a first send cannot be repeated); that each list is written with an element in it is held by the measurement alone, since what it saves is compile time, which no test can see.

**A payload nests at most 32 deep (#897).** protobuf-net refuses a payload nested deeper than its model allows, 512 messages or groups unless told otherwise, and any peer reaches that, in any packet, with a few hundred bytes: groups opened inside one another in a field the packet does not have, which the decoder skips by recursing. It recursed through all 512 before the refusal, about half a millisecond and 130 KB on the connection's read loop for each such frame. `PacketReader` sets the model's limit to `PacketReader.MaxDecodeDepth`, 32, as it is built, which each server does before it prepares what it sends; protobuf-net reads the limit as it reads and writes, not as it builds a serializer, so a type built before the limit was set (by a test or a tool that encodes first) is bound by it all the same. The deepest packet contract nests 5 (the quest log, which the world sends) and the deepest a server reads nests 2, so 32 is more than six times what any packet needs, and such a frame is refused in about a twentieth of the time. Within the limit nothing changes: groups the packet does not know are skipped as before. The limit is the model's and the process has one model, so it also bounds what a server writes: a packet that came to nest deeper would be refused when sent. `PacketReaderShould` holds every contract, sent or received, to a quarter of the limit, so the limit is raised with the contracts and never met by one.

**A sealed frame that does not open is also what two ends that disagree about the session look like.** A client whose key derivation differs from the server's fails exactly as a tampered packet does, at its first sealed packet, and neither end can tell which it is. That was an Error per connection and is now a Warning and a count, so watch `network.in.protocol_kicks` with `reason` `seal_not_authentic`: a rate that follows logins or world entries, rather than scans, is a client build or a server change that derives another key ([session crypto](crypto-v1-derivation.md), whose vectors pin the derivation in CI).

**A connection's receive queue is capped (#927).** A connection may have `Network:MaxReceiveQueueDepth` packets (2,048 by default: about 34 seconds of one client's input at 60 a second) queued and not yet dispatched or dropped by the tick, a head held between the two passes included. A packet a filter accepts that arrives with that many waiting is not queued and closes the connection (`WorldConnection.OnReceive`, on the read loop), so the depth never passes the cap, and a burst of exactly the cap is accepted whole. The close is silent, as a dropped connection's is: no `SDisconnect` and no `DisconnectReason`, one Warning naming the connection, its account and the opcode, and one count in `network.in.backlog_kicks`, each once per connection (`Close` marks the connection closing before it returns, and from then on the read loop discards what it reads from that connection, undecoded: see [graceful shutdown](networking-graceful-shutdown.md#what-a-closing-connection-reads)). It is the connection's normal close: what was queued is dropped by the tick's next pass, which finds the connection no longer authorized, and the session ends and the character is saved on the tick, as on any disconnect. The depth is counted, not read off the queue (`ConcurrentQueue.Count` is no per-packet read): the read loop counts each packet it queues, and the tick each packet it takes out, dispatched or dropped (a stale in-map packet, the drain of a connection that lost its authorization or is closing), through one method (`ReleaseReceivePacket`); a held head is not counted out until it leaves. Each count has one writer, so neither is interlocked, and the read loop reads the tick's count only when its own figure reaches the cap, about once in a cap's worth of packets for a connection the tick keeps up with. The tick counts a packet out just after taking it, so the depth can read one above what the queue holds and never below: a connection is closed only with at least the cap less one really waiting. `ReceiveQueueShould` holds the rule and the count. The tick takes at most 150 packets a pass from a connection (`WorldConnection.MaxPacketsPerUpdate`, about 9,000 a second; a pass that has taken that many stops, where until #883 it stopped one later and so took 151; `ReceiveQueueShould`), so the cap is reached by sending faster than that for long enough, by a queue that is wedged (above), by an instance whose update throws every tick before it reaches its characters' packets, or by time: a client sends one input per 1/60 s step and little else, so the cap is about 34 seconds of it arriving, or waiting, together. That is a tick stalled that long, or a path between the client and the world that stalled that long without the connection ending and then delivered what the client's socket had buffered faster than the tick takes it. The default is set against that last case (owner decision): a client's socket buffer, 64 KiB by default where the client runs, holds about a thousand inputs at the 70 to 90 bytes one takes on the wire (an estimate, not a measurement), and the cap is twice that. A wedged queue, and an instance that no longer takes its characters' packets, end the same way: in a close after about 34 seconds of the client's input. Short of that an honest connection stays far under the cap: the deepest backlog of any connection in the capacity ramp of 2026-10-12 was 2 to 3 packets at 950 bots, each sending input at 60 Hz as the client does. **Known limits (owner decisions).** The cap counts packets, not bytes: what a connection can have waiting is the cap times the size of what it sends, and this does not bound a packet's size. There is no arrival-rate budget and none per opcode: a flood the tick keeps up with is not refused, only bounded per tick by `MaxPacketsPerUpdate`. A packet dropped as it arrives (one no filter accepts, a `CMSG_PONG` with no ping left to answer) is never queued and never counted, though the read loop has read and decoded it. Once the connection is closing nothing more is decoded, but what the peer goes on sending is still read off the socket and discarded until the socket closes, which is at most about 0.6 s on a world (the close's wait for the outbox).

**Reflection-bound registration — a reference grep proves nothing.** Packet handlers are discovered by attribute scan, and AI/ability scripts by type name: `ScriptManager` keys every `AiScript` subclass by `t.Name` (except those marked `[ChainedScript]`), and `ICreaturePlacementService.AttachScript` resolves `creature.ScriptName` from the DB and builds it with `ActivatorUtilities.CreateInstance(_sp, scriptType, creature, instance)`. So "nothing references this type" says nothing about whether it is used — and note that call site passes exactly two runtime arguments, so a script constructor needing anything beyond `(ILoggerFactory, ICreature, ISimulationContext)` will throw and be swallowed into a logged error. Check constructibility against that call site, not against grep — `AiScriptConstructibilityShould` does exactly that for every nameable script, against the production container. Ability scripts are bound the same way: `ScriptManager` keys every `AbilityScript` subclass by `t.Name`, `AbilityTemplate.ScriptName` names one (the column was `SpellScript` until #163), and `InstanceAbilityCastSystem` builds it from `(ability, caster, aim, arena)` (an `AbilityAim` and the instance as `IAbilityArena`) through its `AbilityScriptActivator` (`Avalon.World/Abilities`, #925): one `ActivatorUtilities.CreateFactory` factory per script type, shared by every instance and called with an argument array each cast system keeps and clears after the call. `ScriptManager.Load` has each type's factory made as it registers the type, off the tick (making one compiles the constructor call: about half a millisecond, and some ten more for the first in a process); a type that reaches a cast any other way has its factory made by that cast. A factory binds by the declared types `IAbility`, `IUnit`, `AbilityAim` and `IAbilityArena`, not by the runtime types of the arguments as `CreateInstance` did: a constructor must take each of the four through a parameter of that type or of one it is assignable to (anything else it asks for is resolved from the container), so one declaring a narrower type (the concrete ability, a creature, the map instance) is refused on every cast, logged, and the cast refused. An ability script has exactly one public constructor accepting the four, or marks one `[ActivatorUtilitiesConstructor]`: with two that fit, a factory is refused ("Multiple constructors accepting all given argument types"), where `CreateInstance` picked the longer. The aim, a struct, reaches the constructor out of one box each cast system keeps and overwrites for every cast, unboxed into the `AbilityAim` parameter, so each script keeps its own copy; a script type with a public constructor parameter that could take the aim as a reference (`object`, `ValueType`, an interface the aim implements) would be handed the shared box, and is refused the same way. The factories are held weakly by their type (a `ConditionalWeakTable`), so none keeps a script assembly loaded, and the cast system asks `ScriptManager` for the type on every cast, so a type the manager no longer names is never built; a type that cannot be bound leaves no factory behind. `AbilityScriptConstructibilityShould` builds every seeded one through the activator. Quest scripts too (#433): `ScriptManager` keys every `QuestScript` subclass by `t.Name`, `QuestTemplate.ScriptName` names one, and `QuestService` builds it with `ActivatorUtilities.CreateInstance(new QuestScriptServices(services), type)`, no runtime arguments, from a provider that hands over only `ILoggerFactory`, `ILogger<T>` and `TimeProvider` (#738); `QuestScriptConstructibilityShould` builds every shipped one that way (see Quests). Item scripts too (see Item use): `ScriptManager` keys every `ItemScript` subclass (`Avalon.World/Items`, World-side) by `t.Name`, once, at `Load()`; `ItemTemplate.UseScript` names one; `ItemUseService` builds it once per type with `ActivatorUtilities.CreateInstance(new QuestScriptServices(services), type)`, no runtime arguments; `ItemScriptConstructibilityShould` builds every shipped and every seeded one that way. The world publishes their names in its script catalog (`item`), and an item template save checks `useScript` against it. Aura scripts too (see Auras): `ScriptManager` keys every `AuraScript` subclass (`Avalon.World/Auras`, World-side) by `t.Name`, once, at `Load()`; `AuraTemplate.ScriptName` names one; `AuraScripts` builds it once per type with `ActivatorUtilities.CreateInstance(new QuestScriptServices(services), type)`, no runtime arguments; `AuraScriptConstructibilityShould` builds every shipped and seeded one that way (none is shipped or seeded yet). The world publishes their names in its script catalog (`aura`), and an aura template save checks `scriptName` against it. Doodad scripts too (see World simulation): `ScriptManager` keys every `DoodadScript` subclass (`Avalon.World/Doodads`, World-side) by `t.Name`, once, at `Load()`, never hot reloaded; `DoodadTemplate.ScriptName` names one, resolved by the doodad catalog at load (a name no class has refuses the template); `DoodadScripts` builds it once per type with `ActivatorUtilities.CreateInstance(new QuestScriptServices(services), type)`, no runtime arguments, and shares it with every doodad and instance; `DoodadScriptConstructibilityShould` builds every shipped and seeded one that way (the stock `LootDoodadScript`, `ShrineDoodadScript` and `FountainDoodadScript` are shipped; no template seeds one yet). Packet handlers themselves (#822): `WorldHostGraphShould.Build_every_packet_handler_from_the_production_container` builds every `[PacketHandler]` type in `Avalon.World` from the production World container as the `WorldServer` constructor does (handing the world server to a handler that names it), and every `IPacketHandlerNew` type in `Avalon.Server.World` as `ServerBase` does per packet (`ActivatorUtilities.CreateFactory` with no runtime arguments, over a scope), and fails naming each handler and the service it could not get.
