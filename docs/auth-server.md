# Auth server login flow

The TCP login flow of `Avalon.Server.Auth`: the handshake, password and MFA login, MFA management, the world list, the login budgets shared with the REST API, account sessions and the Redis keys involved. World entry no longer passes through the auth server: it is the REST game admission ([World entry](#world-entry)).

## Auth Flow

```
CRequestServerInfoPacket → SServerInfoPacket (the client's version against Application:MinClientVersion; an older one is refused with ClientVersionTooOld and the connection closed)
→ CClientInfoPacket → SHandshakePacket → CHandshakePacket → SHandshakeResultPacket
→ CAuthPacket → SAuthResultPacket (per-source limit, per-username limit, lockout, BCrypt verify, then non-Active Status refused as BANNED/DEACTIVATED, then MFA check)
→ [MFA only] CMFAVerifyPacket → SAuthResultPacket (per-source limit, per-hash attempt limit, per-username limit, lockout, TOTP ±1 step, each step once; Status re-checked)
→ CWorldListPacket → SWorldListPacket (PostLoginGuard; the worlds the account may enter, each with its host, port, versions and derived status)
   CMFASetupPacket / CMFAConfirmPacket / CMFAResetPacket (MFA management, each after PostLoginGuard)
```

A login that passes every check ends in `GameLoginCompletion`. An account already online is answered `ALREADY_CONNECTED`: the server publishes the account on `world:accounts:disconnect` (noting its own publish, see the key list below) and closes the account's other auth connection, or, when it finds none, clears the stale flag with `MarkOfflineAsync`. Otherwise the login is written by column (`TryRecordLoginAsync`, with this connection's id as the online session), the connection keeps the account, its credentials version and the login time, `auth:accounts:online` is published, and `SAuthResultPacket` answers `SUCCESS` with the account id.

## World entry

The auth server no longer selects a world or issues a world key. TCP world select (`CMSG_WORLD_SELECT`), the world-key exchange (`CMSG_EXCHANGE_WORLD_KEY`) and the TCP game-ticket login (`CMSG_AUTH_GAME_TICKET`) were retired with the TLS join-ticket admission, and their opcodes (0x201B/0x301B, 0x201C/0x301C, 0x200F) are unassigned. A client enters a world through the REST API's identity service ([API services](api-services.md)):

1. It holds a game context credential from `/client/auth`: a store proof through `provider-attempts` and `store/proof`, or the launcher's game ticket (`POST /client/auth/game-ticket`), handed to the game and redeemed through `handoffs/redeem`.
2. `POST /game/worlds` lists the worlds that context may enter (`GameServerAllocator`): an Active, unlocked account at the context's credentials version, the world's access level (`AccessLevels.ForWorld(...).Allows(...)`), a ready heartbeat, an available world database, a workload assigned to the world and, for a non-Admin, no maintenance cutoff in force.
3. `POST /game/join-tickets` (or `/game/reconnect-tickets`, to return to the session the account holds) issues a join ticket bound to the context, the world, the character and the world server, for at most 30 seconds (`GameAuthPolicy.JoinTicketLifetime`), under an `Idempotency-Key`. A live session elsewhere is refused as `ActiveGameSession` unless the request confirms the takeover.
4. The client connects to the world server over TLS, pinned to the leaf the join reply names, and sends `CGameAdmissionPacket` (the ticket and its public key). The world server redeems the ticket (`/internal/game/join-tickets/redeem`) and activates the session (`/internal/game/sessions/activate`) over its mutually authenticated workload connection, off the tick, then answers `SGameAdmissionPacket` with its own public key, or with a refusal and a close.
5. `CWorldHandshakePacket` (the client's version, encrypted; at least 0.2.0 and the world's `MinVersion`) → `SWorldHandshakePacket`. Character selection follows ([character login flow](character-login-flow.md)).

The world renews the session every 15 seconds and stops gameplay before its lease runs out ([game server admission](steam-authentication-workloads.md)). The ticket's checks at issue and at redemption, and the world's own at character select and spawn ([world maintenance](world-maintenance.md)), replace the old world select's.

## Login budgets, sessions and accounts

**Login throttling** (`CAuthHandler`, `CMFAVerifyHandler`, `SourceBudget`, #471). The rules in this paragraph and the next live in `Avalon.Infrastructure.Login` (`PasswordLoginPolicy`, `MfaLoginPolicy`), and the REST API runs them too, over the same keys (see [REST API authentication](api-authentication.md), #478). Every password or MFA-code attempt takes a slot from its source's budget *before* any work, by an atomic increment whose returned value decides: past `MaxFailedLoginsPerSource` inside `FailedLoginSourceWindowMinutes` it is answered `LOCKED` before any account is looked up, so parallel connections cannot all slip past a check made before the first is counted. A slot is given back (`DecrementFloorAsync`, only its own, never the whole count) only once an MFA hash is issued or a login completes, as the per-username budget below describes; every other attempt keeps its slot, a correct password refused on the way and an attempt on a locked account included. The source is the full IPv4 address, or the /64 prefix for IPv6 (IPv4-mapped addresses count as IPv4); `LastIp`/`LastAttemptIp` store the full address (`RemoteAddress`). An unknown username still costs one BCrypt verify, against `BCryptPasswordVerifier.UnknownAccountHash`, and a wrong password is answered *before* its write, so response time does not reveal which usernames exist.

**The account lock is a per-username budget** (`UsernameBudget`, #484), built on the same `AttemptBudget` mechanics as the source budget. Every password attempt takes a slot keyed by the username as it is looked up (trimmed, upper-cased, then SHA-256 in the key) *before* `FindByUserNameAsync`, from every source alike and whether or not an account has that username, and every MFA code takes one from its account's username before the code is checked. The count the increment returns is the attempt's place in the window (`LockoutDurationMinutes`, fixed from the first attempt), and it alone decides, never the row as read: past `MaxFailedLoginAttempts` the attempt is answered `LOCKED` before the lookup; a wrong password (or wrong code) in the last slot is answered `LOCKED`, locks the row, and holds the key with `HoldCounterAtLeastAsync`, one Lua script that raises the count to at least `MaxFailedLoginAttempts + 1` (`UsernameBudget.HeldValue`, one past anything a run of failures reaches, so the reset below can tell a held key apart) and restarts its expiry, recreating the key if it expired after the take (a plain `EXPIRE` did nothing then, and an unknown username went back to `INVALID_CREDENTIALS` while a known one's row stayed locked); `UsernameBudget.RecordFailureAsync` computes the row's `LockedUntil` before the hold, so it always ends first, catches and logs a hold error, writes the row anyway (with `CancellationToken.None` whenever it locks, so a closing connection never skips the lock), and only then rethrows, which closes the connection; an earlier one is answered `INVALID_CREDENTIALS` (`MFA_FAILED`). An unknown username goes through exactly the same steps, answers and expiry, minus the database write. Before it, the lock was decided from the row each request read before its BCrypt verify, so parallel guesses spread over sources got about ten verifies per lockout, and the right password, reaching its success write after the batch's failures had locked the row, was the one answered `LOCKED`. Slots are given back late: a correct password gives back its own source and username slots only when it issues an MFA hash (no reset there: each password login makes a fresh hash, so a reset would hand out a fresh set of code guesses per login), and otherwise only once `TryRecordLoginAsync` has recorded the login. A **completed** login (non-MFA once recorded; MFA once the code is accepted and the login recorded) gives the source its own slot back and deletes the username's key (`UsernameBudget.ResetAsync`, owner decision), so a player's own typos do not carry over. The delete is one script (`RemoveCounterIfBelowAsync(key, heldValue)`) that runs only while the count, which still includes the login's own slot, is below `HeldValue` (the limit + 1): four typos and a login leave five and the key goes, but a hold that a concurrent last-slot failure set (with its row lock) is not deleted by a reset. The MFA-hash give-back cannot bring a hold back within reach either: `UsernameBudget.GiveBackAsync` is its own script (`DecrementCounterIfAtMostAsync(key, limit)`) that decrements only while `0 < v <= limit`, so a held value is left alone (a plain floored `DECR` let a give-back lower six to five, after which a reset deleted it, or two give-backs reached four and the next guess was verified); `SourceBudget` keeps the floored `DECR`. Known edge case: an attempt refused past the budget that lands between a login's take and its reset raises the count to six or more, so the reset keeps the key and the player is answered `LOCKED` until the window ends, with no row lock behind it. It fails closed and needs a race of a few milliseconds. The source key is never reset. Known limit: the window is fixed, not sliding, so an attacker who stays one short of the limit, four guesses every 15 minutes, never locks the account: about 384 guesses a day per username (4 × 96 windows). A budget window longer than the lockout (say a day, with the refusal still ending when the row's lock does) would close that; the mechanism is unchanged for now. Failed logins are still counted in SQL (`IAccountRepository.RecordFailedLoginAsync`, one `UPDATE` whose right-hand sides all read the old row), never by writing back the row that was read, so concurrent failures are not lost; the caller passes `lockUntil` when the budget says the failure locks, and the row stays locked until `LockedUntil`. An expired lock is lifted there too, and by the success write, `TryRecordLoginAsync`, which refuses if the account is locked at write time, so a success can never write away a lock set after it read the row; that refusal is answered as a wrong password in the same slot would be (`INVALID_CREDENTIALS`/`MFA_FAILED`, or `LOCKED` in the last slot) and keeps both slots, so on the offline, Active, non-MFA path (and at MFA verify, the offline Active path) it does not single out the right password in a parallel batch. `MFA_REQUIRED`, `ALREADY_CONNECTED` and `BANNED`/`DEACTIVATED` do single out a correct password inside the budget, by design. A lock with `LockedUntil = null` never expires; the migration that added the column gave every earlier lock a 15-minute end. The row's lock check stays before the password (and code) check on purpose: after it, a locked account would still tell right from wrong passwords. Each MFA hash allows `MaxFailedMfaAttempts` codes, counted on the `auth:account:{accountId}:mfa` hash before the code is checked; the last failure deletes the hash, so the client must log in again, and a code whose hash is gone (no reverse key, or `attempts` of -1) is refused without being checked. All these settings are under `Application` in the Auth server's config, and again, with the same names, under `Application:Authentication` in the API's; the two must match, since both count on the same keys.

**Account rows are written by column, never whole** (#484). The auth server never calls `UpdateAsync(account)`: clearing a stale `Online` flag at login or MFA verify is `MarkOfflineAsync`, a disconnect is `MarkOfflineAsync` with the session's seconds added to `TotalTime` (`AuthConnection.RecordDisconnectAsync`), and the start-up reset is one `MarkAllOfflineAsync`. Each is an `ExecuteUpdate` that never touches `Locked`, `LockedUntil`, `FailedLogins` or `Status`, so a ban or a lock written between the read and the write survives it.

**`Online` belongs to one connection (#487).** A TCP login (`TryRecordLoginAsync`) stores the logging-in connection's `Id` in `Accounts.OnlineSessionId` with `Online = true`. `MarkOfflineAsync(id, sessionId, seconds)` clears both only while `OnlineSessionId` still equals `sessionId`, in one statement, and adds the seconds to `TotalTime` either way, so a close that lands after a newer session of the account logged in leaves that session online. A disconnect passes its own connection id; the stale-flag clear at login or MFA verify passes the session id it read. **Exactly one auth server is supported:** the start-up `MarkAllOfflineAsync` clears every `Online` flag and session, and the `ALREADY_CONNECTED` check looks only at this server's connections, so a second server would break both (the Helm chart runs one replica). **A liveness sweep (#555)** relies on the same assumption: every `Application:OnlineSweepIntervalSeconds` (default 30, startup refuses below 1), `OnlineSweep`, run from `AuthServer.ExecuteAsync` on an absolute `TimeProvider` due time (a late pass sweeps once), reads only the online rows' id and session (`ListOnlineSessionsAsync`) and calls `MarkOfflineAsync(id, sessionId, 0)` for each whose session is none of this server's live connections, so a close whose write failed does not leave the account online until the next restart; the compare keeps a login that landed since, and a sweep that throws is logged and the next still runs. A half-open TCP connection is still live to it, so every socket the shared `ServerBase` accepts (auth and world) has TCP keepalive on (#571, `TcpKeepAlive`; `Hosting:TcpKeepAliveTimeSeconds`/`TcpKeepAliveIntervalSeconds`/`TcpKeepAliveRetryCount`, default 60/10/3, startup refuses below 1 or above the OS maximum), and the OS closes one within about 90 s, which runs the close path. **The accept loop (#578, #584)** is one awaited `AcceptTcpClientAsync` loop started by `ServerBase.StartListening`, which `ServerBase.StartAsync` calls at host start unless the server's `ListenOnStart` is false; the world server's is (#665), and it calls `StartListening` at the end of `ExecuteAsync`, once scripts, the world, the cache subscription, the connection listener and the tick thread are ready, so no client is accepted while the world loads or after a load that failed (a port that cannot be bound fails the start and stops the tick; `WorldServerStartupShould`): only a stop ends it (`StopAsync` cancels it and awaits it before `OnStoppingAsync`, and is idempotent); a failed accept outside a stop is counted (`avalon.tcp.accept.errors`), warned at most once per 10 s, and retried, at once for a peer reset and otherwise after a backoff of 100 ms doubling to 5 s. A client accepted once the stop began is closed, and a packet arriving then is dropped, not dispatched; the shutdown closes its connection.

**What a username may be (owner decision, #487 re-review):** 3 to 16 ASCII letters, digits or underscores (`UsernameRule`, `^[A-Za-z0-9_]{3,16}$`), checked as sent, before trimming or upper-casing. `POST /account/register` refuses anything else with a 400 validation error (`UsernameRuleAttribute` on `RegisterRequest.Username`, and again in `AccountService.Register`). A login with anything else (`PasswordLoginPolicy`, so TCP and REST alike) is answered exactly as an unknown username: both budgets, the lookup, one dummy verify, `INVALID_CREDENTIALS` or the generic 401, whatever row holds the normalised form. With ASCII letters only, .NET and Postgres upper-case alike, so the check constraint below cannot disagree with the code.

**One account per username (#487).** `Accounts.Username` has a unique index (`IX_Accounts_Username`). Usernames are stored trimmed and upper-cased, the form login looks up, so the index is on the normalised name. Registration still checks first; a registration that loses the race to the index gets the check's answer, "Username already exists". A check constraint, `CK_Accounts_Username_Normalised` (`"Username" = upper(trim("Username"))`), refuses a row that is not stored normalised, whoever writes it. The migration that added the index refuses to run, naming the accounts, when two accounts share a normalised username or a username is not stored normalised; it never deletes or rewrites a row.

**One account per email (#503).** `Accounts.Email` has a unique index (`IX_Accounts_Email`) and a check constraint, `CK_Accounts_Email_Normalised` (`"Email" = lower(trim("Email"))`). Emails are stored trimmed and with the whole address lower-cased, local part included (`AccountEmail.Normalise` in `Avalon.Domain.Auth`, chosen over folding the domain only), and `FindByEmailAsync` normalises what it is given, so `A@x.com` and `a@x.com` are one account. An email must be printable ASCII with exactly one `@`, neither first nor last (`AccountEmail.IsValid`; `[EmailAddress, AccountEmailRule]` on the request and again in the service, 400 otherwise): outside ASCII .NET and Postgres can lower-case differently, and the check constraint would refuse what the code stored. A check violation (SQLSTATE 23514) on `Accounts` that still reaches the API, direct or wrapped by SaveChanges, is a 400 (`ExceptionHandlerMiddleware`), not a 503. Registration and the start of an email change refuse a taken address as "Email already exists"; both take a slot of the source's budget before the lookup, kept on that answer, so it is never free; a registration or an email confirm that loses the race to the index gets the same answer. The migration that added the index refuses to run, naming the accounts, when two accounts share a normalised email or an email is not stored normalised; it never deletes or rewrites a row.

**TOTP codes are single-use** (`MFAService`, #471). `MfaSetups.LastAcceptedTotpStep` stores the step of the last accepted code, set at confirm and advanced by `TryAcceptTotpStepAsync`, which writes only when the new step is later. A code at or before that step is refused, and the window is ±1 step for both confirm and verify. A hash has one winner (#478): once a right code's step is accepted, the code spends the hash with `IMFAHashService.TryConsumeAsync`, and only the caller whose `DEL` removed the reverse key goes on, so two verifies of one hash with codes of adjacent steps cannot both pass. The step is accepted first on purpose: a replayed code (right, already used) is refused as `MfaCodeRefusal.Replayed` without spending the hash, and like a code that lost the hash (`HashSpent`) it is not a failed login: `MfaLoginPolicy` gives its slots back and writes nothing to the row. A replay also gives back the attempt it counted on the hash (`IMFAHashService.GiveBackAttemptAsync`, a script that decrements `attempts` only while the hash exists, never below zero); a code that lost the hash does not, since that per-account key may already hold the next login's hash.

**Every post-login auth handler starts with `PostLoginGuard.AccountOrCloseAsync`** (#495 review): MFA setup, confirm and reset, and the world list. It reads the account fresh and closes the connection unless it is logged in, the account exists, is `Active`, and is still at the `CredentialsVersion` this connection's login proved; so a session banned, deactivated or outdated by a credentials change since its login can neither change MFA nor list the worlds. MFA confirm and reset also carry the session's version into their write (`IMFAService.ConfirmMFAAsync`/`ResetMFAAsync(accountId, credentialsVersion, ...)`): `MfaSetupRepository.TryConfirmAsync` and `ResetConfirmedAsync` start their transaction with `HoldCredentialsVersionAsync`, so a change committed between the guard and the write refuses it (`MfaSetupWrite.CredentialsChanged`, `CredentialsChanged` on the result); the TCP handler then closes the connection and the REST endpoint answers 401.

**World access** is decided by `AccessLevels.ForWorld(world.AccessLevelRequired).Allows(account.AccessLevel)`, the same test in `CWorldListHandler` (what the TCP world list shows) and in the REST game admission (`GameServerAllocator`, through `GameApplicationAccessPolicy.AllowsWorldAccess`: what `POST /game/worlds` lists and what a join ticket can be issued for). A Player world admits every player, Tournament and PTR included; a Tournament or PTR world admits holders of that flag plus staff; a staff-gated world admits its staff mask. Never compare a world's level with `<=`: `AccountAccessLevel` is `[Flags]`, and PTR (32) and Tournament (16) are numerically above Admin (4), which is how PTR accounts used to reach the Admin-only world.

## Redis keys

**Key Redis patterns** (string literals in `CacheKeys`; the launcher code, game ticket and game-auth keys are in [Redis keys](redis-cache-keys.md)):
- `auth:mfa:hash:{sha256}` — an MFA hash's reverse key, named by the SHA-256 of the hash rather than the hash itself (#535); value `{accountId}:{credentialsVersion}` (#495), 2 min TTL; its `DEL` spends the hash
- `auth:account:{accountId}:mfa` — Redis Hash with MFA state (2 min TTL); its `attempts` field counts MFA codes tried against it (`HINCRBY`, only while the hash exists); a replayed right code gives its attempt back (one script: `HINCRBY -1` only while the hash exists and the field is above zero)
- `auth:source:{source}:failedLogins` — attempt budget per source (IPv4 address, or IPv6 /64 as `prefix::/64`), shared by the TCP login and the REST API (#478), `INCR` with the expiry set on the first attempt (fixed window, default 15 min); a correct password or MFA code gives its own slot back with a floored `DECR`
- `auth:source:{source}:accountsCreated` — accounts created by one source through `POST /account/register` (#495 review), `INCR` before the insert with the expiry set by the first (fixed window, default 60 min, cap default 5); given back only when no account is created
- `auth:emailChange:{sha256}` — a pending email change, keyed by the lowercase hex SHA-256 of its confirm token, never the token itself (#510 review); value `{accountId}|{credentialsVersion}|{email}`, 15 min TTL; the confirm hashes the presented token, and its `DEL` spends it
- `auth:account:{accountId}:emailChangePending` — the token hash of the account's one pending email change (15 min TTL). A start whose confirmation was sent swaps it in one script (`SwapAsync`: `GET` and `SET ... PX` together) and deletes the entry the old value names, so only the latest token confirms; a successful confirm deletes it only while it still names the confirmed token's hash (`RemoveIfEqualsAsync`, one script)
- `auth:account:{accountId}:emailChangeSends` and `auth:email:{sha256(normalised new email)}:emailChangeSends` — email-change confirmations sent per account and per new address (#510 review), `INCR` just before the send with the expiry set by the first (`Application:Authentication:EmailChangeSendWindowMinutes`, default 60; `MaxEmailChangeSendsPerAccount` and `MaxEmailChangeSendsPerAddress`, default 3 each, startup refuses below 1); never given back; past either, 429 `LOCKED` and nothing is stored or sent
- `auth:username:{sha256}:failedLogins` — attempt budget per username (lowercase hex SHA-256 of the trimmed, upper-cased username, whether or not an account has it), shared by password and MFA-code attempts from every source and by both servers (TCP and REST, #478); `INCR` with the expiry set on the first attempt (`LockoutDurationMinutes`, default 15 min); the failure that reaches `MaxFailedLoginAttempts` holds it with one script (raise to at least the limit + 1, `SET ... PX` the window, recreating an expired key); a correct password that issues an MFA hash gives its own slot back with one script that decrements only while `0 < v <= limit` (never lowering a held value); a completed login deletes it with one script, only while its value is below the held value, limit + 1 (so a reset never deletes a hold)
- `world:accounts:disconnect` — pub/sub, force-disconnect by accountId: published by the Auth server and the API (duplicate login, password change, MFA reset or removal, ban, email change, role change, refresh-token reuse); subscribed by the World server, which closes every connection of the account (`WorldServer.CloseAccountSessions`, #504 review; not only the first), and, since #495, by the Auth server, which closes that account's logged-in TCP connections with `DisconnectReason.Kicked` (`AuthServer.CloseAccountConnections`). The message is the bare id and cannot say why, so both servers tell the player the same neutral "Your session has ended. Please log in again." with `Kicked`; only the world server's own duplicate-login kick at character select says "logged in from another location". A TCP MFA reset therefore ends the connection that made it, too. The message is the bare account id the World server parses, so it carries no origin: before its own duplicate-login publish (`ALREADY_CONNECTED`) the auth server notes it (`NoteOwnDisconnectPublish`), and for `OwnPublishWindow` (10 s) a connection of that account that logged in after the note (`IAuthConnection.LoggedInAt`) is spared, so the retry that follows is not kicked by its own attempt (the note lasts its whole window, whatever messages arrive, because a ban and the echo cannot be told apart and a note consumed by the first let the second kick the retry; expired notes are dropped on read and pruned on every write, so the map holds only the last window's publishes); `PostLoginGuard`'s status and version checks, and the join ticket's own, cover anything else that lands in that window. One connection that throws while closing is logged and the rest are still closed.
- `auth:accounts:online` — pub/sub: login event (reserved, no subscriber yet)
- `world:{worldId}:ready` — the world's ready heartbeat (`CacheKeys.WorldReady`, value `1`, 5 s TTL), set every second by `WorldReadyHeartbeatService` only while the listener is open and ticks complete, removed on a graceful stop; absent or unreadable means offline (see [World maintenance](world-maintenance.md))
- `world:{worldId}:maintenance` — pub/sub: a committed maintenance revision (`CacheKeys.WorldMaintenance`), a hint only; the world reads the row itself
- `world:{worldId}:presence` — one world's live presence snapshot (`WorldPresenceSnapshot`: its instances and the characters in them), captured on the tick about once a second by that world server's `PresenceCapture` (`Avalon.World/Presence`; `WorldServer.Update` calls `CaptureIfDue` in the serial phase after the world update, timed by the container's `TimeProvider`, no timer) and handed through one volatile reference to `PresenceSnapshotService` (`Avalon.Server.World`), which polls every 250 ms off the tick and writes each snapshot it takes once (#639), with `CacheKeys.PresenceTtl` (5 s); a stalled tick captures nothing, so the keys expire, and a capture that finds nobody in the world drops any snapshot not yet written
- `presence:world:{worldId}:character:{id}` — which instance of that world holds character `{id}` (`CharacterPresenceIndex`), same writer and TTL. It names the world because character ids are unique only per world (#556). A deploy that changed a presence key loses the entries under the old key; they expire within the TTL and each world server writes the new ones on its next capture, so nothing needs migrating

The old TCP world select's entry keys (`world:{worldId}:keys:*`, `account:{accountId}:inWorld`) and its `world:{worldId}:select` channel went with it.
