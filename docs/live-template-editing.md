# Live template editing

Editing item, ability, creature and aura templates on a running world through the REST API, and how the world applies them without a restart.

## Live template editing

Admins edit item, ability, creature and aura templates on a running world, and the world applies them without a restart.

- **Endpoints** (`[Authorize(Policy = AvalonRoles.Admin)]`, `[WorldScoped]`): `PUT /world/{worldId}/item-template/{id}`, `/ability-template/{id}`, `/creature-template/{id}` and `/aura-template/{id}`. The body is the read DTO minus `Id`, `Version` and `Editable`. The reads carry `version` (a lowercase hex SHA-256 of the row's stored values) and `editable`, and set `ETag: "<version>"`. An aura's modifier list replaces the stored one, merged by stat (updated, added, removed), and its version covers the modifiers; its `scriptName`, when changed, must be in the world's published script catalog (`aura`), and the aura must still fit every ability that applies it. An aura also carries its crowd control (#770): `control`, the flags as an integer mask (1 stun, 2 root, 4 silence, 0 none; the slow is derived from the modifiers, never a flag), which only a Harmful aura may set (else a 400 keyed `control`), and `breakOnDamagePct` and `breakPerSecondPct`, each a percentage from 0 to 100 (else a 400 keyed by its name). A creature template carries `stunDurationPct`, `rootDurationPct`, `silenceDurationPct` and `slowDurationPct`, each null (its rarity's) or a percentage from 0 to 100 (else a 400 keyed by its name); the rarity table they fall back to has no REST surface. These fields are in the version, so every aura's and creature's version changed once with #770. The ability template carries `auraId`: the aura must exist, pass the world's aura rules and fit what the ability affects (`AuraRules.LinkProblem`), else a 400 keyed `auraId`; a foreign-key violation that slips past (the aura deleted meanwhile) is a 400 too.
- **Editability is configuration, never code.** A world is editable only if its id is in `Application:Templates:EditableWorlds` (default empty; Helm `templates.editableWorlds`; the AppHost lists the local Development world). Anything else answers 403 `This world is not editable`, checked before the body is read. Production worlds stay out of the list. `Application:Templates:ReloadTimeout` (default `00:00:10`) bounds the wait for the world's answer.
- **If-Match and 409.** A `PUT` needs `If-Match: "<version>"`: missing gives 428, a stale one 409 `Changed since you opened it`. Other answers: 404 for an unknown id, 400 ValidationProblem keyed by camelCase field name. A `200` carries `{ template, reload: { status: "applied"|"failed"|"pending", summary } }`. The write is committed before the reload is requested, so `failed` and `pending` leave the saved row in place. Each edit runs in one Serializable transaction (#1179 part B2), so two edits that each check a row the other changes cannot both commit: a unique pointed at a base while another edit changes that base's kind or level, each checked against the other's row as it stood, would otherwise both pass and leave the unique out at the next reload. Postgres fails the loser with a serialization failure, at a read, at the save or at the commit (Npgsql wraps it as a transient failure, so the whole inner-exception chain is searched, `TemplateDbErrors.Postgres`), nothing is written, and it answers its own 409, `Another template edit was saved at the same moment` ("Nothing was saved. Try again."), apart from the stale version's `Changed since you opened it`. Since the item checks read the whole `ItemTemplates` table, two edits of unrelated item templates saved at the same moment collide too; resending the same request succeeds (the version did not change), while two saves of one version get the stale-version 409 on the retry. A row lock (`SELECT ... FOR UPDATE` on the cross-referenced templates) would not do under repeatable read: an edit that waits on a lock the other only took keeps its older snapshot. This holds on Postgres only; the tests' SQLite runs one writer at a time.
- **Reload over Redis.** After the commit the API publishes `{ requestId, areas }` on `world:{id}:reload` (`CacheKeys.WorldReloadChannel`); the world re-reads the areas (`Items`, `Abilities`, `Creatures`, `Auras`) through `IReferenceDataReloader`, the one `/reload` uses, and answers on `world:{id}:reload:result` (`CacheKeys.WorldReloadResultChannel`), matched by `requestId`. No answer within `ReloadTimeout` (world down, not yet subscribed: pub/sub is not queued) reports `pending`.
- **What players see.** A reload is forward-only, like `/reload`: new creature spawns use the edited template (live ones keep theirs), an aura already on a unit keeps the template it was applied with, abilities are read at character select (a held ability keeps its old metadata until the next select), and items are read from the templates afterwards.
- **Versions changed once with #1142.** Every item template's version changed once. `AllowedClasses` is now stored as class numbers (`smallint[]`) and no longer has a converter, so the version, which used to hash its comma-joined text, now hashes the list of class names. The versions of abilities 230-235 changed too, because their class's enum name changed from Healer to Cleric. An editor holding an older version gets a 409 and reads the row again.
- **An empty `allowedClasses` means every class, for items (#1171).** On a read and in a `PUT`, an item template's `allowedClasses: []` lets every class equip the item (the list limits equipping only, never a use); list classes only to restrict it to some (listing all four works but is not the intended form). Abilities have no list since #1181 (below). The migration `ItemsAllowEveryClassWhenEmpty` emptied the lists of the 16 seeded items that named all four classes (ids 1-3, 9-11 and 56-65), so their versions changed once.
- **Damage types, resistances, ward and attribute requirements (#1178).** An ability template carries `damageType` (`Physical`, `Fire`, `Cold`, `Lightning`, `Blight`, or null): an Ally ability names none, a class ability (one the talent tree grants, #1181) that deals damage, directly or through a damaging aura, names one, and a creature-only ability may leave it null to deal its creature's type (`AbilityRules.Problem`, `AuraRules.DamageTypeProblem`); a refusal is a 400 keyed `damageType`. A creature template carries `damageType` (its basic attack's, and its null-typed abilities'), `fireResistance`, `coldResistance`, `lightningResistance` and `blightResistance`, each a percentage from -100 to 100 (negative takes more), and `evasionModifier` and `wardModifier`, each finite and 0 or more (0 is none); a value out of range is a 400 keyed by its name. An item template carries `requiredStrength`, `requiredAgility` and `requiredIntellect` (null for none), checked when the item is equipped. The public item and ability reads carry the same requirements and damage type, and a link preview says `Requires 12 Strength` or `Fire damage`.
- **No `allowedClasses` on an ability (#1181).** An ability template's read and `PUT` body no longer carry `allowedClasses`: a class ability is one the talent tree grants (a class start or a node links it), and the edit reads that from the world's `TalentNodeAbilities` in its own transaction, so editing a granted ability holds it to the class rules (a granted Cleave with no `damageType` is a 400 keyed `damageType`). The public ability read carries `granted` instead of `allowedClasses`, and a link preview no longer names classes. Item templates keep `allowedClasses`. The World migration `AbilitiesFromTheTree` dropped the column, so every ability template's version changed once (the version hashed the class list); an editor holding an older version gets a 409 and reads the row again.
- **Versions changed once with #1178.** The new columns joined the version, so every ability, creature and item template's version changed once; a creature's damage type is hashed under its property's name, `DamageType` (the column was `DmgSchool` until part B renamed it). An aura with a stat 5 modifier changed too, because the stat is now named `Evasion`, not `DodgePct`. An editor holding an older version gets a 409 and reads the row again.
- **The offence model (#1178, part B).** An ability template carries `tags` (names joined by commas, such as `"Attack, Melee, Area"`, or `"None"`: at most one of `Attack`, `Spell` and `Heal`, plus `Area`, `Projectile` and `Melee`; `DamageOverTime` is an aura's, never an ability's), `damageEffectiveness` (percent of the weapon's damage an Attack deals), `spellBaseMin`, `spellBaseMax` and `spellBasePerLevelPct` (a Spell's or a Heal's level-1 roll and its linear growth per level), `convertToType` and `convertPct` (the element an Attack converts part of its weapon's physical damage to, and how much, 0 to 100), and `addedType`, `addedMin` and `addedMax` (its own added damage). The ability rules decide what fits (`AbilityRules.Problem`, and `AuraRules.SourceProblem` for the aura it applies), and each refusal is a 400 keyed by the field it is about: `tags` for tags that do not fit what the ability affects, deals or is shaped as (or that its damaging or healing aura cannot scale with), `spellBaseMax` for a Spell or a Heal with nothing to roll, `damageEffectiveness`, `convertPct`, `convertToType`, `addedMax`, `addedType` and `spellBasePerLevelPct` for their own values, `damageType` for a class Attack that is not physical, and `cooldown` for a basic Attack whose cooldown is not 0 (its weapon paces it). An aura template carries `periodicEffectiveness`, the percent of its source's base roll added to `periodicBase` (finite and 0 or more, else a 400 keyed `periodicEffectiveness`). A weapon's attack time, which this part put on the item template as `attackTimeMs`, is a base stat since #1179 (part B2, below); the public ability read carries the ability's offence fields. The retired `effectValue`, `scalingStat`, `scalingCoefficient` and `baseDamageCoefficient` are gone from the reads and the bodies.
- **Target cap (#1181).** An ability template carries `maxTargets`, the most units a circle or a cone affects and the hit a piercing projectile ends on, the nearest it may affect; 0 is no limit. A negative one is a 400 keyed `maxTargets` (`AbilityRules`, the rule the world's ability catalog applies). Like every field it is written from the body, so a body without it saves 0: an editor reads it back with the rest. The column joined the version, so every ability template's version changed once; the public ability read carries it too.
- **Versions changed once with #1178, part B.** The new columns joined the version, and the retired ones left it, so every ability, aura and item template's version changed once. An editor holding an older version gets a 409 and reads the row again.
- **Bases and rarity (#1179).** An item template carries `baseKind` (the kind of base it is, such as `PlateChest`, `Sword` or `Ring`; null for a consumable or quest item) and `requiresAnyAttribute` (true when any one of its set attribute requirements is enough, as on a mace's Strength or Intellect; false when every set one is needed). Each refusal is a 400 keyed by its field: `rarity` for anything but `Common` or `Unique` (Magic and Rare are rolled on a copy, never a template's own; the table's `CK_ItemTemplates_Rarity`), `baseKind` for an unknown kind, a kind on an item with no `slot`, or a kind worn in another slot than the item's (`ItemBaseKindSlots.SlotOf`: what rolls on a base is read by its kind, so the two agree), `requiredLevel` above 32767 (a copy takes it as its item level, a `smallint` column), and `maxStackSize` above 1 on an item with a `slot` (equipment never stacks). A change of `rarity` or `baseKind` is also held against the modifiers the template links (part B, `ItemModifierCatalog.RarityRefusal`, read narrowly: the template's links and their rows only): it is refused, keyed `baseKind` when the kind changed and `rarity` otherwise, unless a `Unique` template links exactly one unique modifier (or none at all, which the world keeps too), a `Common` base exactly one implicit and a `Common` template without a kind nothing, since the world's Items reload would leave such a template out whole. And a change of `rarity` to `Unique` on an item a quest pays, as a fixed reward or a choice, is refused keyed `rarity`, as a newly set `Unique` flag is keyed `flags` (`ItemUseRules.QuestRewardProblem`, the rule the Quests reload applies). The item power is gone from the reads and the bodies; a copy's item level is on the inventory read instead. The columns changed with the bases, so every item template's version changed once; an editor holding an older version gets a 409 and reads the row again.
- **Base stats, a unique's base and the damage type (#1179, part B2).** An item template carries `baseStats`, the ranges every copy rolls within (`stat`, one of `Armour`, `Evasion`, `Ward`, `BlockChance`, `DamageMin`, `DamageMax` and `AttackTime`, with `min` and `max`; the rows of `ItemTemplateBaseStats`, [item modifiers](item-modifiers.md#base-stats)), a whole-list replace like `allowedClasses`, merged by stat; `damageType`, the type of a weapon's damage (it replaced `damageType1`; `damageMin1`, `damageMax1`, `damageMin2`, `damageMax2`, `damageType2` and `attackTimeMs` are gone from the reads and the bodies, World migration `DropTemplateWeaponColumns`); and `baseTemplateId`, the base a unique is made on. Each refusal is a 400: `baseStats` for a stat listed twice or an unknown one, or when the ranges break the world's rule (`ItemBaseStatRules.RangesProblem`: exactly the stats the template's kind carries, none on a unique, jewellery, a trinket or an item that is no base; each range from at least 0 up to its maximum; an attack time of at least 1 ms; a weapon's highest minimum damage at or under its lowest maximum); `damageType` for an unknown type, or a type on anything but a Common weapon, or none on one (`ItemBaseStatRules.DamageTypeProblem`: a unique weapon deals its named base's type, as it rolls its base's ranges, so it names none); and, for the base a unique names (`ItemBaseStatRules.NamedBaseProblem`, the rule the world's Items reload applies): a Unique template names a base and any other names none, and that base exists, is kept by the world, is `Common`, of the unique's kind and at or under the unique's required level. That refusal is keyed by the field the edit changed (`baseTemplateId`, `baseKind`, `requiredLevel` or `rarity`), and the same rule holds for a base a unique names: a change of its `rarity`, `baseKind` or `requiredLevel` that would leave a unique made on it out is refused, keyed by the field changed (`TemplateItemUsers`). The version covers the base-stat ranges, by stat, so every item template's version changed once with this part. **An edit of a base's ranges reaches only copies made afterwards**: each copy keeps the values it rolled (`ItemInstanceBaseStats`), and a worn copy is never changed by it.
- **Implicits and modifiers are not template fields (#1179, part B).** A base's implicit modifier is rolled on each copy, and the modifier catalog (`ItemModifierGroups`, `ItemModifiers`, `ItemModifierStats`, `ItemModifierWeights`, `ItemTemplateModifiers`, and the Resonance themes `ItemThemes`, #1180) is balance data changed only by a migration, never by a `PUT` ([item modifiers](item-modifiers.md)). The template's stat lines are still editable, and a line added to a base counts on every worn copy beside its base stats and implicit, since the stats fold reads them all. An edit that makes an item a vendor stocks anything but `Common` is refused, keyed `rarity` (a vendor sells commons only, `ItemUseRules.VendorStockProblem`).
- **Resonance effect auras are editable like any aura (#1180 part A2).** Auras 16-44, which worn gear's Resonance effects apply ([auras](auras.md#resonance-effects-1180)), are aura templates: `GET` lists them and `PUT` edits them with the same fields, checks and versions, and the edit reloads the Auras area, so the next application of the effect uses it. The API knows nothing of the effects, so it refuses no edit for being an effect's aura: an edit that breaks an effect's rules (a `kind` that no longer fits its target, a stun, a damage type that no longer matches what the aura deals) is saved, and the world's Auras reload holds the effect rows against the edited auras and leaves that effect out, logged at Error, from every wearer's next firing, online characters included ([auras](auras.md#resonance-effects-1180)); every other effect keeps firing, with its source built from its aura as edited. The effect rows themselves (`ItemThemeEffects`) are balance data changed only by a migration, never by a `PUT`.
- **Capstones hold the abilities they shape (#1181 part D).** A capstone's modifier rows (`TalentAbilityModifiers`, [talents](talents.md)) are checked by the world's talent catalog against the ability each shapes and that ability's aura, and one that fails refuses the whole tree. So an ability edit, and an aura edit for each ability applying the aura, runs the same check (`TalentModifierRules.AbilityProblem`, read in the edit's transaction) and refuses with a 400 worded "The world would refuse the talent tree: node N's {Kind} modifier: ...": keyed `auraId` for a stack or duration modifier (the ability's aura removed, or changed to crowd control) and `effects` for a second hit or an explosion (the ability's direct amount removed); on an aura edit keyed by the field that made it so: `control` (a stun, a root or a silence), `kind` or `modifiers` (a slow: a Harmful kind with a negative movement speed modifier, keyed `kind` when the kind changed) or `stacking` (a stack modifier on an aura that no longer stacks). The modifier rows themselves are balance data changed only by a migration, never by a `PUT`.
- **Caveat: a release that changes a template in code overwrites the live edit.** The templates are seeded from `WorldDbContext`, so a migration that changes that seed rewrites the row, edit included. Re-apply the edit after such a release.
