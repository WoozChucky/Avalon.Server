# World simulation

The world server tick, its threading rules, instances, creature AI and locomotion, abilities and combat, loot, replication and reference-data reload.

## World Simulation

`WorldServer` is an `IHostedService` that runs the tick loop at ~60 Hz (16.67ms intervals). On each tick it calls `World.Update(deltaTime)`, which ticks all active `MapInstance` objects via `IInstanceRegistry`.

**Two-pass tick architecture:** Each tick runs in two passes. Pass 1 — `WorldServer.Update` calls `connection.UpdateSession()` on every connected client, processing pre-character packets (`CMSG_PONG`, character list/select/create/delete) via `WorldSessionFilter`. Pass 2 — `World.Update → MapInstance.Update` calls `connection.UpdateMap()` on every in-map client, processing in-map packets (movement, attack, chat) via `MapSessionFilter`. Only the tick dequeues received packets. A packet refused by one pass stays in a tick-owned pending slot ahead of later packets until the other pass accepts it; a stale map packet left by a character that has gone is dropped by the session pass. This preserves FIFO without `ConcurrentQueue.TryPeek`, which would prevent queue segments from reusing their slots. **The receive queue is bounded (#927):** a connection may have `Network:MaxReceiveQueueDepth` packets (2,048) received and not yet dispatched or dropped, the pending slot included; one that arrives with that many waiting is not queued and closes the connection from its read loop, without a notice (the rule, its count and its limits are under [packet handlers](packet-handlers.md)). The depth is two counts, the packets the read loop queued and the packets the tick took out, each written by its one thread; the cap and the receive-depth gauge both read their difference, so the gauge no longer walks the queue. Both filter instances are stored on `WorldConnection` and reused each tick — no per-tick allocation.

**Tick-thread rules (#639).** World state changes on the tick thread only. Slow work (database reads, the navmesh bake, a whole instance build, saves, reload prepares, script compiles, Redis writes) runs off the tick and hands its result back through a queue the tick drains or a connection continuation (`EnqueueContinuation`, flushed at the end of `WorldServer.Update`); it touches only what it owns and immutable snapshots, never a live instance, index, party or character. Instance membership (`World.SpawnInInstance`, `TransferPlayer`, `LeaveWorldAsync`'s synchronous part), the registry's indexes and pending builds, every `PartyService` mutator, `OnlineCharacters` writes and `IgnoreList` writes call `TickThreadGuard.AssertOnTick` (`Avalon.World/Threading`, a DI singleton): `WorldServer`'s tick loop binds its thread to it when it starts and unbinds it when it ends, and while the check is enabled and a thread is bound, a call from any other thread throws `InvalidOperationException` naming the operation. It checks the thread only (every serial step and every instance tick run on that one thread today; a phase check is for parallel ticking, not built). It is compiled into every build and checks only while enabled (owner decision): `Game:TickThreadGuard` (bool, default `false`; a local World server turns it on with `Game__TickThreadGuard=true` in its environment, since the World server has no `appsettings.Development.json`) turns it on when `WorldServer.ExecuteAsync` starts the tick, and the World test assembly turns it on for itself with a module initializer (`TickThreadGuardOn`), so its tests exercise it in Debug and Release alike. The switch is one process-wide static volatile flag that is only ever turned on, so off it costs one read per check. It throws rather than `Debug.Assert`, which would end the process. Unbound (before the tick starts, the shutdown despawn after it is joined, and tests that bind nothing) it lets every thread through; the shutdown despawn calls each connection's despawn on its own, so one the guard refuses (a tick that outlived its 5 s join) costs the others neither their despawn nor the wait for saves. Reads stay free (telemetry reads the instance list). The holders take it as an optional constructor parameter; `WorldHostGraphShould` pins that production hands the one instance to the world, the party service, `OnlineCharacters` and `CharacterSelectHandler` (for each `CharacterEntity`'s ignore list).

**Tick thread placement (#1002).** The tick thread runs at normal priority (`ThreadPriority.Highest` does nothing on Linux without `CAP_SYS_NICE`) and may land on any CPU: on one that takes the node's network interrupts, or on a core whose other hyperthread is busy with the world's own pool or send threads, the same tick runs 1.13–1.16 times slower ([#1001](https://github.com/WoozChucky/Avalon.Server/issues/1001), section 6). `Game:TickThreadCpu` (unset by default; chart value `server.tickThread.cpu`) pins it, on Linux, to that CPU alone and keeps every other thread of the world off that CPU's core (`TickThreadPlacement`, `Avalon.World/Threading`, through `LinuxCpuAffinity`'s `sched_setaffinity`). It runs once, on the tick thread before its first tick: nothing per tick. How the rest is kept off: Linux starts a new thread on its creator's CPUs, but the .NET runtime moves every thread it starts onto the CPUs of the process's main thread as the thread begins (`CPalThread::ThreadEntry`), whichever thread created it. So the main thread is restricted to every CPU but the core first, the tick is then pinned, and every thread that already exists is moved off the core, in passes repeated until one moves nothing (at most five, with a warning when the last still moved threads), for a thread that was starting during a pass. From then on the thread pool's workers (those the tick itself asks for included), the send threads, the timer thread and any thread a library starts through the runtime land off the core. **Not covered:** a thread created by native code calling `pthread_create` directly from the tick thread (nothing does), and server GC's heap threads, which the runtime binds one to each CPU at start: the two on the tick's core are left there and counted in a warning unless `DOTNET_GCHeapAffinitizeRanges` (chart value `server.tickThread.gcHeapAffinitizeRanges`, read at process start) lists every CPU but the core; with it, server GC runs one heap fewer per CPU left out. Startup refuses a negative CPU, one above 1,023, a CPU the process may not run on, and one whose core is every CPU it has (`TickThreadCpuValidation`); on another system, or when a call fails, the world logs one warning and the tick runs unpinned. The siblings are read from `/sys/devices/system/cpu/cpuN/topology/thread_siblings_list`, and are always reserved (when they cannot be read, a warning says only the CPU itself is); the other threads are not confined to the tick's core complex. **The pod's CPU set must not be rewritten while it runs:** a change to it (the kubelet's `static` CPU manager policy moving a Burstable pod's shared pool as Guaranteed pods come and go) resets every thread's CPUs, and on a kernel before 6.2 that undoes the pin silently; keep the kubelet's default `none` policy on the node, or make the pod Guaranteed with whole CPUs. Nothing re-checks the placement after start. **Checking it on a node:** the start logs `The tick thread is pinned to CPU 8 (Game:TickThreadCpu) and runs on CPU 8; the world's other threads run on CPUs ...`, the second CPU read with `sched_getcpu` once pinned, and from a debug container attached to the pod ([tick profiling](tick-profiling.md#capturing-on-a-deployed-world)), `grep -H Cpus_allowed_list /proc/1/task/*/status` lists every thread's CPUs (the tick, `WorldServer.Tic` as Linux cuts its name to 15 characters, alone on its CPU; `cat /proc/1/task/<tid>/comm` names a thread) and `ps -L -o tid,psr,comm -p 1` where each runs now. The same checks ran in a Linux container (24 CPUs, server GC, CPU 2 with sibling 3): with `DOTNET_GCHeapAffinitizeRanges=0-1,4-23` no thread of 135 could run on 2 or 3 but the tick, which ran on 2 alone, including 90 pool workers, a thread and the background GC threads started after the pin, many of them at the tick's request; without it, only the two GC heap threads bound to 2 and 3.

**Logging on the tick (#819).** The world server runs at Information (`Serilog:MinimumLevel:Default` in its `appsettings.json`; see [Log Levels](configuration-reference.md#log-levels)). Routine combat events, a hit on a character, a death, and a cast refused for its cost, interrupted by movement or dropped because its caster left, are Debug lines through generated `LoggerMessage` methods (`CombatLog`, `Avalon.World/Combat`), which cost a few nanoseconds and allocate nothing while Debug is off. A line written on the tick costs hundreds of nanoseconds before any console I/O (`CombatLoggingBenchmarks`), so a new per-event line on the tick follows the same pattern; faults stay at Warning and Error.

- **MapInstance** (`Avalon.World/Instances/MapInstance.cs`) is the core simulation unit: manages entities in a flat tick context, runs `InstanceAbilityCastSystem`, creature AI scripts, broadcasts state to clients. Implements `ISimulationContext`. Holds a single `MapNavigator` (combined navmesh) and the `ChunkLayout` that produced it.
- **Each instance is ticked on its own (#639).** `World.Update` hands the live instances to `InstanceTicker` (`Avalon.World/Instances`), which contains every `instance.Update`: one that throws is logged at Error (at most once per instance per `InstanceTicker.FailureLogInterval`, 10 s, with how many throws were left out since) and the other instances, and the tick loop's flushes after the world update, still run; the instance stays live. Before, the throw left `World.Update`, so every instance after it went unticked and that tick's flushes and continuations were skipped. Each update is timed into `world.instance.update.duration` (µs) and each throw counted in `world.instance.update.failures`, tagged `map.type` only. The instances are still ticked one after another on the tick thread; #639 records what parallel ticking would need. They come from `InstanceRegistry.TickInstances` (tick thread only, #851), an array in publication order that the registry rebuilds only after it publishes or removes an instance, so a tick that changes neither allocates nothing for the walk; one published or removed during the walk joins or leaves it from the next tick. `ActiveInstances` (a fresh copy each call) is for the readers off the tick.
- **State broadcasts: every 100 ms, each instance in its own slot (#975).** An instance sends the state updates (its dirty snapshot: what changed on its creatures, characters and projectiles since its last broadcast) once per `BroadcastSchedule.Interval`, 100 ms, ten a second; the adds, the removes and the aura lists and changes still go out on every tick. Instances do not broadcast together: `BroadcastSchedule` (`Avalon.World/Instances`, one per world, owned by `InstanceTicker`, which moves it on by every tick's delta) has six slots a tick apart, and `InstanceRegistry` gives each instance it publishes the slot holding the fewest live instances (the lowest on a tie, so instances published together take consecutive slots), as the phase its broadcast clock starts from (the world's clock plus the slot's share of the interval, so an instance published at any moment lands on its slot's ticks), and frees the slot when it removes the instance or it expires, so the world's broadcast work is spread over the six ticks of an interval instead of landing on one. Each instance keeps its own clock (TimeSpan ticks, an integer) and decides at the top of its tick whether this one broadcasts; the dirty snapshot, the state updates and the tick profile's `broadcast` field all read that one decision. The clock runs on every tick, empty ones included, so an instance keeps its slot through an empty stretch, and it keeps the remainder past the interval rather than resetting to 0, so broadcasts come every 100 ms (six ticks at 60 Hz) rather than on the next tick after it. A tick longer than the interval (a stall) broadcasts once, never a burst of catch-up broadcasts after it, and leaves the clock in its slot. Before, every instance broadcast on the same tick, a timer that reset to 0 kept them in step (any tick of 100 ms or more put every instance in step), and dropping the overshoot made the interval six or seven ticks: 9.1 broadcasts a second in production. The clock runs before anything else in the tick, so nothing that throws can put an instance off its slot. An instance built outside the registry (tests) starts its clock at 0. Under overload the old dropped remainder also throttled the rate (30 ms ticks gave 8.3 broadcasts a second); the carried remainder holds ten a second per instance whatever the tick length. **Every add and update names its tick (#1066):** `WorldTick`, the world's count of completed ticks (`WorldTicks`, one per world: the send scheduler's, `NetworkSendScheduler.Ticks`, which the container hands every instance and `WorldServer` advances as each tick ends), read once per instance as its broadcast begins, so it is the number of the tick whose simulation the packet carries; the time-sync ping carries the same count beside its server time, as its anchor ([packet protocol](networking-packet-protocol.md)).
- **InstanceRegistry** (`Avalon.World/Instances/InstanceRegistry.cs`) owns all live instances. `GetOrCreateTownInstanceAsync` returns a shared persistent instance; `GetOrCreateNormalInstanceAsync` returns per-player instances with a re-entry window of `Game:AbandonedInstanceLifetimeMinutes` (15 by default; an instance nobody has entered yet keeps a fixed 15, see [instanced maps](instanced-maps.md#expiry-cleanup)). `ProcessExpiredInstances` cleans up expired normal instances. Both creators dispatch to `ChunkLayoutInstanceFactory.BuildAsync` for actual instance construction. **A build runs off the tick; it is published on the tick (#639).** The build (layout reads, navmesh bake, `MapInstance` construction, creature placement, script attach) touches only the instance it is building and immutable snapshots, and its last step only queues its outcome (a `ConcurrentQueue`). `World.Update` calls `World.PublishBuiltInstances` after the reference-data patches and the AI script hot reload are applied (so a just-published instance is brought up to date with the reload once, not rebuilt by its walk) and before the party tick and the instance ticks; it is contained, so a throw there costs the instances nothing. `InstanceRegistry.PublishFinished` registers each finished instance, writes its index entry (the character's, or the party's unless the party was forgotten meanwhile), drops the build's pending entry and only then completes the `TaskCompletionSource` its requesters hold; each build's step is contained on its own, so one that throws still answers its requesters (with the failure) and the builds behind it are still published. A requester that polls the task (a connection continuation: a select's, or a portal entry's arrival, which is queued to run whatever the build's outcome, `ISettledContinuations`) runs in that tick's flush; one that settles it through a continuation of its own first (`TownReturn`, `MapTeleport`, `ctx.Then`) waits for a thread-pool thread to run that continuation and runs in the first flush after it. Either way it is answered, never left waiting. One build per town map, per character and map, and per party and map is in flight at a time, kept in a plain dictionary of pending builds: a request arriving mid-build gets the same task (#442), and a build that failed is published as a failure, so its requesters get the exception and the next request starts afresh. **A build has a 30 s deadline (#969):** a timer on the container's `TimeProvider` queues it beside the finished builds, and `PublishFinished` abandons a build still running then (its pending entry dropped, every requester handed an `InstanceBuildTimeoutException`, so each ends its move through its failure path, clears `RespawnInFlight` and sends the player a system line; counted in `world.instance.build_timeouts`, one Error), and discards its outcome if it ever comes (an instance it built is disposed, never registered); nothing is cancelled and nothing is scanned per tick ([instanced maps](instanced-maps.md#build-deadline)). Every index and pending map is written on the tick alone (`_partyIndexGate` and its forgotten-party set are gone: a forget marks the party's pending builds instead); only the instance list stays a `ConcurrentDictionary`, because telemetry reads it from its own thread. Freeing an expired instance removes an index entry only while it still names that instance (a newer build of the map keeps its entry). An instance published after an AI script hot reload was applied gets the reloaded scripts as it is published (`World` keeps every hot-reloaded type by name and rebuilds each living creature whose script is not of that type).
- **ChunkLayoutInstanceFactory** (`Avalon.World/ChunkLayouts/IChunkLayoutInstanceFactory.cs`) — single entry point that builds both town and procedural instances. `IChunkLayoutSourceResolver` picks `PredefinedChunkLayoutSource` (DB-backed `MapChunkPlacement` rows for towns) or `ProceduralChunkLayoutSource` (RNG + `ProceduralMapConfig`) per `MapType`. `ChunkLayoutNavmeshBuilder` stitches chunk objs → DotRecast bake → `MapNavigator`. Server emits `SChunkLayoutPacket` to clients on instance enter; the client bakes the same navmesh from the same chunk objs (deterministic mirror) for prediction parity. See `docs/map-generation.md` for the full pipeline.
- **Creature placement has two paths, and both run from `BuildAsync`.** `CreaturePlacementService.PlaceAsync` rolls a `SpawnTable` against chunk spawn slots and is procedural-only, because it needs a `ProceduralMapConfig` and slots. `PlaceAuthoredAsync` reads `MapCreatureSpawn` rows — hand-placed creature, map, offset from the map's entry spawn point, facing — and runs for every layout kind; it is the only path that puts a creature in a town. Offsets, not world coordinates: a town's coordinates fall out of its `MapChunkPlacement` rows and the cell size. `OffsetY` only centres the navmesh search box, and `SampleGroundHeight` decides the real height (an authored column off the mesh keeps its authored height). **Procedural spawns stand on the ground too (#720):** a slot's height (and a pack member's spread position) only centres the same search, through `MapNavigator.FindGround` (World-side `IGroundNavigator`, the one query `SampleGroundHeight` also runs): with the mesh under it the creature keeps the slot's X/Z at the ground's height; just beside the mesh (a pack spread past its edge, within the 2 m search box) it goes to the mesh's nearest point; with no mesh within the box it is not placed, and a Warning names the slot, creature and position; a map with no navmesh keeps the slot as it is. Skipping rather than guessing, because a creature there has no ground to stand on and a home it cannot walk back to. Both paths wrap each creature in its own try/catch — placement runs inside `MapInstance` construction, so a throw would make the map unenterable for everyone. **On a map with depth bands** (`ProceduralMapConfig.DepthBands`, forest content pass) each procedural creature's level is rolled from its piece's band (`DepthBandLevels`, by `PlacedChunk.Depth`, the grid steps from the entry; every set piece, `PlacedChunk.Group`, from the highest band) and passed to `ICreatureSpawner.Spawn(CreatureInfo, ushort level)`; a depth no band covers rolls from the template's range, a `boss` slot stands at the highest band's top, and a `leader` slot spawns its `leader` entry then a roll of `leader_pack` entries around it (no slot carries `leader_pack`). A map without bands places exactly as before. Set pieces are `ChunkGroups` (`src/Server/Avalon.Server.World/Maps/chunk-groups.json`), placed atomically by `ProceduralLayoutGenerator` as one main-path step, on the main path only: a boss set piece only as its last step, every other one at most once per layout and not before the config's `MinSetPieceStep` (`Maps/ProceduralMaps/<mapId>.json` `minSetPieceStep`, 0 or left out for no limit; the forest's is 8, where its 5-8 band begins, and its main path is 12-16 steps so every run has room for one, owner decisions). A failed layout attempt is retried with the next seed up to 10 times (`MaxRetries`, raised from 3 when the committed forest failed some seeds at 3; `CommittedForestGenerationShould` generates it for 1000 seeds). The forest's `boss` and `leader` slots exist only in its set pieces, so `chunk-groups.json` is required: without it the spawn table's `boss`, `leader` and `leader_pack` entries match no slot and the seeder refuses the catalog, which stops the World start. The generated forest pieces are written by `tools/Avalon.ChunkGen` (see Commands), and `.gitattributes` pins every `.obj` and `.json` under `Maps/` to LF so a regeneration is byte-identical on any machine. See docs/map-generation.md.
- **Town NPCs are creatures.** Templates 1-3 (Uriel, Borin Stoutbeard, Innkeeper), 11 (Marta Ledgerwell, the banker, #463) and 12-14 (Garrick Emberforge, Hilde Brassbuckle and Tobin Marrowfield, the vendors, #432) are placed on map 1 by `MapCreatureSpawns`, carry `Invulnerable = true`, and run `TownNpcScript`. Since the town beautification (2026-10-01) the four squares are generated by `tools/Avalon.ChunkGen -- town` (`TownPieces.cs`: a town hall, a fountain, a gate arch, a watchtower, a hunter's lodge, a smithy, two stalls, a bank, an inn, two houses and a well, each shape an obj object with a `usemtl` line the server ignores and the client colours; `stone`, `wood`, `roof`, `cloth`, `cloth_2`, `plaster`, `metal`, `water`), and the town is laid out for the client's camera, fixed at yaw 45 and 60 degrees down, south-west of what it looks at (owner decision, 2026-10-02): every building's open face is on its -X or -Z side (`TownPiece.Front`, checked by `TownPiecesShould`), and each NPC stands in front of its own building, out from under its roof: Uriel before the town hall porch, Borin before the lodge porch, Garrick before the smithy's lean-to, Hilde and Tobin before their counters, the Innkeeper before the inn porch, Marta on the bank steps (migration `TurnTownNpcsToTheCamera`; `TownNpcPlacementShould` checks every spot against the generated squares: 2 m from any wall, 1 m from any solid, within 3 m of its building, off the doorway lanes, reachable on the baked navmesh, seen by the camera from every zoom with the player anywhere that keeps the NPC in frame, and every doorway and the gate arch walkable). The navmesh climbs any step of 0.8 m or less (`floor(0.9 / 0.2)` voxels, a top rounded up to a 0.2 m voxel), so a top at or under 1.0 m above the ground beside it would be walked over: every solid prop's top is at least 1.05 m up (benches, crates, barrels, counters, the well ring, the cart's shaft included; owner decision), and `TownPiecesShould` pins that every solid piece stops a walk at its edge and that no piece's top is reachable from the arrival point on the baked navmesh (roof tops and building interiors are unreachable islands, as the forest's blocker tops are). A geometry change here needs a restart and a re-export of the navmesh vectors (`schema/vectors/navmesh-v1.txt`, `tools/Avalon.Exporter -- navmesh`), which the client checks its bake against. Each has a dialogue root (`DialogueNodes`, seeded in `WorldDbContext`), so a player can talk to them (#431, closed): `CMSG_INTERACT` (accepted by `MapSessionFilter`) reaches `InteractHandler`, which checks the target is a live creature in the instance, has a dialogue root and is within 5 m, then sends `SMSG_DIALOGUE_NODE`; `CMSG_DIALOGUE_CHOOSE` advances through `DialogueChooseHandler` and `SMSG_DIALOGUE_END` closes it. A rejected interact is a silent drop — a monster's interact gets no reply. `DialogueChooseHandler` drops most rejected choices silently too, but closes the window with `SMSG_DIALOGUE_END` when the NPC is gone or dead, the open node does not belong to it, or an option leads to an unknown node; it also sends it as the ordinary close when the chosen option ends the conversation. **Every choose re-checks range against the dialogue leash (#492)**: `NpcInteraction.IsWithinLeash`, `LeashRange = 6f` (#678, was 15 m), inclusive, NaN counted as out of range. Past it the handler ends the conversation (clears `CurrentDialogue`, sends `SMSG_DIALOGUE_END`) and advances nothing. It is deliberately not the 5 m interact range, which still gates opening a conversation, because stepping back a metre mid-sentence must not close the window; it is only just past it, so walking off does. It is checked only on choose, never on the tick. **Any handler that acts on an open NPC conversation must pass the same check** (a vendor, quest, payment or item effect, #432): `CurrentDialogue` lives until the connection leaves the instance, so an unchecked effect would work from anywhere on the map. A client must not re-check range itself; the server decides whether a conversation is open. Dialogue text lives in `IDialogueCatalog` and `ILocalizedTextCatalog` on `StaticData`, read in memory on the tick. Interacting with a different NPC mid-conversation always ends the old conversation out loud first (`SMSG_DIALOGUE_END` for the old NPC, then the new node); interacting with the same NPC again restarts at its root, and ends the old conversation out loud only when it had the bank or a shop open. A dialogue option can also carry an action (`DialogueOption.Action`, #463), indexed by `DialogueActions` on `StaticData` (rebuilt by `/reload dialogue`) and deliberately not on the World.Public `DialogueOptionView`, so the modding API cannot read or invent one: `DialogueChooseHandler` runs it after the leash check and only on an option that keeps the conversation open, so an `OpenBank` on an option that ends the conversation (or leads to an unknown node) opens nothing. The actions are `OpenBank` and `OpenShop` (#432, stored as 0 and 1, append-only). Each option on the wire carries `Kind` (`SDialogueOptionInfo` field 3): the action choosing it will actually run, or `Conversation` when it runs none, so a client can hide what it has not built; `DialogueOptionKinds` holds the rule for both handlers (#522). A creature whose dialogue offers `OpenBank` anywhere is a banker (`NpcInteraction.IsBanker`), and one that offers `OpenShop` anywhere is a vendor (`NpcInteraction.IsVendor`). `NpcInteraction.EndConversation` is the one way a conversation ends out loud; despawn clears it silently, because the client is gone. It calls `CharacterEntity.CloseNpcWindows()`, which closes the bank and the shop together. Quest options are added to the root per character (see Quests).
- **`ObjectState.CanInteract` (field 20) tells a client whom it can talk to (#489).** It means "interacting with this will do something", so a client can offer an interact prompt without guessing. It is "the template has a dialogue root". A banker and a vendor are both reached through their dialogue, so neither changed it. The rule is one function, `NpcInteraction` (`Avalon.World/Dialogue/`): `InteractHandler` uses it to find the root it opens, and `CreatureSpawner.Spawn` uses it, over `world.Data.Dialogue` read once per call, to fix `Creature.CanInteract` at spawn — so the prompt the client shows and the interact the server accepts cannot drift apart. The value lives on the World-side `Creature`, init-only and deliberately not on `ICreature`, so no mod can make a creature advertise an interaction. `ObjectStateWriter.From(ICreature)` sends it on every creature state whatever is marked changed, like `CreatureMetadataId` and `Name`, and only as `true`: a monster leaves it out, and characters, portals and spells never carry it, so absent means false. It is fixed at spawn, so `/reload dialogue` reaches only creatures spawned afterwards; one already standing keeps the flag it spawned with, while `InteractHandler` still answers from the current catalog. Creatures never respawn and the town instance persists, so after a `/reload dialogue` a town NPC's flag stays stale until the server restarts. Any `ICreature` that is not the World-side `Creature` never advertises the flag: that fails safe, and the handler stays authoritative.
- **`ObjectState.IsDead` (field 12) is true on a dead creature too (#672).** A creature is dead at 0 health, the rule the hit query, `ApplyHeal`, the kill (`CreatureKilled`, from above 0 to 0) and the death broadcast already use, so `ObjectStateWriter` derives it from `CurrentHealth == 0` rather than keeping a flag of its own (a character keeps `CharacterEntity.IsDead`, since it is revived). Nothing is added to `ICreature`, and any `ICreature` reports only what its health says. A creature's add (`GameEntityFields.All`) always carries it; its routine update (`CreatureUpdate`) does not, so a living creature's updates pay nothing for it. `Creature.CurrentHealth` marks `GameEntityFields.IsDead` changed when health reaches 0 (or leaves it), and `MapInstance.DescribeUpdatedObject` adds that mark to the creature's selection, so the broadcast that carries the corpse's 0 health carries `IsDead = true` with it; a client that first sees the corpse later gets it on the add (`CreatureDeathReplicationShould`).
- **`ObjectState.Rarity` (field 22) tells a client how dangerous a creature is (#709)**, for a nameplate coloured by rarity. It is a wire enum, `Avalon.Network.Packets.State.CreatureRarity` (Normal 0, Elite 1, Rare 2, Boss 3, append-only), a copy of the domain's `Avalon.World.Public.Enums.CreatureRarity` declared beside `PowerType` because the packets do not reference the world's domain and the exported schema reaches only packet types; `ObjectStateWriter.ToWire` maps one onto the other value by value, and `ObjectStateWriterShould` pins the two together (a file that imports both namespaces aliases the one it means). `CreatureSpawner.Spawn` fixes it on the World-side `Creature` from the template's `Rarity` (`Creature.Rarity`, init-only, deliberately not on `ICreature`, so no mod can change what a creature advertises), and `ObjectStateWriter.From(ICreature)` sends it on every creature state whatever is marked changed, like `CanInteract`, and only when it is not Normal: absent on a creature state means Normal, so most creatures pay nothing. Characters, portals and projectiles never carry it, and any `ICreature` that is not the World-side `Creature` is sent as Normal. It is fixed at spawn, so `/reload creatures` reaches only creatures spawned afterwards; one already standing keeps the rarity it spawned with (the stats that rarity scaled were fixed then too).
- **`ObjectState.DisplayId` (field 25) tells a client which model to draw a creature with (#1022)**, so creature types that look alike share a model and a new creature type needs no client release to get one. It is the template's `DisplayId` (uint), which names a client model, not a template: the models are numbered from 1 in the game client's model list (`game/src/CreatureModels.h` in the client repository), every template that looks alike carries the same id, and 0 is none, so the client draws its default model. The seven town NPCs are seeded 1-7, one model each (Uriel 1, Borin Stoutbeard 2, the Innkeeper 3, Marta Ledgerwell 4, Garrick Emberforge 5, Hilde Brassbuckle 6, Tobin Marrowfield 7); the dungeon creatures 8-14 (#1038: Thornback Boar 8, Old Tuskroot 9, Grey Fen Wolf 10, Bramblemaw Alpha 11, Blightfly Swarmling 12, Husk of the Wold 13, Mother Bramble 14). It is sent on the same terms as `Rarity`: `CreatureSpawner.Spawn` fixes it on the World-side `Creature` (`Creature.DisplayId`, init-only, deliberately not on `ICreature` or `ICreatureMetadata`, so no mod can change what a client draws), and `ObjectStateWriter.From(ICreature)` sends it on every creature state whatever is marked changed, and only when it is not 0: absent on a creature state means none, and the client draws its default, so a creature without one pays nothing. Characters, portals and projectiles never carry it, and any `ICreature` that is not the World-side `Creature` is sent without one. It is fixed at spawn, so `/reload creatures` (or a live template edit) reaches only creatures spawned afterwards; a town NPC, never respawned, keeps the model it spawned with until the server restarts.
- **Every script resolvable by name must construct from `(creature, instance)` alone.** `AttachScript` builds it with `ActivatorUtilities.CreateInstance(sp, type, creature, instance)` — exactly two runtime arguments, anything else resolved from DI; a constructor wanting a plain `float` or array throws, and the throw is swallowed so the creature silently has no script. `ILoggerFactory` is fine (`AggroDefendScript` takes one). `AiScriptConstructibilityShould` builds every nameable script that way through the real World container. A component another script builds and chains with extra arguments (`CreatureRangeDetectorScript`, chained by `AggroDefendScript`) is marked `[ChainedScript]` (`Avalon.World.Public/Scripts`), and `ScriptManager` does not register it by name. `CreatureIdleScript` is gone (#437); use `TownNpcScript` for a passive creature.
- **Patrol paths are data, authored spawns only.** A `CreaturePath` (table `CreaturePaths`) holds ordered `CreaturePathPoint`s (`CreaturePathPoints`, keyed `(PathId, Sequence)`), each an offset from the map's entry spawn point plus a `WaitMs`; `MapCreatureSpawn.PathId` (nullable, shareable between spawns) names one. `PlaceAuthoredAsync` sets each point's height from the navmesh like the spawn itself (`SampleGroundHeight`; X and Z stay as authored) and sets `ICreature.PatrolPath` before attaching the script. `CreaturePatrolScript` walks it in a loop, standing at each point for its wait. **A patrolling creature fights, then resumes (#600):** the patrol chains a `CreatureCombatScript`, as `AggroDefendScript` does, and forwards `OnHit`, `Update` and `OnCharacterLeft` to it; a hit starts the fight under the normal combat rules (health, one kill with loot and experience, the leash). While the combat script's `State` is anything but `None` it drives the creature (the patrol stops its leg at the handover and then issues no `MoveTo`, `Stop` or `MoveState`) and the patrol's point and wait do not advance; once it is back to `None` (home after the leash, a lost, dead or unreachable target, or its target leaving), the patrol resumes at the path point nearest the creature and walks on in the path's order, dropping any interrupted wait. A hit that leaves it at 0 health stops the patrol for good. An invulnerable walker never fights: `CombatService` refuses the hit before any script hears of it. The path does not choose the AI: the template's `ScriptName` still does, and only a script reading `PatrolPath` walks it. No path is seeded, and procedural spawns never get one.
- **ISimulationContext** — the minimal contract AI scripts and the ability system use to reach their instance (`MapInstance` implements it). Exposes `Locomotion`, `MeleeSlots` and the read-only `CreatureClock` (#979: the sum of the deltas of every tick on which the instance updated its creatures; it stands still while the instance is empty) to scripts.
- **Every AI script says when it next needs an update (#979).** `AiScript.NextUpdateIn` is abstract, so every script answers it; the instance reads it after each `Update` of a creature's own script (a chained script's answer is its owner's to use, and the built-in chained ones answer `TimeSpan.Zero`): `TimeSpan.Zero` (or less) is the next tick, which a script that needs every tick answers always, as every script was called before #979; a positive time is a wait on the creature clock (called on the first tick at which that much has passed; a time too long for the clock counts as an endless wait); `Timeout.InfiniteTimeSpan` is a wait for an event alone. There is no other flag (the owner's decision, 2026-10-14: no default, every script decides). **Wake rules:** a waiting creature is woken, and runs on the instance's next creature step (on the same step when the step has not reached it yet, as the every-tick loop would have run it), by a hit (`Creature.OnHit`), an attack that dealt nothing (a dodge, a harmful aura landing or ticking: `CombatService` through `Creature.OnAttacked`), a character leaving the instance, its due time, a new script or patrol path, and joining an instance; it is woken before its script hears the event. A character coming into range is found by the script's own search when it is due; writing a script's `State` from outside wakes nothing. `deltaTime` is always the tick's own: a waiting script is not handed the ticks it waited through, and times across them on `CreatureClock`. The answer grants nothing (`Avalon.World.Public` rule): it only spares calls a script says it does not need. **The world side** is `CreatureScheduler` (`Avalon.World/Creatures`, one per instance, tick thread only): the creatures that run on a step run in the instance's creature-dictionary order, the order the every-tick loop walked, so slot claims, hits and kills fall out alike; each creature has a state (`CreatureWait`: active, waiting for its search, for a time, for an event); every activation (joining, a new script, a wake, a due search or time) goes through `MakeActive` and every wait begins in `Park` (or `ParkForSearch`), the places where a rule that holds or wakes a creature (crowd control, #770) belongs, while a script set to none or a creature leaving drops its state, and reading the roster again only sets each place's bit from its state. Timed waits are a min-heap on their due times. A built-in creature waiting only for its once-a-second range search (`IAwaitsSearch`, World-side) is kept in a cohort with the creatures whose detector timers hold the same float value; each step adds the tick to each cohort's timer exactly as each detector did, and on the step it would reach `CreatureRangeDetectorScript.SearchInterval` the cohort's creatures get their timers back and search on that tick, so detection keeps its cadence to the bit; a due cohort is let go in one pass. **The search filter (#982):** each member of a due cohort is marked, and at its turn, when its Update would be its search alone (`IAwaitsSearch.SearchAlone`: it still awaits its search and the tick brings its timer to the interval) and the instance's spatial grid says no character can be within its range, the search is skipped: its detector's timer goes to zero, as a search that found no one leaves it, and it waits again through `ParkForSearch`, as after that Update, told the answer (waiting, timer at zero) rather than asking the script again, since `SearchAlone` has just answered the same question (`CreatureCombatScript.State` is sealed, so the idle flag its setter keeps is always current); everything else, which character a search finds included, is the search's own. The question is asked at the creature's turn, not when the cohort comes due: a script earlier in the step can move a character (any script holding an `ICharacter` can write its position), kill one, or hit this creature, which then runs its combat and searches with the timer it had, and asked up front the answer would be stale. `MapInstance.SearchEveryDueCreature` runs every due search, for `CreatureSchedulingShould`, which drives two instances side by side through the same seeded changes (characters at a range to the float, positions not finite, characters not indexed, deaths, leaves, a script that moves characters and hits creatures mid-step) and compares every creature and every client's packets after every tick. In `forest-combat` it leaves 124 searches of 46,063 over the measured minute, the bounds deciding 45,815 of the skips and the cells 124 ([benchmarks](benchmarks.md)). **The built-ins** answer for their own type only, so a subclass that does not answer `NextUpdateIn` itself gets every tick (as #916's shortcut did): `AggroDefendScript` (plain, and the seven sealed forest scripts) waits for its search while its combat script is `None` and its detector `Searching`; `CreatureCombatScript` named as a creature's own script waits for an event while idle with no cooldown running; `CreaturePatrolScript` waits for the end of a pause (timed on `CreatureClock`), and for an event with no path or as a corpse; `TownNpcScript` waits for an event always; `CreatureRangeDetectorScript`, never a creature's own script, answers the next tick. Reading the answer of a script that needs every tick is read first, the next tick returning at once: the scheduler costs such a creature 4–5 ns a tick over the loop it replaced (`EveryTickScriptBenchmarks`, see [benchmarks](benchmarks.md)); a built-in search waiter is asked through its search wait instead. `CreatureSchedulingShould` runs forests and a town side by side with `MapInstance.UpdateEveryCreatureEveryTick` (the old loop, for that test) and compares every creature after every tick, holds the wake rules for a script of any author, and holds that a subclass of each built-in gets every tick.
- **Unit broadcasts go through the unit's own instance (#546); there are no static events.** Swings and cast finishes and interrupts are `ISimulationContext.BroadcastAttackAnimation`/`BroadcastFinishCast`/`BroadcastInterruptedCast` (the cast system calls them through its `IAbilityArena`), each sent only for a unit in that instance. A hit's outcome is reported by the instance's own `CombatService` right after the target's `OnHit` returns, through the World-side `ICombatOutcomes` that `MapInstance` implements: a living character's own `SCharacterDamagePacket` then the instance-wide hit (`CharacterDamaged`), and a creature brought from above 0 to 0 health killed once (`CreatureKilled`: corpse, loot, experience), before the encounter death and the death broadcast. `ICreature` has no `Died`, since the modding API must not grant a kill. A character leaving an instance is `AiScript.OnCharacterLeft`, called by `RemoveCharacter` on that instance's own creature scripts only and forwarded to chained scripts.
- **ICreatureLocomotion** (`Avalon.World.Public/Creatures/`) — the only thing that writes a creature's position. Scripts call `MoveTo` / `Stop` / `Teleport` / `HasArrived` and never touch `Position` themselves. `MapInstance` owns one, registers each creature in `AddCreature`, unregisters in `RemoveCreature`, and ticks it **after** the AI scripts — the scripts choose destinations, the locomotion consumes them, so the order matters and is pinned by a test. Two implementations in `Avalon.World/Creatures/Locomotion/`, selected by `GameConfiguration.CreatureLocomotion`: `WaypointLocomotion` (default; walks a navmesh path with no awareness of other agents) and `CrowdLocomotion` (DotRecast `DtCrowd`; agents steer around one another, and around players when `CrowdIncludesPlayers` is set). `Crowd` falls back to `Waypoint` with a warning on a map with no baked navmesh.
- **MeleeSlots** (`Avalon.World/Creatures/MeleeSlots.cs`) — hands each attacker a distinct standing position on a ring around its target so chasers surround rather than stack. Claims are keyed by target, world-fixed in angle (not facing-relative, which would churn every time the player turns), and handed out nearest the claimant's bearing. Attackers beyond `MeleeSlotCount` get no slot and stand off at attack range along their own bearing.
- **`CreatureCombatScript` gives up** and runs home at full health (slot released, target dropped) when a character target dies, the target leaves the instance, the creature is more than 40 m from where the fight began (its home, which may be any position, the origin included), or it has had no way to reach the target for more than 5 s in a row (#606: out of attack range while `ICreatureLocomotion.ResolvedDestination`, where its route really ends, is null or ends farther than attack range plus arrival tolerance from the target (a settled creature out of range re-plans every tick, so the route judged is fresh); never `HasArrived`, which flips while a creature stands at the end of a partial route; the count restarts on a tick that can reach and on a change of target). On the way home it ignores hits entirely (owner decision, #606; how, below under #610). **It always ends the walk home (#715).** Home (where the fight began, often the spawn) need not lie on the navmesh: a procedural spawn keeps its slot's height, a spawn by a wall sits in the mesh's eroded border, and a route's points carry the mesh's own height, so a route home ends at the nearest point the mesh has and a crowd stops within its arrival tolerance of that. It is home once the locomotion has nothing left to walk and it stands within `ArrivalTolerance` (+ 0.05) of home on X/Z (or within 0.1 m in 3D); before #715 only the exact 0.1 m test counted, so such a creature re-planned the same route for ever, standing still and unhittable (reproduced under both locomotions, `CreatureReturnHomeShould`). A route home that ends short (its end farther than the tolerance from home, and the creature standing at it), no route at all, and the safety net all `Teleport` it home and reset it (`SnapHome`), logged once at Warning with the creature and why: the net fires when it has come no 0.5 m closer to home on X/Z for 5 s (`s_returnStallLimit`) or has been returning for 15 s (`s_returnHomeLimit`), timed by the tick's delta. Home rather than where it stands, so repeated kites never drag a creature away from its spawn. The reset is `ResetToIdleAtSpawn` either way (#614: taunt cleared, dropped from its encounter).
- **Creatures fight with abilities (#163).** A creature attacks only with abilities: the raw swing (`RollDamage` and a bare `ApplyDamage`) is gone. **Holding:** `CreatureAbilities` (`Avalon.World/Creatures`), owned by the World-side `Creature` (`Creature.Abilities`, never on `ICreature` or World.Public, #622), holds the creature's own clones of the ability rows its script declares, their cooldowns and its cast state (`IsCasting`). A creature type's script declares a `CreatureAbilityKit` (a basic and its specials, as ids) and passes it to `CreatureCombatScript`'s protected constructor, which loads it from the current `AbilityCatalog` (`StaticData.LoadedAbilities`, null before the first load) when the script is built; an id the catalog lacks is logged at Error and left out, and the creature fights with the rest. So `/reload abilities` reaches creatures spawned (or hot reloaded) afterwards; the rotation is code. The combat script ticks the cooldowns, first thing in each `Update`, and `ResetToIdleAtSpawn` clears them. The scripts data can name as they are (`CreatureCombatScript`, `AggroDefendScript`, `CreaturePatrolScript`) carry no kit: a creature on one chases but never attacks. So no data-named script combines a patrol path with abilities yet: a creature type that should patrol and fight needs its own `CreaturePatrolScript` subclass. `AggroDefendScript` and `CreaturePatrolScript` take a creature type's own combat script through a protected constructor. **The seven forest scripts** (`Avalon.World/Scripts/Creatures/Forest`: `ThornbackBoarScript`, `GreyFenWolfScript`, `BlightflySwarmlingScript`, `HuskOfTheWoldScript`, `BramblemawAlphaScript`, `OldTuskrootScript`, `MotherBrambleScript`, templates 4-10) each subclass `AggroDefendScript` with a nested `[ChainedScript]` combat script (named `<Creature>Combat`, never registered by name) and take an optional `IWorld` from DI; each prefers a ready special whose reach fits, then its basic, and the Blightfly spits only while Sting cannot reach. **Casting:** the cast path takes any `IUnit` (`ISimulationContext.QueueAbility(IUnit, ...)`); a creature's casts are free (`AbilityCost` is skipped for an `ICreature`); its haste is `min(HastePct, HasteCap)`, scaling cast times and cooldowns; its basic's cooldown is its `SwingInterval` (which already carries the haste, so it is not divided twice), every other one its row's `Cooldown` divided by the haste. A creature that dies or turns for home (`IReturningHome`) during a wind-up has the cast dropped on the cast system's next tick, with the interrupt broadcast, however much was left, and nothing fires; a projectile it loosed that is still in flight is dropped then too, so no corpse or creature walking home deals damage or rejoins an encounter; `MapInstance.RemoveCreature` cancels both as well (a corpse removed or a script hot reloaded). A creature is never interrupted by being moved (a crowd's separation pushing it), only a character is. **The AI hook:** `CreatureCombatScript.ChooseAbility(target, distance)` (protected virtual) answers which ability to start, every tick it fights and is not casting, in reach or not; the base answers the basic when it is ready and reaches; `Ready(id, distance)` and `InReach(ability, distance)` are the helpers. `distance` is to the edge of the target's body (its centre distance less `BodyRadius`), the real reach, with no allowance. Instead the creature's slot or stand-off point is pulled in toward the target so its basic reaches from anywhere within the locomotion's arrival tolerance of it (`WithinBasicReach`); with waypoint locomotion and the default slot nothing moves, while a crowd's 0.6 m tolerance brings the Blightfly's slot in to 1.3 m. What it answers is started only when the creature holds it, it is ready, and it reaches: an instant ability through `RunInstantAbility`, aimed along the facing toward the target (Movement) or at the target's position (Cursor), captured now. **Wind-ups:** a `CastTime` ability is queued with that aim; the creature `Stop`s, the cast system sends the start (with its footprint, #648), and it asks for no movement until the cast ends (fired, or dropped because it died or turned for home), so its own steps never interrupt it and a player can step out of it. The shape scripts' own broadcasts replace the old plain attack animation, and every creature hit carries its ability id. A creature's hit on a player adds no threat, as before.
- **InstanceAbilityCastSystem** (`Avalon.World/Abilities/`, one per `MapInstance`) runs casts: `QueueAbility` for a cast-time cast, `RunInstant` for an instant one, and ticks the unfinished ability scripts (projectiles). The one power rule is `AbilityCost` (#521): the handler checks it and the cast system checks it again and pays it on both paths, only once the cast is accepted (for a queued cast, once its script is built and the queue has taken it), so a refused cast spends nothing. A character leaving an instance (`MapInstance.RemoveCharacter`) has its queued casts interrupted (`CancelCasts`) and its still-running scripts dropped (`CancelScriptsOf`, #541), so a projectile in flight never lands for a caster who is gone: no damage, threat, credit or loot; it leaves the next tick's world objects, so every watcher gets one remove. A script whose `Prepare` or `Update` throws is contained (#530): logged at Error with the ability and caster, dropped (a projectile gets its remove the same way), and its caster sent the interrupt (`SCharacterInterruptedCastPacket`, broadcast to the instance); the other scripts in that tick still run, and what the cast spent stays spent.
- **`AiScript` hot reload** — `IScriptHotReloader` (`Avalon.World.Scripts.Abstractions`) reloads only `AiScript` types from compiled script assemblies; `World.Update` polls it every `Game:ScriptHotReloadIntervalSeconds` (default 5) and applies the reload on the tick thread. It reaches every registered instance, and an instance whose build was in flight during the reload gets the reloaded types when it is published (#639). `AbilityScript` and `QuestScript` types are not hot-reloaded: `ScriptManager` finds them once, at `Load()`.
- **Script generations: how a hot reload loads and unloads (#930).** `ScriptCompiler` compiles every file under `Scripts/HotReload` into one assembly and loads it into a collectible `ScriptAssemblyLoadContext` of its own, never the default context: each compile is a generation, the context kept beside its types (`CompiledScripts`). `ScriptHotReloader` owns the generations. A compile that brings `AiScript` types replaces the generation before: its types go to `ScriptManager.RegisterHotReloaded` (at once, on the compiler's thread) and to `World` (at the next poll, on the tick), and the replaced generation's context is `Unload()`ed. A compile that brings none replaces nothing, and its own context is unloaded at once; so deleting every hot-reload script leaves the last generation in place, as before. Unloading frees nothing yet: the runtime collects a context once nothing references its types, so scripts that are running finish on the old code. What lets go of a replaced generation: `ScriptManager` builds its AI map from the built-in scripts and the newest generation alone (a name only an older generation had is no longer registered); `World._hotReloaded`, which brings instances built during a reload up to date, holds the latest generation applied and nothing older; the tick gives every living creature of every registered instance, and of each instance published later, a script of the new generation; a corpse keeps none (#607); `AbilityScriptActivator`'s factories hold their types weakly, and `ActivatorUtilities` keeps no strong reference to a collectible type. What still keeps one alive: a creature whose script name the new generation no longer has keeps its old script until it dies or leaves; and anything a script hands to something longer-lived (a static, an event on a long-lived object, a timer). A hot-reloaded script takes `ILoggerFactory`, never `ILogger<TScript>` or any other service closed over its own type: the container keeps what it resolved (a singleton such as `ILogger<T>`, and how to build it) for the life of the process, and with it the type. `ScriptHotReloader` checks each AI script type of a compile that brings some, on the compiler's thread before the generation is handed out: a public constructor parameter that is a generic type closed, at any depth, over a type of the same compile, the script's own or another (`ILogger<MyScript>`, `ILogger<HelperInTheSameFile>`, `IOptions<Settings<MyScript>>`), logs one Warning per script type per reload, naming the script, the parameter type and the compiled type it closes over; the script still loads and runs. `ScriptManager.Load` scans only the assemblies the process was built with: not a collectible one (a generation, which reaches it through `RegisterHotReloaded` alone) and not a dynamic one; it lays the current generation over them, so the newest copy of a name always wins and a type something else compiled or emitted at runtime is never named. Only `AiScript` types are swapped at a reload: ability, aura, quest and item scripts come from the built-in assemblies alone. The swap is contained: each creature's new script is built before the creature leaves its instance to take it, so a constructor that throws leaves that creature in place with the script it had (logged once per script per reload) and the rest of the reload, and the tick, carry on; two types of one name in a compile (two namespaces, or names that differ in case only, the world's lookup ignoring case) are no fault either, the last one winning, as in `ScriptManager`. The gauge `avalon.world.scripts.load_contexts` ([instrumentation](instrumentation.md#script-load-contexts)) shows the generations still in memory; `ScriptGenerationsShould` holds a replaced one to being collected.
- **Skills aim; they do not target (#164).** A cast carries an `AbilityAim` captured at cast start: a direction (a Movement skill: toward the cursor when the cast sends a `GroundPos`, else the caster's facing, #716) or the cursor's ground point (a Cursor skill; `CCastAbilityPacket.GroundPos`, refused as `NoAimPoint` when missing or non-finite). `TargetGuid` is ignored. The ability's `Shape` decides who is affected, through one generic script per shape: `CircleAbilityScript` (on the caster, or on the aim point clamped to `Reach` and pulled back from walls by `RaycastWalkable`), `ConeAbilityScript` (never clipped by walls), and `ProjectileAbilityScript`: a world object (`ObjectType.SpellProjectile`, replicated through the world-state add, update and remove packets like any entity, drawn `HeightOffset` 0.5 m above the ground it flies along) spawned at the caster and flying flat toward the aim point at `ProjectileSpeed` metres per second. Each tick it sweeps its whole step, capped at the `Reach` left and cut by `RaycastWalkable`, so a long tick tunnels through nothing; it ends at `Reach`, at a wall (a caster off the navmesh ends it on the first tick), or on its first qualifying hit, where it stops at the point of its step nearest the unit's centre, while with `Pierce` it hits each unit once and flies on. A finished projectile is never ticked again and stays a world object until its final state (where it stopped, zero velocity) has been taken for a broadcast; `InstanceAbilityCastSystem` removes it on a later update, so a client sees every projectile's add, final update and remove, even one that ended on the tick it was first seen. An instance nobody is in drops its finished projectiles at once (`IAbilityCastSystem.DropFinished`, on `MapInstance.Update`'s empty-instance return), since nobody is there to send them to, so the next player to enter never sees one frozen where it stopped. The shapes ask `IAbilityArena.Hits` (`IHitQuery`, World-side, implemented by `MapInstance` over its characters and creatures, found in its spatial grid's cells around the shape, #982, below) for living units whose body circle (`IUnit.BodyRadius`: `CreatureTemplate.BodyRadius`, characters a fixed 0.5 m) overlaps the shape on X/Z, nearest-first, and each unit is affected at most once per cast (`AbilityEffect`). `Hostility` decides: a creature is hostile to a player unless `Invulnerable`; two players only when both are PvP-flagged, the map is not a town and they are not in the same party (`CharacterEntity.PartyId`, see Parties); a creature caster (#163) finds every living player hostile on every map type, and no creature; `Affects = Ally` heals the caster and every player not hostile to it through `ApplyHeal`, which restores health. Heal threat counts the health actually restored, so overheal adds none, and a heal that restores nothing does not add the healer to the encounter (#531). A skill that affects nobody still spends its cost and cooldown. Circles and cones broadcast `SMSG_ABILITY_FIRED` (`SAbilityFiredPacket`: caster, ability, origin, and a circle's centre or a cone's direction, plus the cast id and the whole footprint, #648); hits arrive as the usual damage packets, and `SCharacterDamagePacket.AbilityId` is filled. A shape script resolves from `AbilityScript.Origin`, the caster's position when the cast started (`AbilityAim.Origin`, stamped by the cast system when it takes the cast, #648), never from where the caster stands when it fires, and does it in `Prepare`, never in its constructor. `AbilityCatalog` (the Abilities reload area) refuses an invalid shape row, or one whose `ThreatMultiplier` or `HealThreatPerHp` is not finite and 0 or more (#529, also a database check), with an error naming it.
- **PvP is a flag on the character row (#164).** `Characters.PvpEnabled` and `PvpOffAt` (UTC; null means no timer) are read World-side through `CharacterEntity` and written only by `PvpToggle` (`Avalon.World/Pvp`), never through the modding API. `CMSG_PVP_TOGGLE` (`MapSessionFilter` entry, `PvpToggleHandler`) and `/pvp` (`PvpCommand`, Player access) both call `PvpToggle.Toggle`: off turns on at once; on with no timer starts `Game:PvpOffDelay` (default 5 min), during which the player stays hostile; on with a timer cancels it. Each is answered with `SMSG_PVP_STATE { Enabled, OffInMs }`, which is also sent when the timer turns the flag off (checked each tick in `MapInstance` against the container's `TimeProvider`) and when a character enters an instance. Every player-on-player hit that deals damage to a living player (`CombatService.ApplyDamage` between two `CharacterEntity`) restarts both players' running timers, and the countdown is re-sent when a hit moves the deadline by more than a second (`PvpToggle.CountdownOwed` against `CharacterEntity.PvpOffAtTold`, World-side and never saved), so the client's countdown is exact; the reset does not re-check the town rule itself, relying on `AbilityEffect` checking `Hostility` first. A timer that ran out while the player was offline is expired on entry, before the state is sent. A dead character may toggle. Towns never allow player hostility whatever the flags, and neither does a shared party. The flag is replicated as `ObjectState.PvpEnabled` on every character state, only as true, and saved with the row by every save (`SaveStateTracker.PvpChanged` marks it).
- **The seeded creature abilities** (migration `SeedCreatureAbilities`, #163): ids 300-316, creature-only (`AllowedClasses` empty), cost 0, `EffectValue` 0, damage from the creature's natural range through `BaseDamageCoefficient` (1.0 for each basic, so a basic deals what the old swing did). Gore 300/Trample 301 (boar), Bite 302/Ravenous Claw 303 (wolf), Sting 304/Blight Spit 305 (Blightfly), Slam 306/Rotting Burst 307 (Husk), Maul 308/Rending Frenzy 309/Howling Roar 310 (Alpha), Tusk Gore 311/Earthsplitter 312/Thorn Volley 313 (Tuskroot), Bramble Lash 314/Bramble Nova 315/Thornspray 316 (Mother Bramble). Basics are 90-degree cones listing the 2250 ms swing interval; the wind-ups are 310 (1 s), 312 and 315 (1.2 s); projectiles aim at the cursor (Blight Spit 14 m/s, Thorn Volley 16 m/s and piercing). `SeedIntegrityShould` pins every row and each template's script. `tools/Avalon.Exporter -- ability-catalog` writes `schema/abilities/ability-catalog-v1.json` (id, name, shape, aim, anchor, affects, radius, reach, arc, projectile speed, pierce, cast time, cooldown), for the client to name and draw creature abilities and wind-ups; like `item-catalog` it needs a World database.
- **The seeded starter kit** (migrations `SeedStarterSkillKit`, World, and `GrantStarterSkillKit`, Character): three skills per class, ids 200-202 Warrior, 210-212 Wizard, 220-222 Hunter, 230-232 Healer, each with `AllowedClasses` its class and one of the three shape scripts; `CharacterCreateInfos.StartingSpells` grants them, and the Character migration replaced every existing character's abilities with its class's three. The retired abilities 1, 2 and 100-103, and the two scripts they ran, are gone, and their ids are never reused. 232 Mending Circle is the only ally heal. Every kit cost is payable from its class's pool (`ClassPowerType`: Warrior Fury, Wizard and Healer Mana, Hunter Energy); a Warrior enters with no Fury and builds it with Cleave, which costs nothing (#526). `SeedIntegrityShould` pins it.
- **Every refused `CMSG_CAST_ABILITY` is answered (#512).** `CastAbilityHandler` sends exactly one `SAbilityNotReadyPacket` per refusal, carrying a `CastRejectReason` (`Gcd`, `Cooldown`, `RequiresOutOfCombat`, `RequiresInCombat`, `NotEnoughPower`, `Dead`, `NotOwned`, `InternalError`, `NoAimPoint`, `AlreadyCasting`, `WrongPowerType` (#652); `Unknown = 0` is only what a payload without the field decodes as). `OutOfRange`, `TargetNotFound` and `NotFacing` stay in the enum (append-only) but are no longer sent. `CooldownMs` is the time left for `Gcd` and `Cooldown`, rounded up so it is at least 1, and 0 for every other reason. The one silent path is a connection with no character. A cast the cast system refuses (`QueueAbility` or `RunInstantAbility` returning false: a missing script, or one that cannot be built) is `InternalError` and starts no global cooldown. `CombatConfig` is registered with its defaults and not bound from configuration.
- **Casts aim, they do not target (#164).** `CastAbilityHandler` ignores `CCastAbilityPacket.TargetGuid` and does no range or facing check; there is no facing cone any more, and `AbilityInfo.FacingAngle` is never set. At cast start it captures an `AbilityAim`: the caster's facing from its yaw (`AbilityAim.FacingFromYaw`, a non-finite yaw aims along +Z) and, for a `Cursor` skill, the ground point (`GroundPos`, missing or with a non-finite component is `NoAimPoint`). **A `Movement` skill aims toward the cursor (#716):** when the cast carries a finite `GroundPos`, the handler replaces the facing with the X/Z direction from the caster's position (the position the cast system stamps as `AbilityAim.Origin` in the same call) to it (`AbilityAim.Toward`), so a player walking backwards does not swing behind; missing, non-finite or within a millimetre of the caster keeps the yaw, and a Movement skill is never refused for its point. `Point` stays null for it, so the footprint stays anchored on the caster and its reach measured from there. Resolved once, into `AbilityAim.Facing`, so the footprint, the start and fired broadcasts and the shape script agree by construction (#648). Creatures send no point: their Movement casts still aim along their facing toward the target. The enum keeps the name `Movement` (stored data and in the exported catalog). A cast-time cast fires with the aim it started with. A cast while `Spells.IsCasting` is `AlreadyCasting` (#521). Scripts are `AbilityScript(IAbility, IUnit caster, AbilityAim aim)` and are built by `InstanceAbilityCastSystem` from `(ability, caster, aim, arena)`, where the ability is a copy of the caster's own (timers and a casting flag of its own, so a script cannot reach its caster's; the metadata, which cannot change, shared with it) and the arena is the `MapInstance` as `IAbilityArena` (World-side, not the modding API), through a factory kept per script type and bound by those four declared types (`AbilityScriptActivator`, #925; see [reflection-bound registration](packet-handlers.md)). Every cast is built there, a character's, a creature's and an item's alike. **One power rule on both paths (#521):** `AbilityCost.Check`/`Pay`; a cost above 0 is spent from the pool the ability names (`AbilityTemplate.CostPowerType`, #652: Mana, Fury or Energy, carried to `AbilityMetadata` and sent as `AbilityInfo.CostPowerType`, field 17; in the REST API as `costPowerType` on `AbilityTemplateDto` and `CharacterAbilityTemplateDto`, the string enum `Avalon.Api.Contract.PowerType`), and only a caster whose own `PowerType` is that pool, holding at least the cost, pays it. Points in another pool never count, whoever assigned the ability: a mismatch is refused as `CastRejectReason.WrongPowerType` (14), before anything is built or paid, by the handler and again by the cast system on both paths. A cost of 0 names no pool and is castable by anyone, `PowerType.None` included. A cost whose row names no pool is a data fault: `AbilityCatalog` refuses the row, a check constraint (`CK_AbilityTemplates_CostPowerType`) refuses it in the database, and one that slips through is `InternalError`. The kit's costs are spent from their class's pool (the seed's `ClassPool`, as `ClassPowerType`); the migration `AddAbilityCostPowerType` gave every other row with a cost the pool its allowed classes share, and refuses to run, naming the rows, when their classes spend from different pools or the row allows none. Fury is spent like the others. Fury (#526) is gained per unit an ability damages (`AbilityTemplate.PowerGainPerHit`, Cleave 8, every other seeded ability 0; `AbilityCatalog` and a check constraint refuse a negative one) and from damage taken (`floor(health lost / max health × Game:FuryFromDamageTaken)`, default 50, the health lost capped at what the character had, from any source, only while alive), both in `CombatService` and capped at the maximum, drains at `Game:FuryDecayPerSecond` (default 5) out of combat, with the fraction carried between ticks, and is 0 on select, on every instance transfer (`MapInstance.AddCharacter`) and on death; a level-up or gear change keeps it, capped. `CharacterEntity.GainPower` and `ResetFury` are World-side, not on the modding API. The cast system sets `Casting` and pays only once the queue took the cast, builds a queued cast's script when it is queued, before paying (a script that is missing or cannot be built is refused and costs nothing, and the prebuilt script fires at completion with the aim captured at cast start), drops a cast whose caster died before it completed (clearing `Casting`, and broadcasting the interrupt, so every client's cast bar for it ends, #530), removes finished and interrupted casts after the loop, and keeps only unfinished scripts (projectiles) ticking. `SUnitStartCastPacket` carries the `AbilityId` (#521 item 9).
- **Cast telegraphs (#648).** A cast lands exactly where its telegraph was drawn. `AbilityFootprint` (`Avalon.World/Abilities`) resolves an ability's footprint once, from its row, its aim and its origin: a circle's centre (the origin, or the aim point clamped to `Reach` and cut by `RaycastWalkable`) and radius, a cone's origin, direction (the aim's facing for Movement, already toward the cursor when one was sent, #716; toward the aim point for Cursor), reach and arc, a projectile's lane (toward the aim point, `Reach` cut where the walkable ray stops). The shape scripts fire with `AbilityFootprint.Resolve`, and the cast system resolves the same at queue time, so the two agree by construction; the origin is the caster's position at cast start (`AbilityAim.Origin`), which for a character is where it fires (moving interrupts) and for a creature pushed by a crowd during a wind-up is where it began, so a pushed creature still fires on its telegraph. **The cast system sends the start (#648):** `QueueAbility` broadcasts `SUnitStartCastPacket` once it has taken the cast (`IAbilityArena.BroadcastUnitStartCast`), with `CastId` (field 4), `Footprint` (field 5, `AbilityFootprintDto`, absent only if resolving it threw, which is logged) and `WorldTick` (field 7, #1082: the world tick the cast was taken on, which an item's start carries too, so a client ends the cast bar and the countdown at that tick's server time plus `CastTime`, not at the packet's arrival plus it); `ISimulationContext` has no start broadcast any more, and neither `CastAbilityHandler` nor `CreatureCombatScript` sends one. The start is heard near the caster or near a circle's centre. **Cast ids:** `InstanceAbilityCastSystem` numbers every cast it takes, queued or instant, per instance, never 0 (0 is what a payload from before #648 decodes as), and the start, the finish (`SUnitFinishCastPacket.CastId`, field 3), the interrupt (`SCharacterInterruptedCastPacket.CastId`, field 3, every way a cast is interrupted or dropped) and the fired broadcast (`SAbilityFiredPacket.CastId`, field 6, through `IAbilityArena.CastInFlight`, set only while the script's `Prepare` runs) of one cast carry the same one. The public `ISimulationContext.BroadcastFinishCast`/`BroadcastInterruptedCast` send cast id 0. **Instant casts** send no start and no telegraph (they fire on the tick they are cast); their fired broadcast carries the whole footprint (`SAbilityFiredPacket.Footprint`, field 7) and the finish the same id. Projectiles send no fired broadcast: a cast-time projectile's start carries its lane, and once fired the projectile is a world object. A client draws a telegraph from the start alone, keyed by caster and cast id, and clears it on the finish or interrupt with that id, on a new start from the same caster, when the caster leaves its view, or once `CastTime` has passed. `docs/client-combat-protocol-migration.md` is the client-facing contract.
- **Lag compensation: each hit is judged by the screen it was promised on (#1082).** An instant cast and a projectile are judged by the attacker's screen, a hostile telegraph by the target's; a creature's casts are always judged on the server's present. **Position history:** every character and creature in an instance holds a `PositionHistory` (`CharacterEntity.History`, `Creature.History`, never on `IUnit`), a ring of 18 positions keyed by world tick (`WorldTicks.Completed`), rented from the instance's pool as the unit joins and returned as it leaves, so an instance entry (every transfer, a teleport or town return into the same instance included) starts afresh, holding one entry, the unit's position as it joins; a revive (`CombatService.RevivePlayer`) and a creature's teleport clear it (`Jump()` on the entity), so a rewind never crosses a jump. **Step 4b** of `MapInstance.Update`, after the creatures' locomotion (step 4) and before the dirty snapshot (step 5a), records the position of every member that moved since the last record, so each entry is what the broadcast stamped with that tick carries: the concrete position setters' call into the spatial grid (`SpatialGrid.Moved`) lists the unit once per tick, and the step (`SpatialGrid.RecordMoved`) reads that list and no other unit (most of a forest's creatures are waiting, #979); a unit that never moves keeps its seed, and a jumped one is reseeded where it lands. It allocates nothing, and is timed as its own phase (`historyTicks`, [tick profiling](tick-profiling.md)). **Rewound hits:** a player's instant cast names the tick its client was drawing (`CCastAbilityPacket.ViewTick`, 0 when not sent: no rewind), clamped to `LagCompensation.MaxRewindTicks` (15 ticks, 250 ms) behind the present; `CastAbilityHandler` fires it through the instance's internal `IPlayerCastHost`, which fixes its `CastView`, and the cast system sets `IAbilityArena.HitRewindTicks` and `HitRewindExempt` (the caster, tested where it stands now) around the `Prepare` and puts back what it found. `IHitQuery` then tests and sorts every other unit at its history's position that many ticks ago (its present one when the history does not reach back that far), widening the grid box it visits by how far any unit can have moved since: the grid keeps the largest step (on X or Z) the units it recorded made on each of the last 18 ticks, and the box grows by the sum over the window plus the largest move since the last record (`SpatialGrid.RewindDrift`), so a unit is never missed however fast it moved, and a window in which little moved costs little more than the present; each candidate's rewound position is read once, its hit carrying its distance into the nearest-first sort. Liveness and membership stay the present's. A player's projectile sweeps rewound for its whole flight by that offset less the caster's one-way delay (half its `RoundTripTime`, in ticks), never below 0, since the client draws projectiles where the server has them. A queued cast, a creature's cast and item use are never rewound. **Dodge wait:** when a queued hostile circle or cone fires, each player it hits is held (`PendingHits`, one list per instance) for `min(OneWayTicks(RoundTripTime), 6)` ticks and lands, through `AbilityEffect.Apply`, only if that player is still alive, still a target and still inside the footprint; the held hits are resolved at the start of the cast system's update (step 3), after the tick's inputs. It only removes hits; units that are not players, Ally casts and projectiles never wait; the caster's death does not cancel a held hit, and a caster or target leaving the instance drops it. All of it runs on the tick and allocates nothing at steady state; the `forest-combat` scenario exercises both halves (its fighters cast with `ViewTick` 10 ticks behind and report a 60 ms round trip). The rules in full: [spell-system.md](spell-system.md) §4.
- **Combat reads the derived stats (#506 slice A).** Every hit resolves in `CombatService.ApplyDamageCore`, after the early returns (invulnerable, corpse, walking home), so nothing refused draws a roll; the maths is `HitResolver` (`Avalon.Combat`, pure). The order: **base**, then **dodge** (the hit deals 0 and nothing else is rolled), **crit** (x `CritMultiplier`), **block** (x `BlockMultiplier`), **armour** (x `1 - min(A / (A + ArmorBase + ArmorPerLevel x attackerLevel), ArmorCap)`), floored with a minimum of 1. An ability's base is `EffectValue + ScalingCoefficient x stat + BaseDamageCoefficient x roll` (`AbilityTemplate.ScalingStat` picks AttackDamage or AbilityDamage; the roll is uniform and inclusive over the attacker's base damage: a character's main hand, `DamageMin1..DamageMax1`, none with no weapon, and a creature's natural `DamageMin..DamageMax`, #163; the column was `WeaponCoefficient` until #163); a raw hit's base (the `ApplyDamage` overload with no ability; creatures no longer swing raw, #163) is the damage passed. Chances are percentage points clamped to the formula's caps. A heal (`ApplyHeal`) takes the base and a crit only; one that restored more than 0 is reported through `ICombatOutcomes.UnitHealed` and sent as `SMSG_UNIT_HEALED` (below). Threat, the #526 per-hit gain and the PvP reset read the resolved damage; Fury from damage taken reads the health actually lost. **A dodge still counts as combat**: the encounter forms, the creature gets threat for the base, both sides are tagged in combat, and a creature's script is told through `AiScript.OnAttacked(attacker)`, forwarded down the chain, so it engages the attacker as a landed hit would; but the script is not hit, nobody gains power and nobody dies. A creature's killing blow is broadcast as a hit (0 health left, marked with its result) before the death. Characters attack and defend with `CharacterEntity.Combat`/`Defence`, from the `DerivedCharacterStats` (damage stats, crit, dodge, block, armour, main-hand weapon range) the last stats refresh wrote; creatures with `Creature.Combat` (its natural `DamageMin..DamageMax` as the weapon range, #163)/`Defence`, fixed at spawn by `CreatureStatDeriver` (armour = `round(CreatureBaseStat.Armor x ArmorModifier)`, a modifier of 0 or less counting as 1; crit, dodge and block from `CreatureRarityModifiers`). Both World-side and read-only, never on the modding API. Every roll goes through `ICombatRandom` (`CombatRandom` over `Random.Shared` in production; a service built without one uses `CombatRandom.Steady`, which never procs), creature abilities included (a creature's base-damage roll is the combat service's, #163). **Data:** `CombatFormula` (one row, id 1) and `ClassStatFactors` (one row per class, which `CharacterStatsCalculator` reads instead of constants) are the `/reload combat` area; `CreatureBaseStats.Armor` and the rarity `CritPct`/`DodgePct`/`BlockPct` stay in the creatures area; a bad row fails the reload (or the startup) naming it, and the previous values stay. Each hit reads the formula once. **Wire:** `SUnitDamagePacket.Result` (field 5) and `SCharacterDamagePacket.Result` (field 6) carry `HitResult` (`[Flags]`: None 0, Crit 1, Dodged 2, Blocked 4); a dodge is sent as a hit of 0 marked Dodged, to the same watchers a hit reaches (#532). A creature's own hit broadcast, made by its script's `OnHit`, is marked through `ICombatOutcomes.HitInFlight`, set only for that call.
- **ICorpseRemover** / **CreatureCorpseRemover** — removes a dead creature's corpse from the instance after `ICreatureMetadata.BodyRemoveTimer`. Creatures do not respawn on a timer; the time-based respawn scheduler was removed deliberately.
- **Ground loot (#460)** lives in `Avalon.World/Loot/`. `CreatureTemplate.LootTableId` (nullable) names a `LootTable`; its `LootTableEntry` rows each drop an item or roll another table, exactly one of the two (a check constraint enforces it). Ungrouped entries roll on their own against `Chance` (a percentage); entries sharing a `GroupId` always drop exactly one of them, weighted by `Chance`, so a group that should not drop on every kill belongs in its own table, referenced at the chance it should drop with. `MinGold`/`MaxGold` are **copper** and make one pile. Tables load as the `/reload loot` area into `StaticData.Loot`, a `LootCatalog` that refuses a bad table (a reference cycle, a missing reference, both targets or neither, counts out of order or above 1000, a chance outside 0-100) with an error naming it, and keeps the rest. `MapInstance.CreatureKilled` rolls on the tick (`ILootRoller`), asks `ILootAllocator.Allocate(instanceOwner, instanceParty, eligible)` for an owner once per drop (`PartyLootAllocator`, the only implementation: a solo instance's drops are reserved for its owner character, a party instance's each for one member drawn from the kill's eligible members, see Parties, and either is free for all after `GameConfiguration.LootGracePeriod`; an instance with neither owner, a town, and a party kill with nobody eligible drop free for all at once; the owner and `FreeForAllAt` ride on `LootDropDto`), places each drop on a ring around the corpse snapped to the navmesh, keeps them in the instance's `GroundLootStore`, and broadcasts `SLootSpawnedPacket`. A character entering an instance gets the drops already there at the start of the instance's next tick, after the map transition packets. Drops are never persisted and never despawn on a timer: they leave when picked up, or when the instance is disposed. `CMSG_LOOT_PICKUP` (`LootPickupHandler`, with its `MapSessionFilter` entry) runs its checks in a fixed order in `LootPickup.TryPickUp` and answers with `SLootPickupResultPacket`; a dead character gets no answer.
- **EntityTrackingSystem** tracks which objects each client sees. Membership is keyed by the stable raw GUID, with the original GUID retained for notifications and a last-seen frame stamp replacing the rebuilt seen set. Duplicate inputs count once for removal detection but still produce their ordinary per-input dirty notifications; pending removals survive an interrupted callback, and frame-counter wrap rebases stamps without resetting membership. Its candidates come from the instance's spatial index (#982, below), the members near the recipient, rather than from a scan of every member. `CharacterCharacterGameState` feeds it only what `Interest.IsVisible` accepts (#593). Your own character is always visible. Other characters, creatures and projectiles are added within `Game:InterestRadius` (60 m) and removed beyond it plus `Game:InterestRemoveMargin` (10 m), on X/Z, so an object at the edge doesn't flicker. The check measures before it asks (#982): an object within the radius is in view and one beyond radius + margin is not, whatever the client was told, so only one between the two looks itself up in the tracking set (`Interest.IsVisible` with an `Interest.ITrackedSet`, one definition of the rule). Leaving view is a remove, and coming back is a fresh add with full state. **Views are decided on the broadcast cadence (#981, owner decision).** An instance decides its clients' views once per broadcast period, on its broadcast tick, right before the state broadcast (`MapInstance.DecideViews`), not on every tick: an object is listed or removed up to one period (100 ms, six ticks) after it came into range or left it, and the scan costs a sixth of what it did, spread over the ticks with the broadcasts' slots (#975). Movement and state updates are unchanged: they went out only on the broadcast tick already. Between decisions each view holds (`CharacterCharacterGameState.Hold`), so `Knows` and the tracking sets always say what the client was told, never what is in range; hysteresis is the same, applied at each decision. Two things do not wait for the broadcast tick. A client entering the world or an instance (a new state, or `Reset`: `ScanOwed`) is listed itself and everything in view on its own first tick, as before; the clients already there list it at their next decision. A character that left the instance is removed from every client that held it on the instance's next tick, as before (`TellCharactersLeft`, `CharacterLeft`): a character's guid comes back with it, and a client still holding it when it came back would never hear what changed while it was elsewhere; one back before that tick (a move into the instance it was in) is left as it is, as a decision every tick left it. A creature or projectile that leaves (a corpse removed, a summon gone, a projectile ended) is removed at the next decision: its guid is never reused, and a script hot reload's remove and re-add happens in one call. A broadcast tick that throws before the decision leaves it owed, and the next tick decides. Each client's broadcast is contained (`BroadcastStateContained`): every view is decided before any client is sent anything, so a throw reaching the tick would leave the clients after it with views they were never told of, until each object left and came back. The others go on; the one that threw is started over as a move between instances starts it (#611): told to drop everything it was told of there, its own character included, and listed itself and its view in full on the next tick, since what reached it before the throw cannot be known. The failure is logged at most once per `ThrottledErrorLog.Interval`. "who" (the candidates and `Interest`) is `CharacterCharacterGameState`'s and "when" is `MapInstance`'s; the spatial index (#982) changed the candidates alone. Nothing in gameplay reads the views: effect broadcasts (`EffectAudience`), hits, creature detection, loot, chat, targeting, the threat mirror and NPC dialogue read positions or the instance, so a client can hear an effect of a unit up to a period before the unit's add (before #981, earlier in the same tick). Loot, said chat (`ChatChannel.Say`), PvP state and threat are still instance-wide. **The replication state is World-side (#612)**: `CharacterEntity.CharacterGameState` (a `CharacterCharacterGameState`), not on `ICharacter`, and World.Public has no `ICharacterGameState`, so no mod can drive what a client is told it sees; `MapInstance` replicates only to characters that are `CharacterEntity`. **Changing instance starts replication over (#611).** The client keeps every object until a remove names it, even across a map transition, so `MapInstance.AddCharacter` resets the arriving character's state (`Reset`, which forgets everything without raising removes) and sends, at once and only when it had any, one `SMSG_WORLD_STATE_REMOVE` naming everything the client knew in the instance left, its own character included; that goes out ahead of the map transition the handler sends next. The first tick in the new instance then adds, in full, the character itself and everything in view there, a character that crossed just before it included. Every move between instances (map entry, respawn at town, a transfer into the instance the character is already in) goes through `World.TransferPlayer` and so through `AddCharacter` (`InstanceTransferReplicationShould`). Today portals come only with the map, in `SChunkLayoutPacket.Portals`, and are not put into the tracking systems. A portal spawned at runtime (on a kill, say) is meant to replicate as a world object through `ObjectState`'s portal fields, which stay in the wire schema for that; the server writer for it gets built, and tested through the tracking systems, when runtime portals are designed.
- **Views find their candidates in a spatial grid (#982).** Each `MapInstance` keeps its characters and creatures in a `SpatialGrid`: a uniform grid on X/Z over its layout's chunks, one cell per chunk cell (`ChunkLayout.CellSize`, 30 m), from the lowest chunk corner to the far side of the highest, with coordinates clamped to the edge cells, so an entity off the layout is in the nearest edge cell. Each indexed entity has a slot in one array holding its X, Z, raw guid, the entity, its kind and its cell, and each cell is an intrusive doubly-linked list through the slots, so a move to another cell is an unlink and a link. The two concrete position setters keep it current (`Creature.Position`, `CharacterEntity.Position`; a write through `IWorldObject.Position` lands there), relinking an entity only when its cell changes, and `AddCharacter`, `RemoveCharacter`, `AddCreature` and `RemoveCreature` keep it equal to the instance's dictionaries (another object added under a guid already there replaces it in both). An entity holds its handle (`SpatialHandle`) only while a member, so a position written outside an instance touches no grid. **A member's position changes through its setter only**: a row written directly moves the character without its entry (a portal arrival wrote its row so before #982; over the grid every view around the spawn, the arriving character's own included, would have looked for it where it stood before). An entity whose position has a component that is not finite is in no cell but in a list every query visits, so the watcher's own character always sees itself wherever it stands; an entity of another type (a test's double), or one indexed by another instance's grid (a character added to an instance while still in another), is kept in a list every query visits, its position read live. Projectiles are not indexed (few and short-lived): every view still checks each one. A decision over the grid (`CharacterCharacterGameState.UpdateProfiled`) visits the entries of every cell the circle of radius + margin overlaps (70 m, widened by a part in 1,024 and 0.25 m against rounding; `Interest.Reach`), and decides each entry of a cell on the grid's own copy of its guid and X/Z, without reading the entity (a character's position is on its row, a second object): the rule's steps in its order, the watcher's own character in view, nothing else for a watcher whose position is not finite, then the rule's own distance measure (`Interest.DecidedByDistance`), in view within the radius and out beyond radius + margin. Only an entry in the margin, where whether the client already holds it decides, reads the entity and asks the tracking set, through the unchanged `Interest.IsVisible`, as does every entry in no cell or not indexed. An entry of a cell has every component of its position finite (`SpatialGrid` puts any other in no cell) and holds the entity's own X/Z, so the answer is the rule's for every entry; a Debug build checks each entry against its entity as a query reaches it and throws when they differ, so a position written past the setter fails the tests that decide views (free in Release: `[Conditional("DEBUG")]`). The views, and what each client is told, are the full scan's (`SpatialVisibilityShould` drives an instance over the grid and one scanning every member, `MapInstance.DecideViewsByFullScan`, through the same seeded changes and compares them after every tick), except that within a kind the objects are listed in the cells' order rather than the dictionaries' (the owner's decision: the client applies each entry by its guid). The grid runs in every instance, towns included; it is per instance and tick thread only (#639), grows only when an entity joins and finds no free slot (an instance's creatures join off the tick, as it is built), allocates nothing per tick, and is World-side: nothing of it is in World.Public. Over 300 generated forests a view along the main path visits 1.6 creatures for each one in view, 46% of what a full scan checks, and a forest's tick is 10% to 36% cheaper; a town's grid prunes nothing, and deciding on the copy is what it gains: one crowded town's tick is 6% to 19% cheaper than the full scan in most measured pairs, while twenty towns of 15 players measured 1% to 3% dearer at 300 players in one session and 2% to 4% cheaper in another, likely the grid's upkeep on every input not being paid back there (inferred, not measured apart; [benchmarks](benchmarks.md)). **Hit queries find their candidates in the grid too (#982).** `UnitHitQuery` visits the cells of the shape's box on X/Z (`SpatialGrid.VisitBox`): a circle's centre or a cone's apex widened by its radius or reach, a segment's own box, each widened by the largest body radius the grid has indexed (`SpatialGrid.LargestBodyRadius`, taken as each entity joins: a body radius is fixed for an entity's life, a creature's copied from its template at spawn and a character's a constant, so a `/reload` or a live template edit reaches the box with the next creature spawned) and by more than any rounding of the exact tests (a part in 1,024 of the extent, 1/1,024 m and a part in 2^40 of the largest coordinate, worked out in double and rounded outwards to floats), plus the grid's lists of entities in no cell and not indexed, whole. A cell's entry outside the box is left on the grid's copy of its X/Z without its unit being read (exact, as for views: the copy is the entity's own); every other candidate is tested on the unit as before, alive and then the exact overlap, and the hits are sorted nearest-first with the raw-guid tie-break, so the list does not depend on the order they were found in. No unit outside the box can overlap the shape, so the hits, their order, and everything that follows from them (rolls, packets) are the full scan's: `UnitHitQueryShould` asks the same casts of an instance over the grid and one scanning every member (`MapInstance.FindHitsByFullScan`) and compares the lists, and `forest-combat` fights the same fight either way, byte for byte. A box that is not finite (a position, a size or the largest radius not finite) scans every member, as before; a finite box larger than the layout is clamped to the edge cells, so it visits at most every cell. In `forest-combat` a query reads 0.36 units on average instead of the 203 its forest holds ([benchmarks](benchmarks.md)). **Creature detection asks the grid first (#982):** a creature whose range search comes due runs it only when `SpatialGrid.MayHaveCharacterWithin` says a character can be within its range (the scheduler's search filter, under the AI scheduling above). The answer is conservative and never skips a search that would find someone. First the X/Z bounds of the characters in a cell, widened by the range: four float comparisons, exact with no margin (float subtraction rounds monotonically, so a creature whose `minX − x` is above the range is that far from every character inside the bounds, and the search's distance is never below that difference). The grid keeps a version that every link, unlink and move of a character moves (each character's entry also has its place in a packed list of character slots), and binds the bounds again over those characters, lazily, only when a creature asks after the version moved: a character moved earlier in the step is where the bounds say, and a forest's due creatures of one step share one binding. A Debug build checks that every character in a cell lies within the bounds whenever they are read. Within the bounds, each cell also counts its characters (kept by the same links and unlinks), and the probe walks only the cells around the creature that hold a character, with the reach widened as a view's is, and measures each character as `Vector3.Distance` does with the Y term left out (the same float differences, double squares and sum order, so with every component finite the search's 3D distance is never below it); a creature or range that is not finite, any character in no cell (a component of its position not finite: the search's NaN distance is not above any range) and any character not indexed always let the search run, before the bounds are read, and a dead character counts as any other.
- **Character updates carry accumulated dirty fields.** Unchanged position, velocity and yaw assignments do not mark a character dirty (exact comparisons, so small corrections survive). Dirty bits remain set until the next broadcast, including a stop followed by repeated idle inputs. Updates send only those fields, with the usual name/class/gender and PvP presence semantics; newly visible characters still receive full state. Motion is suppressed for the owner, whose input ACK carries it, and a motion-only update therefore sends no owner state. A character's `Experience` and `RequiredExperience` go to its own client alone (#993, the owner's decision): the client reads them for its own experience bar only, so every other recipient's add and update leaves both out, and an update whose only change is experience sends them nothing (`MapInstance.MaskForRecipient`, both rules; `CharacterDeltaReplicationShould`). Power amounts are selected independently of the power-type bit: spending or regeneration must replicate even when the type stays the same. The input ACK rate and broadcast cadence are unchanged. **Each entity's add and update is encoded once per broadcast (#980).** A recipient's `SMSG_WORLD_STATE_ADD` and `SMSG_WORLD_STATE_UPDATE` are their entries one after another, so `StatePacketAssembler` (`Avalon.World/Serialization`, one for adds and one for updates per instance, tick thread only) keeps each entity's entry, keyed by the entity and its fields (the fields marked changed for an update, all of them for an add), as the first recipient sent it in the broadcast encodes it (`SInstanceStateAddPacket.WriteEntry`, `SInstanceStateUpdatePacket.WriteEntry`), and copies it into every other recipient's packet; a character's add or update to its own client, the one entry that depends on who receives it (motion left out, experience kept), is described and encoded for that client alone. A broadcast with fewer characters than `StatePacketAssembler.MinRecipientsToShare` (2) has nothing to share: an entry encoded on its own costs about 1.6 times its share of a whole encode, so each recipient's list is encoded whole by the packet's `Create`, as before, and a solo player's instance pays nothing for the sharing (the threshold's measurements are in [benchmarks](benchmarks.md#results--shared-state-and-aura-encoding-980-2026-10-14)). The packets are byte for byte those the per-recipient encoding wrote (`StateUpdateEncodingShould`). Which entities a recipient is sent, and with which fields, stays the tracking systems' to decide: the assembler only encodes. Each changed unit's aura update is shared the same way (`SharedAuraUpdates`, [auras](auras.md)).
- **Effect broadcasts are local (#532).** `MapInstance`'s one-shot effect broadcasts (unit hit, heal, start, finish and interrupted cast, ability fired, attack animation, death, revive) go only to connections within `Game:InterestRadius` (default 60 m, X/Z, inclusive) of the effect or involved in it (`EffectAudience`).
- **CreatureStatDeriver** (`Avalon.Combat`) — turns a creature template plus a rolled level into the stats it spawns with: `CreatureBaseStats` by level, scaled by the template's modifiers and its `CreatureRarity` via `CreatureRarityModifiers`. It lives on `StaticData` (`StaticData.CreatureStats`), and `CreatureSpawner.Spawn` reads it, together with the templates, off `world.Data.Creatures` once per call; before it existed every creature spawned as level 1 with 100 health whatever its template said. The level is the template's own roll, or the depth band's on a banded procedural map. `CreatureTemplate.Exp` overrides the derived experience when set — `null` means derive.
- **`/reload <area>`** (`Avalon.World/Chat/ReloadCommand.cs`, game-master only) drives `IReferenceDataReloader` to apply changed dialogue, creature, ability, item, progression, loot, vendor, combat, quest or aura rows without a restart. Forward-only: `StaticData.PrepareAsync` reads the database and builds a whole `StaticDataPatch` off the tick thread; `ApplyOnNextTickAsync` queues it, and `World.Update` applies every queued patch at the top of `World.Update`, before the map pass and any instance ticks (the session pass — character create/select — runs earlier, in `WorldServer.Update`, so it sees a reload one tick later) — so nothing already spawned or already built is touched, only what gets built afterward. The Items and Progression patches publish their rows as `KeyedRows` (`Avalon.World/Reload`, #883): the rows and a lookup by key (item template id, level) in one object, which a kill uses to find each drop's template and each level's requirement without walking them, and which `StaticData.FindItemTemplate` and `FindLevel` answer from for any reader that wants one row; being one object with the rows, it is replaced with them and can never be stale against them, and a reader that keeps a lookup of its own over reference data must be replaced the same way. Each area is published as a single immutable `volatile` reference to its patch, because instance construction — and therefore `CreatureSpawner.Spawn` — runs on the thread pool, not the tick thread; a reader that needs more than one creature-area property together must take the `StaticData.Creatures` snapshot once rather than chain two property reads, or a reload landing in between could pair a new template with an old deriver. Maps and chunk layouts are excluded: live instances have already baked a navmesh from them, and the client mirrors that bake, so a change needs a restart. Spawn tables and town spawns need no reload of their own — `CreaturePlacementService` reads `ISpawnTableRepository`/`IMapCreatureSpawnRepository` straight from the database on every instance build, never from `StaticData`. Spawn tables and procedural map configs (with their depth bands) are themselves seeded from `src/Server/Avalon.Server.World/Maps/spawn-tables.json` and `Maps/ProceduralMaps/<mapId>.json` by `ChunkCatalogSeeder` on every World start (like chunks, town layouts, pools and chunk groups), not by migrations (owner decision, forest content pass), so a change to them needs a restart. Trade-offs: the balance simulator reads `HasData` only and never sees them, and the REST API's layout preview and observability show them as of the last World start. `/reload vendors` rebuilds the `VendorCatalog` from `VendorStocks`, validating it against the item templates it reads in the same prepare. On their next vendor pass, the town instances carry each live stock count over by row id, and every open shop hears the new list. `/reload quests` rebuilds the `QuestCatalog`, validated against the creature and item templates and the dialogue nodes read in the same prepare (#737) and the loaded quest scripts; characters keep the quests they hold, each settled once against the new catalog on the next flush (#738, see Quests). `/reload auras` rebuilds the `AuraCatalog`; `/reload abilities` checks each ability's `AuraId` against the auras its own prepare reads. Forward-only: an aura on a unit keeps the template, snapshot and stacks it was applied with; one whose template a reload dropped expires on its next tick (see Auras).
- **The seeded loot** (migration `SeedForestLoot`): hostile templates 4-10 each name their own table (2-8) and a copper range; the town NPCs (1-3) name none. Loot tables are generic, and shared tables are pools. Each creature table rolls a Health Potion and a Mana Potion on their own, then references the pools: table 1 "Forest common", table 9 "Forest weapons" at 2 % (a group of one weapon per class, items 5-8), table 10 "Forest scrolls" at 10 % (a group of three collectible scrolls, items 9-11, which do nothing when used yet), and table 11 "Forest armour" at 100 % (20 Uncommon pieces, items 12-31, one per class in each of five slots, each its own entry at 2 %). So a kill drops at most one weapon and at most one scroll. Item 4, the Rusted Sword, is left as it is (it may become a starting item) and is in no table. Items 5-31 can be sold (no `NoSell`). Every armour piece carries Armor, cloth (Wizard, Healer) below leather (Hunter) below plate (Warrior) in each slot. Potion and common-table chances rise with the creature's rarity; the pool references are the same for every creature. `SeedIntegrityShould` pins all of it.
- `CreatureTemplate.Invulnerable` **is** read — `CreatureSpawner` copies it onto the creature and `CombatService.ApplyDamageCore` returns early on it, ahead of `ResolveOrSpawn`, so an invulnerable target also creates no encounter and does not combat-tag its attacker.
- **A creature walking home ignores hits entirely (#610).** Once its `CreatureCombatScript` is `Returning` (after the leash or a lost target), `ApplyDamageCore` returns early beside the invulnerable and corpse checks: no encounter, no threat, no `OnHit`, no broadcast, no combat tag, and `ApplyHeal` gives it no heal threat (splitting it across the hostiles still fighting), so nothing from the walk home outlives the reset at home. It asks `IReturningHome` (`Avalon.World/Scripts/Creatures`), internal and read-only: `CreatureCombatScript` answers it, and a script that chains one (`AggroDefendScript`, `CreaturePatrolScript`) must forward it, or its creature takes hits on the way home. Being internal, no mod or script can declare it directly, so none can make a creature unhittable on its own; a subclass of `CreatureCombatScript` (hot-reloaded or not) inherits it, with its behaviour. `ApplyTaunt` and `EnterCombat` do nothing on a returning creature either (#614). **Home and reset, a creature leaves its encounter** (#614): `ResetToIdleAtSpawn`, the one place `Returning` goes back to `None`, clears the creature's taunt (`TauntedBy`, `TauntExpiresAt`) and calls `IHostileEncounterExit.DropHostileFromEncounter` (`Avalon.World/Combat`, internal, implemented by `CombatService` and deliberately not on the modding API's `ICombatService`, where a mod could call it every tick to keep a creature from ever holding threat), which removes the creature and its threat list (`Encounter.RemoveHostile`) and leaves the players in the encounter with their threat on every other hostile; an encounter left with no hostile ends after its grace, as after a kill. So no threat from before the leash, not even a seed from a player it swung at, and no old taunter steers its next fight. **Combat runs on the container's clock** (#610, #614): `CreatureCombatScript` times taunts by `TimeProvider` (an optional constructor parameter, resolved from DI by `AttachScript` and passed down by the chaining scripts), and `MapInstance` hands its own `TimeProvider` to `EncounterRegistry` (and so every `Encounter`: last damage and the end grace), `CombatService` (a taunt's end) and `ThreatBroadcastService` (the broadcast throttle), and uses the same clock for `LastEmptyAt` (instance expiry). `CharacterEntity` takes the container's `TimeProvider` (an optional constructor parameter, passed by `CharacterSelectHandler`) for the combat tag (`MarkCombat`/`IsInCombat`, so `RequiresOutOfCombat` and in-combat regen) and the cast-regen suppression. Threat decay itself runs on the tick's delta.
- **Haste, creature cadence and movement speed (#627).** One rule, `Haste.Scale` (`Avalon.Combat`): a time becomes `time / (1 + haste / 100)`, a negative or unreadable haste counting as none. **Haste** is a character's worn `StatType.AttackSpeed` total (`DerivedCharacterStats.HastePct`, a percentage; swords and bows seed 3, maces 2, staves 0), and `CharacterEntity.EffectiveHastePct` is that, 0 to `CombatFormula.HasteCap` (50), fixed at each stats refresh. `InstanceAbilityCastSystem` reads it once per cast: a queued cast's `CastTimeTimer` is the scaled cast time, fixed at its start (the start-cast broadcast carries it), and the cooldown a cast sets when it fires is scaled by the same value, set once, so a gear change mid-cast changes neither and never rescales a running cooldown. The global cooldown (`CombatConfig.GcdMs`), costs and damage are not scaled; a `CharacterEntity` caster has its haste and a World-side `Creature` its own (`min(HastePct, HasteCap)`, #163). **Creature cadence:** a creature's basic ability waits `Creature.SwingInterval` (#163; the raw swing is gone) = `BaseAttackTime` (seconds, a real, 2.25 for every seeded template, at least 0.5 and finite: a check constraint, and the Creatures reload area refuses the area naming the template) divided by `1 + min(Creature.HastePct, HasteCap) / 100`, both fixed at spawn except `HastePct`, a World-side value (never on `ICreature`, #622) that nothing sets yet. The first attack lands at once (cooldowns are cleared when the creature resets at home), the cooldown runs down every tick its combat script runs, in reach or not, and the basic is cast on the tick it reaches 0; the interval is read when the basic fires, so a haste change applies from the next. Any other `ICreature` waits its basic row's own cooldown. **Movement speed** is `CharacterMovement.SpeedFor`: `4.0 x (1 + clamp(gear MovementSpeed %, MoveSpeedFloor, MoveSpeedCap) / 100)`, floor -50 and cap +35 (`CombatFormula`, the cap owner-set so a whole change from the base, 4 x 0.35 x 0.1 s = 0.14 m, stays under the client's 0.15 m snap, validated finite with `-100 < floor <= cap`), recalculated at every stats refresh; `PlayerInputHandler` steps at `GetMovementSpeed()`. Select's `CharacterInfo.MovementSpeed` is the speed held when the selected packet leaves (the base, since the gear is read later in the chain); the derived one reaches the client in the sheet. No seeded item carries MovementSpeed; a +10 % change drifts the client's prediction 0.04 m over a 100 ms round trip, under its 0.15 m snap (`CharacterMovementSpeedShould` pins it for the default cap, which fails past 37.5 %, and against every seeded item). The three formula columns are part of `/reload combat` and reach a character at its next refresh, a creature at its next spawn.
- **Regeneration carries the fraction of a point.** `CharacterEntity.Update` regenerates, each tick: health out of combat (`Stamina x HealthRegenOutOfCombatPerStamina` a second, 0.5), never in combat or dead; Mana and Energy from the class's stat (`PowerRegen.StatOf`: Intellect for Wizard and Healer, Agility for Hunter) at `PowerRegenOutOfCombatPerStat` (0.3) or, in combat, `PowerRegenInCombatPerStat` (0.05) a second, none within `PowerRegenCastSuppressSeconds` (5 s) of a cast in progress (`RegenConfiguration`). Each earns `rate x dt` into its own carry and gives only the whole points (`PowerRegen.Amount` for power, `PowerRegen.TakeWholePoints` for health), keeping the fraction for the next tick, so the per-second rate holds at any tick rate; the carry is dropped whenever the pool cannot regenerate (full, suppressed, in combat for health, dead). Before, every tick that regenerated gave at least one whole point, 60 a second at 60 Hz whatever the stat. Fury never regenerates. The arithmetic the server and `tools/Avalon.Balance` share lives in pure rules in `Avalon.Combat`: `PowerRegen`, `PowerPool` (`Gain`, a power gain capped at the maximum and nothing for a dead unit or a pool a cast does not spend; `EmptiesOnReset`, Fury only, on death and every transfer) and `HealRules.After` (a heal never raises health past the maximum and never lowers health already above it, #548), called by `CharacterEntity.GainPower`/`ResetFury` and `CombatService.ApplyHeal`.
- Deliberately still unread on `CreatureTemplate`: `ManaModifier` (creature casts are free and creatures have no pool, #163) and `RegenHealth`. Do not assume any of them work.

**Two contracts worth knowing before touching creature movement or AI scripts:**
- The calling script owns the *moving* `MoveState` and `Speed`; a locomotion writes `MoveState` only when a creature comes to rest, setting `Idle` and zeroing `Velocity`. A locomotion that writes a moving value stomps the script every tick.
- `HasArrived` means "no further destination", which includes *no destination was reachable*. Treating it as "arrived successfully" turns a pathing failure into a silent success.
- `Velocity` is metres per second in both locomotions, the same as a character's, and zero at rest (#424). The client extrapolates by `position + Velocity * secondsSinceUpdate`, so a bare unit direction would move every creature at 1 m/s between broadcasts. `LocomotionVelocityUnitsShould` pins it for both. The same rule holds for every `IWorldObject.Velocity` writer — characters publish the step `PlayerInputHandler` actually took (zero against a wall, zero once dead), a projectile its flight speed (`ProjectileSpeed`) — and the rule is listed per writer on that property.
